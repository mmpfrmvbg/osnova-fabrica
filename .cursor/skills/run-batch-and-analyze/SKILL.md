# run-batch-and-analyze

## Что делает
Анализирует результаты batch-прогона и выдаёт конкретный actionable фикс.

## Authoritative sources
- `runs/traces.jsonl` — трейсы (не коммитятся, только локально)
- `docs/traces-v1.md` — схема трейса, статусы, поля
- `docs/pipeline-v1.md` — архитектура пайплайна

## Структура трейса (ключевые поля)

```json
{
  "task_id": "...",
  "status": "success | partial | failed",
  "repair_exhausted": true | false,
  "attempts": 1..3,
  "parserErrors": ["..."],
  "compilerErrors": ["..."],
  "task": "текст задачи"
}
```

## Алгоритм анализа (выполнять по порядку)

1. **Подсчитай статистику**
   - Всего задач / success / partial / failed
   - repair_exhausted: сколько раз пайплайн исчерпал 3 попытки

2. **Кластеризуй ошибки**
   - Сгруппируй `parserErrors` + `compilerErrors` по тексту
   - Найди ТОП-3 повторяющихся ошибки

3. **Найди паттерн**
   - Ошибка в конкретной конструкции → фикс в промптах
   - Ошибка в конкретном типе задач → фикс в IntakeAgent
   - repair_exhausted > 20% → RepairEngineer не знает правил языка

4. **Выдай фикс**
   - Один конкретный файл для изменения
   - Одно конкретное правило для добавления/исправления
   - Ожидаемый эффект на success rate

## Формат финального отчёта

```
## Batch-анализ [дата]

### Статистика
- Всего: N | ✅ success: N | ⚠️ partial: N | ❌ failed: N
- Success rate: N%
- repair_exhausted: N задач

### ТОП-3 ошибки
1. `текст ошибки` — встречается N раз
2. ...
3. ...

### Диагноз
[одна фраза — в чём системная проблема]

### Следующий фикс
Файл: `путь/к/файлу`
Изменение: [что добавить/убрать/изменить]
Ожидаемый эффект: success rate +N%
```

## Anti-patterns

- ❌ Выдавать список всех ошибок без группировки
- ❌ Предлагать "переписать промпт целиком"
- ❌ Останавливаться на статистике без конкретного фикса
- ❌ Игнорировать repair_exhausted — это главный сигнал

## Definition of done
Отчёт содержит статистику, ТОП-3 ошибок, диагноз и **один конкретный следующий шаг**.
