# AGENTS.md — карта проекта (читать первым)

> Последняя сверка с кодом и git-историей: 2026-09-19.

## Что это

**Основа** — кириллический язык программирования под VLIW-процессоры (модель
e2k/Эльбрус) и фабрика вокруг него: компилятор (`.osnova` → `.osvbc`), стековая и
регистровая VM, VLIW-планировщик, self-hosting компилятор. Дальняя цель — ОС, где
ИИ сам пишет приложения и управляет ими как единой библиотекой.

**Сейчас работа идёт через DSH-агента напрямую**, а не через LLM-пайплайн ниже.

## ПРАВИЛО GIT (A4-5в, задача 0; из ловушек среза 5б)

**Откат staged — только `git checkout HEAD -- <путь>`, со сверкой sha256 ДО и ПОСЛЕ.**
`git checkout -- <файл>` **НЕ откатывает staged** (файл проиндексирован — рабочая копия восстанавливается
из индекса, а не из HEAD): в срезе 5б это дало два перемерных замера, молча снятых СО СТОРОЖЕМ, и числа
выглядели «не сдвинулись». Замер, снятый с неизвестной ревизии дерева, — не замер.
`git show HEAD:<путь> | Set-Content` **запрещён**: портит кодировку и переводы строк (в 5б дал
`TransformError` и sha, не совпавший ни с одной ревизией) — только `git checkout HEAD -- <путь>`.

**Перед обновлением закреплённого числа — `grep` по ВСЕМУ дереву.** Число живёт в нескольких файлах:
151 отказ тела лексера стоял и в `src/self-host/foundationE2k.test.ts`, и в
`src/e2k/callWindowRefusals.test.ts`, и второе нашёл ШЛЮЗ, а не глаз. Порядок: `grep` по числу →
правка всех мест → прогон → сверка байт-в-байт после откатa.

**ЛОВУШКА `report[0]` (A4-5в, задача 5; четвёртая тихая ложь, случай 58 реестра).**
Проверка отчёта раскладки, читающая ТОЛЬКО первый элемент — `report[0]`, `отказы[0]`, `first()`,
`[0]` — молча теряет отказ ВСЕХ остальных процедур: в 5в `src/e2k/programImage.ts#loweredProgram`
смотрел `allocation.report[0]`, поэтому программа, у которой отказывала процедура №2 и далее,
собиралась «успешно» и отдавала неверное число. Правило: **отказ — по ВСЕМ записям отчёта**
(`allocation.report.every/some/for…of`), и в тексте отказа обязано стоять ИМЯ процедуры
(«раскладка отказала: процедура «ИМЯ»: причина»), иначе отказ неотличим от чужого. Это не единичный
баг, а ПАТТЕРН: то же место — любая сводка «сколько отказов» (`docs/verification-debt.md`, случай 58).

**ЧЕРНОВИКИ В `.tmp` НЕ ДОЛЖНЫ ДУБЛИРОВАТЬ ИМЕНА ФАЙЛОВ РЕПОЗИТОРИЯ (A4-5г, задача 1).**
`src/scripts/e2kCodeRefs.ts#buildBareIndex` обходит ФАЙЛОВУЮ СИСТЕМУ от корня (пропускает только
`node_modules` и `.git`) и считает имена БЕЗ пути: копия дерева исходников в `.tmp` сделала имя
`compiler.ts` неоднозначным, и `src/scripts/e2kDocRefs.audit.test.ts` («голое имя нашего файла»)
покраснел. Копию держи поштучно и с суффиксом (`predicatePairing.pre.ts`), а лучше — не держи вовсе:
доказательство должно быть скриптом и числом, а не копией дерева.

**ЛОВУШКА ЖИВОЙ МАШИНЫ: `;`, `|`, `&&` И `>` В АРГУМЕНТЕ `ssh` НЕ РАЗБИРАЮТСЯ (A4-5г, задача 4;
`>` найден на железе куска 4 среза 7, 2026-11-07).**
`ssh хост "uname -a; ls /tmp"` приходит на машину ОДНИМ аргументом и падает как `uname: неверный ключ
-- ;` — оболочка на той стороне его не разбирает. Проверено и на `|` (`od: неверный ключ -- 3`).
То же с `>`: `ssh хост "программа > /tmp/out.txt"` редиректа НЕ делает — `>` уезжает в программу
аргументом (на железе куска 4 исполнилось именно так, а не «файл создан»). Рабочий приём: ssh
вызывается ОДНОЙ простой командой (`sh /tmp/…/run-all.sh`), а всё составное — включая `>` — живёт в
ЗАЛИТОМ скрипте. Отсюда же: отчёт такого прогона надо `tee`-ить в файл на машине и забирать `scp`,
иначе потеряешь его хвост. Заодно проверяй переводы строк: `expected.tsv` читается `IFS=tab`, и CRLF в конце
значения даёт ЛОЖНОЕ расхождение — пиши файлы `LF` (в PowerShell: `[IO.File]::WriteAllText`).

**ЛОВУШКА ТАБЛИЦЫ СТЕНДА: БЕЗ ЗАВЕРШАЮЩЕГО ПЕРЕВОДА СТРОКИ ТЕРЯЕТСЯ ПОСЛЕДНЯЯ СТРОКА (TD-0003,
2026-11-05).** `while IFS=tab read -r …; do … done < table.tsv` на последней строке БЕЗ `\n` получает
от `read` ненулевой код, поэтому ТЕЛО ЦИКЛА не исполняется — а заголовок уже пропущен счётчиком
`first`, и стенд честно печатает «совпало 0, расхождений 0». Выглядит как «проб нет», а не как ошибка.
Поймано только `sh -x` (видно `read`, за которым сразу идёт финальный `say`). Пиши таблицу с
завершающим `\n` — и вообще проверяй стенд трассой, а не его итогом.

**ЛОВУШКА ТЕКСТА В `.sh`: ОБРАТНЫЕ КАВЫЧКИ ИСПОЛНЯЮТСЯ (TD-0003, 2026-11-05).** Правя комментарий или
строку `say` «по-документационному», следи за `` ` ``: оболочка подставит команду и ВЫРЕЖЕТ текст из
строки (`Б1 ( под )` вместо `Б1 (`длина с` под `если`)`), а на stderr пойдёт `длина: команда не
найдена`. В `.sh` кириллические имена в кавычках безвредны, обратные кавычки — нет.

**ЛОВУШКА СТЕНДА: ПЕРЕЗАПИСЬ АРТЕФАКТОВ БЕЗ УДАЛЕНИЯ (A4-5г, задача 2).** Стенд, который на каждом
прогоне ПЕРЕЗАПИСЫВАЕТ `*.elf`, но НЕ удаляет файлы проб, которые теперь ОТКАЗЫВАЮТ, оставляет на диске
образ ДРУГОЙ ревизии под тем же именем: в 5г после отката правки в `.tmp/a5g-hw/` остался `8d.elf`,
собранный С правкой (4864 б), и он уехал бы на железо как «собран из HEAD» (там 8d отказывает и ELF не
даёт вовсе). Правило: перед прогоном ЧИСТИ папку артефактов, а на машину вози только то, что собрано
СЕЙЧАС (сверка sha256 до прогона — `verify.sh`), и называй наборы по происхождению (сдаваемое дерево /
черновик), чтобы число не приписали не той ревизии.

**ЛОВУШКА РЕЕСТРА: `project_os_register_update` С НЕСКАЛЯРНЫМ ПОЛЕМ ТЕРЯЕТ ФОРМУ (2026-11-05).**
Правка поля ЦЕЛИКОМ (`update` с многострочным `what`) не дополнила запись `TD-0005`, а ЗАМЕНИЛА её, и
файл был перезаписан (`write_mode: rewrite`, «форма потеряна»): разделы (1)–(7) исчезли. Разделы (2)–(5)
удалось поднять ДОСЛОВНО из журнала сессии (журнал хранит РЕЗУЛЬТАТЫ чтения файла, а в них — строки с
НОМЕРАМИ: `.tmp/восстановление-реестра.mjs`), (6)–(7) восстановлены по §3.170.3/§3.170.4, НАЧАЛО (1) не
восстановлено — и это записано в самой записи, а не сглажено. Правило: поле реестра правится ВСТАВКОЙ
через `edit`, а `update` — только СКАЛЯРНЫМИ полями (status/tags/связи/даты); после любой правки реестра

нечем — копию перед правкой держи сам.

**ЛОВУШКА ПУСТОГО РЕЕСТРА: `register_add` В РЕЕСТР С МЕТКОЙ `[]` ОСТАВЛЯЕТ МЕТКУ И ЛОМАЕТ YAML

здесь единственная защита: `registers/` в git не отслеживается, откатывать нечем.

## Системная модель: собрана, доходит до входа в системный вызов (2026-10-03)

`qemu-system-e2k` — **другая** модель, не та, что под паспортом: полная машина `-M e2k`, а не
процесс. Публично доступен только PoC сообщества (ветка `e2k-softmmu`, QEMU 6.0.91, 2021-08-26):
у МЦСТ системного режима нет вовсе, у ALT он рабочий (QEMU 7.2, грузит ALT-образы), но только
бинарём под e2k — исходников в открытом доступе нет. Наша сборка — `tools/qemu-e2k/system/`
(скрипты; sha256 воспроизводится побайтово), разбор и замеры — `docs/e2k-qemu-system.md`.
Замер: машина стартует на нашем ELF и **исполняет наши байты**. Геометрия окна приведена к нашей
одной правкой (`osnova-local-system-window.patch`: `wd.size` 16 → 24, то есть `size_q = 12`) —
после неё программа **доходит до ВХОДА в системный вызов** и встаёт на нём (`EXCP_ILLEGAL_OPCODE`
на `0x100358`: `sdisp` в ветке есть только под `CONFIG_USER_ONLY`, а в системном режиме вход в
syscall = вход в ядро). В окне вызова стоит наш ABI: `r0 = 1` (номер `exit`), `r1 = 2` (эталон
записи `11`). Дальше — стена прошивки/ядра: своя прошивка не изобретается, bootblock не
подделывается (решение владельца 2026-10-03) — это названный долг, не задача. Паспорт user-mode
модели этой сборкой не тронут. **Линия ЗАКРЫТА 2026-10-03** (док переведён в `frozen`, §6 дока —
долги по адресатам: МЦСТ — прошивка `e2k.bin` и системные патчи ALT; модель — `sdisp`; наша

## Возврат внутри `если` и место образа: случай 47 ЗАКРЫТ, стена места СНЯТА (2026-10-23, §3.134)

## A4, срез 2: куча массивов — В ПАМЯТИ (2026-10-24, §3.136)

**Состояние рантайма массивов ушло из регистров.** Указатель кучи больше не живёт в `%b[15]`: он
лежит в **первом слове самой области кучи** (`heapAddress` = `HEAP_OFFSET`), а `%b[15]`
(`heapSlot`) несёт только её адрес — величину постоянную и одинаковую во всех окнах. Причина именно
такая: `%b[N]` адресуется **только внутри своего окна**, а у вызываемой окно своё (`setwd`/`setbn` её
пролога роста), поэтому состояние, общее для процедур, регистром плоскости не выражается. Пролог
образа кладёт адрес ячейки `movtd` и **пишет в неё начало кучи**; `создать` и `добавить` работают
через `ldd`/`std` — 64-битного литерала внутри последовательностей операций **нет** (их форму
раскладка берёт заранее и без плоскости, §3.135).

**Измерено:** `создать` — 4 команды (`ldd`, `std`, `addd`, `std`), `добавить` — 12 (хвост из трёх:
прочитать ячейку, сдвинуть на элемент, положить назад). Шлюз массивов целиком зелёный — **17/17**,
включая «два массива» и **FIR = 181**: числа ПОТОКА НОСИТЕЛЕЙ удержаны, а числа УПАКОВКИ сдвинулись и перемерены (см. ниже) — сдвиг кучи остался ровно на
слово заголовка (`создать`) и на элемент (`добавить`), поэтому последовательности рантайма стали длиннее: `fir` команд 229 → **255**, пакетов 177 → **209**, линейных байт 1896 → **2104**, пакетами 1792 → **2000**, слогов 87 → **76**, адресной арифметики 88 → **86**; пять ядер команд 821 → **895**, раскладка 8800 → **9624**, линейно 6856 → **7448**, пакетами 6384 → **7080**. ## A4, срез 3: адрес ячейки кучи — в окно вызываемой; стена глубины 2 оказалась стеной МОДЕЛИ (2026-10-29, §3.137)

**`создать` в вызываемой РАБОТАЕТ.** Стена была оконная: кучу адресует `%b[15]`, а `%b[15]`
вызываемой — чужая клетка (закон окна), и адрес в её плоскость никто не клал. Теперь его кладёт
**пролог роста самой процедуры**: носитель `IR.array_slot` (одна `movtd imm64(heapAddress) → %b[15]`)
встаёт в группу `[рост окна, пролог значений, шаг адреса ячейки]`, обязательно ПОСЛЕ
`setwd wsz = 12`/`setbn rsz = 7`. Отдельный носитель, а не третий шаг `IR.array_values`: у шага своя
форма, и раскладка обязана знать её длину заранее и без плоскости (`twoPassLayout#carrierFormWithReason`).
Куча при этом ОДНА на все процедуры (она в памяти, §3.136) — различающая проба П2 это и проверяет.

**Резерв `%b[15]` — УСЛОВНЫЙ** (как у арены и коллекций): клетка закрепляется только у образов, где
какая-то вызываемая процедура выделяет массив, поэтому у всех прочих программ (и у всех программ с
закреплёнными числами) не изменилось ничего — проверено полным прогоном. Слово «резерв сделан» уезжает
в `imageOfCarriers` и сверяется там с нуждой, сочтённой ПОСЛЕ раскладки: разойдись они — `создать` в
вызываемой остаётся названным отказом, а не читает чужую клетку.

**`добавить` в вызываемой — отказ, но причина переназвана честно: она РАЗМЕРНАЯ.** Пяти его ролям нужно
пять клеток, бюджет вызываемой даёт три (`one` и `scratch2` — псевдонимы), поэтому последовательность
посчитала бы новую длину как «прочитанная + 0».

инструкции между переходом и целью НЕ исполняются, поэтому регистр приходит на цель со значением,
записанным ДО перехода, — пара «сравнение → переход» выбрасывала значение, и цель читала **мусор**.

## ПРАВИЛО 1 (из случая 48): отказ, воспроизводящийся на МОДЕЛИ и НЕ воспроизводящийся на ЖЕЛЕЗЕ, — долг МОДЕЛИ

Формулировка обязательна к применению: если конструкция отказывает (или петляет) на модели, а тот же
образ на живой машине проходит замером, то **слой = МОДЕЛЬ**, запись идёт классом «модель»
(`docs/verification-debt.md`, случай 48), и **отказ снять нельзя** — все числа проекта снимаются с
модели, поэтому снятие означало бы объявить место проверенным там, где проверять нечем. Смена политики
верификации («принимать это место по железу») — решение владельца, а не побочный эффект правки.
Обратная сторона того же правила: **программа, которая на модели РАБОТАЕТ, а на железе падает, — это
НЕ долг модели, а долг НАШЕГО образа** (случай 52: сегменты перекрывались, модель терпела) — здесь
модель как раз права не была, и виновата сборка.

## ПРАВИЛО 3 (из срезов 4 и 5): СОВПАДЕНИЕ МОДЕЛИ И ЖЕЛЕЗА — НЕ ДОКАЗАТЕЛЬСТВО ВЕРНОСТИ

Два замера, и они разные по знаку:

## ПРАВИЛО 4 (из ловушки среза 5): ОТЧЁТ О ЖЕЛЕЗЕ ЧИТАЕТСЯ ПО СТРОКЕ «ХОСТ» — ДО ССЫЛКИ НА НЕГО

`tools/e2k-hardware/report.txt` — файл, который **переживает прогоны**: он может остаться от
ЛОКАЛЬНОГО запуска под WSL1 (`хост: x86_64 / Linux 4.4.0-…-Microsoft`), и прочитать его как машинный
ничего не стоит. Машинный прогон отличается ровно одной строкой — `хост: e2k / Linux <ядро>`: её читают
**ПЕРВОЙ**, до любой ссылки на отчёт и до любой цифры из него. Замер среза 5: прежний `report.txt`
(«совпало 29, расхождений 2») был снят локально — числа выглядели машинными, а машинными не были.
Прогон считается машинным **только если** в отчёте есть строка `хост:` со значением, отличным от WSL1
(`…-Microsoft`); иначе это замер модели под другим именем, и называть его железом запрещено.

## Правила работы в этом дереве

- **Проверять состояние, а не вывод команды** (дважды окупилось: молча не применившаяся правка;
  массовое удаление строк, снёсшее файл оракула, — восстановлен из git).
- **Код возврата — 8-битный канал, и это ловушка для широких чисел** (измерено 2026-09-27).
  Всё, что наблюдается через `exit`, видно только как `значение mod 256`: тело
  `70000 div 10 = 7000` даёт код **88**. Поэтому «46 против 2350» у 21 и «188 против 956» у 25 —
  не дефект счёта (46 = 2350 mod 256, 188 = 956 mod 256), и обе прежние пробы по ширине
  (`.tmp/osnova-quiet-lie.ts`, `.tmp/osnova-literal-probe.ts`) **не различали** дефект и усечённый
  канал: их ответ читался через тот же `exit`. Различает **усилитель внутри программы** —
  операция, не сохраняющая сравнение по модулю 256 (умножение/деление), после которой ответ
  влезает в байт: `.tmp/osnova-byte-width-discriminator.ts` (`movts 1000` → ÷10 = **100** против
  23 при усечении). Оракул корпуса `src/scripts/examplesE2k.audit.test.ts` сравнивает код возврата
  с `expected.txt` напрямую, значит **эталон ≥ 256 через него пройти не может** — таких записей
  сейчас нет (это проверено), но при появлении это структурный отказ, а не дефект.
- **`div` с вычисляемым делимым давал не число — ПОЧИНЕНО 2026-09-27** (`7b52684`): `978 div 10`
  (оба операнда — литералы) давало **97**, а `(1000 - 22) div 10` — **0** вместо 97. Причина:
  в `regInstructionUses` (`src/vliw/regGraph.ts`) знали `div` и `rem`, но не знали `idiv`
  (понижение целочисленного деления), поэтому узел получал ноль предшественников и `sdivs`
  выдавался раньше записи делимого и делителя. После правки — **97** (замер
  `.tmp/osnova-div-order-check.ts`). Сторож — на класс: все бинарные операции IR обязаны
  объявлять чтение обоих операндов (`src/vliw/regGraphWar.test.ts`, негативный контроль пройден).
  Усилитель для зеркал теперь можно брать и делением.
- **Взял — довёл в том же коммите; не довёл — отдал с конструкцией.** Плоскость не пробка.
- **Тяжёлые прогоны — с `TEMP=D:\tmp-osnova`**: на `C:` около 2 ГБ, `ENOSPC` уже срывал прогон.
- **Сторож, собравший НОЛЬ проверок, выглядит зелёным так же, как работающий** (случай 22,
  `docs/verification-debt.md`). Поэтому полный прогон считает **собранное**, а не только файлы:
  `npm run check:test-files` требует, чтобы каждый файл отчёта и **каждая запись негативного
  контроля** (`src/scripts/e2kLayoutNegativeControl.ts`) собирали проверки своим конфигом; запись,
  мёртвая по структурной причине, называется по имени в `KNOWN_DEAD_CONTROLS`. Замер повода:
  **23 записи из 36** собирали ноль четыре дня и выглядели зелёными. Новая проверка обязана быть
  проверена негативным контролем — иначе это сторож, который сам мёртв.
- **Не запускать два полных прогона одновременно**: `.tmp/vitest-report.json` общий, чужой
  прогон даёт ложное «красное».
- **Убитый по таймауту `qemu-e2k` — ЗОМБИ, и он держит файл образа** (Windows, измерено 2026-10-29).
  Проверки, которые держат петлю модели, кончаются убийством процесса по таймауту; если процесс не
  успел умереть, следующий заход падает на `fs.writeFileSync` с `UNKNOWN: unknown error, open
  '…\.tmp\a4s3-write2-loop.elf'` — и это выглядит как красное у проверки, хотя модель тут ни при чём.
  Признаки: проверка падает за десятки миллисекунд (настоящий прогон — секунды), а в системе висят
  процессы `qemu-e2k` с прошлых заходов. Лечение: завершить их по именам (**не** «чинить» проверку),
  удалить образы пробы (тест перепишет их сам) и перегнать шлюз. Проверено: до лечения —
  `arrayWriteDepthTwo` красный 3/3 за 60 мс, после — 4/4 зелёные, петля держится 5063 мс.
  **Отсюда шаг подготовки, а не лечение по факту: ПЕРЕД прогоном `gate:qemu` (и любого модельного
  шлюза) процессы `qemu-e2k` от прошлых заходов завершаются ПО ИМЕНАМ.** Проверка дешёвая, а цена
  пропуска — ложное «красное» у честной проверки (срез 5 гонял шлюз десятки раз).
- **`git worktree remove --force` в этом дереве опасен:** он идёт по junction'ам и удаляет
  **содержимое** целей, а не ссылки. Измерено 2026-09-27: сначала пропал `node_modules`
  (симптом — `'tsx' is not recognized`), затем `.tmp/e2k-sources` (12 проверок в 5 audit-файлах
  покраснели). Восстановление: `npm install` для `node_modules`; зеркало источников — по описи
  `docs/e2k-sources-raw.md` (в git его нет), с обязательной сверкой sha256 архива
  (`15b29347…`). Правило: воркеров запускать с `isolation: shared`, а не в worktree.
- **Вывод внешнего инструмента разбирать ПО АДРЕСАМ, не по порядку строк.** Дизассемблер МЦСТ
  печатает `nop` между командами, и разбор по индексу строки съезжает со второго образца: так
  `addd` был прочитан как `nop`, и это дало ложный вывод «порт читает наши байты как чужую
  команду» (отозван в тот же день). Готовый разбор — `parseObjdumpOutput` (поле `address`).
- Расхождения раскладывать **по слоям** (обвязка → понижение → кодировка → модель); в данных
  поле `e2k.layer`; «дефект модели» без разложения не пишется.
- Границы имеют **сторож поведения**: граница обязана быть отклонена раннером, иначе тест краснеет.
- **Проба с системным вызовом обязана ставить окно (`setbn`), как `buildHelloProgram`.** Иначе окно
  сломано, и порт падает утверждением про полуслог `AAS2`, которое легко принять за дефект
  кодировщика: так ложный вывод «сравнение в модели не исполняется» прожил два коммита (отозван
  в `a59262f`). Сами формы сравнения (`cmplsb`, ALF7) верны и исполняются — проверено на
  работающих примерах `45` и `46` их же конвейером.
- **`setbn` в рантаймах не ставить:** пролог образа даёт `rsz = 7` (шестнадцать единиц области
  вращаемых регистров), а `rsz = 5` сужает её до двенадцати — `%b[11]` и `%b[12]` перестают
  адресоваться, и модель встаёт исключением на первом обращении.
- **Адрес в память кладётся `movtd`, а не `movts`:** `movts` такой константы не несёт (адрес
  буфера печати — `0x101EC0`, 21 бит). Работающий образец — `buildHelloProgram`.

  --registration-token <token>`; `--url https://gitflic.ru` даёт HTML вместо JSON и не работает.

| форма | `quick` | `npm run typecheck`, `lint`, `docs:check`, `check:language-schema`, `check:yaml-drift`, `validate:spec`, `check:test-files` | рассинхрон кода, доков, реестра и схемы языка — тот самый класс «тихой лжи» |
| поведение | `tests` | `npm test` | оракулы VM/раскладки, шлюзы e2k, закреплённые числа (458 / 53 / 511, FIR 181, образ 6856) |
| смысл | `gate` (по кнопке) | `golden`, `gate:reorder`, `gate:pack` | изменения, которые точечные тесты не видят: эталонные приложения, независимость от порядка команд, упаковка |

**`npm run ci` в конвейере НЕ используется намеренно:** он рвётся на первом падении и прячет
все следующие шаги (измерено: так был скрыт красный `validate:spec` — `src/scripts/ciChain.ts`).
В CI каждый шаг — отдельная строка, чтобы отказ называл свой слой.

**`gate:qemu` в конвейер НЕ включён:** он требует собранной модели с паспортом
(`src/e2k/qemuModelPassport.ts`), а на машине агента модели нет. Ложное «зелено» без модели
хуже, чем честное «не проверено»: шлюз гоняется локально или на лабораторной машине, а число
заносится в отчёт. Кто включит его в CI без модели — получит красное, не связанное с кодом.

## Воспроизведение локально (то же, что в CI)

```powershell
npm ci --prefer-offline --no-audit --no-fund
npm run typecheck; npm run lint; npm run docs:check
npm run check:language-schema; npm run check:yaml-drift; npm run validate:spec; npm run check:test-files
npm test
npm run golden; npm run gate:reorder; npm run gate:pack   # смысловой шлюз
```

Зелёный `quick` + `tests` на своей машине и на агенте — **разные** доказательства: локально
проверяются изменения рабочего дерева, на агенте — ровно то, что лежит в ветке.

## Владелец — НЕ программист: issue, PR и слияния ведёт агент (2026-11-12)

Владелец проекта не читает код, диффы и логи CI и не разбирается в `issue`/`pull request`.
Это **не пробел, который надо закрыть**, а условие работы: ему там нечего смотреть, и просить
его об этом — значит тратить его время и подменять работу агента. Весь цикл от «надо сделать»
до «влито в `main`» обязан проходить **без него**.

**Агент делает сам, не спрашивая:**

- заводит `issue` с задачей или дефектом (текст — для истории и для следующей сессии, не для владельца);
- ветка `feat/…`/`fix/…` → коммит → `git push origin <ветка>` → PR (`gh pr create` для GitHub-зеркала);
- ждёт проверки; **красные чинит** — это его работа, а не повод звать владельца;
- зелёные сливает: `npm run pr:merge -- --apply` (без `--apply` — только показывает и объясняет);
- прибирает: бот зависимостей сгруппирован (`.github/dependabot.yml` — ≤3 PR вместо десятка),
  слитые ветки удаляются настройкой репозитория (`delete_branch_on_merge: true`);
- отчитывается владельцу **обычными словами**: «что теперь работает», «что сломалось»,
  «дальше предлагаю X», без жаргона и без ссылок на строки кода.

**К владельцу идёт ТОЛЬКО решение** — вопрос из 2–3 вариантов, без кода и без «посмотри»:

- необратимое: стереть данные, переписать историю, потратить деньги, выдать доступ;
- смена направления: что вообще строим;
- смена политики верификации (например, «числа — с модели или с железа»);
- точка, где агент обязан остановиться по названному отказу.

**Запрещено в отчётах и вопросах владельцу:** «посмотри diff», «одобри ревью», «проверь лог CI»,
«прочитай PR». Зелёные проверки — **работа агента**, а не приглашение к верификации.

**Почему слияние не верит `mergeStateStatus: CLEAN`** (проверено 2026-11-12: защита ветки `main`
на GitHub не включена — `gh api repos/…/branches/main/protection` → 404). Без защиты GitHub
выставляет `CLEAN` и пока проверки ещё идут, поэтому слияние «по CLEAN» влило бы PR с красными
тестами. Решение принимается по списку проверок (`statusCheckRollup`): пустой список — «не знаю»,
а не «хорошо». Границы и оракул — `src/scripts/prMerge.ts` + `src/scripts/prMerge.test.ts`.

```powershell
npm run pr:merge                          # сухой прогон: что можно слить и почему ждём остальное
npm run pr:merge -- --apply               # слить всё зелёное и безопасное
npm run pr:merge -- --only 115 --apply    # один конкретный PR
```

## Порядок работы (ветки, MR, теги)

> В GitHub-зеркале (`origin`) то же самое называется **PR** и создаётся агентом (`gh pr create`);
> ниже — терминология GitFlic (основной репозиторий), где это **MR** и кнопка в веб-интерфейсе.


- **`main`** — только проверенное: прямой push запрещён защитой ветки, слияние — через MR админом.
- **`feat/<тема>`** — рабочая ветка агента; одна ветка = одна тема, влили — удалили.
  **`fix/<тема>`** — то же для исправлений (имя нужно только читаемости истории).
- **Атом = один коммит** (правило проекта). Сообщение: что изменено, чем измерено, какие числа
  сдвинулись и почему.
- Перед push — `npm run typecheck`; перед MR — `npm test`. Агент прогонит то же на своей машине,
  но локальный зелёный и зелёный на агенте — РАЗНЫЕ доказательства (у агента ровно то, что в ветке).
- Конвейер `quick` + `tests` стартует сам на каждый push. `gate` (эталоны, перестановка, упаковка) —
  кнопкой перед слиянием смысловых изменений; кнопка нажимается в веб-интерфейсе конвейера.
- **В MR — таблица**: «что сдвинулось / было → стало / чем проверено». Без чисел MR не сливается.
- Теги `vX.Y.Z` — на `main` после зелёного `gate`; в описании релиза те же числа.
- `gate:qemu` и железо — **вне** CI и вне MR-гейта: их числа приносятся в отчёт и в сообщение коммита.
  Ложное «зелено» без модели хуже честного «не проверено».

```powershell
git fetch origin --prune
git switch -c feat/<тема>        # от свежего origin/main
# … работа, локальные проверки, коммит …
git push                          # уходит в GitFlic (origin), конвейер стартует сам
```

MR создаётся в веб-интерфейсе: «Запросы на слияние» → «Создать», источник `feat/…`, цель `main`.

## CI/CD на GitFlic: четыре слоя (сверено конвейером #6, 2026-11-12)

| Слой | Задание | Когда | Что доказывает |
|---|---|---|---|
| **форма** | `quick` | каждый push | типы, линт, доки (169 / 0 ошибок), схема языка, дрейф YAML, спецификация |

| **смысл** | `gate`, `qemu`, `hardware` | по кнопке | эталоны/порядок команд/упаковка; шлюз QEMU (только при собранной модели); кит на стенде E8C2 |
| **доставка** | `release` | по тегу + по кнопке | `npm run build`, `npm run hardware:kit`, `npm pack` — артефакты задания |

**Честные границы (все проверены, а не предположены):**

  Слой `release` объявлен `only: tags` и запускается кнопкой в интерфейсе GitFlic.
- Агент не запущен ⇒ задания висят в очереди; «PENDING» — не «зелено».
