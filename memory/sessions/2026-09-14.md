# 2026-09-14 — регистровое ядро VM (первый срез)

Ветка `reg-vm`. Стековая VM **не тронута** — регистровый бэкенд построен рядом.

## Зачем этот слой

Стековая машина имеет один последовательный разделяемый ресурс — вершину стека:
каждый `push`/`pop` его трогает, поэтому независимые цепочки вычислений
сериализуются, а планировщик был вынужден перейти на in-order упаковку. В
регистровой форме зависимость видна по номерам (`add d, a, b`), то есть ILP
возможен по построению. Это предпосылка для VLIW, а не украшение.

## Что сделано

1. **`src/runtime/vm/regcode.ts`** — формат `osnova-reg` (`.osvreg.json`):
   трёхадресные инструкции (`d`, `a`, `b`), абсолютная адресация кода, тот же
   пул констант, что в `.osvbc`; `localToVreg` (отладочная карта), `vregs` —
   размер регистрового файла процедуры; валидатор `isRegModule()`.
   Опкоды: `const`/`const.true|false|null`, `move`, `add…ge`, `and`/`or`/`not`,
   `invoke`, `call`, `jmp`/`jmp_if`/`jmp_if_not`, `ret`, `obj.new/get/set`.
2. **`src/compiler/regcodegen.ts`** — AST → регистровый код. Переменная занимает
   фиксированный vreg (0..localsCount-1), временные выражения — по отметке
   (`RegAllocator`: mark/alloc/freeTo). Литерал в `пусть x = …` пишется прямо в
   регистр переменной. **Один AST на два бэкенда** (компилятор отдаёт
   `CompileResult.moduleAst`).
3. **`src/runtime/vm/reginterpreter.ts`** — регистровая VM (`RegVM`): кадр =
   регистровый файл, аргументы — регистры `0..argc-1`, семантика опкодов
   повторяет стековую (`add` со строками = конкатенация, деление/остаток на ноль
   = ошибка, `obj.new` без прототипа, объекты/массивы — ссылки с мутацией).
4. **`src/oracle/parity.ts`** — дифференциальный оракул: один исходник →
   стековый артефакт + регистровый, обе VM с одной фабрикой хоста, сверка
   **трассы вызовов** и итогового значения. `runParity()` возвращает
   `{ok}|{skipped}` — вне среза бэкенда отдаёт явную причину, а не тихое
   расхождение. CLI: `npx tsx src/cli.ts parity file.osnova` (0/1/2).

## Оракул (канон «слой без оракула не считается»)

- Трасса — только вызовы хоста + возврат точки входа: внутренние возвраты
  вложенных процедур стековая VM наружу не отдаёт, поэтому и регистровая их не
  пишет (иначе сравнивались бы разные определения трассы).
- Тесты: `src/oracle/parity.test.ts` (30) — целевой кейс, приоритеты, строки,
  ветвления, короткое замыкание, рекурсия, вложенные вызовы, объекты/массивы,
  хост-вызовы, реальные фикстуры, отказы вне среза;
  `src/compiler/regcodegen.test.ts` (21), `src/runtime/vm/reginterpreter.test.ts` (19).
- У части кейсов задан `expectedReturn` — независимое ожидание (оракул оракула).
- `func_params.osnova` (реальная фикстура) → 152 на обеих VM.

## Находки (важно для следующих сессий)

- **Баг парсера (вечный цикл/OOM) — исправлен** (см. «Часть 2»): корневая причина —
  `advance()` не двигал `pos` с токена `конец_файла`, а `syncToStmtBoundary()`
  возвращался на новой строке, не потребляя её. Любой цикл восстановления
  `while (peek() !== "конец_файла")` зацикливался навсегда.
- **`тип Имя = { … }` (запись через `=`) — теперь парсится** (LLM-эргономика).
- `compileProgramToReg` использует стековый `compileProgram` только как источник
  префиксации имён процедур — при полном паритете это надо снять.
- **Дрейф `docs/osnova/language-schema.json`** (не мой): `npm run check:language-schema`
  падал и до правок — в схеме нет `чистый`, `система.оценить`, `система.оценить_в`
  (появились в прошлых сессиях). Лечится `npm run generate:language-schema`
  (+70 строк). Не делал, чтобы не мешать чужие правки в своём диффе; гейт
  `npm test` из-за этого красный.

## Часть 2 — баги парсера (по замечанию владельца)

Владелец: находки парсера — не «отложить», вечный цикл превращает опечатку в
зависание/OOM. Закрыто полностью:

1. **Вечный цикл (корень):** `parser.ts` `advance()` теперь двигает `pos` и на
   `конец_файла` (раньше стоял запрет — токены кончались, `pos` замирал).
   `syncToStmtBoundary()` получил **гарантию прогресса**: если восстановление
   ничего не потребило (текущий токен — «голова инструкции»), оно съедает один
   токен. Плюс `skipNewlines()` после успешного разбора — чтобы границы блоков
   (новые строки перед `конец`/`иначе_попытка`) шли прежним путём и «активный
   съедатель» в норме не участвовал.
2. **`поймать` — алиас `иначе_попытка`** (`LLM_KEYWORD_ALIASES` + `catch`).
   Работает и в парсере, и в исполнении (`попробовать … поймать ошибка` реально
   перехватывает `выбросить`).
3. **`тип Имя = { … }`** — запись через `=` принимается (знак `=` пропускается,
   дальше общий разбор тела). Перечень `тип X = а | б` не сломан, `тип X { … }`
   канон тоже работает.
4. Тесты: `src/compiler/parser-robustness.test.ts` (22 теста) — каждый с лимитом
   времени 5 с, поэтому вечный цикл падает как падение теста, а не как OOM всего
   прогона; 9 видов мусорного ввода (пустой файл, обрывы, незакрытые блоки) —
   на каждом разбор завершается ошибкой.
