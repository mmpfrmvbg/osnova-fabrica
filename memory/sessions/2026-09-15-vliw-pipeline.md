# 2026-09-15 — объединённый конвейер VLIW

## Задача от владельца

После отчёта по упаковке владелец назвал следующий шаг: **не Фаза 3, а объединение
перестановки и упаковки**, потому что «две половинки, которые не проверены вместе» —
это неизвестность, а не сделанная работа. Требования:

- оракул: тот же `gate:pack`, но с **четырьмя конфигурациями** (линейно,
  перестановка, упаковка, перестановка+упаковка), программа прогоняется 4 раза,
  все результаты совпадают;
- плотность упаковки после объединения **≥** плотности от одной упаковки;
- отдельно: усилить формулировку про шаги VM — «не метрика скорости, не
  использовать в отчётах как ускорение», жирным, первой строкой, в обоих документах.

Подключение к CLI не просили (и не делали: сначала оракул).

## Что сделано

1. **`src/vliw/vliwPipeline.ts`** — `buildVliwConfigs(module, model, options,
   defects?, pipelineDefects?)`: четыре конфигурации. Ключевая идея — каждая
   конфигурация отдаёт `keys`: `keys[элемент][слот]` = индекс инструкции в
   **исходном** коде. Без этого конфигурации несравнимы: переставленные инструкции
   это глубокие копии, а сравнение по содержимому сломало бы `jmp*` (адрес входит в
   содержимое и меняется законно).
2. **`applyReorderToWholeModule`** теперь возвращает `originalIndex` (обратную
   карту) — чистое добавление, поведение не менялось.
3. **`src/vliw/packGate.ts`** — gate переписан на четыре конфигурации. Что чем
   проверяется: `packets` — ПОСЛЕДОВАТЕЛЬНОСТЬ с эталоном; `reorder` — НАБОР +
   трасса вызовов + значение + ошибка; `reorder+packets` — набор с эталоном И
   **порядок** с `reorder`. Плюс `verifyPackets` для обеих упакованных и требование
   к плотности.
4. **`PipelineDefects { packOriginalAfterReorder }`** — пятый дефект, про **стык**
   конвейера, а не про упаковщик.
5. Тесты: `src/vliw/vliwPipeline.test.ts` (12) и обновлённый
   `src/vliw/packGate.test.ts` (12, включая негативный контроль в CI). Аудит
   `packetPacker.audit.test.ts` расширен: флаги дефектов конвейера тоже не выходят
   за пределы негативного контроля, и конвейер не подключён к рабочему пути.

## Измерено (`npm run gate:pack`, 19 программ, модель e2k 24 канала)

```
все четыре конфигурации эквивалентны на всех 18 завершающихся программах
verifyPackets — ok в обеих упакованных конфигурациях
элементов: 1575 (linear) / 1575 (reorder) / 1118 (packets) / 1089 (reorder+packets)
плотность упаковки 1.41 (упаковка) → 1.45 (перестановка+упаковка)
исполнено инструкций 13709 — ОДИНАКОВО во всех четырёх конфигурациях
шагов VM 13709 → 7577   (не скорость — см. шапку memory/_index.md)
```

Требование владельца выполнено на каждой программе: плотность после объединения не
ниже, чем от одной упаковки. На 14 программах выше (`ilp-high` 1.63 → 1.83,
`cycle-chains` 1.61 → 1.76), на 5 совпадает.

**Перестановка меняет порядок на 16 из 19 программ** — то есть конфигурация
`reorder` не пустая, и совпадение объединённой конфигурации с ней по порядку
что-то значит.

## Главное открытие: стык ловится ТОЛЬКО сравнением порядка

Пятый дефект («на стыке упакован исходный модуль вместо переставленного»):
верификатор — **0 красных** (пакеты легальны), сравнение по НАБОРУ — проходит
(набор совпадает с эталоном), и только сравнение ПОСЛЕДОВАТЕЛЬНОСТИ с
конфигурацией перестановки краснит gate — на **16 программах** (ровно там, где
порядок отличается).

Вывод, который дороже самого числа: при объединении инструментов проверять надо не
только каждый инструмент, но и **передачу результата между ними**. Сумма двух
проверенных половин не покрывает стык: обе половины были зелены, а стык — нет.

## Ограничение сравнения (записано в коде рядом с проверкой)

Для незавершающейся `todo.osnova` набор с эталоном **не сравнивается**: за один и
тот же лимит шагов упакованная сторона исполняет больше инструкций (шаг VM —
элемент кода, а в пакете их несколько), поэтому длины трасс разные по построению.
Проверяется порядок относительно `reorder` на общем начале, а сама перестановка
сверена с эталоном по набору отдельной строкой. Это ограничение, а не послабление:
первая версия gate сравнивала набор и давала ложное красное на `todo.osnova`, что и
было исправлено.

## Найдено по пути

1. Ложное красное на `todo.osnova` (см. выше) — ошибка сравнения, а не дефект
   конвейера.
2. Расхождение нумерации негативных случаев в `packetVerifier.test.ts` (два «7») —
   поправлено (`c4f1994`).
3. Итоговые числа упаковки в `docs/vliw-ilp-calibration.md` §0 устарели после
   добавления метрики шагов VM — приведены к выводу gate (`e21f1ae`).

## Что не сделано

1. Замеров на железе нет; **шаги VM — не метрика скорости**.
2. Конвейер не подключён к CLI: под флагом `OSNOVA_VLIW_PACKETS`, gate в CI,
   golden-тесты дважды — отдельное решение владельца.
3. Задержки внутри пакета не учитываются: плотность упаковки не является оценкой
   тактов.
4. Оценки тактов у объединённого конвейера нет — счётчики
   `TICKS`/`EXEC`/`BUB_E2` считаются для расписания перестановки, не для пакетов.
