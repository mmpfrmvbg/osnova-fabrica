# 2026-09-15 — решение B и что из него следует

## Решение

**Владелец решил: идём в B.** Уточнённая формулировка (важно, не сокращать):
**«Целевой класс — B: специализированные задачи с высоким ILP. Цель — разноплановый
софт, который работает на e2k, с выигрышем там, где он возможен. Кратное ускорение
везде не является целью».**

B — это **не** «сделать всё быстрым». Это:

- строить **разноплановый** софт, который идёт на e2k;
- стремиться к выигрышу там, где он возможен (высокий ILP);
- признавать, что программы с низким ILP не ускорятся — это **свойство задачи, а не
  дефект**.

**Следствие для подмножества e2k:** оно должно быть достаточно **широким**, чтобы
поддерживать разноплановый софт, а не одну нишу. Иначе инфраструктура окажется
построена под ML-инференс (или DSP, или обработку сигналов), а остальной софт
останется без эмиттера. Требования — `docs/e2k-subset-requirements.md`.

Источник: прямой промпт владельца от 2026-09-15. Записано в `memory/_index.md`
(блок «Стратегическое решение: B»), следствия и фазы 3–7 —
`docs/vliw-phases-plan.md`.

| фаза | что делается |

## Доступ к железу: ни железа, ни симулятора

Ответ владельца 2026-09-15. Прямое следствие: Фаза 6 не закрывается, а критерии Фаз
3–4 **обязаны** опираться на внешний эталон (опубликованные примеры кодировки,
независимый дизассемблер), иначе доказывают только самосогласованность. Реестр —
`docs/hardware-debt.md` (разделы 3.1–3.5).

## Чего решение НЕ содержит: конкретной задачи

B — это **класс**, а не задача. Кандидаты названы владельцем: ML-инференс, DSP,
обработка сигналов. От выбора зависит:

- какое подмножество e2k специфицировать (FMA и векторные операции — для
  инференса свёрток; насыщение и фиксированная точка — для DSP; табличные операции
  и плавающая точка — для обработки сигналов);
- какой корпус строить (матричное умножение / свёртка / БПФ);
- как измерять выигрыш.

**Выбор — за владельцем.** Пока задача не выбрана, спецификация Фазы 3 не
начинается: иначе специфицируем не то. Требования описаны диапазоном по трём
кандидатам (в плане), это и есть подготовка к решению.

## Методологический вывод, записанный жирным

**Композиция проверенных компонентов не наследует их корректность. Каждое
соединение — отдельный оракул.**

Основание — измерение: перестановка и упаковка проверены по отдельности (обе
зелёные), а дефект их стыка («упакован исходный модуль вместо переставленного») не
видит **ни** верификатор, **ни** сравнение по набору инструкций. Ловит только
сравнение ПОСЛЕДОВАТЕЛЬНОСТИ с конфигурацией перестановки — на 16 из 19 программ.

Правило распространено на другие стыки проекта: компилятор + эмиттер, эмиттер +
симулятор, симулятор + железо, стековая VM + регистровая VM, планировщик +
аллокатор регистров. Зелёные части не дают зелёного соединения.

## Критический путь при B

```
эмиттер e2k → симулятор e2k → корпус с высоким ILP → замер тактов → (позже) железо
```

«Минимальный эмиттер» (~20 универсальных инструкций) доказывает, что эмиттер
собирает, а симулятор исполняет, но для B не даёт выигрыша: выигрыш даёт
специализация — те операции, на которых задача тратит время. Поэтому сначала
задача, потом подмножество.

## Новый документ: реестр долга перед железом

`docs/hardware-debt.md` — всё, что нельзя подтвердить без реального Эльбруса, с
указанием, чем заменено сейчас и какие выводы окажутся неверными, если модель
разойдётся с железом. Записи: реальная стоимость такта (Д1), плотность упаковки
как оценка качества (Д2), шаги VM (Д3), задержки внутри пакета (Д4), кодировка
e2k (Д5), поведение ОС и оборудования (Д6), ABI вызовов (Д7).

Доступ к железу: **нет**, ни одного прогона не делалось. Это вопрос владельца, а
не секретаря.
