# 2026-09-15 — Шаг 2: VLIW на регистровом коде

## Что сделано

1. **Модель железа e2k** (`src/vliw/e2kDevices.ts`): 24 канала выдачи (6 АЛУ +
   СТ + 3 PL + 6 QP + 4 APB + 4 LIT, стр. 54–56), возможности каждого АЛУ
   (деление и корень — только АЛУ5; запись — только АЛУ2/АЛУ5; чтения нет у
   АЛУ1/АЛУ4), таблица длительностей (стр. 71–72), регистровый файл 256 и
   предикатный 32 (стр. 57), кластеры АЛУ (стр. 194).
2. **Планировщик с задержками** (`latencyScheduler.ts`, стековый код) — вставляет
   `nop`-такты, как настоящий e2k (стр. 70, 193).
3. **Перестановка независимых операций** (`reorderScheduler.ts`, регистровый код)
   — in-order снят там, где это законно. Корректность проверяется явно
   (`validateRegSchedule`).
4. **Счётчики конвейера** (`pipelineCounters.ts`): `TICKS`, `EXEC`, `BUB_E2` в
   терминах `dprof` (стр. 63–64). Не моделируемые счётчики возвращаются `null`,
   а не нулём.
5. **Оракул эквивалентности исполнения** (`reorderEquivalence.ts`) + CLI
   `osnova reorder` — линейный и переставленный код на одной `RegVM`.
6. **Аудит опкодов** (`opcodeAudit.test.ts`, 43 теста) — по СПИСКУ опкодов, а не
   по данным.

## Два дефекта, найденных оракулом (не видели ни статические проверки, ни тесты)

1. **`ret` убегал вперёд.** В регистровом графе у возврата не было
   предшественников, планировщик выдавал его первым, и процедура завершалась до
   срабатывания эффектов (`storage_demo.osnova`, `блокнот.osnova`).
   `validateRegSchedule` проверял рёбра — а рёбер не было. Исправлено: `ret`
   объявлен эффектом, терминаторы закрывают участок, проверка стала структурной.
2. **Адреса многоproцедурного модуля.** `applyReorderToModule` обновлял адреса
   только внутри планируемой процедуры — `codeOffset` остальных указывал внутрь
   переставленного тела (`task_stats.osnova`).

Аудит опкодов сразу нашёл третий пропуск: **`obj.new` не был эффектом**.

## Класс дефекта (формулировка владельца)

Три случая одного паттерна: `state.yaml` с passrate 1.0 при нуле сделанных
атомов; `isolate: false` с протечкой мока между сюитами; `ret` без ребра.
Общее: **валидатор проверяет то, что в артефакте ЕСТЬ, и не видит отсутствия.**
Вывод: неявные барьеры проверять структурно, а не через граф.

## Ошибки, которые я допустил и исправил

1. **Кластеры.** Утверждал «50 из 52 рёбер в одном кластере, 0 в разных» как
   результат. Замер с baseline (`respectClusters: false`) показал: расписания
   **побитово совпадают**, а на корпусе пересечений стало 24 → 25 при неизменных
   тактах. Предпочтение кластера — no-op. Знание о кластерах оставлено как
   ИЗМЕРЕНИЕ (`crossClusterEdges`), а не как оптимизация.
2. **Источник тактов.** Сказал владельцу, что таблицы задержек в руководстве
   нет. Она есть — стр. 71–72, называется «таблица длительностей». Искал не теми
   словами.
3. **39 падений тестов.** Списал на отсутствие `DEEPSEEK_API_KEY`. Неверно:
   каждый мой прогон шёл с флагом `--no-isolate`, который перекрывал уже
   настроенный в конфиге `isolate: true` (коммит `7853a50`). Я сам создавал
   протечку. Голый `vitest run` без ключа даёт **77 файлов, 1598 тестов, 0
   падений**.
4. **Регистровая ветка.** Докладывал как незакоммиченную — была закоммичена в
   `7853a50`. Доверился подагентам, не проверил.

- Точные таблицы главы 12 (`relative_latency` по фазам конвейера) не реализованы;
  погрешность модели против них неизвестна. **Одно правило из главы 12 всё же

  корректно сдвигаются).

## Шаг 3 (2026-09-15): флаг и gate

- Флаг `OSNOVA_VLIW_REORDER` — по умолчанию **выключен**; принимается только
  явное `1`/`true`/`on`/`yes`, включая `0` не считается согласием.
- `OSNOVA_VLIW_CLUSTERS` — отдельный флаг (замер показал: на корпусе не даёт
  ничего).
- Gate `npm run gate:reorder`: весь корпус дважды (линейно и с перестановкой) на
  одной `RegVM`, сверка значения, трассы и набора инструкций. 11 доказано,
  `todo.osnova` исключён явно, итог зелёный, exit 0.

### Негативный контроль gate — что он ловит и что нет

| Что сломали | Gate | Вывод |
|---|---|---|
| выбросили каждое второе ребро графа | КРАСНЫЙ, exit 1, 6 программ из 11 | ловит нарушение порядка |
| убрали `ret` из эффектов | зелёный | не ловит: `ret` защищён структурно |
| убрали рёбра в `ret` | зелёный | та же причина |
| заменили класс `mul` с `fp` на `int` | зелёный | не ловит и не должен: задержки не влияют на результат |

**Вывод:** gate подтверждает корректность ПОРЯДКА, но не корректность модели
задержек и не полноту защиты барьеров. Зелёный gate не означает, что таблица
длительностей верна. Нужны обе проверки: gate (поведение) и `opcodeAudit.test.ts`
(структура). Ни одна не заменяет другую.
