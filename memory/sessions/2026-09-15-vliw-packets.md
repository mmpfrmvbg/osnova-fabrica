(2) диагностика: почему `while.osnova` дала `49` вместо `1049` при упаковке по

## Главное измерение

```
программ 19 (18 завершающихся + todo.osnova исключён явно)
плотность упаковки 1.00 → 1.41   (по программам 1.00–1.72)
элементов 1575 → 1118, широких пакетов 339, инструкций внутри пакетов 796
verifyPackets ok на всех; эквивалентность совпала на всех 18
```

Исполненных инструкций не прибавилось: `while` 249 → 249, `ilp-high` 3986 → 3986,
`cycle-chains` 4783 → 4783. **Плотность упаковки — статика.**

Отдельным числом измерены **шаги VM** (смена элемента кода): по 18 программам
`13709 → 8273`, `while` 249 → 183, `ilp-high` 3986 → 2193. Падают они потому, что
эта VM считает шагом элемент, а пакет — один элемент. Это свойство счётчика VM,
а не такт e2k: замеров на железе нет, поэтому «шагов меньше» **не значит**
«быстрее». Различать эти величины обязательно.

## Причина дефекта (гипотеза владельца не подтвердилась)

Гипотеза: RAW внутри пакета. **Не подтверждена:** на реальной модели e2k
верификатор не нашёл в сломанной упаковке ни RAW, ни WAR, ни WAW (все 14 пакетов
проходили проверку регистров).

Настоящая причина — `call` (передача управления):
- `case "call"` возвращает `callee.codeOffset`, `executeElement` при
  `next !== packetPc + 1` покидает пакет;
- пакет `t=5`: `63(call)` в слоте 0, `68(move d=6 a=0)` в слоте 1;
- `returnPc = packetPc + 1` перепрыгивает остаток пакета → `move` не исполняется;
- измерено: потеряна ровно одна инструкция, шагов `249 → 248`, результат
  `1049 → 49`.

Верификатор первой версии пропустил это, потому что `call` не был в наборе
передающих управление. Дефект нашла **диагностика, а не тесты**. Правило,
которое из этого следует: если верификатор отвергает пакет не по той причине,
которую мы ждём, — это повод перепроверить ПОЛНОТУ набора причин, а не
подгонять данные.

## Второй найденный дефект: `todo.osnova` краснел из-за ошибки сравнения

Сравнение прогонов в режиме «только префикс» (программа не завершается) всё
равно требовало равенства ДЛИН трасс вызовов — а они обязаны различаться: шаг VM
считается по элементам, в пакете инструкций больше, поэтому упакованный прогон
успевает исполнить больше (200000 → 244453 инструкции). Исправлено: в режиме
префикса сравнивается и общий префикс вызовов.

## Что не сделано (честно)

1. Замеров на железе нет; плотность упаковки — статика.
2. Упаковка не подключена к компилятору и VM.
3. Перестановка и упаковка не объединены (вместе не запускались ни разу).
4. Время готовности операндов при упаковке не учитывается: рядом ставятся
   инструкции, независимые по регистрам, а не готовые к одному такту.
5. Класс задачи A/B/C (решение владельца) не выбран — как и запрещено.
