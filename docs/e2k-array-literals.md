# Массив из трёх и более литералов: диагностика ловушки

**Дата:** 2026-09-20
**Зачем:** `пусть a = [1, 2, 3]` в модели **падает**, а `пусть a = [5, 7]` — работает. Это может быть
блокером FIR (там массив из восьми литералов), поэтому сначала причина, потом правка.
**Чем измерено:** `.tmp/array-literals-diag.ts` (трасса каждой команды с адресом, операндом и
происхождением из носителя), `.tmp/array-order-who.ts` (сравнение двух слоёв: регистровый IR до
эмиттера оболочки и носители эмиттера), `.tmp/array-who-reordered.ts` (замер рёбер графа
зависимостей). Правка в этом коммите **не делалась** — только диагностика.

## 1. Что именно происходит

Программа `пусть a = [1, 2, 3]` + `вернуть система.массив.длина(a)`, раскладка регистров **не
применяется** (как и просил заказчик). Образ: пролог (5 команд) → тело (36) → эпилог.

```
0x00a8 # 20 movts  %b[1], %b[0]      [IR.move]                        ; %b[0] = указатель массива
0x00b0 # 21 ldd    %b[1], %b[12], %b[11]   «система.массив.добавить» ; scratch = длина
...
0x0100 # 31 ldd    %b[2], %b[12], %b[1]    «система.массив.длина»    ; ЧТЕНИЕ ДЛИНЫ → %b[1]!!
0x0108 # 32 ldd    %b[1], %b[12], %b[11]   «система.массив.добавить» ; читает по указателю %b[1]
0x0110 # 33 adds   %b[11], %b[13], %b[10]  «система.массив.добавить» ; ← ЛОВУШКА (IP 0x100110)
```

**Ловушка:** `IP = 0x100110`, команда **#33** `adds %b[11], %b[13], %b[10]`. Виновата
**предыдущая #32** `ldd %b[1], %b[12], %b[11]`: она читает слово по адресу, взятому из `%b[1]`,
а в `%b[1]` к этому моменту лежит **длина массива** (2), а не указатель. Порт называет точку
остановки, а не обязательно саму команду — это измерено на `ct` (`docs/e2k-return-port.md`):
гостевая ловушка памяти всплывает на следующей команде.

**Адрес-нарушитель:** чтение по адресу `2` (значение длины) вместо адреса кучи `0x102000`.

## 2. Почему это произошло: порядок переставил эмиттер оболочки

Регистровый IR **до** эмиттера оболочки имеет правильный порядок (замер `.tmp/array-order-who.ts`):

```
#0 invoke  создать            d=1
#1 const   v2 = 1
#2 invoke  добавить args=[1,2]
#3 const   v3 = 2
#4 invoke  добавить args=[1,3]
#5 const   v4 = 3
#6 invoke  добавить args=[1,4]      ← третий append ЗДЕСЬ
#7 move    d=0 a=1
#8 move    d=2 a=0
#9 invoke  длина   d=1 args=[2]     ← чтение длины ПОСЛЕ
```

Носители эмиттера оболочки — уже переставлены:

```
#0 создать   #1 const %b2   #2 const %b3   #3 const %b4      ← константы подняты
#4 добавить(а=%b1, зн=%b2)   #5 move %b0←%b1   #6 добавить(а=%b1, зн=%b3)
#7 move %b2←%b0
#8 длина(%b2) → %b1          ← ВЫЗОВ ДЛИНЫ ПОДНЯТ НАД ТРЕТЬИМ APPEND
#9 добавить(а=%b1, зн=%b4)   ← берёт %b1, где уже длина
```

То есть компилятор порядок не менял — его изменил **планировщик с перестановкой**
(`src/vliw/reorderScheduler.ts` через `emitShell`, `src/e2k/emitterShell.ts`). Перестановка
независимых инструкций разрешена и документирована, но здесь переставлены **зависимые**:
`длина` пишет `v1`, а `добавить` из него читает. Это нарушение WAR (write-after-read).

## 3. Почему граф зависимостей это позволил (замер)

`buildRegDependencyGraph` (`src/vliw/regGraph.ts:203-257`) ведёт по одному «последнему читателю» на
регистр (`lastUse`, строка 214) и строит WAR-ребро **только от него** (строки 240-244):

```
if (def !== undefined) {
  const reader = lastUse.get(def);
  if (reader !== undefined && lastDef.get(def) !== reader) addEdge(reader, i);
}
```

Замер (`.tmp/array-who-reordered.ts`, три литерала) — читатели `v1`: **#2, #4, #6, #7, #10**,
запись в `v1` — **#9** (`длина`):

| рёбра, входящие в #9 | что это |
|---|---|
| `0 → 9` | WAW: `создать` тоже писал `v1` |
| `7 → 9` | WAR **от последнего читателя** (`move` #7) |
| `6 → 9` | **ОТСУТСТВУЕТ** — третий `добавить` читает `v1`, но с записью не упорядочен |

Отсюда и перестановка: узлы #6 и #9 не связаны ни одним ребром, поэтому топологическая сортировка
вправе выдать запись раньше чтения. Более ранние читатели (#2, #4, #6) точно так же не упорядочены —
просто в этом потоке переставился именно #6.

## 4. Почему два литерала работают, а три — нет

При двух литералах `длина` — **последняя** содержательная инструкция процедуры: читателей `v1`
после неё нет, поднимать её не над кем, и порядок совпадает с исходным (статус 2 = верная длина).
При трёх литералах после чтения длины остаётся ещё один `добавить` — и он-то оказывается под
поднятой записью. Порог «3» — не свойство числа элементов, а следствие того, что при `n ≥ 3`
константа последнего элемента и его `добавить` стоят после чтения длины.

## 5. Что это значит и чего здесь нет

* Причина **названа**: WAR-ребро от последнего читателя вместо всех читателей после последней
  записи; планировщик выдал `длину` раньше последнего `добавить`.
* **Правка не делалась** (так требовал заказчик: диагностика отдельным коммитом). Кандидат на
  правку — вести не один `lastUse`, а набор читателей с последней записи и строить WAR от каждого;
  оракулом должно стать падение `[1, 2, 3]` (ловушка на `#33`) при снятом правиле.
* **Оценка влияния на FIR:** массив входа FIR — восемь литералов, то есть тот же путь; пока это не
  исправлено, FIR не соберётся даже при звуковой раскладке. Порядок работ: сначала это, потом
  раскладка (`docs/e2k-regalloc-debt.md`).
* Диагностика сделана на **нераскладочном** потоке: с раскладкой регистров ловушка та же
  (`.tmp/array-min.ts`: и «с раскладкой», и «без раскладки» — авария), то есть дефект не в раскладке.
