# QEMU-System-e2k: системная модель собрана — программу до конца не доводит

**Дата:** 2026-10-03. **Статус: собран и запускается; ОС на нём не загружается** — четыре
преграды названы по слоям в §5. Правок в исходники ветки не внесено ни одной.

**Что просили.** «QEMU-System-EK2» — это `qemu-system-e2k`, **полносистемная** эмуляция
Эльбруса (машина + ядро), в отличие от **user-mode** `qemu-e2k`, которой измерены закреплённые
числа `src/e2k/**` и `src/vliw/**` (паспорт — `src/e2k/qemuModelPassport.ts`). Это два разных
эмулятора, и путать их нельзя: паспорт описывает только второй.

---

**Вывод.** На x86_64-хосте публично доступен только PoC сообщества — его и собрали. Рабочий
системный QEMU ALT недостижим: это e2k-бинарь (на x86 не запускается), а патчей в открытом
доступе нет. Добыть их — отдельный заход через площадку (§6, шаг 4), а не техническая задача.

**Почему chroot.** На современном Alpine 3.24 (gcc 15.2.0, meson 1.11.1) `configure` проходит,
а `ninja` падает — QEMU 6.0.91 с новым инструментом несовместим:

- `hw/vfio/pci.c:2833: error: implicit declaration of function 'basename'`;
- `fpu/softfloat.c` + `fpu/softfloat-parts.c.inc:1294: error: conflicting types for 'parts128_compare'`.

Alpine 3.14 — ровесник ветки; на нём собирается **без правок исходников**. `ninja` собирает
`qemu-system-e2k` целиком (1081 шаг), предупреждения про отсутствующие подмодули
(`ui/keycodemapdb`, `dtc`, `slirp`, `tests/fp/*`) безвредны: `--with-git-submodules=ignore`, а
нужны они графике, FDT-машинам и тестам, которых у цели нет.

## 3. Машина: что в ней есть, а чего нет

| Что | Значение | Где |
|---|---|---|
| имя машины | `e2k` — `Generic E2K Machine (default)`; `-M help` показывает ровно её и `none` | `include/hw/e2k/e2k.h:223` |
| CPU по умолчанию | `e8c`, до 8 CPU (`-smp`) | `hw/e2k/e2k.c:297-308` |
| RAM | MLO `0x0`…2 ГиБ; вторая банка с `0x400000000` | `include/hw/e2k/memmap.h:23-46` |
| BIOS-область | `0x100000000`, 16 МиБ (сюда грузится `e2k.bin`) | там же |
| SIC, IO, PCICFG | `0x110000000`, `0x101000000`, `0x200000000` | там же, `hw/e2k/sic.c` |
| устройства | PCI (iohub → `iohub-pcibridge`), `escc-pci` (serial A/B) | `hw/e2k/e2k.c:224-250` |
| загрузка кода | `-kernel <ELF>` с `e_machine = EM_MCST_ELBRUS`: сегменты грузятся, PC = `e_entry` | `hw/e2k/e2k.c:147-179` |
| без `-kernel` | `qemu-system-e2k: no firmware provided` — нужна прошивка `e2k.bin` | замер 2026-10-03 |

Чего нет — и это не «мелочи», а прямые преграды (§5):

- **`initrd` не поддержан вовсе** — `/* TODO: load initrd */` (`hw/e2k/e2k.c:170`); устройств
  хранения (virtio-blk и любых дисков) у машины нет. Грузить rootfs нечем.
- **bootblock формируется, но гостю не отдаётся.** `generate_bootblock` (`e2k.c:104-145`) считает
  карту памяти и cmdline, но результат только присваивается полю состояния (`e2k.c:168`) и в
  память гостя не кладётся: ядро о RAM и cmdline не узнает.
- **консоль — не та, что ищет ядро Эльбруса.** Драйвер консоли МЦСТ `lmscon` в дереве есть
  (`hw/char/lmscon.c`), но его инициализация закомментирована (`hw/e2k/e2k.c:88-102`), а машина
  отдаёт `escc` (консоль машин Apple). Ядро Эльбруса ищет `lmscon`.
- прошивка `e2k.bin` публично не выложена ни МЦСТ, ни ALT.

## 4. Замер: что модель делает с НАШИМИ байтами

Взяты не «сферические» пробы, а бинари корпуса из `tools/e2k-hardware/bin` — те же ELF, что
идут на живую машину.

| Замер | Результат |
|---|---|
| ELF | `11-минимум-массива.elf`: ELF64, `EM_MCST_ELBRUS`, entry `0x100000`, один `PT_LOAD` |
| старт | модель начинает с `0x100000`; первая команда — `setbn rbs = 0x0, rsz = 0x7, rcur = 0x0` (наш пролог) |
| исполнено | **6** транслированных блоков, **119** строк команд (107 уникальных адресов); дизассемблер QEMU читает наши байты как наши команды (`movts`, `adds`, `sdisp`, `ipd`, `call`) |
| остановка | на первом `call %ctpr1, wbs = 0x4`: `e2k_cpu_do_interrupt: not implemented 9 at 0000000000100338` |
| исключение | **9 = `EXCP_WINDOW_BOUNDS`** (`target/e2k/cpu.h:303`) — ловушка окна процедур |
| исход | обработчик — заглушка: `exit(1)` (`target/e2k/cpu.c:104-113`), код возврата qemu **1** |
| второй свидетель | `01-свёртка-fir.elf`: 8 блоков и та же остановка на `call` |

**Что это значит.** Слой «наши байты → исполнение» на системной модели **работает**: это второй
независимый свидетель после user-mode модели (и первый, где код исполняется настоящей машиной, а
не процессом). Дальше упирается не в наш код, а в обвязку модели.

## 5. Почему ОС не грузится — четыре преграды по слоям

1. **Окно процедур не настроено.** В user-mode геометрию окна ставит сам порт
   (`target_cpu_copy_regs`; наша правка `psize_q = 4`, `size_q = 12` — паспорт
   `src/e2k/qemuModelPassport.ts`). В системном режиме этого не делает **никто**: на реальной
   машине это делает прошивка. Поэтому первый же `call` даёт `EXCP_WINDOW_BOUNDS`.
2. **Доставки исключений нет.** `e2k_cpu_do_interrupt` — заглушка с `exit(1)`; `raise_exception_ra`
   «глотает» только `EXCP_PROC_STACK_BOUNDS`/`EXCP_CHAIN_STACK_BOUNDS` и (под `CONFIG_USER_ONLY`)
   `EXCP_SYSCALL` (`target/e2k/helper.c:296-310`). Любое исключение в системном режиме убивает
   процесс QEMU, а не отдаётся гостю.
3. **rootfs грузить нечем:** `initrd` — `TODO`, дисковых устройств нет (§3).
4. **Прошивки нет, bootblock не передаётся, консоль не та** (§3): даже с ядром в `-kernel` оно
   не получит ни карты памяти, ни cmdline, ни своего вывода.

## 6. Что дальше (по шагам, с ценой)

1. **Окно в системном режиме** — задать `wd.size_q/psize_q` при сбросе CPU (правка машины/CPU +
   паспорт правки, как это сделано для user-mode). Ожидаемый эффект: `call` проходит, следующая
   стена — системный вызов. Цена: правка в чужом дереве, ~десяток строк + перемер.
2. **Доставка исключений** — минимально: не убивать процесс на классах, которые linux-user
   игнорирует; затем — точка входа обработчика.
3. **`initrd` + `virtio-blk`** на уже существующий PCI (iohub) — иначе ядро без rootfs.
4. **Альтернатива: системные патчи ALT (7.2).** Публично их нет; путь — площадка
   (`git.openelbrus.ru` issue/MR, `@qemu_e2k`) или живая машина. Это разведка, а не сборка.

**Названный долг.** У системной модели **нет паспорта-модуля и сторожа** (в отличие от
user-mode: `src/e2k/qemuModelPassport.ts` + `src/e2k/qemuModelIdentity.test.ts`). Пока числа
этого дока держатся только скриптом `build-system.sh` (он печатает вердикт сверки `sha256`).
Паспорт и сторож — следующий шаг, если линия продолжится.

## 7. Как повторить

```bash
# в WSL-дистрибутиве e2k, от root
bash tools/qemu-e2k/system/build-system.sh   # клон → chroot Alpine 3.14 → configure → ninja → сверка sha256
bash tools/qemu-e2k/system/probe-system.sh   # машины, прошивка, прогон корпусного ELF, сохранность паспорта
```

Проба отдельно проверяет **инвариант «паспорт не тронут»**: `sha256`
`/root/qemu-build/qemu-e2k` = `4e37a37243189dec…` (значение читается из
`src/e2k/qemuModelPassport.ts`, а не держится руками). Замер 2026-10-03: совпал — сборка
системной модели user-mode модель не задела.
