# Рекомендации по построению ИИ-центричной ОС (Основа)

> ⚠️ Этот документ содержит исторические ссылки на ранние спецификации и roadmap.
> Эти ссылки относятся к legacy-контексту и не являются источником истины для генерации кода.
> Актуальный канон: `docs/language-v2.md`, `docs/osnova/language-schema.json`, `docs/pipeline-v1.md`, `docs/traces-v1.md`.

Документ фиксирует направления развития платформы Основа с целью сделать систему удобной для ИИ: машиночитаемые данные, семантические аннотации, единый API, единое хранилище взаимодействий, обучение и адаптация, безопасность и архитектура.

---

## 1. Структурированное хранилище данных (семантическая файловая система)

Обычные файлы — бинарные или текстовые данные, которые ИИ каждый раз вынужден парсить с нуля. Чтобы облегчить понимание, данные должны храниться в формате, удобном для машины и с семантической разметкой.

- **Структурированные форматы по умолчанию**  
  JSON, YAML, а в перспективе — RDF-триплеты или графовые базы на уровне файловой системы. Конфиги приложений, пользовательские настройки, метаданные файлов хранятся в машиночитаемом виде.

- **Файловая система как граф**  
  Каждый объект (файл, процесс, окно, устройство) имеет URI и набор атрибутов, связанных отношениями. ИИ может навигировать по графу, не парся тысячи файлов.

- **Индексация и поиск**  
  Встроенный демон/сервис постоянно индексирует содержимое (не только имена, но и семантика, теги, аннотации) и предоставляет API для быстрого поиска. ИИ может задать запрос вида «найди все настройки, где упоминается Wi-Fi» и получить ответ без полного перебора.

*Связь с текущей платформой:* `система.хранилище` и реестр приложений уже дают ключ–значение и метаданные; расширение в сторону графа и индексации можно планировать в рамках системных сервисов (Этап 2+) и описать в отдельной спеце «семантическое хранилище».

## 2. Язык «Основа» как инструмент для ИИ

Язык уже удобен для чтения человеком; для ИИ важно максимум явной семантики в коде.

- **Аннотации и метаданные в коде**  
  Разрешить помечать функции, переменные, типы тегами, описаниями, условиями. Например:
  ```text
  // @description("Открывает файл, возвращает его содержимое")
  // @side_effects("file_read")
  // @performance("O(n) по размеру файла")
  функция прочитать_файл(путь: Строка): Результат<Строка, Ошибка> { ... }
  ```
  Аннотации могут генерироваться компилятором или задаваться вручную. Они помогают ИИ понимать назначение и свойства кода без разбора тела функции.

- **Интеграция с системой типов**  
  Типы предметной области (например, `Температура`, `ИдентификаторПользователя`) дают ИИ более точные выводы. Имеет смысл рассматривать мерность (units of measure) или opaque-типы.

- **Контракты и предусловия**  
  Встроенные утверждения (`assert`) и контракты (pre/post conditions) помогают ИИ верифицировать соответствие кода заявленному поведению.

*Связь с текущей платформой:* спецификации лексера/парсера и компилятора (`compiler-v0.1.md`, `grammatika-v0.1.md`) — естественное место для расширения аннотаций и контрактов в следующих версиях.

## 3. Системные вызовы с явной семантикой

Понятие «чистых» и «нечистых» вызовов уже введено в `system-invoke-api-v0.2.md`. Для ИИ-центричной ОС этого недостаточно.

- **Метаданные к каждому системному вызову**  
  Для каждого invoke указывать: какие ресурсы использует, типичная длительность, отменяемость, побочные эффекты, зависимость от состояния пользователя. Хранить в машинно-читаемом реестре (например, JSON), доступном и рантайму, и ИИ.

- **Динамическое обнаружение API ИИ**  
  ИИ должен иметь возможность узнавать доступные вызовы через реестр (все сервисы и их API). Тогда ИИ может не только использовать существующие функции, но и предлагать новые при обнаружении потребности.

- **Единый интерфейс для всех действий**  
  Любое действие в ОС (открыть файл, отправить сообщение, изменить настройки) доступно через единый API. ИИ управляет системой через этот API, без эмуляции кликов и ввода с клавиатуры.

*Связь с текущей платформой:* реестр приложений и сервисов (`registry-v0.1.md`), `system-invoke-api-v0.2.md` и раздел «Чистота вызовов» — база для расширения реестра метаданных invoke и единого каталога API.

## 4. Самоописываемые форматы данных и код как данные

- **Код как AST**  
  Хранить не только исходный код, но и синтаксическое дерево (AST) в структурированном виде (JSON, MessagePack). ИИ анализирует код без повторного парсинга. При компиляции можно сохранять `.os.ast.json` рядом с байткодом.

- **Связь кода с трейсами**  
  Трейсы выполнения (`trace-format-v0.1.md`) должны содержать ссылки на конкретные строки кода и при возможности на узлы AST. ИИ сопоставляет поведение программы с исходным текстом.

- **Протоколы взаимодействия приложений**  
  Если приложения общаются через IPC, протоколы описываются в машинно-читаемом виде (IDL). ИИ может автоматически генерировать адаптеры и понимать передаваемые данные.

*Связь с текущей платформой:* `trace-format-v0.1.md`, формат байткода и манифестов; расширение трейсов полями `source_line`, `ast_node_id` и введение IDL для IPC — естественные следующие шаги.

## 5. Постоянное обучение и обратная связь

Трейсы и фидбек уже собираются; для центрального ИИ нужно:

- **Единое хранилище всех взаимодействий**  
  Все действия пользователя, вызовы API, ошибки, генерации кода попадают в единое хранилище (озеро данных), доступное ИИ для анализа.

- **Предиктивные модели на уровне ОС**  
  ИИ может предсказывать, какие файлы или приложения понадобятся, и заранее подгружать их или подготавливать контекст.

- **Автоматическая адаптация интерфейса**  
  По частоте использования ИИ может предлагать изменить расположение элементов, горячие клавиши, скрипты для автоматизации рутины.

*Связь с текущей платформой:* `pipeline-llm-osnova.md`, `trace-format-v0.1.md`, golden-трассы; следующий шаг — явное описание формата «озера взаимодействий» и контракта доступа к нему для ИИ.

## 6. Безопасность и приватность

При доступе ИИ ко всем данным системы безопасность и приватность критичны.

- **Разграничение доступа по контексту**  
  ИИ видит только те данные, которые разрешены политикой безопасности, и только в объёме, необходимом для текущей задачи.

- **Прозрачность**  
  Решения ИИ объяснимы и записываются в журнал. Пользователь может спросить «почему ты сделал это?» и получить ответ.

- **Песочница для ИИ**  
  Если ИИ генерирует и запускает код, этот код выполняется в изолированной среде с ограниченными правами (те же принципы, что в `app-manifest-v0.1.md` и песочнице по манифесту).

*Связь с текущей платформой:* `app-manifest-v0.1.md` (permissions), `sandbox`, golden-тесты без `SandboxError`; расширение — политики доступа для ИИ и форматы журнала решений.

## 7. Архитектурные паттерны для ИИ-центричной ОС

- **Микроядерная архитектура**  
  Все сервисы, включая ИИ, — отдельные процессы, общающиеся через IPC. Это даёт:
  - модульность (обновление ИИ без перезагрузки ОС),
  - изоляцию сбоев (падение ИИ не роняет всю систему),
  - прозрачность (удобный мониторинг действий ИИ).

- **Распределённая архитектура**  
  ИИ может работать не только локально, но и в облаке, с синхронизацией данных и моделей; контракты API и форматы данных должны это допускать.

*Связь с текущей платформой:* реестр сервисов, IPC (`система.обмен` в планах), лаунчер и рантайм — база для перехода к явной микроядерной модели и описанию роли ИИ как одного из сервисов.

## 8. Первоочередные шаги (приоритизация внедрения)

Чтобы не распыляться, ниже — рекомендуемый порядок внедрения: что сделать сначала, что можно отложить.

| Фаза | Что внедрять | Обоснование |
|------|--------------|-------------|
| **1. Старт** | Аннотации в языке (описания, побочные эффекты) + метаданные invoke (реестр в JSON) | Минимальные изменения, сразу дают ИИ и планировщику явную семантику; опираются на уже существующие спеки и реестр. |
| **2. Данные и код** | Семантическое хранилище (структурированные форматы, индексация по тегам) + сохранение AST рядом с байткодом, расширение трейсов (`source_line`, `ast_node_id`) | ИИ получает быстрый доступ к структуре данных и коду без парсинга; трейсы становятся привязываемыми к коду. |
| **3. Взаимодействия** | Единое хранилище взаимодействий (озеро трейсов/логов/генераций), контракт доступа для ИИ | Основа для обучения и анализа; можно начинать с формата и записи, не обязательно сразу строить предиктивные модели. |
| **4. Безопасность и прозрачность** | Политики доступа для ИИ, журнал решений, песочница для сгенерированного кода | Критично по мере роста доступа ИИ к данным; опирается на уже существующую модель permissions и песочницы. |
| **5. Отложить** | Графовая ФС (RDF, полная навигация по графу), микроядерная архитектура, распределённый ИИ, предиктивные модели, автоадаптация UI | Требуют существенных изменений инфраструктуры или тяжёлой интеграции; целесообразны после стабилизации фаз 1–4. |

Итого: начать с **аннотаций в языке и метаданных invoke** (фаза 1), затем **семантическое хранилище и AST/трейсы** (фаза 2), далее **озеро взаимодействий и безопасность** (фазы 3–4); **микроядро и распределённость** оставить на потом (фаза 5).

## 9. Конкретные форматы (прототипы структур данных)

Ниже — наброски структур для ключевых предложений. Их можно уточнить в отдельных спецификациях (JSON Schema, OpenAPI и т.п.) и использовать как основу для реализации.

### 9.1. Метаданные invoke (реестр API)

Машинно-читаемый реестр системных вызовов для ИИ и рантайма. Пример записи:

```json
{
  "name": "система.хранилище.записать",
  "version": "0.2",
  "description": "Записывает значение по ключу в хранилище приложения.",
  "args": [
    { "name": "ключ", "type": "Строка", "description": "Ключ записи" },
    { "name": "значение", "type": "Строка", "description": "Значение для записи" }
  ],
  "returns": "null",
  "pure": false,
  "side_effects": ["storage_write"],
  "resources": ["storage"],
  "cancellable": false,
  "typical_latency_ms": { "min": 0, "max": 50 },
  "user_state_dependent": false
}
```

Поля: `pure`, `side_effects`, `resources`, `cancellable`, `typical_latency_ms`, `user_state_dependent` — расширение текущей разметки «чистый/нечистый»; остальное — для документации и автогенерации подсказок ИИ.

### 9.2. Графовая ФС (узел и связи)

Минимальное представление объекта в «файловой системе как граф» (для фазы 2 или при последующем внедрении графа):

```json
{
  "uri": "osnova://storage/osnova.todo/items",
  "kind": "storage_key",
  "attributes": {
    "app_id": "osnova.todo",
    "key": "items",
    "content_type": "text/plain",
    "tags": ["todo", "user_data"]
  },
  "relations": [
    { "rel": "belongs_to_app", "target_uri": "osnova://app/osnova.todo" }
  ],
  "updated_at": "2025-03-13T12:00:00Z"
}
```

Формат можно расширить (RDF-триплеты, именованные графы); здесь — минимальный вариант для индексации и навигации по URI и тегам.

### 9.3. AST модуля (код как данные)

Фрагмент структуры для сохранения AST рядом с байткодом (например, `.os.ast.json`). Узлы с устойчивыми `id` позволяют связывать трейсы с фрагментами кода:

```json
{
  "version": 1,
  "module": "todo",
  "source_path": "todo.osnova",
  "root": {
    "id": "n1",
    "kind": "module",
    "children": [
      {
        "id": "n2",
        "kind": "procedure",
        "name": "запуск",
        "loc": { "start": { "line": 1, "column": 1 }, "end": { "line": 5, "column": 2 } },
        "children": []
      }
    ]
  }
}
```

В трейсах тогда можно указывать `ast_node_id: "n2"` и при необходимости `source_line`, `source_column`.

### 9.4. Расширение трейса (связь с кодом)

Дополнение к `trace-format-v0.1.md` для секции invoke или шага выполнения:

```json
{
  "invoke": "система.хранилище.записать",
  "args": ["items", "..."],
  "result": null,
  "source_line": 42,
  "source_column": 3,
  "ast_node_id": "n15",
  "procedure": "handle_add"
}
```

Поля `source_line`, `source_column`, `ast_node_id`, `procedure` — опциональные; при их наличии ИИ может сопоставлять вызов с конкретным местом в исходниках и в AST.

## 10. Метрики успеха (когда ОС можно считать ИИ-центричной)

Чтобы оценить прогресс, полезно зафиксировать несколько ключевых показателей. Ниже — примеры; пороги и веса можно задать отдельно.

| Метрика | Описание | Пример целевого значения (условно) |
|---------|----------|-------------------------------------|
| **Доля действий через ИИ** | Процент операций (запуск приложений, изменение настроек, поиск, генерация кода), инициированных или выполненных через единый ИИ-интерфейс, а не «вручную» (клики, консоль). | Рост от 0% к 20–30% в пилотной группе. |
| **Точность предсказаний** | Если реализованы предиктивные модели (следующее приложение, нужный файл) — точность или recall предсказаний. | Определяется после внедрения предикций. |
| **Генерация кода** | Количество приложений/скриптов, сгенерированных ИИ и успешно прошедших golden-тесты (или аналог). | Рост числа «зелёных» сборок от ИИ-генерации. |
| **Покрытие реестром API** | Доля системных вызовов и сервисов, описанных в реестре метаданных (описание, побочные эффекты, ресурсы). | 100% используемых в проде invoke. |
| **Объём данных для ИИ** | Доля структурированных/индексированных данных (хранилище, конфиги, метаданные) от общего объёма данных, к которым имеет доступ ИИ. | Рост к 80%+ по объёму, доступному ИИ. |

Итог: ОС можно считать «ИИ-центричной» не по одному числу, а по комбинации: значимая доля действий идёт через ИИ, реестр API и данные машиночитаемы и используются ИИ, сгенерированный код проходит автоматические проверки (golden, линтеры), есть прозрачность и контроль доступа (см. раздел 6).

## 11. Управление версиями и обратная совместимость

При введении новых аннотаций, форматов и метаданных важно не ломать существующие артефакты и контракты.

- **Аннотации в коде**  
  Новые аннотации (например, `@performance`, `@side_effects`) считаются опциональными. Старый код без аннотаций продолжает компилироваться и выполняться; компилятор и ИИ игнорируют неизвестные аннотации или трактуют их как пустые. При изменении семантики существующей аннотации — новая версия аннотации (например, `@side_effects_v2`) или явное упоминание в спецификации языка (breaking change с увеличением мажорной версии).

- **Метаданные invoke**  
  Реестр API версионируется (поле `version` у формата реестра и при необходимости у каждой записи). Добавление новых полей в запись invoke — обратно совместимо (старые клиенты их игнорируют). Удаление или смена смысла полей — только с новой мажорной версией реестра и объявлением в релизных заметках.

- **Форматы данных (граф, AST, трейсы)**  
  Каждый формат имеет поле `version` в корне документа. Новые поля и новые значения enum — обратно совместимы. Удаление полей или смена семантики — только с увеличением версии формата; парсеры и ИИ по `version` выбирают стратегию разбора. Рекомендуется описать политику в отдельном документе «Политика совместимости» (как для байткода в `roadmap-osnova-ideal-os.md`, этап 1.1).

- **Итог**  
  Новое по умолчанию добавляется опционально или с новыми версиями полей/форматов; удаления и смена смысла — явные breaking changes с версионированием и документированием.

## Резюме

Для построения ОС с ИИ в центре целесообразно:

| Направление | Действия |
|-------------|----------|
| **Данные** | Машиночитаемые форматы (JSON, YAML, графы/RDF), индексация и семантический поиск. |
| **Язык и API** | Семантические аннотации (описания, побочные эффекты, типы), контракты, единый интерфейс для всех действий. |
| **Единый интерфейс** | Системные вызовы и IPC через один согласованный API; реестр метаданных для динамического обнаружения. |
| **Взаимодействия** | Единое хранилище трейсов, логов и генераций; доступ ИИ для анализа и обучения. |
| **Обучение и адаптация** | Предиктивные модели, автонастройка интерфейса, обратная связь по использованию. |
| **Безопасность** | Разграничение по контексту, прозрачность и журнал решений, песочница для кода, порождённого ИИ. |
