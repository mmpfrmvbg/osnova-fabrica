# Реестр долга перед железом

> **Поправка 2026-09-25.** Файлы фикстур переименованы к канону языка (§13.3 `docs/language-v2.md`): дефис заменён подчёркиванием. Содержимое не менялось, поэтому все числа ниже относятся к тем же программам; перемер не требовался.

**Дата:** 2026-09-15
**Зачем:** одно место, где перечислено всё, что **нельзя проверить без реального
Эльбруса**. Каждый факт — с датой и формулировкой. Правило проекта: непроверенное
не выдаётся за проверенное.

**Состояние доступа (ответ владельца, 2026-09-15): НИ ЖЕЛЕЗА, НИ СИМУЛЯТОРА.**
**Уточнение 2026-09-15 (вечер): исходники официального QEMU-порта e2k получены** (МЦСТ,
`qemu-e2k.tar.gz`, QEMU 11.0.1 — `docs/e2k-sources-raw.md`), **но не собраны**: в окружении нет
POSIX-оболочки и C-инструментов (`docs/e2k-qemu-build.md` §2). Доступа к симулятору по-прежнему
нет; изменилось другое — **кодировка e2k больше не «НЕТ В ДОКУМЕНТЕ»** (§3.7).
Значит всё, что ниже, закрывается **не в этом проекте и не сейчас**. Прямое
следствие для плана: критерии приёмки Фаз 3–4 должны быть переформулированы в
терминах **внешнего** эталона (опубликованные примеры кодировки, независимый
дизассемблер, опубликованные результаты) — иначе они доказывают только
самосогласованность. Это записано в `docs/vliw-phases-plan.md`, чтобы не выяснилось
через полгода.

**Критический путь — не железо, а ISA-справочник** (уточнено владельцем 2026-09-15,
раздел 3.6). **Уточнение 2026-09-15 (вечер):** часть этого пути пройдена **без письма в МЦСТ** —
кодировка извлечена из открытых источников (§3.7). Железо нужно для тактов; справочник нужен
для того, чтобы всё построенное перестало быть моделью. Даже без покупки Эльбруса он снимает
долг 3.6 целиком и большую часть 3.1/3.2.

## 3.2. Кластеры АЛУ

| | |
|---|---|
| **долг** | **величина штрафа** за передачу между кластерами АЛУ неизвестна |
| **откуда факт** | руководство МЦСТ, стр. 194: каналы 0,1,2 — один кластер, 3,4,5 — другой; «байпас не может работать между кластерами, работая в каждом отдельно» |
| **чем заменено** | в модели задержек штраф **не добавлен вообще**. В коде это сказано прямо: `src/vliw/e2kDevices.ts#crossClusterEdges` — «Наша модель задержек этого не учитывает (нет величины штрафа), и пока не учитывает, пересечения нужно хотя бы считать». То есть эффективно штраф = 0, но **отдельной константы с таким именем в коде нет** — есть функция `crossClusterEdges`, которая считает пересечения, и предпочтение кластера как baseline-переключатель |
| **что сломает долг** | если штраф не нулевой, часть расписаний невыполнима за посчитанное время; измеренный ранее вывод «кластеры на корпусе не дают ничего» (идентичные расписания при `respectClusters: false` и `true`) остаётся верным **для этой модели**, но не для железа |
| **как закрыть** | замер на железе: время зависимой пары с байпасом внутри кластера против пары через границу кластеров |
| **дата записи** | 2026-09-15 |

## 3.6. Слой замены покрывает только кодировку

Записано по прямому указанию владельца 2026-09-15: **это два долга, а не один.**

| | |
|---|---|
| **долг 1** | swap-слой (`docs/e2k-backend.md`) заменяет **кодировку**, но **не модель устройства** |
| **что не покрыто заменой** | `src/vliw/e2kDevices.ts` и `docs/vliw-e2k-model.md` остаются допущением: длительности по классам операций (глава 6, стр. 71–72), состав кластеров АЛУ (стр. 194), штраф за передачу между кластерами (принят нулевым — см. 3.2), классы передачи операндов (таблица 12.2, стр. 199–200, извлечена с допущением о порядке столбцов) |
| **следствие** | когда появится реальный e2k, менять придётся **два** слоя: кодировку И модель устройства. Замена `src/e2k/e2k.ts` второй слой не закрывает |
| **долг 2** | **сам интерфейс `Encoder` не проверен на соответствие e2k** |
| **что в нём предположено** | форма обмена (ассемблерная форма, стр. 19 — документ говорит «большинство операций»), размер инструкции, набор полей и соответствие «список операндов ↔ поля» (наше соглашение) |
| **чем это грозит** | если у реального e2k другая форма обмена или другой набор полей, менять придётся не только `shell.ts`, но и `backend.ts`, а за ним — эмиттер. Утверждение «замена — один файл» верно **только** для замены на другую реализацию **того же** интерфейса |
| **что проверяет тест и чего не проверяет** | `src/scripts/e2kBackend.audit.test.ts` проверяет замену реализации и правило изоляции. Соответствие интерфейса e2k он **не проверяет** и не может: сравнивать не с чем |
| **общий источник риска** | оба долга опираются на **один и тот же** документ — руководство МЦСТ (выпуск 1.2, 28.02.2024). Это **не два независимых риска**, а один источник риска, размноженный на два слоя: ошибка чтения или пробел в документе бьёт по кодировке и по модели устройства **одновременно**, и закрытие одного долга второй не уменьшает |
| **критический путь** | **ISA-справочник, а не железо.** Справочник превращает модель в реальность даже без доступа к Эльбрусу: он закрывает долг 2 целиком (интерфейс переписывается по нему) и большую часть долга 1 — длительности, кластеры, классы передач становятся фактами со страницами. Железо остаётся нужным для того, что не закрывает и справочник: реальных тактов |
| **как закрыть** | получить ISA-справочник (письмо в МЦСТ) либо опубликованное описание кодировки; затем — железо для 3.1–3.3 и 3.5 |
| **дата записи** | 2026-09-15 |

### Действие с наибольшей отдачей: письмо в МЦСТ

Записано по указанию владельца 2026-09-15: это **самый дешёвый шаг с самым большим
потенциалом**, и он **не конкурирует** с эмиттером — оба идут параллельно.

| свойство | почему так |
|---|---|
| **не блокирует эмиттер** | эмиттер идёт **на оболочке** (`docs/e2k-emitter-plan.md`): кодировка e2k ему не нужна, конвейер строится в любом случае |
| **не требует железа** | нужен документ, а не машина |
| **может закрыть долг 2 целиком** | кодировка перестаёт быть «НЕТ В ДОКУМЕНТЕ»: интерфейс `Encoder` сверяется со справочником, а не с нашими предположениями |
| **закрывает большую часть долга 1** | длительности, кластеры и классы передач становятся фактами со страницами, а не чтением одного документа |
| **дёшево** | один вечер |

**Что именно просить:** описание формата команд (бинарной кодировки) и справочные таблицы
главы 12 (`relative_latency`, классы передачи операндов) — либо ссылку на открытую публикацию
с ними. Если такой публикации нет, это **тоже ответ**: он снимает ожидание «вот-вот
появится» и переводит планирование в режим «оболочка — единственная опора, и её границы
известны».

**Чего в этом пункте нет:** адресатов, каналов и текста письма — это действие владельца, а не
проектной части; здесь зафиксированы предмет запроса и цена шага.

## 3.7. Кодировка e2k извлечена — долг 2 закрыт ЧАСТИЧНО

**Дата записи:** 2026-09-15 (вечер). **Что изменилось:** кодировка e2k перестала быть
«НЕТ В ДОКУМЕНТЕ» — она извлечена из **открытых** источников, без письма в МЦСТ и без железа.

| | |
|---|---|
| **что извлечено** | таблица опкодов МЦСТ (`opcodes/e2k-opc.h`, 4 271 запись, 3 096 имён), битовая раскладка слогов (HS/ALS/ALES), длина команды |
| **откуда** | четыре независимых описания: binutils-gdb (MCST-патч), LLVM-порт (`e2k-dev`), QEMU-порт МЦСТ 11.0.1, реверс `elbrus-docs` — `docs/e2k-sources-raw.md` |
| **что реализовано** | `src/e2k/e2k-real.ts`: 23 операции в трёх формах (ALF1, ALF2, ALES/ALOPF11), короткая форма 8 байт и длинная 16 байт; `getEncoder("e2k")` |
| **что проверено** | round-trip на 132 образцах; сквозной прогон пяти ядер: **268 из 517** инструкций понижены и закодированы на ту дату (сейчас — 346, см. §3.10.2), расхождений 0 — `docs/e2k-real-run.md` |
| **чего это НЕ доказывает** | что байты примет MCST-objdump или QEMU: **ни то, ни другое не собрано** — компилятора C в окружении нет (`docs/e2k-qemu-build.md` §2). Совпадение четырёх **описаний** — свидетельство, а не замер |
| **что осталось долгом** | приёмка кодировки независимым инструментом; формы, не реализованные (LTS-литералы, CS/SS-управление, AAS-адресация, предикаты, MAS) |

### Долг 2 «интерфейс `Encoder` не проверен на соответствие e2k»: что выяснилось

Извлечение **позволило** впервые приложить интерфейс к реальной кодировке — и это дало
конкретные находки, а не общее «надо проверить»:

| находка | следствие |
|---|---|
| **`instructionSize` — одно число, а команды e2k кратны 8 и занимают 8 или 16 байт** | шлюз `auditEncoder` рассчитан на одну длину: он покрывает короткую форму и **не покрывает длинную**. Это названо в паспорте `REAL_E2K_DESCRIPTION.limitation` и проверено отдельным оракулом |
| мнемоники оболочки (`ADDs/d`) и таблицы МЦСТ (`adds`) — **разные пространства имён** | ключ `e2k` отдан реальной кодировке, заглушка сохранена под ключом `e2k-stub`; реальный бэкенд обязан отвергать мнемоники оболочки, иначе потребитель не отличил бы одно от другого |
| у интерфейса **нет способа выразить предикат** (результат `cmp*`), литерал (LTS), передачу управления (CS/SS), MAS/AAU | понижение пяти ядер останавливается на 249 из 517 инструкций (`docs/e2k-real-run.md` §2) — **это и есть цена пробела интерфейса, измеренная** |
| поле канала `0..23` руководства ↔ индекс слога ALS `0..5` | в кодировке слогов ALS шесть (`allowed_channels[6]` в таблице МЦСТ); `e2k-real` принимает 0..5 и отвергает 6..23 с названной причиной |

**Вывод:** долг 2 закрыт **частично** — интерфейс приложен к реальной кодировке и выдержал её на
подмножестве из 23 операций, но **не выражает** четыре класса операций, и один его параметр
(размер) оказался неверным для переменной длины. Утверждение «замена — один файл» этим
**опровергнуто**: пришлось менять `backend.ts` (реестр), `backend.test.ts` (оракул) и добавлять
два модуля.

## 3.8. QEMU-прогон не заменяет железо

**Дата записи:** 2026-09-15 (вечер). **Состояние: прогона не было.**

| | |
|---|---|
| **долг** | QEMU — **модель**, а не e2k; и он **не собран** |
| **почему не собран** | нет POSIX-оболочки и C-инструментов; `configure` — shell-скрипт — `docs/e2k-qemu-build.md` §2 |
| **почему нечего запускать** | конвейер проекта выдаёт поток команд (`osnova-shell-image`), а не ELF; нужен `e_machine = 175` (`EM_E2K`), компоновщик, стартовый код и libc — `docs/e2k-qemu-run.md` §2 |
| **что нельзя делать, если QEMU однажды соберётся** | называть такты QEMU тактами e2k: QEMU считает **инструкции и переходы**, а не время железа. Числа QEMU — такая же модель, как наши, только чужая. Сравнивать их с нашими можно **как две модели**, нельзя — как замер |
| **что QEMU всё же даёт** | приёмку **кодировки**: если MCST-дизассемблер прочитает наши байты как ту же инструкцию — это внешняя проверка, которой сейчас нет |
| **как закрыть** | собрать QEMU на Linux-хосте, собрать кросс-binutils, написать ELF-обёртку и стартовый код — `docs/e2k-qemu-run.md` §4 |
| **дата записи** | 2026-09-15 |

## 3.23. Шесть тест-целей e2k: карантин с причиной

**Что это.** Шесть файлов написаны как **цель**: они требуют завершённой работы
e2k-линии, а не описывают сегодняшнее состояние. Так они и заводились — красные и
красные **одинаково на всех ветках**: прогон этих файлов давал те же 10 падений
проверок и тот же отказ загрузки в `feat/integration` (`5a8704a`) и в
`feat/form-lengths` (`6b2513f`), что и здесь.

**Что с ними стало 2026-09-24 (важно, чтобы не читать дальше историю как
состояние).** Выполнен пункт 3 порядка работ `docs/e2k-regalloc-debt.md` §5:
звуковые правила раскладки уже были в дереве (`2d3b0ea`), к ним **перемерены
закреплённые числа**. Затем, **решением владельца**, четыре проверки-цели
**возвращены в красное**: там, где измерение давало отказ, стояло закрепление
отказа числом — это состояние, выданное за достигнутую цель, и флаг долга
пропадал. Теперь цель стоит проверкой (красной), а её сегодняшнее значение —
комментарием рядом. Итог: `npm run test:e2k-targets` — **113 проверок, 0 красных** (четыре прежние цели достигнуты минимальным вытеснением в память, `docs/e2k-regalloc-debt.md` §14);
долг линии (спилл либо точная живость по CFG, правка рантайма массивов, понижение
`IR.call`/`IR.invoke` у fir и correlation) **не закрыт** и назван поимённо.

неразличимы: полный прогон становится **всегда** красным, и его красный перестаёт
что-либо означать — тот же класс дефекта проверки, что случай 12 реестра
проверяемости (`docs/verification-debt.md`). До карантина `npm test` был красным

## 3.26. Ширина окна вызываемой — **настраиваемый параметр порта**, а не предел ISA

**Что говорит описание архитектуры.** Стек процедур в «Эльбрусе» существует именно ради
переполнения регистрового окна: «для каждой запускаемой процедуры в регистровом файле
отводится окно (фрейм) требуемого размера… По мере запуска новых процедур ресурс свободных
регистров РгФ может быть недостаточным для очередного окна. В этом случае нижняя часть стека
автоматически откачивается в память. И наоборот, после завершения запущенной процедуры и
возврата к прерванной процедуре необходимые данные автоматически подкачиваются из памяти в
РгФ». То есть глубина вызовов и размер окна ограничены **не архитектурой**, а объёмом
регистрового файла плюс откачкой.

**Замер (2026-09-27, диагностическая пересборка порта).** Начальная геометрия окна задаётся в
`init_main_thread` числами: `psize_q = 4`, `size_q = 8` (`qemu/linux-user/e2k/cpu_loop.c:302-308`,
вторая пара строк — наша локальная правка, см. паспорт модели). `call wbs = 4` уменьшает
`size_q` вдвое, поэтому вызываемая получает `size_q = 4` → `size_d = 8`, то есть восемь единиц.
Проверка: то же место, но `size_q = 16` (и `size_d = 16 * 2`), пересборка, оракул
`src/e2k/e2kCallWindowQemu.test.ts`:

| начальное `size_q` | что видит вызываемая | оракул |
|---|---|---|
| 8 (паспорт) | `%r0..%r7`; `%r8`, `%r9`, `%r10` — недоступны | 6 из 6 зелёных |
| 16 (опыт) | `%r8`, `%r9`, `%r10` **доступны** (`expected [true,true,true] to equal [false,false,false]`) | 2 красных — признак сдвинулся |

**Что это значит.** «Восемь регистров у вызываемой» и «процедура, которой нужно больше
восьми, вызвана быть не может» — свойство **этой сборки порта с этими начальными числами**, а
не e2k. Долг §3.18/§3.24 из «долга перед железом» становится долгом перед **конфигурацией
модели**, и упирается он в другое: объём регистрового файла (`E2K_RF_WIN_INTERNAL_SIZE`), куда
обязана помещаться вся цепочка окон, и **автоматическая откачка/подкачка стека процедур**,
которой в порте нет вовсе — у нас вытеснение **ручное** (`src/vliw/spill.ts`, резерв в хвосте
образа). Пока откачки нет, увеличение окна просто переносит предел на объём РгФ.

**Чего замер НЕ доказывает.** Что на железе окно именно такое и что его можно расширять
настройкой: числа начальной геометрии ставит порт (или загрузчик), а не программа; на железе
это дело ОС и `psize`. Кроме того, **модель под паспортом не менялась** — опыт снят, порт
восстановлен, sha256 бинаря совпал с паспортным; менять геометрию в дереве значило бы
объявить другую модель, и тогда закреплённые числа требуют перемера (правило паспорта).

**Путь, если владелец решит расширять.** (1) Собрать порт с `size_q = 16` и заново измерить
все закреплённые числа — это смена модели, а не правка. (2) Проверить, что окно не упирается в
`E2K_RF_WIN_INTERNAL_SIZE`, и назвать предел числом. (3) Только после этого трогать соглашение о
вызовах и бюджет вызываемой (`calleeWindow`), потому что до расширения `фильтр` FIR (десять
регистров) в восемь не влезает, а после — влезает.

**Рядом — другой реестр:** `docs/verification-debt.md`. Этот документ — про то, что
нельзя проверить **без железа**; тот — про то, что нельзя считать проверенным
**из-за побочных эффектов самих проверок** (инструмент проверки или восстановления
меняет проверяемый объект). Правило у них общее: непроверенное не выдаётся за
проверенное.

## 3.25. `CMPAND*` — это НЕ вторичный предикат: «И» над двумя регистрами, а не связка сравнения с предикатом
> **ПОПРАВКА 2026-09-27 (вечер).** Первая редакция этого раздела утверждала, что слитая форма
> `CMPAND*` даёт вторичный предикат «сравнение + логическое И с предикатом-источником» и потому
> есть штатный путь снять наш отказ сопоставления пар. **Это неверно, и вывод снят**: форму
> реализовали в кодировщике и сверили с ассемблером МЦСТ — четвёртый операнд-предикат `as`
> **отвергает**, «И» считается над двумя **регистровыми** источниками. Подробности и замер —
> ниже.

**Что сделано и что этим измерено (коммиты `8fdb521`, `5d99a04`).** В кодировщик добавлены
**восемь** записей ALF7 семейства `CMPAND*` (`cmpandesb`/`cmpandsb`/`cmpandpsb`/`cmpandlesb` и
`d`-варианты) — `src/e2k/e2k-real.ts`, оракул `src/e2k/e2kCmpand.test.ts` (21 проверка). Байты
сверены **двумя внешними инструментами**:

| инструмент | что дал |
|---|---|
| `as-new -mcpu=elbrus-v5` | `cmpesb,0 %b[1], %b[2], %pred0` → `01 01 00 04 40 02 01 20`; `cmpandesb,0 …` → `01 01 00 04 40 02 01 22` — восемь байт, отличие ровно в байте кода операции |
| `objdump` (дизассемблер МЦСТ) | наши байты читаются по адресам как `cmpandesb,0 %b[1], %b[2], %pred0`, `cmpandssb`, `cmpandpsb`, `cmpandlesb`, `cmpandedb,0 %db[1], %db[2], %pred0`, `cmpandsdb`, `cmpandpdb`, `cmpandledb` |

**Три поправки к прежней записи, каждая — замером:**

1. **Коды операции — `0x22`/`0x23`, а не `0x16`/`0x17`.** В прежней редакции стояли десятичные
   номера таблицы (22/23) в виде шестнадцатеричных; так их прочитал бы и любой, кто взял бы
   раздел за основу. Источник: `opcodes/e2k-opc.h:1069,1089`. Заодно: значения `0x22/0x23`
   заняты и формой ALF11 (`umulx`/`smulx`), поэтому код операции читается **только вместе с
   формой**, и «просто подменить байт» — операция небезопасная.
2. **Предиката-источника в команде НЕТ.** Семантика по порту:
   `res = ((src1 & src2) == 0)` (`qemu/target/e2k/tcg/translate-al-c2.c:683-720`) — то есть
   `CMPAND` это слитое «побитовое И + проверка на ноль», а **не** связка сравнения с предикатом.
   Набор условий усечён: есть только `2`, `4`, `5`, `7`; условия `0/1/3` — `UNDEF`, а «меньше»
   (6) отсутствует вовсе (`opcode-tables.c:1320-1341`).
3. **Отказ «значение обязано жить в регистре» этой формой НЕ снимается.** `predicatePairing`
   продолжает отказывать на двух читателях одного сравнения, и прежний «путь закрытия» долга
   (§3.25 в первой редакции) был **неверным**. Долг остаётся открытым, но уже без ложного пути.

**Что из этой работы действительно ново и полезно.** Настоящий механизм предиката-**условия** у
ALU-команды — слог **`CDS`** (формат `CDF1_RLP`), а не `SS.psrc`: поля `opc[15:14]` (0 для
ALC0..2, 1 для ALC3..5), `mask[13:10]` и `neg[9:7]` = `1 << (канал внутри тройки)`, `pred[6:0]` =
`0x60 | N`. Это и есть `? [~]%predN` — условие **на отдельной операции**. Оно реализовано в
кодировщике (`5d99a04`) и проверено: команда с условием занимает **16 байт** (`HS.ale` при этом
**не** ставится, второе слово — нулевой литеральный слог `LTS0`; без этого байты с `as` не
совпадают). Дизассемблер печатает их как `cmpandesb,0 %b[1], %b[2], %pred0 ? %pred1`,
`…,4 … ? ~%pred5`.

**Чего эта работа НЕ закрывает.** Слог-условие **не подключён к понижению**: `LOWERING` и
`CARRIER_FORMS` не трогались, поэтому двухпроходная раскладка размер такой команды ещё не
считает, а упаковщик отвергает её **названной причиной**. Исполнение в модели по-прежнему
невозможно: порт падает утверждением `op_descr->is_al` (`translate-lookahead.c:318`) — это
проверено патчем одного байта в рабочем бинаре примера `45-обратный-перебор` (контроль даёт
код возврата **14**, `CMPAND` — **134**). То есть приёмка сделана инструментами кодировки
(`as` + `objdump`), а «исполняется» не заявлено.

**Рядом — другой реестр:** `docs/verification-debt.md`. Этот документ — про то, что
нельзя проверить **без железа**; тот — про то, что нельзя считать проверенным
**из-за побочных эффектов самих проверок** (инструмент проверки или восстановления
меняет проверяемый объект). Правило у них общее: непроверенное не выдаётся за
проверенное.

по номеру; реестр-сосед назван выше и относится к документу целиком.

## 3.27. Ширина адресной арифметики: `adds` кладёт результат в младшую половину

> **ПОПРАВКА 2026-09-27 (вечер): механизм назван, долг ЗАКРЫТ.** Ниже остаётся первая редакция —
> она верна по таблице, но её вывод «сегодня это не проявляется» **снят**: дефект проявлялся
> молча и уже исправлен (§3.30). Что именно добавилось замером:
>
> - **`adds` — действительно 32-битная операция, и это видно в исходнике порта**:
>   `TRANS(ADDS, e2k_sss, tcg_gen_add_i32)` против `TRANS(ADDD, e2k_ddd, tcg_gen_add_i64)`
>   (`target/e2k/tcg/translate-al-c2.c:59-60`). То есть это не «запись в младшую половину», а
>   **сложение 32-битных величин** — и результат тоже 32-битный.
> - **Мои опыты этого не различали** (`.tmp/osnova-width2.ts`): `(2^32 + 5) − 2^32` даёт 5 при
>   любой ширине, потому что младшие слова совпадают. Различающий случай построен отдельно:
>   адрес `0x100002000` через `adds` усекается до `0x2018` и обращение падает (код возврата
>   **9**, `IP = 0x100000070`), а через `addd` тот же адрес работает (**42**).
> - **Исправлено:** адресная арифметика рантайма массивов переведена на `addd`/`subd`
>   (`45ad1b1`), закреплённые числа при этом **не сдвинулись** (обе формы ALF1 по 8 байт,
>   меняется только код операции). Подробности и таблица — §3.30.
>
> Вывод для будущих записей: **«не проявляется» — это утверждение, которое надо проверять
> различающим случаем, а не следовать из «опыт прошёл»**. Здесь оно было неверным.

**Что говорит справка по кодировке** (внешний источник, прислан владельцем 2026-09-27):
«adds — store result in lower half of 64-bit register; loads — store result in whole
register». То есть `adds`/`subs` (формат `S`) — не «32-битная арифметика вообще», а операция
**над младшей половиной** 64-битного регистра; `addd`/`subd` (формат `D`) — над регистром
целиком.

**Проверено внешним инструментом (2026-09-27, `.tmp/osnova-width-probe.ts`).** Наши байты
отданы дизассемблеру МЦСТ (`/root/build/binutils/objdump`, GNU Binutils 2.41.0-29.023 — тот
же, которым получена двусторонняя валидация, §3.9.2):

| наш код | байты (последний) | читает МЦСТ |
|---|---|---|
| `adds` | …`10` | `adds,0 %b[1], %b[2], %b[3]` |
| `addd` | …`11` | `addd,0 %db[1], %db[2], %db[3]` |
| `subs` | …`12` | `subs,0 %b[1], %b[2], %b[3]` |
| `subd` | …`13` | `subd,0 %db[1], %db[2], %db[3]` |
| `ldd` | …`67` | `ldd,0 …` |

Различение ширин **выражено в нашей кодировке** и подтверждено не нашим кодом: у `S`-форм
операнды — `%b`, у `D`-форм — `%db`.

**Где это касается нас.** Рантайм массивов считает **адреса** через `adds`
(`src/e2k/arrayRuntime.ts`: `timesEight` — три `adds`, сдвиг кучи — `adds(heap, eight, heap)`,
адрес элемента — `adds`). Значит арифметика адресов у нас **32-битная по записи**: старшая
половина результата `adds` не формируется. Сегодня это не проявляется, и вот почему — это
инвариант, а не везение:

1. пролог кладёт в регистры значения через `movts`/`movtd`, а `movts` в 64-битный регистр
   пишет ноль в старшую половину (иначе `movts 0, %b[12]` не давал бы нуля вовсе);
2. все адреса у нас малы (образ грузится по `0x100000`, куча — `+0x2000`), и все суммы
   укладываются в 32 бита.

**Открытый долг.** Инвариант «старшая половина нулевая» нигде не проверяется, а держится на
двух свойствах сразу. Первый же адрес ≥ 4 ГиБ или значение, пришедшее из 64-битного источника
(`ldd` пишет регистр **целиком**), сломает адресную арифметику молча — тем же классом, что
разобранные расхождения «исполняется, а число неверное». **Путь:** либо перевести адресную
арифметику на `addd`/`subd` (форма `D`, байты уже проверены дизассемблером выше), либо
закрепить инвариант сторожем: `adds` допустим только там, где оба операнда заведомо 32-битные.
Решение — за владельцем: это правка общего рантайма, за ней прогон инвариантов.

**Чего это НЕ доказывает.** Что на железе `adds` ведёт себя так же, как в модели: формулировка
взята из справки, а исполнением на железе не проверена (доступ к машине ещё не открыт).

## 3.29. `mas` у нас нет вовсе: все наши `ld`/`st` идут в режиме NORMAL

**Что это за поле.** `mas` — не поле команды памяти, а **отдельная команда `setmas`**, несущая
**четыре семибитных значения** — по одному на канал 0, 2, 3 и 5, то есть на четыре АЛУ с
устройством обращения к памяти (стр. 56: чтение умеют АЛУ0/2/3/5, запись — АЛУ2/АЛУ5). В порте
это `C1F1_PARAM.mas0/mas2/mas3/mas5` (`target/e2k/syllab-format.h:107-110` — поля 27:21, 20:14,
13:7, 6:0). Из внешней справки по кодировке (`#e2k`): `setmas |31 28|27 21|20 14|13 7|6 0|` →
`0110 | mas0 | mas2 | mas3 | mas5`.

**Чего у нас не было.** *(Первая редакция. Снято — «Дополнено 2026-09-27 (§3.32)» ниже: `setmas` сделан, и форма `mas=` у команды памяти тоже, §3.33.)* В шапке `src/e2k/e2k-real.ts` (шапка, «Чего здесь НЕТ») `MAS` числился среди непокрытого:
наша таблица `setmas` не выпускала, поля `mas` нигде не заполнялись. **Следствие: все наши
обращения к памяти шли с `mas = 0`, то есть в режиме `NORMAL`** — на всех четырёх АЛУ сразу.

**Как порт читает `mas` (это и есть механизм).** `target/e2k/mas-format.h` разбирает трёхбитное
поле `mod` в режим — отдельно для чтения (`e2k_parse_mas_lds1`, стр. 109) и для записи
(`e2k_parse_mas_sts1`, стр. 250):

| `mod` | чтение (`ld`) | запись (`st`) |
|---|---|---|
| 0 | `NORMAL` | `NORMAL` — **наш случай** |
| 1 | `DISABLED_TRANSLATION` | `DISABLED_TRANSLATION` |
| 2 | `CHECK` (на АЛУ0/3 без quadro — `RESERVED`) | `WAIT_UNLOCK` |
| 3 | `CHECK_UNLOCK` (там же — `RESERVED`) | `STORE_UNLOCK` (только каналы 2 и 5) |
| 4 | `FILL_OPERATION` | **`NO_CHECK`** |
| 5 | `LOCK_WAIT_1` (только канал 0) | `UNLOCK` (каналы 2 и 5) |
| 6 | `IO_OPERATION` (**только каналы 2 и 5**, не quadro) | `IO_OPERATION` |
| 7 | `SPECIAL_MMU_AAU` (**только каналы 2 и 5**) | `SPECIAL_MMU_AAU` |

**Отсюда — три следствия, каждое подтверждает указание, полученное от человека, знающего порт**
(цитата в §3.28), и объясняет его слова буквально:

1. **«Проверить работу DAM можно, если вместо `st` поставить `ld` с `mas = 3`»** — теперь
   понятно, почему именно так: `SPECIAL_MMU_AAU` (mod 7 у `ld`) — это и есть ход в устройство
   AAU/DAM, разрешённый **только на каналах 2 и 5**; а mod 4 у `st` даёт `NO_CHECK`, то есть
   запись в обход проверки прав, и ею работу DAM не проверить. Оба указания — про одно: путь к DAM
   идёт **чтением** на каналах 2/5, а не записью.
2. **«Для загрузки с `mas 0x4` нужен спекулятивный режим и нельзя на 2 и 5 каналы»** —
   подтверждается разбором: у `ld` mod 4 даёт `FILL_OPERATION`, а mod 7 (`SPEC_LOCK_CHECK` при
   `spec`) требует `is_aa` и на каналах 2/5 без quadro уходит в `RESERVED`.
3. **«`st` пишет в `ro`-секцию, поэтому некорректен»** — и вот здесь у нас есть **своё**
   измерение, которое ложится на это слово в слово: запись в страницу кода даёт
   `QEMU internal SIGSEGV {code=ACCERR}` (`src/e2k/e2kMemoryQemu.test.ts`). То есть наша проба
   упиралась ровно в то, о чём сказано.

**Что это значит для нас.** «Отказы памяти» — не одна причина, а два разных вопроса: (а) **куда**
мы пишем (страница кода против страницы данных — измерено); (б) **в каком режиме** (у нас всегда
`NORMAL`, а DAM требует явного `mas` и каналов 2/5). Пока `mas` у нас нет, ни один наш опыт не
касается DAM: мы его не включаем, поэтому «DAM не работает» и «DAM не проверяли» — разные
утверждения, и верно второе.

**Что проверено кодом порта, а не опытом.** Соответствие `mod → режим` прочитано в
`mas-format.h`; поведение `NO_CHECK` — в `translate-mem.c:1445-1470`: при этом режиме запись
**не** помечается монитором DAM (`is_dam_st_monitor` не ставится) и уходит в общий путь вместо
быстрого. Опытом модели это **не подтверждено**: чтобы его поставить, нужен кодировщик `setmas`,
которого у нас нет, — то есть сначала работа в `src/e2k/e2k-real.ts` (форма `CS1_SETMAS`), потом
проба. Это открытый долг, а не сделанное.

**Чего это НЕ доказывает.** Что `mod → режим` на железе совпадает с портом: таблица прочитана в
порте, а не в руководстве, и на машине не проверена (доступа ещё нет).

> **Дополнено 2026-09-27 (§3.32).** Кодировщик `setmas` **сделан**: слог `CS1_SETMAS` (opc 6, четыре
> поля `mas0/mas2/mas3/mas5`) с байтами, сверенными с ассемблером МЦСТ, и оракулом
> `src/e2k/e2kSetmas.test.ts`. Проба модели поставлена — и показала другое, чем ожидалось:
> `mas` действует **только в своей широкой команде** (отдельная команда следующую загрузку не
> меняет), а путь `SPECIAL_MMU_AAU` (mod 7, ход в DAM) в порте — **заглушка**, которая падает
> утверждением `tcg.c:4800:temp_load: code should not be reached`. То есть «DAM не проверяли»
> уточняется до «путь в DAM в модели не реализован, и это измерено громким отказом». Выводы этой
> записи (о `mod → режим` и о том, что DAM мы не включали) остаются в силе.

## 3.30. Адресную арифметику рантайма массивов считает `addd` — и это измерено исполнением

**Что было и что стало.** §3.27 записал долг: адреса рантайма массивов считались `adds` (форма `S`,
результат — младшая половина 64-битного регистра), и держалось это не проверкой, а двумя свойствами
сразу — `movts` пишет ноль в старшую половину, а адреса малы. Правка (`45ad1b1`) переводит **всю**
адресную арифметику рантайма на `addd` (форма `D`, операнды `%db`, регистр целиком): `timesEight` —
три `addd`, сдвиг кучи, адрес элемента, приращение длины — `addd`. Величины `0`, `1`, `8`
материализуются **как прежде** (`movts`), и это не послабление: `%b[N]` и `%db[N]` — один и тот же
регистр, а `movts` пишет ноль в старшую половину, поэтому `addd` с ним считает полноценную
64-битную сумму (проверено случаем «малый адрес, `addd`» ниже).

**Разложение по слоям** — по одному утверждению на слой, каждое со своим свидетелем:

| слой | что утверждается | чем подтверждено |
|---|---|---|
| **источник** | `adds` — результат в младшую половину 64-битного регистра; `addd` — в регистр целиком | внешняя справка по кодировке, прислана владельцем 2026-09-27 (§3.27) |
| **наша кодировка** | адресная арифметика понижения теперь `%db`, а не `%b` | дизассемблер МЦСТ на **наших** байтах понижения «получить»: `addd,0 %db[…]` — **5**, `adds,0 %b[…]` — **0** (`.tmp/osnova-addd-probe.ts`, слой кодировки) |
| **модель (порт)** | `adds` считается 32-битно, `addd` — 64-битно | чтение исходника порта: `TRANS(ADDS, e2k_sss, tcg_gen_add_i32)` против `TRANS(ADDD, e2k_ddd, tcg_gen_add_i64)` — `qemu/target/e2k/tcg/translate-al-c2.c:59-60` (сверено в `.tmp/e2k-sources/`) |
| **исполнение** | на широком адресе `addd` считает адрес, `adds` — нет | таблица ниже |

**Замер исполнением** (`.tmp/osnova-addd-probe.ts`, `npx tsx` из корня; ELF грузится по адресу
`0x100002000`, куча — на той же странице). Тело считает адрес элемента **тем же способом, что
`система.массив.получить`**: три удвоения (×8), слово заголовка, указатель кучи, — затем `std` и
`ldd` по этому адресу, код возврата — прочитанное значение (ждём 42):

| случай | адрес кучи | сложение | код возврата |
|---|---|---|---|
| `высокий-выход` (образ по широкому адресу вообще исполняется) | `0x100002000` | — | **42** |
| `высокий-direct-addd` (запись и чтение прямо по адресу из `movtd`) | `0x100002000` | — | **42** |
| `высокий-addd` | `0x100002000` | `addd` | **42** |
| `высокий-adds` | `0x100002000` | `adds` | **9** — исключение `IP = 0x100000070`: адрес усечён до `0x2018`, это ниже образа |
| `малый-addd` (**положительный контроль**) | `0x102000` | `addd` | **42** |
| `малый-adds` (контроль прежней формы) | `0x102000` | `adds` | **42** |
| `малый-direct` (контроль прямого обращения) | `0x102000` | — | **42** |
| `рантайм-высокий` (**сама плоскость правки**: `lowerArrayCall` целиком) | `0x100002000` | `addd` | **42** |
| `рантайм-высокий-снятая` (**негативный контроль**: та же последовательность, `addd`→`adds`) | `0x100002000` | `adds` | **9** — исключение `IP = 0x100000040`: то же усечение, адрес `0x2000` |
| `рантайм-малый` (контроль рантайма) | `0x102000` | `addd` | **42** |

Строка `рантайм-высокий-снятая` — это снятая правка: последовательность берётся у `lowerArrayCall` и
у неё меняется только мнемоника. Она и отличает «работает `addd`» от «работает что-то ещё»: различие
идёт от формы команды, а не от программы. Положительный контроль обязателен и он есть — в этой линии
уже было четыре ложных вывода из-за проб без контроля.

**Граница слоя, найденная первой: адреса ≥ 4 ГиБ в модели по умолчанию НЕТ.** Порт резервирует под
гостя **1 ГиБ** (`QEMU_RESERVED_VA = 1073741824`, ключ `-R size`) и отказывается грузить образ выше:
`qemu-e2k: … requires more than reserved virtual address space (0x1000020b0 > 0x3fffffff)`, код
возврата **1**. Поэтому все строки таблицы запущены с `-R 8G` (резерв 8 ГиБ), и проба печатает
отдельной строкой исход **того же** образа на штатном запуске — отказ загрузчика, а не результат.
Это не свойство правки: ширина гостевого адресного пространства задана запуском модели, и на железе
такого ограничения нет.

**Что сдвинулось в числах.** Имена команд в потоке FIR: `adds` **117 → 5** (остались от понижения
`IR.add`), `addd` **0 → 112**. Это замена кода операции, а не пересчёт: сумма арифметики та же
(**120**), команд **259** и байт **2120** не сдвинулись, потому что обе формы — ALF1 по 8 байт
(`src/e2k/e2kWideFir.test.ts`, перемер 2026-09-27). Закреплённые числа не двигались: **464 / 47 /
511 / 8944**, `iir` 119, **FIR 181** — длина формы адресной арифметики та же.

**Чего это НЕ доказывает.**

1. **Что так поведёт себя железо.** QEMU — модель по паспорту (`src/e2k/qemuModelPassport.ts`), а
   `-R 8G` — изменение **запуска**, а не модели; на железе обе величины (`adds`/`addd`) не проверены.
2. **Что `adds` «вообще нельзя».** Внутри 32 бит обе формы дают один исход — это и показывают две
   строки контроля (`малый-adds` = `малый-addd` = 42). Различие начинается там, где адрес перестаёт
   влезать в младшую половину, и **расхождения 21/25 им не объясняются** (это уже снято в §3.27).
3. **Что адрес ≥ 4 ГиБ у нас встречается.** Он не встречается: образ грузится по `0x100000`, куча —
   `0x102000`. Правка снимает **латентный** дефект, а не чинит наблюдаемую ложь, и это надо читать
   именно так.
4. **Что `adds` остались только там, где безопасно.** `adds` живут ещё в двух местах, и правка их не
   трогала: понижение `IR.add` (языковое сложение, `src/e2k/e2kRealRun.ts`) и перенос регистра
   возврата в **оконный** `%r` (`src/e2k/programImage.ts#programBytes`, `src/e2k/programImage.ts#imageOfCarriers`). Второе — перемещение
   значения, а не адрес: оконные регистры 32-разрядные (§3.28), и младшая половина там и есть нужная
   (код возврата `exit` берёт младший байт). Эти точки замером не покрыты и остаются как есть.

**Отдельно: дефект печати пробы §3.27** (не кодировки). Проба `.tmp/osnova-width-probe.ts` берёт
строку дизассемблера по индексу образца, а дизассемблер печатает после **каждого** нашего образца
добивочный `nop`, поэтому со второй строки вывод пробы сдвинут на один (`addd` печатается как `nop`,
`subs` — как `addd`). Сами образцы и их чтения верны: сырой вывод даёт `adds` → `adds,0 %b[…]`,
`addd` → `addd,0 %db[…]`, `subs` → `subs,0 %b[…]`, `subd` → `subd,0 %db[…]`, `ldd` → `ldd,0 %db[…]`,
то есть таблица §3.27 подтверждается, а вводит в заблуждение только печать пробы.

## 3.31. Старший байт теряет **канал наблюдения**, а не модель; и второй дефект — порядок деления

**Дата записи:** 2026-09-27. **Что спрашивалось:** где теряется старший байт значения — в регистре,
в операндах или в нашей кодировке литерала (LTS). **Ответ:** нигде. Значения шириной до 64 бит
доезжают целыми; наружу через `exit` виден только **младший байт**, потому что код возврата
процесса — 8-битный канал. «Тихая ложь» примеров 21 и 25 (`46` против `2350`, `188` против `956`) —
свойство **канала наблюдения**, а не счёта: 46 = 2350 mod 256, 188 = 956 mod 256.

### 3.31.1. Почему прежние пробы этого не различали — и почему заказанный случай не различает тоже

Код возврата несёт **только младший байт результата**. Значит любой опыт, который просто читает
результат через `exit`, **не различает** «значение цело» и «значение урезано до байта»: у обоих
вариантов младший байт один и тот же. Именно поэтому `.tmp/osnova-quiet-lie.ts` и
`.tmp/osnova-literal-probe.ts` давали «232 у `movts 1000`» — это ровно `1000 & 0xff`, и это
согласуется с обоими объяснениями.

Заказанный различающий случай `(0x11170 + 1) − 1` в исходной редакции **тоже не различает**:
и при широкой, и при байтовой арифметике выходит 0x70 = **112** (`0x11170 & 0xff = 0x70`;
`0x70 + 1 − 1 = 0x70`). Различает только редакция, где старшие биты **сдвигаются в младший байт**
перед выходом (`shrs 8`, деление, чтение старшего слова из памяти) — тогда ответ влезает в байт и
несёт информацию о старших разрядах. Это записано как правило: опыт без различающего наблюдаемого
— не опыт.

### 3.31.2. Замер: различающие опыты с положительными контролями

| опыт | что делает | вернулось | что это значит |
|---|---|---|---|
| A1 | `movts 1000` → `shrs 8` | **3** | 1000 >> 8; при урезании до байта было бы 232 >> 8 = 0 |
| A1d | `movtd 1000` → `shrs 8` | **3** | форма команды ни при чём (то же у `movts`) |

### 3.31.3. Разложение по слоям

| слой | что утверждается | чем подтверждено |
|---|---|---|
| **кодировка (наша)** | литералы LTS (0xd4/0xd8/0xdc) доносят значения любой ширины, включая 64-битные | B1: после `movtd` 64-битного литерала старшее слово читается как 0x11223344; A1d: `movtd` и `movts` дают одно и то же |
| **модель: регистр** | `movts`/`movtd` пишут значение целиком | A1, A1d, A2, B1 |
| **модель: ALU** | `adds`/`subs`/`muls`/`udivs`/`sdivs` считают широко, и **оба** операнда читаются целиком | M1, S1, S2, D1, D2, Z1–Z5 (плюс все контроли) |
| **понижение констант** | константа материализуется в регистр без потери разрядов | `вернуть 1000` → 232, `956` → 188, `2350` → 46 = `X mod 256` |
| **обвязка (канал наблюдения)** | код возврата `exit` несёт **только младший байт** — шире число наружу не выходит | A5 против A4; вся колонка «модель» последней таблицы = VM mod 256 |

**Что говорит источник.** Код возврата процесса в POSIX/Linux — 8 бит (`exit(status)` отдаёт
`status & 0xff`), и порт QEMU передаёт его так же; наш образ кладёт результат в **оконный** `%r9` и
вызывает `SYS_EXIT` (`src/e2k/programImage.ts#programBytes`, `src/e2k/syscallRuntime.ts`). Это не
дефект модели и не дефект кодировки: у программы просто нет другого выхода наружу, кроме 8-битного.

### 3.31.4. Найдено по дороге: `div` с вычисляемым делимым выдаётся РАНЬШЕ своих операндов

Сквозные строки B и E («не канал») объясняются **отдельным** дефектом: в линейном потоке команда
деления стоит **до** команд, которые пишут её операнды. Дизассемблер МЦСТ, разбор **по адресам**:

| образ | адрес | команда | что не так |
|---|---|---|---|
| E (`((1000-22)-22) div 256`) | `0x100050` | `sdivs,5 %b[0], %b[2], %b[4]` | делимое и делитель ещё не записаны |
| | `0x100058` | `subs,0 %b[1], %b[3], %b[2]` | здесь пишется делитель (1000 − 22) |
| | `0x100070` | `subs,0 %b[2], %b[1], %b[0]` | здесь получается делимое (956) |
| | `0x100078` | `movts,0 _f16s 0x100, %b[2]` | здесь пишется 256 — делитель |
| B (`(сумма*100+квадраты) div 256`) | `0x1002d8` | `sdivs,5 %b[0], %b[2], %b[4]` | то же: делитель пишется позже |
| | `0x1002e0` | `muls,0 %b[1], %b[3], %b[2]` | 22 · 100 |
| | `0x1002f8` | `adds,0 %b[2], %b[1], %b[0]` | 2200 + 150 — делимое |

Это **линейный** поток (по 8 байт на команду), а не пакет: порядок значим. Исход разный и оба
неверные: у E делитель оказывается нулём — `exc_div`, исключение; у B исключения нет вовсе —
**тихая ложь**, вернулся 0.

**Где корень** (`.tmp/osnova-div-order.ts`, без модели): порядок уже испорчен на шаге эмиттера
оболочки — `emitShell.instructions` для E даёт `#0 const`, `#1 const`, **`#2 IR.idiv b0, b1, b2`**,
`#3 IR.sub b2, b3, b4`, `#5 IR.sub b1, b2, b3`, то есть деление раньше определений. Причина:
`regInstructionUses({op: "idiv"})` возвращает **пустой список**, предшественников у узла `idiv` в
графе зависимостей — **ноль**. Перечень в `src/vliw/regGraph.ts#regInstructionUses` рукописный и знает `div` и
`rem`, но не `idiv` (тот же класс, что уже был в `emitterRoundtrip.ts`, где `idiv` отсутствовал в
перечне операций). Узел без входных рёбер для планировщика с перестановкой свободен.

**Путь закрытия проверен наложением (в коммит не взят).** Одна строка — `case "idiv":` рядом с
`div`/`rem` в `regInstructionUses` — даёт: сквозной опыт B = **9** и E = **3** (совпало с VM),
`npm run gate:qemu` — **78/78**, среди них «FIR целиком: 181», а также `464` / `511` / `8944`
(`e2kPredicatePairs`) и **181 ребро** графа FIR (`regGraphMemory`) — закреплённые числа **не
сдвинулись**. После опыта `src/vliw/regGraph.ts` восстановлен из копии, sha256
`A19DA211CDEC87541DD77CDD33E01FF34266EEB604C08A7CCD93E595BF8FA00A` совпал, `git diff` пуст.
Поэтому это **предложение с замером**, а не сделанная правка: причина другая, значит и коммит другой.

**Чего это НЕ доказывает.**

1. **Что так поведёт себя железо.** QEMU — модель по паспорту; про ширину регистров это ровно тот
   же довод, что в §3.30.
2. **Что у примеров 21/25 нет дефекта счёта вообще.** Доказано, что **ширина** их расхождений
   объясняется каналом (46 = 2350 mod 256, 188 = 956 mod 256), и что арифметический путь
   (`muls`, `adds`, сдвиг, круг через память) считает широко. Это не проверка самого сравнения
   корпуса — за неё отвечает другой оракул (`shellPathFaithfulness.test.ts`).
3. **Что канал наблюдения надо «чинить» в модели.** Там нечего чинить: `exit` 8-битный по
   определению. Менять надо **наблюдение** (см. путь ниже), а не порт.
4. **Что дефект порядка деления этим и исчерпан.** Измерен только `regInstructionUses`. Тот же
   класс рукописного перечня есть ещё в `src/vliw/reorderScheduler.ts` (`regOpClass` знает `div` и
   `rem`, но не `idiv`) и в `src/vliw/dependencyGraph.ts` (стековый уровень) — **не измерено**,
   названо как подозрение, а не как факт.
5. **Что `-R 8G` и прочие условия запуска тут не при чём.** Все опыты шли штатным запуском с шимом
   `mmap`; резерв адресов не поднимался.

**Путь закрытия канала наблюдения** (решение — за владельцем, это правка общего раннера):

1. **Короткий:** там, где эталон ≥ 256, а единственный канал — код возврата, раннер обязан **не
   сравнивать** его с эталоном, а отказывать с названной причиной (тем же приёмом, что
   `MultiReturnRefusal` в `src/scripts/e2kProgramRun.ts`). Тихая ложь класса «неверное число»
   превращается в названный отказ; сейчас таких записей корпуса нет — это проверено, — но
   появление первой станет структурным отказом, а не дефектом.
2. **Настоящий:** вывести число целиком через `write` — то есть печать (`AGENTS.md`, «Печать на
   e2k»). Пример `42` (978) тогда становится прямо наблюдаемым: 978 не влезает в байт, и печать
   отдаёт его целиком.
3. **В данных:** у записей 21/25 поле `e2k.layer` сейчас читается как «модель». По этому замеру
   слой — **канал наблюдения**; переименование в данных — смена классификации, а не правка кода.

### 3.32.1. Внешняя сверка: мнемоники у `as` нет, но слог — тот же

**Отдельной мнемоники `setmas` у ассемблера МЦСТ НЕТ** (измерено, `.tmp/mas-gas.sh`):
`unknown instruction 'setmas'` на всех испробованных написаниях (`setmas …`, `setmas 0x0`,
`mas 0x0`, `setmas`). Поэтому текст «`setmas mas0=…`» подать внешнему ассемблеру **нельзя**, и
придумывать кодировку по такому тексту было бы вымыслом. Ассемблер знает **другую** форму той же
команды — `mas=` у команды памяти, и там слог CS1 лежит в байтах открыто. Отсюда замер:

| текст ассемблеру | слог CS1 в его байтах | что это значит |
|---|---|---|
| `ldd,0 %db[1], %db[2], %db[3], mas=0x7` | `00 00 e0 60` = `0x60e00000` | `7 << 21` — поле `mas0` |
| `ldd,2 %db[1], %db[2], %db[3], mas=0x7` | `00 c0 01 60` = `0x6001c000` | `7 << 14` — поле `mas2` |
| `ldd,3 %db[1], %db[2], %db[3], mas=0x7` | `80 03 00 60` = `0x60000380` | `7 << 7` — поле `mas3` |
| `ldd,5 %db[1], %db[2], %db[3], mas=0x7` | `07 00 00 60` = `0x60000007` | `7 << 0` — поле `mas5` |
| `ldd,2 %db[1], %db[2], %db[3], mas=0x55` | `00 40 15 60` = `0x60154000` | `0x55 << 14` — значение шире `0x7` |

**Наши байты для `setmas` дают ровно те же слова** (`01 80 00 00` — HS, дальше слог):

| наш вызов | наши байты | слог |
|---|---|---|
| `setmas 0, 0, 0, 0` | `01 80 00 00 00 00 00 60` | `0x60000000` |
| `setmas 0, 7, 0, 0` | `01 80 00 00 00 c0 01 60` | `0x6001c000` — совпал с `mas2=7` ассемблера |
| `setmas 0, 0, 0, 7` | `01 80 00 00 07 00 00 60` | `0x60000007` — совпал с `mas5=7` |
| `setmas 7, 0, 0, 0` | `01 80 00 00 00 00 e0 60` | `0x60e00000` — совпал с `mas0=7` |
| `setmas 0, 0, 7, 0` | `01 80 00 00 80 03 00 60` | `0x60000380` — совпал с `mas3=7` |
| `setmas 0, 0x55, 0, 0` | `01 80 00 00 00 40 15 60` | `0x60154000` — совпал с `mas2=0x55` |

Сверка **живая**, а не табличная: оракул сам собирает `ldd … mas=` тем же ассемблером и сравнивает
слово CS1 (`src/e2k/e2kSetmas.test.ts`, блок 2). Оракул также проверяет отказ на значении шире
семи бит (`0x80` → `setmas: mas0 = 128 вне 0..127`) и **негативный контроль**: подмена любого из
четырёх значений меняет ровно своё поле, а одно и то же значение в разных каналах даёт разные байты.

**Разложение по слоям:**

| слой | что утверждается | чем подтверждено |
|---|---|---|
| **кодировка (наша)** | слог `CS1_SETMAS` собирается верно: opc 6 и четыре поля на своих местах | побайтовое совпадение с ассемблером МЦСТ в пяти случаях (таблица выше), `.tmp/osnova-setmas-bytes.ts`, `src/e2k/e2kSetmas.test.ts` |
| **модель (порт)** | `mas` **разбирается** и различается по `mod`; путь `SPECIAL_MMU_AAU` у загрузки — заглушка (`/* TODO */` в `translate-mem.c:1086-1089`) и падает утверждением | таблица C: mod 1/2/4/6 → 42, mod 7 → 134 с текстом `temp_load: code should not be reached` |
| **привязка `mas` к команде** | `mas` принадлежит **широкой команде**, а не потоку: отдельная 8-байтовая `setmas` следующую загрузку не меняет | случай B против случая C; источник — `decoder.c:41` (сброс `mas_valid`) и `translate-mem.c:1081` |
| **наш конвейер** | широкую команду ALS+CS1 мы не выпускаем — проба DAM упирается в это, а не в кодировщик | `src/e2k/widePacker.ts#packetableRefusal`: слоги управления «становятся командой из одного слота и разделяют пакеты» |

### 3.32.3. Что это меняет в формулировке долга

Было (§3.29): «`mas` у нас нет вовсе, поэтому ни один наш опыт не касается DAM». Стало:
**`mas` у нас есть**, и опыт поставлен — но он показывает, что **в модели** ход в DAM упереться не
во что: ветвь `SPECIAL_MMU_AAU` у загрузки не реализована и падает утверждением. То есть
«DAM не работает» и «DAM не проверяли» теперь **третье**: «путь в DAM в порте — заглушка, и это
измерено громким отказом». Молчаливой лжи здесь нет — есть названный отказ порта.

**Чего это НЕ доказывает.**

1. **Что так поведёт себя железо.** QEMU — модель по паспорту: заглушка в порте ничего не говорит
   о железе, а утверждение TCG-механизма — тем более свойство порта.
2. **Что отдельная команда `setmas` бессмысленна на железе.** Измерено лишь, что **в порте** она
   на следующую загрузку не влияет: `mas` читается из слога той же команды. Форма `setmas` как
   самостоятельной 8-байтовой команды — наша возможность выразить слог, а не утверждение о железе.
3. **Что заголовочный слог `01 80 00 00` для `setmas` измерен.** Он взят у `setbn` — единственной
   измеренной CS1-команды без ALS; ассемблер эту форму не собирает, и проверить HS нечем, кроме
   признания дизассемблером длины команды (адреса идут по 8 байт).
4. **Что `mod` 4/6 «работают».** Их код возврата 42 означает лишь, что загрузка дала тот же
   результат; поведение `FILL_OPERATION` и `IO_OPERATION` этим не проверено.
5. **Что путей в DAM больше нет.** Проверена загрузка на канале 2 с `mod 7`; запись (`st`), другие
   каналы (5) и остальные операции AAU (`e2k_parse_mas_lds1` перечисляет ещё TLB/кэш-операции,
   `mas-format.h:95-107`) не трогались.

**Путь закрытия (два раздельных шага, ни один не сделан):**

1. **Наш слой:** научить конвейер собирать **широкую команду ALS + слог управления** (сейчас
   `widePacker` такие слоги не пакует) — тогда проба DAM пойдёт нашим же кодировщиком, а не
   байтами ассемблера. Это правка `src/vliw/**` + `src/e2k/**`, за ней прогон инвариантов.
2. **Слой модели:** реализовать ветвь `SPECIAL_MMU_AAU` в порте (или заменить заглушку названным
   отказом с причиной). Это уже не наш кодировщик: порт — модель под паспортом
   (`src/e2k/qemuModelPassport.ts`), и его правка означает **перемер** всех чисел модели.

> **Дополнено 2026-09-27 (§3.33).** Шаг 1 **сделан**: конвейер собирает широкую команду
> «операция ALS + слог CS1» (поле `control` в `src/e2k/backend.ts`, раскладка —
> `wideCommandBytes` в `src/e2k/e2k-real.ts`, паковка — `src/e2k/widePacker.ts`), оракул —
> `src/e2k/e2kWideControl.test.ts` (14 проверок, сверка с `as` и `objdump` МЦСТ живьём). Проба
> модели, поставленная **нашими** байтами (`.tmp/osnova-setmas-pair.ts`), дала ровно те же исходы,
> что проба этого раздела на байтах ассемблера: контроль 42, `mas=7` → 134 с падением
> `tcg.c:4800:temp_load`, `mod` 1/2/4/6 → 42. То есть слог CS1 порт читает из нашей команды так же,
> как из команды ассемблера, и шаг 2 (заглушка в порте) остаётся единственным незакрытым.
> Выводы этого раздела про `mod → режим` и про привязку `mas` к широкой команде остаются в силе.

## 3.33. Широкая команда «ALS + управляющий слог CS1» собирается нашим кодировщиком

**Дата записи:** 2026-09-27. **Что сделано:** пара «операция ALS + управляющий слог» стала
выразимой в нашем представлении инструкции и пакуется конвейером; форма сверена с ассемблером и
дизассемблером МЦСТ живьём и подтверждена прогоном в модели.

**Зачем это было нужно.** Управляющие слоги и операции ALS жили в **разных** командах:
`packetableRefusal` отвергал управляющие слоги, и такая инструкция становилась командой из одного
слота и разделяла пакеты. Между тем `mas` принадлежит **широкой команде**, а не потоку
(`decoder.c:41` сбрасывает `mas_valid` на каждой команде, `translate-mem.c:1081` читает
`instr_decoded->mas[ch]`) — то есть выразить «загрузка с `mas`» одной инструкцией было нечем, и
проба пути в DAM собиралась **байтами ассемблера** (§3.32.2). Теперь она собирается нашим
кодировщиком.

### 3.33.1. Форма: измерено ассемблером МЦСТ

`.tmp/osnova-wide-control-probe.ts` — `as-new -mcpu=elbrus-v5`, тот же инструмент, что в §3.32:

| текст МЦСТ | байты (hex) | длина | HS: `lng` / `mdl` / `al` / `ale` / `cs` |
|---|---|---|---|
| `ldw,2 %db[14], %db[12], %db[10]` | `01 00 00 10 0a 0c 0e 66` | 8 | 0 / 1 / 4 / 0 / 0 |
| `ldw,2 …, mas=0x7` | `12 80 00 10 0a 0c 0e 66 00 c0 01 60 00 00 00 00` | **16** | 1 / 2 / 4 / 0 / **2** |
| `{ adds,0 …; ldw,2 … mas=0x7 }` | `13 80 00 14 03 02 01 10 0a 0c 0e 66 00 c0 01 60` | 16 | 1 / 3 / 5 / 0 / 2 |
| `{ adds,0; adds,1; ldw,2 … mas=0x7 }` | `24 80 00 1c … 00 c0 01 60 00 00 00 00` | 24 | 2 / 4 / 7 / 0 / 2 |
| `{ muls,0 …; ldw,2 … mas=0x7 }` | `23 80 10 14 03 02 01 20 0a 0c 0e 66 00 c0 01 60 00 00 c0 01 00 00 00 00` | 24 | 2 / 3 / 5 / **1** / 2 |

Отсюда три правила, которых у одиночной команды не было и которые теперь стоят в коде:

1. слог управления идёт **после** всех слогов ALS и **до** полуслогов ALES0/1/3/4 (последняя строка:
   у `muls` полуслог ALES0 оказался **за** слогом `mas`, а не перед ним) — `docs/e2k-wide-commands.md`
   §2.3–2.4;
2. `mdl` считает слова до средней точки **вместе** со слогом управления (`mdl = 2` у пары,
   `mdl = 3` у пары с двумя слотами ALS);
3. присутствие слога отмечает поле `cs` заголовочного слога (CS1 — бит 15), длина — по `lng`, а
   добивка до чётного числа 4-байтовых слогов считает и второй слог (`24 80 00 1c` — 6 слов).

**Наши байты совпали с этими пятью строками байт в байт** — не «похоже», а побайтово, включая
добивку (`12 80 00 10 0a 0c 0e 66 00 c0 01 60 00 00 00 00` для формы из указания владельца).

**Поправка к постановке задачи (найдено замером).** В задании 8-байтовая форма без `mas` была
записана как `12 80 00 04 03 02 01 67`; ассемблер на самом деле даёт `01 00 00 10 03 02 01 67`
(`lng = 0`, `mdl = 1`, `al = ALS2`, `cs = 0`) — и наши байты **уже** совпадали с ним. Строка с
`12 80 00 04` замером не подтверждается; эталон формы `mas=0x7` подтверждён дословно.

### 3.33.2. Где это в коде

| что | где |
|---|---|
| представление: инструкция несёт и ALS, и управляющий слог | `src/e2k/backend.ts` — необязательное поле `control?: AsmInstruction` (аддитивное: без него всё как было) |
| раскладка: HS + ALS по каналам + CS1 + ALES + добивка | `src/e2k/e2k-real.ts` — `wideCommandBytes`, `wideControlSyllableOf` (одна раскладка на одиночный кодировщик и на группировщик) |
| паковка | `src/e2k/widePacker.ts` — `packetableRefusal` больше не отвергает пару, `packWide` несёт управляющий слог пакета (`groupControl`), в одной команде слог управления **один** |
| оракул | `src/e2k/e2kWideControl.test.ts` — 14 проверок |

**Границы названы отказом, а не вымыслом.** В пару с ALS кладутся только формы, чей слог занимает
ровно одно слово и не тянет за собой ни `SS`, ни литерал: `setbn` и `setmas`. `setwd` (литерал
`wsz`), `call`/`ct` (`SS`), `disp`/`sdisp` (`CS0`) отвергаются с причиной: порядок `SS`/`LTS`
относительно слогов ALS ассемблером не измерялся. Отдельная 8-байтовая команда `setmas` при этом
кодируется **прежними байтами** (`01 80 00 00 00 c0 01 60`) и остаётся границей пакета — это
проверено оракулом, а не обещано.

### 3.33.3. Проба модели: наши байты порт читает так же, как байты ассемблера

`.tmp/osnova-setmas-pair.ts`. Программа собирается **нашим** упаковщиком (`packWide`, поле
`control`), тело — та же загрузка из области по `[%b[14] + %b[12]]`, код возврата — прочитанное:

| случай | что в потоке | код возврата | вывод |
|---|---|---|---|
| A контроль | `ldw` без `mas` | **42** | загрузка работает — положительный контроль |
| B | `ldw` + CS1 `mas=0x7`, **наши байты** | **134** | порт уходит в ветвь-заглушку `SPECIAL_MMU_AAU` и падает утверждением `tcg.c:4800:temp_load: code should not be reached` |
| C `mod` 1/2/4/6 | `ldw` + CS1 `mas=1/2/4/6`, наши байты | **42**, **42**, **42**, **42** | режим разобран, поведение то же |

Исходы **совпали** с прогоном §3.32.2, который был собран байтами ассемблера. Значит различие
«свои байты против чужих» на этом пути снято: слог CS1 из нашей команды доходит до порта тем же
путём. Совпадение A и C — законный результат, а не провал пробы: путь в DAM в порте — заглушка
(§3.32.3), и наша работа этот слой не двигает.

### 3.33.4. Второй свидетель: дизассемблер МЦСТ печатает форму целиком

Наши байты, поданные дизассемблеру (`objdump -d`, разбор **по адресам** — `parseObjdumpOutput`):

```
0x100000  ldw,2 %db[14], %db[12], %db[10], mas = 0x7      ← 16 байт
0x100010  ldw,2 %db[14], %db[12], %db[10]                  ← 8 байт
0x100018  adds,0 %b[1], %b[2], %b[3] ldw,2 %db[14], %db[12], %db[10], mas = 0x7
```

То есть дизассемблер признаёт и длину команды (адреса идут по 16/8/16), и **оба** слога, и значение
`mas`. Это сильнее оговорки §3.32.1: там «пустая строка» относилась к отдельной мнемонике `setmas`,
которой у ассемблера нет вовсе; форму `mas = 0x7` эта сборка binutils печатает. Оракул держит это
как вторую (независимую от `as`) сверку, с различающим контролем: те же байты со значением `0x55`
читаются как `mas = 0x55`, и `0x7` в них уже нет.

**Найденное замером сверх задания.** Оговорка §3.32.3 о том, что HS `01 80 00 00` для **одиночной**
`setmas` внешне не измерен, **остаётся в силе**: форма `mas=` у ассемблера всегда идёт с ALS, и
изолировать слог CS1 без операции памяти нечем. Измерено другое — HS **с** управляющим слогом:
`0x10008012` (`lng = 1`, `mdl = 2`, `cs = 2`), и это ровно то, что строится нашим `wideCommandBytes`.

### 3.33.5. Чего это НЕ доказывает

1. **Что так поведёт себя железо.** Всё измеренное — ассемблер, дизассемблер и порт под паспортом
   (`src/e2k/qemuModelPassport.ts`), а не машина.
2. **Что путь в DAM работает.** Он в порте заглушка, и `mas=7` это подтверждает падением (134).
3. **Что в пару с ALS кладутся прочие управляющие формы.** Порядок `SS`/`LTS` относительно слогов
   ALS **на момент этой записи** не измерялся — такие пары отвергались, а не кодировались.
   **Дополнено 2026-09-27 (§3.34):** измерен; `ct`, `call`, `disp`, `sdisp` и литерал теперь
   кладутся, а непарными остаются `return` и `setwd`.
4. **Что `mas` действует на команду памяти из ДРУГОЙ команды.** Наоборот: §3.32.2 показал, что не
   действует, и наша работа это не меняет — она лишь даёт выразить `mas` там, где он работает.
5. **Что печать (`write` вместе с арифметикой) уже уложена в один такт.** Пара «ALS + CS1» — это
   кирпич для неё. **Дополнено 2026-09-27 (§3.34):** вторая половина кирпича — `SS`, `CS0` и
   литерал `LTS` — тоже измерена и кладётся в ту же команду, включая `call`, который несёт `SS`
   **и** `CS1` сразу.

## 3.34. Порядок слогов `SS`, `CS0` и `LTS` в широкой команде — измерен; пара собирается кодировщиком

**Дата записи:** 2026-09-27. **Что сделано:** измерен порядок слогов `SS` (`ct`, `call`), `CS0`
(`disp`, `sdisp`) и литерала `LTS` относительно слогов ALS; раскладка стала выразимой и
**собирается кодировщиком** — сверено с ассемблером МЦСТ **побайтово на 14 формах**. Пары `SS` и
`CS0` включены и в упаковщик; литерал в упаковщик **не включён** — причина названа в §3.34.2.

**Почему это было нужно.** §3.33 закрыл пару «ALS + CS1», но **честно отказался** класть в ту же
команду `SS`, `CS0` и литерал: «порядок `SS`/`LTS` относительно слогов ALS ассемблером не
измерялся». Без этой половины арифметика и передача управления остаются в **разных** командах, а
печать (`write` вместе с арифметикой) и условные переходы — это ровно такие пары.

### 3.34.1. Форма: измерено ассемблером МЦСТ, разбор по словам

`.tmp/osnova-ss-lts-probe.ts`, `-probe2.ts`, `-probe3.ts` — `as-new -mcpu=elbrus-v5`. Разбор
**по словам команды и по адресам**, а не по строкам дизассемблера: дизассемблер МЦСТ печатает `nop`
между командами, и разбор по индексу строки уже давал ложный вывод (отозван 2026-09-27).

| текст МЦСТ | слова (4 байта) | длина | вывод |
|---|---|---|---|
| `adds,0 %b[1], %b[2], %b[3]` | `04000001` `10010203` | 8 | контроль: ALS без прочего |
| `ct %ctpr2` | `00001001` `c0000820` | 8 | контроль: `SS` без ALS, `cs = 0` |
| `sdisp %ctpr1, 3` | `00004001` `60000003` | 8 | контроль: `CS0` без ALS |
| `{ adds,0 %b[2],%b[3],%b[4]; sdisp %ctpr1,3; ct %ctpr2 }` | `04005013` `c0000820` `10020304` `60000003` | 16 | **SS, ALS, CS0** |
| `{ adds,0 …; call %ctpr1, wbs=4 }` | `04009013` `c0000420` `10020304` `50000004` | 16 | **SS, ALS, CS1**; у `call` `ss = 1` И `cs = 2` |
| `{ adds,0 %b[2],%b[3],%b[4]; movts,1 42, %b[1] }` | `0c000012` `10020304` `60c0d401` `002a0000` | 16 | **ALS, ALS, LTS** — литерал последним, добивки нет |
| `{ adds,0 …; adds,2 …; movts,1 42 }` | `1c000023` `10020304` `60c0d401` `10020304` **`00000000`** `002a0000` | 24 | **добивка ПЕРЕД литералом** |
| `{ muls,0 …; sdisp %ctpr1, 3 }` | `04104012` `20010203` `60000003` `01c00000` | 16 | `ALES0` — **за** слогом CS0 |
| `{ muls,0 …; movts,1 42; ct %ctpr1 }` | `0c101023` `c0000420` `20020304` `60c0d401` `01c00000` `002a0000` | 24 | `SS` первым, `ALES0` перед литералом |

Отсюда порядок слов команды — **измеренный**, а не выведенный:

```
HS, [SS], ALS…, [CS0|CS1], [ALES…], [добивка], [LTS]
```

Три правила, которых у команды без литерала не было:

1. `SS` идёт **первым**, до слогов ALS; присутствие отмечает бит 12 заголовка (`HS.ss`);
2. `CS0` (бит 14) и `CS1` (бит 15) идут **после** слогов ALS; `call` выставляет **оба** бита сразу
   (`cs = 2` и `ss = 1` в одном заголовке);
3. **литерал входит в счёт добивки**: `LTS` занимает последнее слово, поэтому до него число
   4-байтовых слогов обязано быть **нечётным**. Это и есть разница между 16 и 24 байтами выше.

**Что замер опроверг.** §3.33 называла `call` и `ct` формами, которые «в пару не кладутся»; замер
показал, что кладутся обе, причём `call` несёт два слога сразу. **Найденная замером мелочь:**
`{ … ; sdisp %ctpr1, N; ct %ctpr1 }` ассемблер **отвергает** — «the wide instruction contains CT and
CTP instructions making use of the same `%ctpr` register which is not supported on elbrus-v5». Это
ограничение уровня `elbrus-v5`, а не наша граница: с разными `%ctpr` та же пара собирается.

### 3.34.2. Где это в коде

| что | где |
|---|---|
| слоги `SS`/`CS0`/`CS1` одной инструкции | `src/e2k/e2k-real.ts` — `wideSyllablesOf` (было `wideControlSyllableOf`, знавшее только `setbn`/`setmas`) |
| слот ALS **вместе с литералом** | `src/e2k/e2k-real.ts` — `wideAlsSlotOf` + общая раскладка `literalLayoutOf` (одна на одиночную команду и на широкую) |
| раскладка слов | `src/e2k/e2k-real.ts` — `wideCommandBytes`: `[SS], ALS…, [CS], [ALES], [добивка], [LTS]` |
| паковка | `src/e2k/widePacker.ts` — `packetableRefusal` берёт пары `SS`/`CS0`/`CS1`; литерал по-прежнему **барьер** пакетов, и причина названа (ниже) |
| оракул | `src/e2k/e2kWideSsLts.test.ts` — 6 проверок, из них одна **живая** сверка с `as` на 14 формах |

**Границы названы отказом.** `return` (измеренная форма несёт CS0 **без** слога ALS) и `setwd`
(его `wsz` живёт в литерале — раскладка «ALS + CS1 + LTS» именно для `setwd` не проверялась)
отвергаются с причиной. Два литерала в одной команде — отказ: измерены формы с **одним** словом
`LTS`. 64-битный литерал (`imm64`, форма `0xdc`) несёт **два** слова LTS — тоже отказ.

**Литерал: раскладка есть, в упаковщик не включена — и это названо, а не спрятано.** Раскладка
«ALS + LTS» измерена и кодируется (`wideAlsSlotOf`, `wideCommandBytes`; оракул собирает ею все
формы с литералом и сверяет с `as` побайтово). Но `packetableRefusal` литерал по-прежнему
отвергает, **потому что включение сдвигает закреплённые числа корпуса**: измерено
2026-09-27 — пакетов **220 → 210**, «литеральных с отказом» **20 → 0**, отказы упаковки по `movts`
исчезают, меняются байтовые замеры пяти ядер. По правилу проекта сдвинутое число — **отдельный
коммит с датой** (`AGENTS.md`, «Инварианты правок в `src/e2k/**`»), поэтому включение — следующий
шаг, а не побочный эффект этого. Отказ упаковщика называет и саму причину, и эти числа.

### 3.34.3. Чего это НЕ доказывает

1. **Что так поведёт себя железо.** Всё измеренное — ассемблер МЦСТ и наша сборка, а не машина.
2. **Что выбор канала — наш.** `packWide` берёт **первый свободный** канал, ассемблер чтит
   записанный; поэтому байты сравнимы только при совпадающем выборе канала. Это записано в оракуле,
   а не спрятано: расхождение «наши против `as`» на трёх операциях объяснялось именно каналом, а не
   порядком слогов.
3. **Что печать уже сделана.** Пара — **кирпич**: сам `write` вместе с арифметикой ещё не уложен,
   и `programImage` по-прежнему требует возврат значения (`AGENTS.md`, «Печать на e2k»).
4. **Что `LTS` в широкой команде проверен моделью.** Замер — ассемблерный; прогон в QEMU этих форм
   не ставился.
