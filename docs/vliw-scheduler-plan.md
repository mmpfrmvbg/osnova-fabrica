# План первого простого планировщика под e2k

Документ задаёт пошаговый план реализации **первого простого планировщика** VLIW-пакетов под архитектуру e2k (Эльбрус). Планировщик строит поверх уже существующего формата .osvbc v2, пакетов и зависимостей (см. `vliw-considerations.md`, п. 4–5) и готовит код к эмиссии в машинные пакеты e2k или в расширенный байткод с заполненными слотами.

---

## 1. Цель и границы

**Цель:** из .osvbc v1/v2 получить **расписание операций по VLIW-пакетам** с учётом зависимостей и ограничений слотов e2k, без ломания существующего байткода и VM.

**Границы первого этапа:**

- Планировщик — **отдельный проход** (или отдельный тул): вход — `OsVbcModule`, выход — расписание (пакеты с назначением операций по слотам) или обновлённый .osvbc v2.
- **Не входит в первый план:** полная эмиссия машинного кода e2k (нужна спецификация ISA и кодировщик); предикатное выполнение; полноценный software pipelining с прологом/эпилогом.
- **Входит:** модель слотов e2k, упаковка независимых операций в пакеты, использование `deps` и подсказок из формата v2, тесты на `vliw-example.osvbc.json`.

---

## 2. Упрощённая модель e2k

Для первого планировщика достаточно **абстрактной модели** с фиксированной шириной пакета и типами слотов. Точную привязку к реальному e2k (количество и типы функциональных устройств) можно уточнить по документации Эльбрус; ниже — минимальная рабочая схема.

**Параметры модели:**

| Параметр | Значение (первая итерация) | Описание |
|----------|----------------------------|----------|
| Ширина пакета | 4 | Число слотов в одном VLIW-пакете (можно взять 2 или 4 под конкретный вариант e2k). |
| Типы слотов | `I0`, `I1`, `M`, `B` | Целочисленный 0, целочисленный 1, память, ветвление. Либо упрощённо: `ALU`, `MEM`, `BR` (3 слота). |
| Задержки | 1 такт | Для простоты все операции — latency 1; в следующих итерациях — таблица по типу операции. |

**Маппинг байткода Основа → тип слота:**

| Операция / группа | Слот (пример) |
|-------------------|----------------|
| `add`, `sub`, `mul`, `div`, `rem`, сравнения, `const`, `local.get`/`set` (без памяти «вне» стека) | `I0` или `I1` |
| `field.get`, `field.set`, будущие load/store | `M` |
| `jmp`, `jmp_if`, `jmp_if_not`, `call`, `ret` | `B` |
| `invoke` | Барьер (не переставлять через него); трактовать как занятие одного слота или отдельный «системный» слот. |

Конкретное разнесение по слотам e2k (сколько именно integer/FP/memory устройств) задаётся в конфиге планировщика и при необходимости выносится в отдельный файл `e2k-model.ts` / `e2k-model.json`.

---

## 3. Вход и выход планировщика

**Вход:**

- `OsVbcModule` (v1 или v2). Для v1 — весь `code` трактуется как линейная последовательность инструкций; для v2 — учитываются уже существующие пакеты и `procedures[].deps` (блоки, рёбра), а также `deps` внутри пакетов.

**Выход (на выбор или оба по флагу):**

1. **Расширенный .osvbc v2** — тот же модуль, в котором линейные участки по возможности заменены на пакеты: операции с учётом зависимостей разложены по слотам, заполнены `slots` и при необходимости `deps` пакета.
2. **VLIW-IR** (внутреннее представление) — массив пакетов; каждый пакет — массив слотов (операция или пусто), плюс привязка к индексам кода. Дальше из VLIW-IR можно генерировать текст/бинарник e2k или отладочный дамп.

Первый проход можно реализовать с выходом только (1) или только (2), чтобы не раздувать объём работ.

---

## 4. Этапы реализации

### Этап 1: Один базовый блок (линейный код без ветвлений)

**Задача:** для последовательности инструкций без `jmp`/`jmp_if`/`jmp_if_not`/`call`/`ret` построить граф зависимостей (по стеку: кто производитель, кто потребитель) и упаковать операции в пакеты фиксированной ширины (например, 4 слота), соблюдая типы слотов.

**Шаги:**

1. Выделить из `code` один «блок» — от начала до первого перехода/ret (или до конца процедуры).
2. Построить **граф зависимостей**: каждая инструкция — узел; ребро (A → B), если B использует результат A (по стеку: порядок push/pop задаёт зависимости). Для стековой машины: симуляция стека по ходу кода и запись def-use.
3. **List scheduling**: на каждом «такте» выбирать до N готовых (без неудовлетворённых зависимостей) операций и назначать их в свободные слоты подходящего типа; учитывать задержку (пока 1 такт). Повторять, пока все операции не расписаны.
4. Сформировать выход: массив пакетов (каждый пакет — до 4 операций с указанием слота).

**Тест:** процедура из `vliw-example.osvbc.json`: уже есть один пакет и линейный код вокруг; планировщик может либо оставить как есть (валидация), либо переразложить линейную часть в пакеты и проверить, что результат (2) не меняется при интерпретации (если выход — .osvbc v2).

---

### Этап 2: Несколько базовых блоков (procedure deps)

**Задача:** использовать `procedures[].deps.blocks` и `deps.edges` для разбиения кода на базовые блоки; планировать каждый блок отдельно (пока без глобального trace scheduling).

**Шаги:**

1. По `deps.blocks` разбить `code` на блоки (диапазоны индексов).
2. Для каждого блока вызвать планировщик Этапа 1 (линейный list scheduling).
3. Собрать выход: последовательность пакетов по блокам; на границах блоков — контроль перехода (jmp/ret) в отдельном пакете или в последнем слоте блока.
4. Убедиться, что переходы (jmp, jmp_if, jmp_if_not, ret) не «размазываются» по пакетам некорректно: одна ветвь — один слот типа B.

**Тест:** модуль с двумя базовыми блоками и одним условным переходом; сравнить число пакетов до/после и сохранение семантики (golden: результат выполнения через VM).

---

### Этап 3: Учёт готовых пакетов и deps внутри пакета

**Задача:** если во входном .osvbc v2 уже есть элементы с `packet: true` и `deps`, использовать их как готовые подсказки: не разбивать пакет на отдельные инструкции, а проверять соответствие `deps` модели (consumer/producer по слотам) и при необходимости переразмещать операции только внутри пакета по слотам e2k.

**Шаги:**

1. При обходе `code` различать линейные инструкции и готовые пакеты.
2. Для готового пакета: проверить, что типы операций в слотах допустимы для выбранной модели e2k; при несоответствии — выдать предупреждение или попытаться переназначить слот по типу операции.
3. Использовать `deps` пакета для проверки: не нарушен ли порядок producer → consumer при назначении слотов (в e2k слоты выполняются параллельно, поэтому зависимые операции должны быть в одном пакете только если задержка 0, иначе — в разных пакетах).

**Тест:** `vliw-example.osvbc.json` — пакет с `add`, зависящий от слотов 0 и 1; планировщик не должен менять семантику и должен сохранить или улучшить упаковку.

---

### Этап 4: Циклы и развёртка (опционально, после 1–3)

**Задача:** для цикла (диапазон кода между меткой и jmp назад) при наличии подсказки `разворачивать N` или при ручном развёртывании — строить несколько пакетов для итераций и при необходимости простой software pipeline (пролог, ядро, эпилог).

Границы: без полноценного modulo scheduling; достаточно развернуть цикл 2–4 раза и спланировать каждую копию тела как отдельный блок. Детали — в отдельном подпункте плана после стабилизации Этапов 1–3.

---

## 5. Место в кодовой базе и тесты

**Размещение:**

- Вариант A: отдельный пакет/каталог `src/tools/osnova-vliw/` (или `osnova-runtime/vliw/`) — модули `e2k-model.ts`, `scheduler.ts`, `dependency-graph.ts`, входная точка `schedule-module.ts`.
- Вариант B: подкаталог внутри `osnova-compiler`, например `osnova-compiler/vliw/`, если планировщик рассматривать как фазу компилятора.

Рекомендация: **Вариант A** (отдельный тул/пакет), чтобы не смешивать с текущим кодогеном v0.1 и иметь возможность вызывать планировщик как отдельный шаг (например, `osnova schedule module.osvbc.json -o scheduled.osvbc.json`).

**Тесты:**

- Unit-тесты: построение графа зависимостей для фиксированной последовательности инструкций; упаковка в пакеты (ожидаемое число пакетов и назначение по слотам).
- Golden: на входе `vliw-example.osvbc.json`, на выходе — либо тот же модуль с сохранённой семантикой (VM возвращает 2), либо VLIW-IR с одним/несколькими пакетами; при изменении формата выхода — обновить эталон.

**Интеграция с osnova-check:**

- После появления CLI планировщика можно добавить шаг: `osnova schedule fixtures/vliw-example.osvbc.json` и проверка, что выход валиден и VM даёт результат 2. Так регрессии планировщика будут ловиться в CI.

## 6. Порядок работ (краткий чеклист)

1. **Модель e2k** — завести конфиг/типы: ширина пакета, типы слотов, маппинг op → slot type.
2. **Граф зависимостей** — по линейному коду (стековая симуляция) построить def-use; формат: узлы = инструкции, рёбра = зависимости.
3. **List scheduling** — один базовый блок, упаковка в пакеты, выход VLIW-IR или .osvbc v2.
4. **Тесты Этапа 1** — на примере из 2–3 инструкций и на процедуре `пример` (без ветвлений внутри блока).
5. **Разбиение по блокам** — использование `deps.blocks`/`edges`; планирование по блокам; тесты с переходами.
6. **Учёт готовых пакетов и packet.deps** — валидация и при необходимости переразмещение; тест на vliw-example.
7. **CLI и интеграция** — команда `schedule`, опционально вызов из `osnova-check`.

После этого линия VLIW получает **реальный планировщик** под e2k поверх уже проверяемого формата v2 и живой фикстуры, без блокировки на полной эмиссии машинного кода e2k.

---

## 7. Реализовано (Этап 1 + CLI)

- **e2kModel.ts** — `VLIW_SLOTS`, типы слотов I0/I1/M/B, `classifyOpcode`.
- **dependencyGraph.ts** — граф зависимостей по стеку и store/load: `lastStore[localIndex]`, ребро `lastStore(i) → local.get(i)` при `i >= argc`; опции `callArgc`/`invokeArgc`/`argc`.
- **scheduler.ts** — list scheduling, `packetsToCodeElements`.
- **cli.ts** — `npm run osnova-schedule input.osvbc.json [-o output.osvbc.json]`; один процедура, линейный код, в конце ret.
- **Тесты** — unit + интеграция (VM возвращает 2); тест CLI на `fixtures/linear-sum.osvbc.json`.
- **Скрипты:** `test:vliw`, `osnova-schedule`; `osnova-check` включает `test:vliw`.
