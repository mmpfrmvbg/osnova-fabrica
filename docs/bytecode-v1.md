# Байткод Основа v1

Формальная спецификация формата байткода `.osvbc` и поведения VM. Синхронизировано с `src/compiler/codegen.ts` и `src/runtime/vm/interpreter.ts`.

**Основа v1** — минимальный стабильный набор инструкций и структур, на который опираются компилятор и VM.

---

## 1. Структура OsVbcModule

Модуль байткода описывается объектом со следующими полями:

| Поле | Тип | Описание |
|------|-----|----------|
| `version` | number | Версия формата байткода (1 для v1) |
| `moduleName` | string | Имя модуля (из `модуль имя`) |
| `constants` | unknown[] | Константный пул: числа, строки, булевы |
| `procedures` | ProcedureDef[] | Таблица процедур |
| `code` | CodeElement[] | Линейный поток инструкций (или смесь с VLIW-пакетами) |
| `vliwSlots` | number? | (v2) Макс. слотов в пакете, опционально |

---

## 2. Структура ProcedureDef

| Поле | Тип | Описание |
|------|-----|----------|
| `name` | string | Имя процедуры |
| `codeOffset` | number | Смещение в `code`, с которого начинается тело |
| `argc` | number | Количество аргументов |
| `localsCount` | number | Количество слотов локалов (включая аргументы) |
| `returnsValue` | boolean? | Опционально: возвращает ли значение |
| `deps` | ProcedureDeps? | Hint для VLIW-планировщика, VM игнорирует |

**Использование интерпретатором:**
- При `call fi` интерпретатор загружает процедуру по индексу `fi`
- Снимает со стека `argc` значений (в порядке: первый аргумент — первым)
- Инициализирует `locals[0..argc-1]` этими значениями, остальные — `null`
- Устанавливает `pc = proc.codeOffset` и продолжает выполнение
- При `ret` — снимает значение с вершины стека как возвращаемое, восстанавливает `pc` из кадра

---

## 3. Элементы кода (CodeElement)

### 3.1. Линейная инструкция (RawInstruction)

Линейная инструкция — объект с полем `op` и дополнительными полями по типу.

### 3.2. VLIW-пакет (v2)

```json
{
  "packet": true,
  "slots": [ /* массив RawInstruction */ ],
  "deps": [ [from, to], ... ]  // опционально, hint для планировщика
}
```

VM исполняет `slots` последовательно: slot[0], slot[1], ... slot[N-1]. Поле `deps` VM игнорирует.

## 4. Инструкции v1

### 4.1. Константы

| op | Поля | Стек до | Стек после | Особые случаи |
|----|------|---------|------------|---------------|
| `const` | `type`, `k` | — | `constants[k]` | `k` вне [0..constants.length) → InterpreterError |
| `const.true` | — | — | `true` | |
| `const.false` | — | — | `false` | |
| `const.null` | — | — | `null` | |

`const`: `type` ∈ `i32` \| `f64` \| `str` \| `bool` \| `null`.

### 4.2. Локальные переменные

| op | Поля | Стек до | Стек после | Особые случаи |
|----|------|---------|------------|---------------|
| `local.get` | `i` | — | `locals[i]` | `i` вне [0..localsCount) → InterpreterError |
| `local.set` | `i` | `value` | — | `i` вне [0..localsCount) → InterpreterError |

### 4.3. Арифметика

**Конвенция стека:** `push a; push b; op` → результат `a ∘ b`. Второй операнд (b) на вершине.

| op | Стек до | Стек после | Особые случаи |
|----|---------|------------|---------------|
| `add` | [a, b] | [a+b] | |
| `sub` | [a, b] | [a-b] | |
| `mul` | [a, b] | [a*b] | |
| `div` | [a, b] | [a/b] | `b === 0` → InterpreterError |
| `rem` | [a, b] | [a%b] | `b === 0` → InterpreterError |

### 4.4. Сравнения

| op | Стек до | Стек после |
|----|---------|------------|
| `eq` | [a, b] | [a === b] |
| `ne` | [a, b] | [a !== b] |
| `lt` | [a, b] | [a < b] |
| `le` | [a, b] | [a <= b] |
| `gt` | [a, b] | [a > b] |
| `ge` | [a, b] | [a >= b] |

Для `eq`/`ne` порядок pop: `b = pop()`, `a = pop()`, сравнение `a === b` / `a !== b`.

### 4.5. Управление и вызовы

| op | Поля | Стек до | Стек после | Поведение |
|----|------|---------|------------|-----------|
| `call` | `fi` | [arg0..argN] | — | Вызов процедуры по индексу `fi` |
| `invoke` | `name` | [arg0..argN] | [result?] | Системный вызов; результат пушится, если не null/undefined |
| `jmp` | `off` | — | — | Переход на `pc = off` |
| `jmp_if` | `off` | [cond] | — | Если `cond === true` → `pc = off`, иначе → next |
| `jmp_if_not` | `off` | [cond] | — | Если `cond !== true` → `pc = off`, иначе → next |
| `ret` | — | [value?] | — | Возврат из процедуры |

**call:** аргументы снимаются в порядке от последнего к первому (`unshift(pop)`), чтобы `args[0]` = первый параметр.

**invoke:** число аргументов задаётся таблицей `inferInvokeArgCount` в интерпретаторе. Неизвестный invoke → argc=0.

### 4.6. Инструкции, определённые в типе, но не реализованные в VM v1

Следующие опкоды присутствуют в `bytecode.ts` (типы, VLIW-модель), но **не эмитируются компилятором** и **не обрабатываются интерпретатором** в v1:

- `global.get`, `global.set` — глобальные переменные
- `result.unwrap`, `result.tag` — работа с `Результат<T,E>`

Использование этих опкодов в `.osvbc` приведёт к `Unknown op` в VM.

## 5. Пример

**Исходник на Основе:**

```osnova
модуль storage_demo

процедура запуск()
  система.хранилище.записать("last_run", "ok")
  система.лог.вывести(система.хранилище.прочитать("last_run"))
конец
```

**Упрощённый OsVbcModule (иллюстрация структуры):**

```json
{
  "version": 1,
  "moduleName": "storage_demo",
  "constants": ["last_run", "ok"],
  "procedures": [
    { "name": "запуск", "codeOffset": 0, "argc": 0, "localsCount": 0 }
  ],
  "code": [
    { "op": "const", "type": "str", "k": 0 },
    { "op": "const", "type": "str", "k": 1 },
    { "op": "invoke", "name": "система.хранилище.записать" },
    { "op": "const", "type": "str", "k": 0 },
    { "op": "invoke", "name": "система.хранилище.прочитать" },
    { "op": "invoke", "name": "система.лог.вывести" },
    { "op": "ret" }
  ]
}
```

## 6. Ограничения v1

- Один модуль на файл; мультимодульность — в следующих версиях
- Нет `global.get`/`global.set` в работающем VM
- Нет `result.unwrap`/`result.tag` в работающем VM
- `maxSteps` в VM ограничивает количество выполненных инструкций (защита от бесконечного цикла)
