# Системные invoke-функции Основа (v0.2)

Черновик расширения системного API рантайма: какие invoke стоит добавить, чтобы писать более живые приложения (GUI, IPC, хранилище, сеть, уведомления).

---

## 1. Реализовано в vm-runner

**Лог, файлы, время:** `система.лог.вывести`, `система.файлы.прочитать_все` / `записать_все` / `существует`, `система.время.сейчас` / `спать`.

**Хранилище:** `система.хранилище.записать` (ключ, значение), `прочитать` (ключ), `удалить` (ключ), `ключи` (). Каталог: `os.tmpdir()/osnova-storage/{appId}/store.json`.

**Сеть:** `система.сеть.запрос` (url, метод?, заголовки?, тело?) — только при `permissions.network.outbound !== false`.

**Окно:** `система.окно.создать_окно` (заголовок, ширина, высота) → id, `показать`/`скрыть`/`закрыть` (id), `установить_заголовок` (id, заголовок), `получить_события` (id) → массив событий (клик_виджета, закрытие, изменение).

**Виджеты:** `система.интерфейс.контейнер` (окно_id, родитель_id?, id?), `кнопка`/`поле_ввода`/`текст`/`область_текста` (родитель_id, текст/подсказка, id?), `получить_значение`/`установить_значение` (виджет_id, значение?). События приходят через `получить_события`; при «изменение» значение синхронизируется в `получить_значение`.

**Диалоги (заглушки в Node):** `диалог_сообщение`, `диалог_подтвердить`, `диалог_ввод` — пока только логирование.

---

## 2. GUI (система.окно и система.интерфейс)

Цель: простое окно с контентом и базовыми контролами без тяжёлого фреймворка. Варианты реализации: WebView (локальный HTML/JS от рантайма), тулчейн генерирует вызовы в DOM/дерево виджетов, либо нативное окно (например через Tauri/Electron позже).

### 2.1 Окно (жизненный цикл и контент)

| Invoke | Аргументы | Возврат | Описание |
|--------|-----------|--------|----------|
| `система.окно.создать_окно` | (заголовок, ширина, высота) | окно_id | Создать окно; id — целое или строка-хэндл |
| `система.окно.показать` | (окно_id) | — | Показать окно |
| `система.окно.скрыть` | (окно_id) | — | Скрыть |
| `система.окно.закрыть` | (окно_id) | — | Закрыть и освободить |
| `система.окно.установить_заголовок` | (окно_id, заголовок) | — | Сменить заголовок |
| `система.окно.получить_события` | (окно_id) | массив_событий | Неблокирующее чтение очереди событий (клик, закрытие, ввод и т.д.) |

Формат события (логически): например `{ тип: "закрытие" }`, `{ тип: "клик", x, y, кнопка }`, `{ тип: "клавиша", ключ, модификаторы }`. В байткоде можно передавать как структура/словарь.

### 2.2 Простые виджеты (внутри окна)

Минимальный набор, чтобы собирать формы и кнопки без полноценного UI-фреймворка:

| Invoke | Аргументы | Возврат | Описание |
|--------|-----------|--------|----------|
| `система.интерфейс.контейнер` | (окно_id, родитель_id?, id) | контейнер_id | Контейнер (панель/div); корень если родитель не задан |
| `система.интерфейс.кнопка` | (родитель_id, текст, id?) | виджет_id | Кнопка |
| `система.интерфейс.поле_ввода` | (родитель_id, подсказка?, id?) | виджет_id | Однострочное поле ввода |
| `система.интерфейс.текст` | (родитель_id, содержимое, id?) | виджет_id | Статический текст |
| `система.интерфейс.область_текста` | (родитель_id, строки?, id?) | виджет_id | Многострочный текст/редактор |
| `система.интерфейс.получить_значение` | (виджет_id) | строка | Текущее значение (поле, область_текста) |
| `система.интерфейс.установить_значение` | (виджет_id, строка) | — | Записать значение |
| `система.интерфейс.подписаться_на_клик` | (виджет_id, callback_ref?) | — | При клике по виджету — вызвать процедуру или положить событие в очередь (зависит от модели: callback в байткоде или событийная очередь) |

Для v0.2 достаточно событийной очереди: клик по кнопке добавляет в очередь окна событие `{ тип: "клик_виджета", виджет_id }`; приложение в цикле вызывает `система.окно.получить_события` и реагирует.

### 2.3 Диалоги

| Invoke | Аргументы | Возврат | Описание |
|--------|-----------|--------|----------|
| `система.интерфейс.диалог_сообщение` | (заголовок, текст) | — | Модальное сообщение (OK) |
| `система.интерфейс.диалог_подтвердить` | (заголовок, текст) | логический | Да/Нет |
| `система.интерфейс.диалог_ввод` | (заголовок, подсказка?, значение_по_умолчанию?) | строка? | Ввод одной строки; отмена = пусто или отдельный код |

## 3. Хранилище (система.хранилище)

Ключ–значение в рамках приложения (аналог localStorage), с областью по манифесту (id приложения).

| Invoke | Аргументы | Возврат | Описание |
|--------|-----------|--------|----------|
| `система.хранилище.записать` | (ключ, строка) | — | Сохранить значение |
| `система.хранилище.прочитать` | (ключ) | строка? | Прочитать; нет ключа — пусто/null |
| `система.хранилище.удалить` | (ключ) | — | Удалить ключ |
| `система.хранилище.ключи` | — | массив_строк | Список ключей (для обхода) |

Права: по манифесту `permissions.storage` или по умолчанию только для своего id.

---

## 4. IPC между приложениями/модулями ОСи

Цель: одно приложение может отправить сообщение другому (по id приложения или по «каналу»), получить ответ или подписаться на канал.

### 4.1 По идентификатору приложения

| Invoke | Аргументы | Возврат | Описание |
|--------|-----------|--------|----------|
| `система.обмен.отправить` | (id_приложения, метод_или_канал, тело_сообщения) | строка? | Отправить сообщение приложению; тело — строка или JSON-строка; возврат — ответ или null при таймауте |
| `система.обмен.подписаться` | (канал) | — | Подписаться на канал (имя строки); сообщения в канал приходят в очередь приложения |
| `система.обмен.получить_сообщения` | — | массив_сообщений | Неблокирующее чтение входящих сообщений (от других приложений/каналов) |

Формат сообщения: например `{ от: id_приложения, канал: строка, тело: строка }`. Права: в манифесте можно указать `permissions.ipc: [ "com.osnova.other.app" ]` — разрешить обмен только с перечисленными id.

### 4.2 Внутри процесса (между модулями одного приложения)

Если в одном процессе загружено несколько модулей Основа (или один модуль с несколькими «акторами»), можно ввести лёгкий обмен без выхода в ОС:

| Invoke | Аргументы | Возврат | Описание |
|--------|-----------|--------|----------|
| `система.обмен.отправить_локально` | (имя_получателя, тело) | — | Отправить в очередь получателя внутри процесса |
| `система.обмен.получить_локально` | (имя_очереди) | сообщение? | Прочитать одно сообщение из своей очереди |

Имя_получателя может совпадать с именем модуля или с именем «актора» (если в грамматике есть акторы/каналы).

## 5. Сеть (система.сеть)

При `permissions.network.outbound: true`:

| Invoke | Аргументы | Возврат | Описание |
|--------|-----------|--------|----------|
| `система.сеть.запрос` | (url, метод?, заголовки?, тело?) | строка или Результат | HTTP(S) запрос; тело и ответ — строки; при ошибке — Неудача |
| `система.сеть.запрос_асинхронно` | (url, метод?, тело?, callback_ref?) | — | Запуск запроса без ожидания; результат в callback или в очередь событий |

Для v0.2 достаточно синхронного `запрос` с таймаутом; асинхронный вариант — следующий шаг.

## 6. Уведомления (система.уведомления)

| Invoke | Аргументы | Возврат | Описание |
|--------|-----------|--------|----------|
| `система.уведомления.показать` | (заголовок, текст, иконка?) | — | Системное уведомление (трей/тост) |
| `система.уведомления.по_клику` | (идентификатор_действия) | — | При клике по уведомлению приложение получает событие (например в очередь окна или обмен) |

Права: `permissions.notifications: true` в манифесте.

## 7. Буфер обмена (система.буфер_обмена)

| Invoke | Аргументы | Возврат | Описание |
|--------|-----------|--------|----------|
| `система.буфер_обмена.записать_текст` | (строка) | — | Записать текст в буфер обмена |
| `система.буфер_обмена.прочитать_текст` | — | строка? | Прочитать текст из буфера |

Права: `permissions.system.clipboard: true`.

## 8. Приоритет внедрения (рекомендация)

1. **Хранилище** — мало зависимостей, сразу даёт «память» между запусками приложения.
2. **Буфер обмена** — уже есть флаг в манифесте; простая обёртка над API ОС.
3. **Окно + получить_события** — чтобы приложение могло реагировать на закрытие и клики (сначала окно = WebView/HTML, события из JS в рантайм).
4. **Интерфейс: контейнер, кнопка, поле_ввода, текст** + очередь событий по клику — минимальная форма.
5. **Диалоги** — сообщение, подтвердить, ввод.
6. **Сеть.запрос** — уже есть проверка `allowNetwork`; добавить реализацию fetch/axios.
7. **Обмен (IPC)** — после того как лаунчер/рантайм умеет держать несколько приложений и маршрутизировать сообщения.
8. **Уведомления** — поверх системных API (например Electron/Browser notifications или нативные).

В рантайме при добавлении нового invoke достаточно: добавить имя в таблицу аргументов (или в общий парсер сигнатур), реализовать обработчик в `createInvokeHandler` с проверкой прав и вызовом нативной обёртки (файлы, сеть, окно, хранилище и т.д.).

## 9. Чистота вызовов (для будущего VLIW)

Для будущего VLIW-оптимизирующего бэкенда важно явно размечать, какие invoke **не допускают перестановки** и образуют точки синхронизации:

- **Нечистые (I/O, побочные эффекты):** все вызовы к файлам, хранилищу, окну, интерфейсу, сети, буферу обмена, уведомлениям, IPC — зависят от порядка выполнения и от внешнего состояния; их нельзя свободно переставлять или выполнять параллельно без анализа зависимостей.
- **Потенциально чистые:** чистая арифметика и сравнения в байткоде не идут через invoke; вспомогательные invoke вроде `система.массив.длина`, `система.объект.получить`, `система.строка.объединить` при детерминированных аргументах дают детерминированный результат и теоретически могут рассматриваться как «чистые» для целей планирования, если гарантируется отсутствие скрытых зависимостей.

Рекомендация: в реализации (`vm-runner.ts`) и в этой спецификации при добавлении новых invoke помечать их как **чистые** или **нечистые**, чтобы планировщик VLIW не вносил нежелательных зависимостей и не переставлял операции через нечистые вызовы. Подробнее: `vliw-considerations.md`. Для ИИ-центричной ОС целесообразно расширить метаданные (ресурсы, длительность, отменяемость, побочные эффекты) и вести машинно-читаемый реестр API — см. `ai-centric-os-recommendations.md` (раздел 3).
