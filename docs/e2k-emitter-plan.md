# План эмиттера e2k: вход, выход, проверка

**Дата:** 2026-09-15
**Статус:** ПЛАН. **Это не эмиттер.** Эмиссии инструкций нет: развилка «достаточно ли
процедурной разметки для DSP» проверена (`src/scripts/dspBoundarySufficiency.test.ts`,
6 тестов проходят) — процедурной разметки для пяти ядер достаточно, — и поэтому план
составлен, а код эмиттера не начат.

**Отношение к документам:** спецификация подмножества — `docs/e2k-subset-dsp.md`; сырые
данные — `docs/e2k-dsp-instructions.md`; границы атомов — `docs/osnova-atom-boundaries.md`
и `src/compiler/atomRegions.ts`; фазы — `docs/vliw-phases-plan.md`; долги —
`docs/hardware-debt.md`, `docs/verification-debt.md`.

---

## 3.1. Что эмиттер получает на вход

| вход | что это | откуда |
|---|---|---|
| **регистровый модуль** | `RegModule`: процедуры, линейный код, адресация абсолютная | `src/compiler/regcodegen.ts` |
| **разметка атомов** | `module.atoms`: `{atom, optimizable, procedure, start, end}` | `annotateAtomRegions` (`src/compiler/atomRegions.ts`) |
| **спецификация подмножества** | какие операции разрешены, их классы задержек и страницы | `docs/e2k-subset-dsp.md` |
| **модель машины** | 24 канала, возможности АЛУ, кластеры, классы передачи операндов | `docs/vliw-e2k-model.md`, `src/vliw/e2kDevices.ts` |

Форма входа:

```json
{
  "ir": "osnova-reg",
  "procedures": [{"name": "фильтр", "codeOffset": 0, ...}],
  "code": [...],
  "atoms": [{"atom": "A5", "optimizable": true, "procedure": 0, "start": 0, "end": 42}]
}
```

**Чего во входе нет и не должно быть:** человекочитаемых строк, доменных правил, выбора
пользователя — это шкура (`docs/osnova-semantic-skin.md`), а не атомная часть.

## 3.2. Что эмиттер возвращает

| выход | что это | когда доступен |
|---|---|---|
| **пакеты** | `RegModule` с элементами-пакетами: код, который исполняет регистровая VM | сегодня — только для целой программы (`src/vliw/vliwPipeline.ts`), по атомам не разделён |
| **машинный код подмножества** | поток команд e2k: кодировка, регистры, предикаты, широкие команды | после кодировки подмножества (Фаза 3 закрыта для DSP как *спецификация требований*; кодировка — работа эмиттера) |

**Обязательный элемент выхода — карта размещения:** какой элемент машинного кода какому
атому принадлежит. Без неё нельзя сказать, чей инвариант нарушен, если что-то разошлось.

**Проверяемость выхода:** до появления симулятора выход проверяется на уровне пакетов
(`verifyPackets`) и эквивалентности прогонов (`npm run gate:pack`: четыре конфигурации,
19 программ). Машинный код проверить нечем, пока нет симулятора, — и это сказано прямо, а
не замалчивается.

## 3.3. Как читаются флаги `optimizable`

1. Флаги берутся **только из `module.atoms`**, а не из разметки вызывающего и не из
   манифеста приложения: источник истины — каталог (`src/compiler/atomRegions.ts`),
   сверяемый с документом `docs/osnova-signature-spec.md` §2 тестом.
2. `optimizable: true` → эмиттер **вправе** применить перестановку и упаковку внутри
   участка атома (в границах, описанных в `docs/osnova-atom-boundaries.md` §2.3).
3. `optimizable: false` → порядок операций сохраняется; упаковка в порядке допустима
   (она не меняет порядок), перестановка — нет.
4. Отсутствие поля `atoms` → эмиттер **отказывается** оптимизировать: без разметки он не
   знает границ. Это не ошибка формата (поле необязательное), но для эмиттера —
   отсутствие входных данных.

**Проверка перед эмиссией:** `verifyAtomRegions(module)` обязан вернуть пустой список —
иначе эмиттер останавливается и сообщает, что именно не так (непокрытая процедура,
пересечение, расхождение флага с каталогом).

## 3.4. Как используются границы процедур

| что можно | что нельзя |
|---|---|
| переставлять и упаковывать операции **внутри** участка атома с `optimizable: true` | переставлять операции **через** границу атома |
| упаковывать соседние инструкции **в порядке** внутри атома с `optimizable: false` | переставлять внутри атома с `optimizable: false` |
| открывать новый пакет на границе участка (граница — точка входа) | начинать пакет с середины участка |
| сохранять вызовы как границы (тела видны только внутри своего атома) | «протаскивать» операцию через границу по признаку «регистры независимы» |

Границы берутся из `atoms`: `start` — точка входа, `end` — конец участка. Регион обязан
совпадать с границами процедуры (`verifyAtomRegions` это проверяет), поэтому на текущей
гранулярности «граница атома = граница процедуры».

## 3.5. Как проверяется корректность

| шаг | оракул | состояние |
|---|---|---|
| 1. код собирается | `npm run typecheck`, `npm test` | есть |
| 2. пакеты легальны | `verifyPackets` (`src/vliw/packetVerifier.ts`) | есть |
| 3. поведение не изменилось | `npm run gate:pack` — четыре конфигурации на 19 программах | есть |
| 4. **пять DSP-ядер дают те же значения** | `src/scripts/dspKernels.test.ts` против `tests/dsp/reference.json` (независимая реализация на Python) | **есть — и это первый тест для эмиттера**: FIR 181, IIR 119, БПФ 4, свёртка 90, корреляция 32 |
| 5. машинный код исполняется | симулятор e2k: трассы совпадают с регистровой VM | симулятора нет (Фаза 5) |
| 6. такты | счётчики модели против `dprof` на железе | железа нет (`docs/hardware-debt.md`) |

**Порядок проверки при появлении эмиттера:** сначала шаги 1–4 на пакетах, затем шаг 5 на
симуляторе, и только потом любые утверждения о тактах. Пока шаг 5 недоступен, результат
эмиттера проверяем **только на уровне пакетов**, и это ограничение нельзя скрывать в
отчёте.

## 3.7. Чего в плане нет (долги, а не забытое)

| долг | почему важен для эмиттера |
|---|---|
| **насыщение** отсутствует в руководстве | эмиттер не может выбрать насыщающую операцию: контроль диапазона — кодом (`docs/e2k-subset-dsp.md` §2.8) |
| **фиксированная точка** как формат отсутствует | масштабирование делается сдвигами; для БПФ больших N это ограничение N (`docs/b-task-candidates.md` §4.2) |
| **кольцевые буферы** отсутствуют | адресация — обычные load/store с ручным индексом: потеря на вычислении адресов, не блокировка |
| **таблица 12.2** извлечена с допущением о порядке столбцов | времена передач операндов читаются как «значения по классу», а не как время конкретной передачи (`docs/e2k-dsp-instructions.md` §1.8) |
| **варианты семейств не раскрыты** | спецификация достаточна для корректности, недостаточна для оптимальности |
| **железа и симулятора нет** | любые такты — модельные, и называть их иначе нельзя |

## 3.8. Маркировка: «эмиттер на внутренней оболочке», не «эмиттер e2k»

Пока ISA-справочника нет, кодировки e2k не существует, поэтому эмиттер **не может** выдавать
код e2k — он выдаёт код на оболочке. Требования к маркировке (указание владельца, 2026-09-15):

| где | что обязано быть |
|---|---|
| имя модуля | «на оболочке», а не «e2k»: модуль эмиттера называется по оболочке |
| паспорт выхода | идентификатор бэкенда (`internal-shell`) и его статус (`ДОПУЩЕНИЕ`) |
| отчёт | «эмиттер на внутренней оболочке»; формулировка «эмиттер e2k» без оговорки запрещена |
| артефакт кода | карта размещения плюс запись, каким бэкендом получен код (`docs/e2k-backend.md` §4.2, §4.6) |

Причина не в аккуратности формулировок: код на оболочке — **гипотеза о e2k**. Если она уйдёт
в отчёт как e2k, следующий сеанс (в том числе мой собственный) будет считать непроверенное
проверенным. Долги — `docs/hardware-debt.md` §3.6: **кодировка и модель устройства — два
долга, а не один**, и замена `src/e2k/e2k.ts` второй не закрывает.

**Что меняется, когда появится справочник:** если он подтвердит форму обмена, набор полей и
размер — переписывается только `src/e2k/e2k.ts`, и маркировка меняется на «e2k». Если не
подтвердит — сначала переписывается интерфейс, затем эмиттер (`docs/e2k-backend.md` §4.6).
