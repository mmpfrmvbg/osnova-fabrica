# Данные для выбора B-задачи: три кандидата

**Дата:** 2026-09-15
**Что это:** анализ трёх кандидатов внутри класса B (ML-инференс, DSP, обработка
сигналов). Документ сам выбора не делает и рекомендации не содержит.

**РЕШЕНИЕ ВЛАДЕЛЬЦА (2026-09-15): выбран DSP.** Анализ всех трёх кандидатов сохранён
целиком: он объясняет, почему выбор сделан именно так, и остаётся справкой, если
подмножество позже расширят. Спецификация под DSP — следующий шаг.

**Напоминание о классе B (уточнённая формулировка владельца):** целевой класс — B:
специализированные задачи с высоким ILP. Цель — разноплановый софт, который работает
на e2k, с выигрышем там, где он возможен. Кратное ускорение везде не является целью;
программы с низким ILP не ускорятся — это свойство задачи, а не дефект.

**Общая оговорка для всего документа.** Наличие конкретных операций e2k ниже помечено
**ТРЕБОВАНИЕ, НЕ ФАКТ**: в этой работе их наличие и кодировка по руководству МЦСТ
**не сверялось**. Проверено по документу ровно следующее (и только оно):
24 канала выдачи, возможности АЛУ (деление и корень — только АЛУ5; запись — АЛУ2/АЛУ5;
чтения нет у АЛУ1/АЛУ4, стр. 56), не более одной передачи управления в команде
(стр. 57), регистровый файл 256 и предикатный 32 (стр. 57), длительности классов
операций (стр. 71–72), кластеры АЛУ и невозможность байпаса между ними (стр. 194) —
см. `docs/vliw-e2k-model.md`.

**Общая для всех кандидатов проблема измерения:** железа и симулятора e2k **нет**
(ответ владельца 2026-09-15). Значит до Фаз 5–6 любой выигрыш — **модельные такты**,
и называть их тактами e2k нельзя (`docs/hardware-debt.md`).

## Кандидат 1: ML-инференс

### 4.1. Какие атомы атласа задействованы

| атом | роль | `optimizable` |
|---|---|---|
| **A6 Вектор** | веса, активации, метрика, ANN | **true** |
| **B5 Чистое вычисление** | само ядро вывода: детерминизм, свободная параллельность | **true** |
| A1 Запись/факт | конфигурация, факты о модели (схема, версии) | false |
| A7 Блоб | файл весов, если он не в векторе | false |
| A5 Временной ряд | метрики инференса (латентность, качество) | **true** |
| C1 Найти | поиск по индексу (для retrieval-части, если она есть) | false |

Ядра два — A6 и B5, и обе стороны границы между ними оптимизируемы; разбор границы —
`docs/osnova-atom-boundaries.md` §2.5, пример 1.

### 4.2. Какие инструкции e2k нужны (**ТРЕБОВАНИЕ, НЕ ФАКТ**)

| требование | зачем | статус |
|---|---|---|
| FMA (умножение с накоплением) | ядро свёртки и линейного слоя | **ТРЕБОВАНИЕ, НЕ ФАКТ** — наличие на e2k не сверялось |
| векторные операции над упакованными данными | плотность для поэлементных активаций | **ТРЕБОВАНИЕ, НЕ ФАКТ** |
| быстрая загрузка весов (широкие чтения) | узкое место по памяти, а не по АЛУ | **ТРЕБОВАНИЕ, НЕ ФАКТ**; из документа известно только про уровни кэша `Ld L1/L2/L3/mem 3/11/40/~100` (стр. 71) |
| длинные независимые цепочки умножений-сложений | это и есть источник ILP для широкого выпуска | следствие природы задачи, а не операция |

**Достаточно ли скалярного FMA для первого замера:** да, если он на e2k есть:
развёрнутый скалярный цикл даёт ILP без вектора. Вектор нужен для плотности, а не для
доказательства принципа.

### 4.3. Какой корпус строить

| шаг | что писать на Основе | зачем именно это |
|---|---|---|
| 1 | скалярное умножение матрицы на вектор с развёрткой | минимальное ядро с высоким ILP и известным эталоном результата |
| 2 | свёртка (одномерная, затем двумерная) | узор с повторным использованием весов |
| 3 | один слой линейной сети + активация | проверка, что ILP не рассыпается на «настоящей» структуре |
| 4 | (необязательно) маленькая сеть целиком | только после того, как шаги 1–3 сходятся по эталону |

Эталон результата обязателен для каждого шага: без него «выигрыш» неотличим от
«считает не то». Готовых прикладных бенчмарков в проекте нет; есть синтетические
фикстуры ILP (`ilp-low/mid/high.osnova`), они для калибровки, а не для задачи.

### 4.4. Как измерять выигрыш

| где | что получаем | чем ограничено |
|---|---|---|
| симулятор e2k (когда появится) | **модельные такты** | симулятора нет; каждая его гипотеза идёт в `docs/hardware-debt.md` |
| наше текущее измерение | плотность упаковки (`1.41 → 1.45` по корпусу) и шаги VM | это **не** скорость: VM считает шагом элемент кода, а не такт |
| железо e2k | реальные такты `dprof` | доступа нет |

### 4.5. Что уже есть, что нужно построить

| уже есть | нужно построить |
|---|---|
| язык Основа, компилятор, регистровая VM | кодоген под задачу (шаги 4.3) |
| VLIW-конвейер: перестановка + упаковка, gate `npm run gate:pack` (четыре конфигурации) | эмиттер e2k (Фаза 4) |
| требования к подмножеству (`docs/e2k-subset-requirements.md`) | спецификация подмножества под задачу (Фаза 3) |
| реестр долга перед железом | симулятор e2k (Фаза 5) |

### 4.6. Главный риск

**Риск не в задаче, а в расстоянии до неё.** Настоящий инференс требует не только
FMA: нужны форматы данных, веса, слои, численная устойчивость, и всё это вне границ
проекта. Если объявить целью «ResNet», проект уйдёт в реализацию фреймворка, а не в
e2k. Поэтому в 4.3 первым шагом стоит скалярное умножение матрицы на вектор, а не
сеть: оно проверяет принцип, но не требует строить ML-инфраструктуру.

## Кандидат 2: DSP

### 4.1. Какие атомы атласа задействованы

| атом | роль | `optimizable` |
|---|---|---|
| **A5 Временной ряд** | входной/выходной сигнал как ряд; окна | **true** |
| **B5 Чистое вычисление** | фильтр как чистая функция окна | **true** |
| A6 Вектор | коэффициенты фильтра, накопление | **true** |
| A1 Запись/факт | конфигурация фильтров, параметры | false |
| A4 Лог / события | поток отсчётов в порядке поступления | false |
| E3 Наблюдать | контроль качества обработки | false |

### 4.2. Какие инструкции e2k нужны (**ТРЕБОВАНИЕ, НЕ ФАКТ**)

| требование | зачем | статус после сверки с руководством |
|---|---|---|
| **операции над упакованными векторами (Vect)** | параллельная обработка отсчётов | **ФАКТ**: класс операций АЛУ «над упакованными векторами (Vect)» — стр. 54 |
| **операции с упакованными целочисленными значениями шириной 8, 16, 32 бита** | основной инструмент DSP на этой ISA | **ФАКТ**: такие устройства есть в составе АЛУ0, АЛУ1, АЛУ3 и АЛУ4 — стр. 56 |
| **арифметика над упакованными 32-разрядными вещественными числами** | фильтры в вещественных числах | **ФАКТ**: там же, в составе тех же четырёх АЛУ — стр. 56 |
| **сдвиги** | масштабирование, выравнивание разрядности | **ФАКТ**: сдвиговое устройство входит в состав всех АЛУ (стр. 56); мнемоники `SHL`/`SHR`/`SCL` и описание сдвигов — стр. 162; `shl, shr, sar` в перечне целочисленных операций — стр. 71 |
| **штраф класса fp за упакованные операции** | планирование цепочек: упакованные целочисленные операции получают штраф класса fp | **ФАКТ**: «дополнительный штраф в классе fp получают упакованные (векторные) целочисленные операции, а также операции целочисленного умножения и деления» — стр. 72 |
| **цепочки из двух зависимых операций** | фильтр с накоплением — цепочка зависимостей | **ФАКТ**: «целочисленные устройства в АЛУ1 и АЛУ4 позволяют исполнять две последовательно зацепленные…» — стр. 56 |
| **упакованный MAC** | ядро КИХ/свёртки/корреляции | **ЕСТЬ**: `PMADDH`, `PMADDUBSH` — умножение с накоплением, класс `out_2m`, стр. 196. Исправлено 2026-09-15: прежде здесь стояло «не найдено» (см. ниже) |
| скалярный MAC как одна операция | ядро скалярного фильтра одной инструкцией | **НЕТ В ДОКУМЕНТЕ**: слов «накопление» и «сумма произведений» в полном тексте нет ни одного раза, скалярного `MADD` в перечнях стр. 196–198 нет; собирается из `MULs`/`SMULHd` + `ADD` (см. `docs/e2k-subset-dsp.md` §2.7) |
| операции с насыщением | фиксированная точка без переполнения | **НЕ НАЙДЕНО В ДОКУМЕНТЕ**: слова с корнем «насыщ» в полном тексте нет ни одного раза |
| фиксированная точка как формат | DSP-арифметика с гарантией диапазона | **НЕ НАЙДЕНО В ДОКУМЕНТЕ**: словосочетание не встречается; 4 вхождения корня «фиксированн» относятся к фиксированному числу параметров и фиксированной длительности `mova` |
| целочисленное деление | нормировка, редкое | по документу: деление и корень — только АЛУ5 (стр. 56) |
| предсказуемая задержка | важнее пиковой производительности | свойство задачи, не операция |

**Как читать эту таблицу.** Сверка с руководством МЦСТ (извлечённый текст покрывает все
208 страниц PDF; ссылки — **физические страницы PDF**, как и в остальных документах
проекта: кластеры стр. 194, таблица длительностей стр. 71–72) изменила картину риска: **упакованные
целочисленные операции 8/16/32 бита, упакованная вещественная арифметика и упакованное
умножение с накоплением в документе есть** — это и есть естественная основа DSP на этой
ISA.

**ИСПРАВЛЕНО 2026-09-15 (в тот же день).** Сначала здесь было записано «MAC как одна
операция не найден» — это **неверно**. Ошибка была в способе проверки: искались СЛОВА
(«насыщение», «накопление»), а не МНЕМОНИКИ, и семейство `PADD*` искалось без
звёздочки. В разделе 12.1.1.2 (стр. 196) есть перечень мнемоник по классам задержек, и
там названы `PMADDH`, `PMADDUBSH` (умножение с накоплением, класс `out_2m`),
`PMULHRSH`, `PSADBW`, а также семейства `PADD*`, `PSUB*`, `PAVG*`, `PSHUF*`,
`PHADD*`, `PHSUB*`. Верным остаётся только одно: **скалярного** MAC в документе нет и
слова «насыщение» нет.

Значит DSP-подмножество специфицируется вокруг упакованных операций, **включая
упакованный MAC**, а насыщение эмулируется (разрядность с запасом, сдвиги,
предикатное ограничение).

**Достаточно ли этого для первого замера:** да. КИХ-фильтр на упакованных целочисленных
операциях с развёрткой даёт и независимые цепочки, и векторную плотность; эталон
результата считается вручную. Ограничение, которое надо помнить: без насыщения
переполнение придётся контролировать самим — либо разрядностью упакованных значений,
либо сдвигами.

### 4.3. Какой корпус строить

| шаг | что писать на Основе | зачем именно это |
|---|---|---|
| 1 | КИХ-фильтр (свёртка с коэффициентами) на целом сигнале | эталон результата считается вручную; ILP очевиден |
| 2 | тот же фильтр в фиксированной точке с масштабированием | проверяет сдвиги и насыщение (если они есть) |
| 3 | каскад фильтров (несколько звеньев) | проверяет, что ILP сохраняется между звеньями |
| 4 | (необязательно) БИХ-фильтр с обратной связью | честный случай с зависимостью по выходу — там ILP может исчезнуть |

Шаг 4 важен как негативный контроль задачи: БИХ содержит зависимость по выходу, и
если он не ускоряется, это **свойство задачи**, а не дефект (формулировка класса B).

### 4.4. Как измерять выигрыш

То же, что у кандидата 1: модельные такты на симуляторе, реальные — только на железе
(которого нет). Для DSP добавляется дополнительная величина: **предсказуемость**
задержки (разброс времени на окно), а не только среднее. Измерять её сейчас нечем —
это долг перед железом.

### 4.5. Что уже есть, что нужно построить

| уже есть | нужно построить |
|---|---|
| язык, компилятор, регистровая VM | кодоген фильтров (4.3) |
| VLIW-конвейер с оракулом и негативным контролем | эмиттер e2k |
| требования к подмножеству (§2.2, §2.3) | спецификация целочисленных операций с насыщением — если их нет, задача упирается в это |

### 4.6. Главный риск

**Фиксированная точка и насыщение могут не входить в подмножество.** Тогда DSP-задача
либо вырождается в целочисленную арифметику без гарантий диапазона (и результат
приходится проверять руками), либо требует расширения подмножества до спецификации
Фазы 3 — то есть ещё одного круга работ до первого замера. Второй риск: «предсказуемая
задержка» не проверяется без железа.

## Кандидат 3: Обработка сигналов

### 4.1. Какие атомы атласа задействованы

| атом | роль | `optimizable` |
|---|---|---|
| **A5 Временной ряд** | сигнал во времени, окна, сжатие | **true** |
| **B5 Чистое вычисление** | преобразование окна (бабочка, фильтр, спектр) | **true** |
| A6 Вектор | спектр, коэффициенты, метрика | **true** |
| A4 Лог / события | порядок отсчётов и событий | false |
| A7 Блоб | записанные сегменты сигнала, если не в ряду | false |
| E3 Наблюдать | контроль качества (SNR и подобное) | false |

Замечание: у этого кандидата ядер **три** (A5, A6, B5), а связок между ними больше,
чем у DSP, — и именно поэтому он сложнее для проверки границ.

### 4.2. Какие инструкции e2k нужны (**ТРЕБОВАНИЕ, НЕ ФАКТ**)

| требование | зачем | статус |
|---|---|---|
| MAC и/или FMA | бабочка и фильтрация | **ТРЕБОВАНИЕ, НЕ ФАКТ** |
| табличные чтения (индексные обращения) | поворотные множители БПФ | **ТРЕБОВАНИЕ, НЕ ФАКТ**; из документа известно только про уровни кэша (стр. 71) |
| обмены/перестановки данных | переупорядочивание для БПФ | **ТРЕБОВАНИЕ, НЕ ФАКТ** |
| плавающая точка | спектр в вещественных числах | по документу: `Fp` и штрафы домена `fp→int +2`, `int→fp +1` (стр. 72, 194) |
| предикаты | условные ветви бабочки без переходов | по документу: 32 предиката, три ПЛ-устройства (стр. 54, 57) |

### 4.3. Какой корпус строить

| шаг | что писать на Основе | зачем именно это |
|---|---|---|
| 1 | дискретное преобразование Фурье «в лоб» (O(N²)) | эталон прост, но ILP высокий: независимые пары |
| 2 | бабочка БПФ (одна ступень, затем полное) | проверяет обмены и табличные чтения — самое трудное для упаковки |
| 3 | оконная функция (Хэмминг/Ханн) поверх | покомпонентное умножение — чистый ILP |
| 4 | спектр → метрика (например, энергия по полосам) | связка A5 → B5 → A6 без больших зависимостей |

### 4.4. Как измерять выигрыш

Как у остальных: модельные такты на симуляторе, реальные — на железе которого нет.
Дополнительно: у БПФ выигрыш зависит от **обменов данными**, а наш упаковщик их не
моделирует (в модели нет стоимости перестановок между регистрами и каналами). Значит
модельный выигрыш на БПФ может оказаться **оптимистичнее** реального сильнее, чем на
DSP — это надо помнить при чтении чисел.

### 4.5. Что уже есть, что нужно построить

| уже есть | нужно построить |
|---|---|
| язык, компилятор, регистровая VM | кодоген БПФ с таблицами (4.3) |
| VLIW-конвейер (перестановка + упаковка) | модель стоимости обменов данными — её нет ни в планировщике, ни в упаковщике |
| требования к подмножеству | спецификация табличных чтений и обменов |

### 4.6. Главный риск

**Обмены данными не моделируются.** Планировщик и упаковщик считают независимость
регистров и совместимость каналов, но не стоимость перестановок и табличных чтений.
На БПФ это ядро задачи: если модель их не учитывает, модельный выигрыш может
расходиться с реальным сильнее, чем у других кандидатов. Второй риск: три ядра и
больше границ — больше мест, где ошибка композиции пройдёт незамеченной (правило:
каждое соединение — отдельный оракул, `memory/_index.md`).

## Критерии выбора

**Рекомендации нет: выбор — решение владельца.** Ниже — вопросы, ответы на которые
определяют, что специфицировать в Фазе 3, и что известно по каждому кандидату.

| критерий | почему важен | что нужно знать владельцу |
|---|---|---|
| **понимание задачи владельцем** | спецификация пишется под задачу; непонятая задача даёт спецификацию «вообще» | насколько близка ему тема: сеть, фильтр или спектр |
| **наличие бенчмарков** | без внешнего эталона доказательство самосогласованно | есть ли у него эталонные реализации/числа и на чём их считать |
| **спрос** | определяет, останется ли работа нужной через год | нужен ли результат кому-то, кроме проекта |
| **сложность спецификации** | чем больше «тяжёлых» операций, тем длиннее Фаза 3 | у ML-инференса — FMA/вектор; у DSP — насыщение/фиксированная точка; у сигналов — таблицы/обмены/плавающая точка |
| **объём корпуса** | одна программа — курьёз; нужен ряд | сколько шагов из 4.3 реально написать на Основе |
| **наличие внешнего эталона результата** | иначе не отличить «быстрее» от «считает не то» | есть ли независимая реализация для сверки |
| **проверяемость без железа** | железа и симулятора нет; часть выводов останется модельной | готов ли он принять модельные числа как промежуточный результат |
| **риск задачи** | см. 4.6 каждого кандидата | расстояние до результата: у ML оно самое большое, у DSP — среднее, у сигналов — среднее с риском модели обменов |

**Что уже известно точно и не зависит от выбора:** подмножество под B должно быть
**широким** (разноплановый софт), ядра несут четыре атома (A5, A6, B4, B5), границы
жёсткие, эмиттер и симулятор отсутствуют, железа нет. Выбор задачи определяет только
**специализацию** внутри широкого подмножества.
