# AST Основа, формат 1.0 — типизированное дерево и его лента

> Статус: активный фронт (D50, Phase 0 AST-embedding). Источник истины — код
> `src/compiler-v3/astFormat.ts`; этот документ фиксирует **формат**, а не реализацию парсера.

## 1. Зачем отдельный AST

Это **не** AST парсера v2 (`src/compiler/ast.ts`) и **не** parse tree. Один формат обслуживает
три адресата сразу (решение D50):

1. статический чекер фазы 1 (D42): типы, контракты, регион-дисциплина;
2. AST-embedding в бинарь (Phase 0): секция, версия, детерминизм;
3. recompile (Phase 1): достаточно информации, чтобы собрать программу заново.

Отсюда три требования, каждое проверяется оракулом:

- **типизированные узлы**, а не токены и не «сырое дерево»;
- **позиции в кодовых точках**, а не в байтах и не в UTF-16;
- **плоская числовая лента**, пригодная для печати на цели e2k, где записей и структур нет.

## 2. Версия и заголовок

| Поле | Значение |
|---|---|
| `формат` | `osnova-ast` |
| `версия` | `1.0` (`мажор.минор`) |
| магия ленты | `20261108` |

Мажор меняется при несовместимой правке структуры, минор — при добавлении полей/видов без ломки
читателя. Лента несёт те же числа (`1`, `0`) в заголовке, поэтому читатель не обязан разбирать
JSON, чтобы узнать версию.

## 3. Детерминизм (Phase 0)

В формате **нет** таймстампов, случайных id, путей и хэшей.

- Порядок процедур — порядок объявления.
- Порядок параметров и аргументов — порядок исходника.
- Поля объектов записываются в фиксированном порядке (`канонизировать`), поэтому
  `каноническийJSON` одного AST побайтово одинаков на любой машине.
- Стабильный id процедуры — `p<индекс>` в порядке объявления. Это детерминированный id **модуля**,
  а не «уникальный во вселенной»; для межмодульных ссылок будет отдельная таблица (Phase 1).

Сортировка ключей по алфавиту не используется намеренно: порядок задан схемой, а не сортировкой,
иначе добавление поля меняло бы байты канонического JSON.

## 4. Позиции

```ts
interface Позиция {
  начало: number;   // 0-based смещение первой кодовой точки узла
  конец: number;    // смещение СРАЗУ ЗА последней кодовой точкой (исключающая граница)
  строка: number;   // 1-based
  колонка: number;  // 1-based, в кодовых точках
}
```

Кодовые точки — единица языка (D1): символ вне BMP — **одна** позиция, а не две. Лексер
`tokenizeV3` отдаёт `offset`, `length`, `column` в тех же единицах; парсер не пересчитывает байты.

## 5. Узлы

### 5.1 Тип

```ts
type Тип =
  | { вид: 'имя'; имя: string }
  | { вид: 'список'; элемент: Тип }
  | { вид: 'результат'; успех: Тип; ошибка: Тип };
```

Имена (`Число`, `Строка`, `Логическое`, `Пусто`, `Ошибка`, пользовательские) — вид `имя`.
Конструкторы `Список Т` и `Результат<Т, Е>` — отдельные виды, потому что чекеру нужны их
аргументы, а не строка.

### 5.2 Литерал

```ts
type Литерал =
  | { вид: 'число'; текст: string }
  | { вид: 'строка'; значение: string }
  | { вид: 'логическое'; значение: boolean }
  | { вид: 'пусто' };
```

`число` хранит **текст** лексемы, а не `number`: формат не теряет точность и не решает за
семантику, как читать литерал. `строка` хранит **декодированное** значение (без кавычек и
escape-последовательностей).

### 5.3 Выражение

```ts
type Выражение =
  | { вид: 'литерал'; литерал: Литерал; позиция: Позиция }
  | { вид: 'имя'; имя: string; позиция: Позиция }
  | { вид: 'вызов'; имя: string; аргументы: readonly Выражение[]; позиция: Позиция };
```

В v0.1 нет бинарных операторов, индексации, обращений к полям. Всё это — вне подмножества и
обязано быть **названным отказом**, а не пустым узлом.

### 5.4 Оператор

```ts
type Оператор =
  | { вид: 'вернуть'; значение?: Выражение; позиция: Позиция }
  | { вид: 'если'; условие: Выражение; тогда: readonly Оператор[];
      иначе?: readonly Оператор[]; позиция: Позиция }
  | { вид: 'вызов'; вызов: Выражение & { вид: 'вызов' }; позиция: Позиция };
```

`вернуть` без значения и `вернуть выражение` — один вид с необязательным полем: это не два
разных оператора, а один с разной полнотой.

### 5.5 Контракт — зарезервированные поля

```ts
interface Контракт {
  требует: readonly Выражение[];
  обеспечивает: readonly Выражение[];
  эффекты: readonly string[];
}
```

Поля есть у **каждой** процедуры и в v0.1 **пусты**: парсер v0.1 их не разбирает (D42:
«заложено, не реализовано»). Пустое поле — это НЕ «контракта нет», а «парсер v0.1 его не
прочитал»; различие принципиально для чекера, который обязан отличать «не проверено» от
«проверено и пусто».

### 5.6 Процедура и модуль

```ts
interface Процедура {
  id: string;                 // p0, p1, … в порядке объявления
  имя: string;
  параметры: readonly Параметр[];
  возвращает: Тип | null;
  тело: readonly Оператор[];
  контракт: Контракт;
  позиция: Позиция;
}

interface МодульAst { имя: string; позиция: Позиция; }

interface AstФайл {
  формат: 'osnova-ast';
  версия: string;             // '1.0'
  модуль: МодульAst;
  процедуры: readonly Процедура[];
}
```

Один файл v3 = один модуль: шапки `модуль` в v3 нет, имя модуля задаёт вызывающий
(`parseV01(source, filename)`).

## 6. Лента AST

Лента — **поток событий** в порядке обхода, без длин поддеревьев. Так её может печатать
программа на цели, которая не умеет откладывать запись до подсчёта детей. Контейнеры
закрываются событиями `*_конец`, у которых есть конец позиции.

### 6.1 Заголовок

```
[магия=20261108, мажор=1, минор=0, вид=1, длина_имени, …кодпоинты, конец_модуля]
```

`вид=1` — AST; `вид=2` — названный отказ (§7). `конец_модуля` — смещение сразу за последней
кодовой точкой исходника.

### 6.2 События

| Код | Событие | Полезная нагрузка |
|---:|---|---|
| 0 | конец | — |
| 1 | процедура_начало | начало, строка, колонка, конец_токена, длина_имени, …имя |
| 2 | параметр | начало, строка, колонка, длина_имени, …имя, тип, конец |
| 3 | процедура_заголовок | число_параметров, есть_возврат (0/1), [тип] |
| 4 | процедура_конец | конец |
| 5 | если_начало | начало, строка, колонка, конец_токена |
| 6 | иначе | — |
| 7 | если_конец | конец |
| 8 | вернуть | начало, строка, колонка, конец_токена, есть_значение (0/1) |
| 9 | вызов_оператор | начало, строка, колонка |
| 10 | вызов_начало | начало, строка, колонка, длина_имени, …имя |
| 11 | вызов_конец | число_аргументов, конец |
| 12 | литерал | начало, конец, строка, колонка, вид_литерала, значение |
| 13 | имя | начало, конец, строка, колонка, длина_имени, …имя |

Тип в ленте:

- `1` имя: `1, длина, …кодпоинты`;
- `2` список: `2, тип_элемента`;
- `3` результат: `3, тип_успеха, тип_ошибки`.

Литерал в ленте:

- `1` число: `1, длина, …кодпоинты текста`;
- `2` строка: `2, длина, …кодпоинты значения`;
- `3` логическое: `3, 0|1`;
- `4` пусто: `4`.

Лента заканчивается `0` (код `конец`).

### 6.3 Инварианты ленты

- Первое число — магия; второе/третье — версия; четвёртое — вид.
- Число параметров в `процедура_заголовок` равно числу событий `параметр`.
- Число аргументов в `вызов_конец` равно числу выражений между `вызов_начало` и `вызов_конец`.
- Позиции — неубывающие в порядке обхода; конец узла не меньше начала.
- `прочитатьЛенту` на любой ленте либо строит AST, либо бросает исключение с названным местом
  обрыва; молчаливой «пустой AST» нет.

## 7. Лента названного отказа

```
[магия, мажор, минор, вид=2, длина_имени_модуля, …имя, конец_модуля,
 длина_кода, …код_ошибки,
 начало, конец, строка, колонка,
 длина_вида_токена, …вид,
 длина_лексемы, …лексема,
 0]
```

Код ошибки — её **личность**, а не текст. Текст строится из кода и лексемы
(`сообщениеОшибки`), поэтому цель может напечатать только код/вид/лексему, а читатель получит
тот же текст, что и TS-эталон. Так названный отказ не зависит от того, умеет ли цель склеивать
строки (D45).

Коды подмножества v0.1: `OSN-PAR-001` … `OSN-PAR-015`; их смысл — в `astFormat.ts`
(`КОДЫ_ОШИБОК` / `сообщениеОшибки`).

## 8. Канонический JSON

`каноническийJSON(ast)` — `JSON.stringify` значения с фиксированным порядком ключей и отступом
2, с завершающим `\n`. Это форма для сравнения и для встраивания, а не «удобный вывод»:
любое изменение порядка ключей — изменение формата.

`сравнитьAst` сравнивает **канонизированные** значения и называет первое расхождение путём
(`$.процедуры[0].тело[1].условие.позиция.начало`), а не «объекты не равны».

## 9. Граница парсера v0.1

Подмножество v0.1 (`src/compiler-v3/parserV01.ts`):

- `процедура имя(параметр: тип, …) [→ тип] блок конец`;
- операторы: `вернуть [выражение]`, `если … [иначе …] конец`, вызов-оператор;
- выражения: литерал, имя, вызов (аргументы — выражения), скобки;
- типы: ключевые имена, `Список Т`, `Результат<Т, Е>`.

Всё остальное — **названный отказ** `OSN-PAR-003` (или более точный код), а не молчаливое
игнорирование. Пустая AST на невалидной программе — дефект D5, а не «мягкий разбор».

Контракты `требует`/`обеспечивает`/`эффекты` зарезервированы и пусты; их разбор — расширение
v0.1, а не текущая ложь.

Полная фактическая граница — что `parserV01` принимает, что использует целевой парсер и где
self-host упирается в ABI глубины 2 — зафиксирована в `docs/v0.1-semantics.md` §6 (D56). Там же
названо расхождение комментария `parserV01` с кодом: `Успех(1)`/`Неудача(x)` разбираются как
**обычные вызовы** с такими именами, а не как конструкторы пары.

Протокол ленты токенов и backpatch `вернуть` — `docs/parser-protocol.md`. Формат AST 1.0 при
этом **не меняется**: протокол описывает транспорт и упаковку, а не структуру AST.

## 10. Оракулы

- `parseV01` + `лентаИзAst` + `прочитатьЛенту`: roundtrip ленты и канонического JSON.
- Сравнение AST с эталоном по узлам/типам/позициям (кодовые точки).
- Названный отказ: невалидная программа даёт `вид=2` и код, а не `вид=1` с пустым деревом.
- Целевая печать ленты (e2k) сверяется с `лентаИзAst` побайтово; **ELF парсера v0.1 на момент
  этой редакции не собран** — это отдельный факт, а не обещание.

## 11. Что НЕ входит в формат 1.0

- контракты как разобранные выражения (поля зарезервированы);
- бинарные операторы, индексация, поля, `пусть`, циклы;
- межмодульные ссылки и таблица символов;
- отладочные имена/комментарии;
- таймстампы, пути, хэши.

Добавление любого из них — минор/мажор версии с записью здесь и в `docs/decisions.md`.
