# Реестр языка Основа (Language Registry)

Реестр языка — **единый источник правды** о ключевых словах и конструкциях Основа. Изменения (новые конструкции, пометки `implemented`) вносятся в одном месте; генератор (LLM), компилятор, документация и golden-тесты ссылаются на этот артефакт.

---

## 1. Назначение

- **Версионность:** язык имеет версию (`2.0.0`), согласованную с `meta.osnova_version` в трейсах и с `minOsnovaVersion` в реестре приложений (`registry-v0.1.md`).
- **Генератор (LLM):** промпт можно дополнять выдержкой из реестра — список ключевых слов и шаблоны синтаксиса (`syntax`, `bytecodePattern`) — чтобы модель использовала только допустимые конструкции и не «выдумывала» синтаксис.
- **Тулчейн:** лексер/парсер/компилятор могут валидироваться против реестра (например, проверять, что все используемые ключевые слова помечены как `implemented`).
- **Документация:** каноничное человекочитаемое описание — `docs/language-v2.md`.

---

## 2. Расположение артефактов

| Артефакт | Описание |
|----------|----------|
| `src/compiler/language-registry.ts` | **Источник правды:** TS-интерфейсы (`KeywordSpec`, `ConstructSpec`, `LanguageRegistry`) и константа `LANGUAGE_V01`. Импортируется компилятором и скриптами. |
| `docs/osnova/language-schema.json` | JSON-экспорт языка для документации и инструментов. Генерируется скриптом `scripts/generate-language-schema.ts` (`npm run generate:language-schema`). |
| `docs/osnova-language-spec.json` | Расширенная документация языка (philosophy, types, constructs). Не используется в коде; ручное сопровождение. Для справки и внешних инструментов. |
| `docs/language-registry.md` | Этот документ: описание реестра, связь с другими спеками. |

**Обновление JSON после изменений в реестре:**

```bash
npm run generate:language-schema
```

**Авто-проверка согласованности лексера и реестра:** скрипт `validate-language-registry.ts` проверяет, что (1) все ключевые слова, помеченные в реестре как `implemented`, присутствуют в лексере, и (2) все ключевые слова лексера есть в реестре языка. Сравнение идёт с **принимаемыми** лексемами лексера (`ACCEPTED_KEYWORD_LEXEMES` = зарезервированные `KEYWORDS` + контекстные закрывающие `BLOCK_CLOSING_LEXEMES`): после БЛОК 1 v2 `конец` и `конец_*` не зарезервированы — их вид определяет парсер, — но реестр обязан их описывать, и проверка «только против `KEYWORDS`» краснела бы на верном коде. Логика проверки — `src/compiler/registryAgreement.ts` (оракул: `registryAgreement.test.ts`). Запуск:

```bash
npm run osnova-language:validate
```

При расхождении скрипт завершается с кодом 1 и выводит список расхождений. Имеет смысл вызывать его в CI или перед коммитом после изменений в `lexer.ts` или `language-registry.ts`.

## 3. Структура реестра

- **version** — семантическая версия языка (например `0.1.0`).
- **keywords** — массив ключевых слов:
  - `lexeme` — строка как в исходнике (`для_каждого`, `в`, `и`, `или`, `не`, …);
  - `kind` — категория: `module`, `stmt`, `expr`, `block`, `type`, `vliw`;
  - `implemented` — реализовано в текущем компиляторе (`src/compiler`);
  - `since` — версия языка, с которой доступно;
  - `description` — по желанию.
- **constructs** — массив конструкций:
  - `id` — идентификатор (`if`, `while`, `for_each`, `loop`, `return`, `and`, `or`, `not`, …);
  - `syntax` — шаблон для человека и LLM (например `"для_каждого <переменная> в <выражение> ... конец"`);
  - `astNode` — вид узла AST и поля (`kind`, `fields`);
  - `bytecodePattern` — описание реализации в байткоде (для документации/LLM);
  - `since`, `implemented`, `description`.

Полная схема в TypeScript: `src/compiler/language-registry.ts`. Примеры использования: `getImplementedKeywords()`, `getImplementedConstructs()`, `languageRegistryToJson()`.

## 4. Пайплайн osnova-check

Полная проверка тулчейна (команда `npm run osnova-check`) выполняется в фиксированном порядке: сначала согласованность реестра и кода, затем тесты и сборка.

```
npm run osnova-check
  │
  ├─ osnova-language:validate   ← реестр ↔ лексер (ключевые слова)
  ├─ test:vm                    50+ unit-тестов VM
  ├─ test:compile              15 тестов (позитив + негатив + recovery + иначе + для_каждого + и/или/не)
  ├─ osnova-compile:all         *.osnova → *.osvbc.json
  └─ osnova-golden:apps         TODO + File Viewer + Notifications
```

Такой порядок гарантирует: расхождение между реестром и лексером ловится **до** запуска тестов и компиляции фикстур.

**Что закрывает валидация:**

- Ключевое слово добавлено в лексер, но не в реестр → «в лексере есть ключевые слова, которых нет в реестре».
- В реестре помечено `implemented: true`, но лексемы нет в лексере → «реестр помечает как implemented ключевые слова, которых нет в лексере».
- Переименование или удаление в одном месте без второго → та же проверка в обе стороны.

Ключевые слова с `implemented: false` (зарезервированные на будущее) в лексер добавлять не обязательно — валидатор сверяет только наличие лексем: для реестра проверяется, что каждая лексема из лексера есть в реестре (в любой записи), и что каждая реализованная в реестре лексема есть в лексере.

## 5. Связь с другими реестрами и спеками

- **traces-v1.md:** в каждой записи трейса в `meta` задаётся `osnova_version`. Это версия языка, под которую сгенерирован/скомпилирован код.
- **registry-v0.1.md:** у приложений может быть `minOsnovaVersion`. Рантайм/магазин могут проверять совместимость: приложение, собранное под язык v0.1, ожидает наличия конструкций из реестра этой версии; при появлении v0.2 в реестре можно описать, какие конструкции добавлены и как интерпретировать `minOsnovaVersion`.
- **golden-schema.md:** golden-тесты описывают ожидаемое поведение тулчейна; список допустимых конструкций и ключевых слов можно сверять с реестром языка (например, теги тестов привязывать к `constructs[].id`).
- При формировании промпта используйте выдержку из `docs/osnova/language-schema.json`: перечень реализованных ключевых слов и шаблоны синтаксиса.

## 6. Версии языка

Текущая версия языка: **2.0.0** (константа `LANGUAGE_VERSION` в `src/compiler/language-registry.ts`).  
Версия `v1.1.0` выпущена и реализована в компиляторе; `v1.2.0` — обработка ошибок (`попробовать` / `иначе_попытка` / `выбросить`); `v1.3.0` — стабилизация `для_каждого` и индексированная итерация; `v1.4.0` — вызовы пользовательских процедур; `v1.5.0` — импорт/экспорт модулей; `v1.6.0` — именованные типы и аннотации (см. подразделы ниже).

### Новые конструкции в v1.1.0

- `array_index_read` — `массив[индекс]` (sugar над `система.массив.получить`), `since: 1.1.0`.
- `array_index_write` — `массив[индекс] = значение` (sugar над `система.массив.установить`), `since: 1.1.0`.
- `then_keyword` — опциональное `тогда` после условия в `если` / `иначе_если` / `пока`, `since: 1.1.0`.
- `main_with_args` — `процедура главная(аргументы)` для CLI argv, `since: 1.1.0`.

### Новые конструкции в v1.2.0

- `try_catch` — `попробовать/иначе_попытка/конец` (блок обработки ошибок), `since: 1.2.0`, статус: stable (стабилизировано в 1.2.0).
- `throw_stmt` — `выбросить <выражение>` (выброс исключения), `since: 1.2.0`.

### Новые/обновлённые конструкции в v1.3.0

- `for_each` — `для_каждого элемент в массив / конец`, статус: stable (было experimental), `since: 1.0.0`, стабилизирована в `1.3.0`.
- `for_each_indexed` — `для_каждого элемент, индекс в массив / конец`, `since: 1.3.0`.

### Новые/обновлённые конструкции в v1.4.0

- `proc_call` — вызов пользовательской процедуры (передача аргументов и возврат значения), `since: 1.4.0`, статус: stable (стабилизировано в 1.4.0).
- `proc_call_recursive` — рекурсивные вызовы процедур, `since: 1.4.0`, статус: stable (стабилизировано в 1.4.0).

### Новые/обновлённые конструкции в v1.5.0

- `module_import` — импорт экспортированных процедур из другого файла: `использовать модуль <namespace> из "<путь>"`, since: 1.5.0, статус: stable (стабилизировано после 50+ трейсов, 2026-03-19)
- `module_export` — экспорт публичной процедуры модуля: `процедура экспорт <имя>(...) ... конец`, since: 1.5.0, статус: stable (стабилизировано после 50+ трейсов, 2026-03-19)

### Новые/обновлённые конструкции в v1.6.0

- `named_type_declaration` — объявление именованных типов через `тип Имя { поле: Тип ... }`, since: 1.6.0, статус: stable
- `type_annotation` — аннотация переменной `пусть имя: Тип = { ... }`, since: 1.6.0, статус: stable
- `nullable_type` — nullable-поля с префиксом `?`, например `?Строка`, since: 1.6.0, статус: stable

### Новые ключевые слова в v1.2.0

- `попробовать` — начало блока обработки ошибок, `since: 1.2.0`.
- `иначе_попытка` — catch-блок, `since: 1.2.0`.
- `выбросить` — оператор выброса исключения, `since: 1.2.0`.

При появлении новых конструкций или ключевых слов:

1. Обновить `language-registry.ts`: добавить поля с `since: "0.2.0"` (или текущей версией), при необходимости ввести новую константу `LANGUAGE_V02`.
2. Запустить `npm run generate:language-schema`, чтобы обновить `docs/osnova/language-schema.json`.
3. Обновить документацию (грамматика, лексер, парсер) и при необходимости `trace-format` / `registry` в части версий.

Таким образом, язык становится формальным артефактом системы с одним источником правды и явной версионностью.
