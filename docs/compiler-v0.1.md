# Компилятор языка «Основа» v0.1

> **⚠️ Статус:** architecture design document. Текущая реализация может расходиться
> с описанием. Актуальный код: `src/compiler/`.

Спецификация компилятора: пайплайн от исходного кода до артефакта (байткод или нативный код), без реализации — только цели, фазы и форматы.

---

## 1. Общая схема [✅ реализовано]

```
исходник (.osnova)
    → Лексер      → токены
    → Парсер      → AST
    → Типчекер    → аннотированный AST / ошибки
    → Бэкенд      → байткод (.osvbc) или C/Rust/IR
```

Для v0.1 достаточно **одного модуля** на вход; мультимодульность и `использовать` можно обрабатывать на уровне одного скомпилированного пакета (все импорты разрешаются до компиляции).

**Реализовано в коде** (`src/tools/osnova-compiler`, `src/tools/osnova-runtime/vm`): лексер (newline-разделитель, ключевые слова в т.ч. `для_каждого`, `в`, `и`, `или`, `не`), парсер (процедуры, `если`/`иначе`, `пока`, `для_каждого` … `конец`, `цикл`, `вернуть`, выражения с `и`/`или`/`не` и short-circuit), кодоген в байткод, интерпретатор (стековая VM, invoke для `система.*`). Сборка фикстур: `npm run osnova-compile:all`; проверка: `npm run osnova-check`. Единый источник правды о языке (ключевые слова, конструкции, версия): **реестр языка** `src/tools/osnova-compiler/language-registry.ts` и `docs/osnova/language-registry.md`; JSON-экспорт для LLM/документации: `docs/osnova/language-schema.json` (генерация: `npm run osnova-language:export`). Синтаксис и ключевые слова описаны в `grammatika-v0.1.md` (раздел «Реализованный синтаксис MVP»), `lexer-v0.1.md`, `parser-v0.1.md`.

## 2. Фазы компилятора

### 2.1. Лексер [✅ реализовано]

- **Вход:** строка (исходный код).
- **Выход:** массив токенов + список ошибок лексики.
- **Спецификация:** `docs/osnova/lexer-v0.1.md`.

При ошибках компилятор может остановиться или продолжить (best effort), но следующий этап получает только токены без ошибок или с помеченными `Error`-токенами.

### 2.2. Парсер [✅ реализовано]

- **Вход:** токены.
- **Выход:** AST модуля + список синтаксических ошибок.
- **Спецификация:** `docs/osnova/parser-v0.1.md`.

Парсер не проверяет типы и существование символов — только структуру программы.

### 2.3. Типчекер (семантический анализ) [📋 планируется]

- **Вход:** AST.
- **Выход:** тот же AST с разрешёнными типами и привязкой символов, либо список семантических ошибок.

Задачи v0.1:

- Построить таблицу символов: имена типов, процедур, функций, полей, параметров, локальных переменных.
- Для каждого выражения вывести тип; проверить совместимость в присваиваниях, аргументах, возвращаемых значениях.
- Проверить, что в `функция` нет побочных эффектов (вызов процедур, присваивание глобальным/полям по ссылке и т.д.) — по желанию, можно ослабить в v0.1.
- Разрешить перегрузки не обязательно; при наличии — привязка вызова к конкретной сигнатуре.

Ошибки: «неизвестный тип», «несовместимый тип», «символ не найден», «неверное число аргументов».

### 2.4. Бэкенд [🚧 частично]

Два разумных варианта для v0.1:

- **A. Байткод + интерпретатор**  
  Компилятор генерирует бинарный или текстовый байткод; рантайм (`osnova-runtime`) его интерпретирует. Быстрее довести до «работает», проще отладка и портируемость.
- **B. Транспиляция в C или Rust**  
  Компилятор генерирует исходники C/Rust, дальше — системный компилятор. Плюс: нативная скорость, минимум своей рантайм-логики; минус: сложнее отлаживать и держать семантику 1:1.

Рекомендация для первого рабочего цикла: **вариант A (байткод)**. Ниже описан минимальный формат байткода; вариант B можно описать отдельным разделом или в v0.2.

---

## 3. Байткод v0.1 (вариант A) [✅ реализовано в v1 формата байткода]

### 3.1. Назначение

- Промежуточное представление для одного модуля.
- Линейная последовательность инструкций; явные операнды (регистры/слоты стека или индексы в таблице констант/локальных).
- Достаточно для: арифметики, сравнений, вызовов, доступа к полям, ветвлений и циклов, работы с `Результат`/Option (как структуры).

### 3.2. Структура модуля в байткоде

- **Заголовок:** версия формата, имя модуля, размер константного пула и т.д.
- **Константный пул:** литералы (числа, строки), имена полей, сигнатуры (индексы для вызовов).
- **Таблица функций/процедур:** для каждой — смещение в коде, число аргументов, число локальных, тип возврата (или «нет»).
- **Код:** массив инструкций.

### 3.3. Инструкции (минимальный набор)

Условные мнемоники (реальный формат — бинарный или текстовый по вкусу):

| Мнемоника | Назначение |
|-----------|------------|
| `const i32 k` | Загрузить целое из константного пула (индекс `k`) в стек. |
| `const f64 k` | Загрузить вещественное из пула. |
| `const str k` | Загрузить строку из пула. |
| `const.true` / `const.false` | Логические константы. |
| `const.null` | Пусто (для Option). |
| `local.get i` | Загрузить локальную переменную `i` в стек. |
| `local.set i` | Сохранить верх стека в локальную `i`. |
| `global.get i` | Загрузить глобальную/статическую переменную (если появятся). |
| `global.set i` | Сохранить в глобальную. |
| `field.get ti fi` | Со стеком: объект. Загрузить поле с индексом `fi` типа `ti`. Результат на стек. |
| `field.set ti fi` | Со стеком: значение, затем объект. Записать в поле. |
| `add` / `sub` / `mul` / `div` / `rem` | Арифметика: два операнда со стека, результат на стек. |
| `eq` / `ne` / `lt` / `le` / `gt` / `ge` | Сравнения. |
| `call fi` | Вызов функции по индексу `fi`; аргументы на стеке, возврат на стек (если не `Ничто`). |
| `invoke name` | Вызов по имени: внешние и **системные модули** (`система.окно`, `система.файлы` и т.д.). Обязателен для резолва системного API; см. п. 3.5. |
| `jmp off` | Безусловный переход на смещение. |
| `jmp_if off` | Условный переход: снять с стека булево, если истина — перейти. |
| `jmp_if_not off` | То же, но переход при ложь. |
| `ret` | Выход из функции; значение возврата (если есть) на вершине стека. |
| `result.unwrap` | Со стека: значение Result/Option; развернуть (или паника/ошибка в расширенной версии). |
| `result.tag` | Со стека: значение; положить тег (Успех/Неудача) для сопоставления. |

Типы в байткоде можно кодировать номерами (0 = i8, 1 = i16, … 7 = Ничто, 8 = Option(T), 9 = Ref(T), 10 = пользовательский тип по индексу и т.д.).

### 3.4. VLIW-конструкции в v0.1 [📋 планируется]

Конструкции `параллельно`, `предвыбор`, `пакет`, `регион`, `цикл … разворачивать`, `небезопасно` парсер и типчекер обрабатывают как обычные узлы AST. В бэкенде v0.1 они **сводятся к последовательному коду**:

- **`параллельно { ... }`** — генерируется тот же код, что и для обычного блока; порядок операций сохраняется. Семантическая подсказка для будущего VLIW-бэкенда не меняет поведение.
- **`предвыбор`** — компилируется в цепочку условных переходов (аналог if/иначе_если/иначе).
- **`пакет { слотN: ... }`** — операторы в слотах выполняются в фиксированном порядке (слот0, слот1, …); генерируется последовательный код.
- **`регион имя { ... }`** — как обычный блок; имя может использоваться для отладочной информации или аннотаций.
- **`цикл (по x в C) разворачивать N { ... }`** — генерируется цикл с телом, повторённым N раз (ручное разворачивание), либо обычный цикл по коллекции; точная семантика — в грамматике.
- **`небезопасно { ... }`** — тело компилируется как обычно; маркер может использоваться для отключения части проверок или для будущих интринсиков.

Специальных инструкций байткода для этих конструкций в v0.1 нет; фабрика и компилятор согласованы: парсер их принимает, бэкенд их понижает (lowering).

### 3.5. Системные модули и внешние вызовы [✅ реализовано]

Вызовы вида `система.окно.создать_окно(...)` и т.п. разрешаются на этапе типчекера/компиляции:

- Идентификатор, начинающийся с `система.` (или из списка «внешних» модулей рантайма), не компилируется в обычный `call fi` по индексу модуля пользователя.
- Компилятор генерирует инструкцию **`invoke`** с полным именем вызова (например, `система.окно.создать_окно`). Рантайм при выполнении `invoke` смотрит в таблицу системных API и вызывает нативную реализацию (см. `launcher-runtime-manifest.md`).

Таким образом, механизм резолва системных модулей в v0.1 **обязателен**: без него приложения не смогут использовать окна, файлы, хранилище и т.д. Таблица системных имён и сигнатур задаётся рантаймом и должна совпадать с описанием в манифесте рантайма.

### 3.6. Файл .osvbc [✅ реализовано]

- Либо бинарный формат (заголовок + пулы + код), либо текст (например, S-выражения или по одной инструкции в строке) для отладки.
- В пакете приложения (`launcher-runtime-manifest.md`) в `code/` лежит один или несколько `.osvbc`; точка входа задаётся в манифесте (модуль + функция).

## 4. Рантайм и интерпретатор [✅ реализовано]

- **Интерпретатор** читает `.osvbc`, выполняет инструкции по одной: стек операндов, массив локальных, константный пул, диспетчер по коду операции.
- **Системные модули** (`система.окно`, `система.файлы` и т.д.) реализованы на стороне рантайма (хост): при `invoke` или специальном `call` в нативный код.
- Управление памятью в v0.1 можно упростить (без полноценного GC): подсчёт ссылок или «всё на стеке + копирование» для малых объектов.

Спецификация рантайма и API хоста — в `docs/osnova/launcher-runtime-manifest.md`.

## 5. Транспиляция в C/Rust (вариант B, кратко) [📋 планируется]

Если бэкенд — генерация кода:

- Каждая процедура/функция Основа → функция на целевом языке.
- Типы мапятся на нативные (`Целое32` → `int32_t` / `i32`, `Строка` → `char*` или обёртка, `Результат<T,E>` → структура с тегом и полями).
- Блоки, циклы, условия — в прямом соответствии.
- Акторы и каналы требуют рантайм-библиотеки на целевом языке или примитивов ОС (потоки, очереди).

Такой компилятор выдаёт исходники C/Rust; сборка в `.exe` выполняется отдельно. Для лаунчера тогда в пакет кладутся уже скомпилированные бинарники или исходники + скрипт сборки.

---

## 6. Интеграция с фабрикой [🚧 частично]

- Фабрика генерирует исходник на Основа (один или несколько файлов модулей).
- Вызов компилятора: `osnova compile main.osnova [--output main.osvbc]` или аналог.
- При успехе: артефакт (`.osvbc` или исходники C/Rust) кладётся в сборку пакета; при ошибках — логи компилятора возвращаются в фабрику для исправления/ретрая.
- Валидация пакета перед публикацией в магазин включает проверку: компиляция без ошибок, точка входа существует, манифест согласован с байткодом.

---

## 7. Порядок реализации (рекомендуемый) [📋 планируется]

1. Лексер + парсер по существующим спецификациям; тесты на разборе примеров из грамматики.
2. Минимальный типчекер: таблица символов, вывод типов для выражений и проверка присваиваний/вызовов.
3. Генератор байткода от аннотированного AST: только процедуры/функции, арифметика, локальные, вызовы, ветвления, простой `ret`.
4. Интерпретатор байткода (стековая машина) + тесты «собрать и выполнить».
5. Расширение: поля структур, `Успех`/`Неудача`, циклы, затем VLIW-конструкции как маркеры для будущего бэкенда.
6. Сборка пакета `.osvpk` из артефакта компилятора и манифеста; запуск через лаунчер/рантайм.

После этого компилятор Основа v0.1 закрывает цепочку: **спека → фабрика → Основа → компилятор → пакет → рантайм.**
