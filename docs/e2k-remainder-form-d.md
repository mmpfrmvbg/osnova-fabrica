# Остаток в форме `D`: почему `SMODX` берёт делимое как 64-битное

**Дата:** 2026-09-20
**Зачем:** рантайм остатка (`src/e2k/mathRuntime.ts`, форма `SMODX`, канал 5) верно считает
неотрицательные делимые (`7 % 3 = 1`, `8 % 3 = 2`, `9 % 3 = 0` — исполнено в модели), но на
отрицательных расходится с руководством МЦСТ §10.3.3: `(-7) % 3` даёт **0**, `(-8) % 3` — **2**,
тогда как «остаток имеет знак делимого» обещает −1 и −2 (замер `.tmp/math-probe.ts`,
оракул `src/e2k/e2kMathQemu.test.ts`).
**Чем измерено:** `.tmp/math-probe.ts` (восемь программ, коды выхода) и исходники порта QEMU-e2k
(`.tmp/e2k-sources/qemu-e2k/qemu/target/e2k/…`). Правка в этом коммите **не делалась**.

## 1. Что делает форма (порт, по строкам)

```
void e2k_translate_exec_SMODX(int ch, bool spec, DisasContext *dc, const E2KDecodedInstr *instr_decoded)
{                                                                       /* translate-al-c2.c:1424 */
    E2kSrcTemp64 temp_src1 = e2k_translate_get_src_val_dw(dc, ch, 1);   /* :1426 — ДЕЛИМОЕ: 64 бита */
    E2kSrcTemp32 temp_src2 = e2k_translate_get_src_val_sw(dc, ch, 2);   /* :1427 — ДЕЛИТЕЛЬ: 32 бита */
    ...
    /* Check for z2 > z1 */                                             /* :1440-1450 */
    ...
    tcg_gen_div_i64(temp_res, temp_src1.val, temp_src2_64);             /* :1476 */
    tcg_gen_mul_i64(temp_res, temp_res, temp_src2_64);                  /* :1477 */
    tcg_gen_sub_i64(temp_res, temp_src1.val, temp_res);                 /* :1478 — остаток */
    tcg_gen_extrl_i64_i32(temp_res_full.lo32, temp_res);                /* :1479 — в результат младшие 32 */
```

Два факта, которые отсюда следуют и подтверждаются таблицей опкодов
(`opcodes/e2k-opc.h:54`, `ARGS_DSS` — src1 «D», src2 и dst «S»):

1. **делимое читается как 64-битное** (`get_src_val_dw` берёт `e2k_greg_unpacked_t.lo` — 64 бита);
2. **делитель — 32-битный со знаком** (расширяется до 64 перед делением), **результат — младшие 32 бита**
   остатка; плюс проверка «ширина делителя больше ширины делимого» → исключение.

## 2. Почему на отрицательных расходится — причина, подтверждённая арифметикой

Наш код кладёт в регистр 32-битное значение (`movts 0`, `movts 7`, `subs` — вычитание 32-битное),
а форма читает **64 бита**: верхняя половина остаётся нулевой. Тогда «−7» для формы — это не −7, а
**4294967289** (`0x00000000FFFFFFF9`), то есть большое положительное число.

Проверка арифметикой (это не догадка: она предсказывает ИЗМЕРЕННЫЕ числа):

| выражение | что видит форма (64 бита, верх = 0) | остаток | измерено |
|---|---|---|---|
| `7 % 3` | 7 | 1 | **1** |
| `8 % 3` | 8 | 2 | **2** |
| `9 % 3` | 9 | 0 | **0** |
| `(−7) % 3` | 4294967289 | 4294967289 − 3·1431655763 = **0** | **0** |
| `(−8) % 3` | 4294967288 | 4294967288 − 3·1431655762 = **2** | **2** |

Совпадение по обоим отрицательным случаям означает: расхождение объясняется **не «знак теряется»,
а шириной**: форма делит 64-битное беззнаково-положительное значение, а руководство описывает
остаток 64-битного *знакового* делимого. Знак «теряется» не в делении, а в **отсутствии расширения
знака** при записи 32-битного значения в 64-битный операнд.

## 3. Что здесь НЕ проверено и что из этого следует

* **Не проверено**, как форма ведёт себя при настоящем 64-битном отрицательном делимом (нужен способ
  положить 64-битное значение со знаком — отдельный опыт).
* **Не проверено**, нужен ли для корпуса DSP знаковый остаток: IIR выражает целочисленное частное
  через `(a − a % b) / b` при **неотрицательных** `a` (`tests/dsp/kernels/iir.osnova`), и там путь
  верен — измерено (`iir` считается на VM, а остаток в модели даёт верные значения для `0 ≤ a`).
* **Кандидаты на решение** (ни один не выбран). Мнемоника расширения знака **найдена в таблице
  МЦСТ**: `{"sxt", 0xff, parse_alf_args, NULL, ALOPF1, NO_MAS, 0xc, …}` — `opcodes/e2k-opc.h:199`,
  то есть ALOPF1, код операции `0xc`, форма `ARGS_SSD`: источник — слово, источник — слово,
  приёмник — **двойное** слово. В нашем кодировщике она уже есть (`src/e2k/e2k-real.ts`: `sxt`,
  `0x0c`, `argFormats ["S","S","D"]`, все каналы, источник `opcodes/e2k-opc.h:199`).
  Семантика прочитана в порте (`qemu/target/e2k/tcg/translate-al-c2.c:1149-1210`): первый источник —
  **выбор ширины и знаковости**, второй — значение, приёмник — 64-битный результат; ветвь
  `(src1 & 0b100) == 0b000` после отсева 8- и 16-битных даёт `ext32s` — **расширение 32→64 со
  знаком**, то есть ровно то, чего не хватает делимому `SMODX`.
  Отсюда кандидат: `sxt` (режим 32-битного знакового расширения) → `%db[временный]` как делимое →
  `SMODX`. Это **не сделано и не проверено**: константа режима и порядок операндов `sxt` требуют
  отдельного замера ассемблером и прогона, а не вывода из чтения кода порта.
  Альтернатива дешевле: объявить `остаток` беззнаковым (32-битным) и записать это в описание
  функции — корпусу DSP этого достаточно, там делимые неотрицательны.
