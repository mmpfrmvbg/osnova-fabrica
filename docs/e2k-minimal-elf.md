# Минимальный ELF для e2k: `_start` без `exit(42)`

**Дата:** 2026-09-15 (ночь).
**Зачем:** у конвейера не было **ни одного** e2k-исполняемого файла, поэтому прогон в QEMU
(`docs/e2k-qemu-run.md`) упирался не только в хост, но и в отсутствие предмета запуска. Здесь
собран минимальный ELF64: заголовок, один сегмент `PT_LOAD`, `.text` из трёх инструкций и точка
входа `_start`. **Статус: ELF валиден по заголовку и разбирается инструментами МЦСТ, но
`exit(42)` им не выполняется** — два препятствия названы в §5, а не спрятаны.

**Правило то же, что и в `docs/e2k-syllables-real.md`:** у каждой величины — источник
`файл:строка`; байтовые примеры — **измеренные** (ассемблер МЦСТ, дизассемблер МЦСТ, `readelf`
из той же сборки binutils).

Код: `src/e2k/elfMinimal.ts`, оракул: `src/e2k/elfMinimal.test.ts`.

## 1. Заголовок ELF

| поле | значение | источник |
|---|---|---|
| `e_ident[EI_CLASS]` | 2 (`ELFCLASS64`) | загрузчик e2k ждёт `ELFCLASS64` и `EM_E2K` (`qemu/linux-user/e2k/target_elf.h:10-11`) |
| `e_ident[EI_DATA]` | 1 (`ELFDATA2LSB`) | порядок байтов e2k — младший вперёд (`qemu/target/e2k/syllab-format.h`, раскладка полей) |
| `e_type` | 2 (`ET_EXEC`) | статический исполняемый файл |
| `e_machine` | **175** (`EM_E2K`) | `qemu/include/elf.h:195` = `EM_MCST_ELBRUS` (`binutils-gdb/include/elf/common.h:295`) |
| `e_flags` | `0x13000000` | машина `bfd_mach_e2k_8c = 19` (`binutils-gdb/include/elf/e2k.h:114-115`) в старшем байте |
| `e_entry` | `0x100000` | **наше решение**: у linux-user загрузчика адрес свободный; `.text` начинается там же |
| `e_phoff` / `e_phnum` | `0x40` / 1 | один сегмент `PT_LOAD` |
| `e_shoff` / `e_shnum` / `e_shstrndx` | `0x1098` / 5 / 4 | null, `.text`, `.symtab`, `.strtab`, `.shstrtab` (сдвиг с `0x1088` — программа стала на 8 байт короче, §2) |
| `p_flags` | `R|X` (5) | код, не данные |
| `p_offset` / `p_vaddr` / `p_filesz` | `0x1000` / `0x100000` / `0x91` | образ одним сегментом (`.text` — `0x38`, §2) |

Источник чисел системных вызовов: `qemu/linux-user/e2k/syscall_nr.h:9` — `TARGET_NR_exit 1`
(`exit_group` — 300, там же `:293`). Поэтому номер вызова в коде — **1**, а не 60.

## 2. Код: `_start`, который делает `exit(42)` (56 байт)

**Перемерено 2026-09-24** вместе с короткой непосредственной формой: номер вызова `1` кодируется
короткой формой (8 байт), аргумент `42` — литералом LTS (16 байт), поэтому программа стала **56**
байт вместо 64 и адреса после первого `movts` сдвинулись на 8. Замер —
`.tmp/measure-minimal-elf-doc.ts` (тот же прогон, что в оракуле `src/e2k/elfMinimal.test.ts`).

| адрес | байты (измерено) | что это | форма |
|---|---|---|---|
| `0x100000` | `01 80 00 00 00 01 00 44` | `setbn rsz=4, rbs=0, rcur=0` — окно вращаемых `%r0`…`%r9` | CS1, `opc=4` (8 байт) |
| `0x100008` | `01 00 00 04 88 c1 c0 60` | `movts,0 1, %r8` — номер вызова в **оконный** `r0` вызываемого | ALF2 + короткая непосредственная (8 байт) |
| `0x100010` | `11 00 00 04 89 d4 c0 60 00 00 00 00 00 00 2a 00` | `movts,0 42, %r9` — аргумент | ALF1 + LTS (16 байт) |
| `0x100020` | `01 40 00 00 00 00 00 60` | `sdisp %ctpr1, 0` — подготовка `%ctpr1` с тегом `CTPSL` | CS0, `ctp_opc=2` (8 байт) |
| `0x100028` | `12 90 00 00 20 04 00 c0 04 00 00 50 00 00 00 00` | `call %ctpr1, wbs=4` — системный вызов | SS + CS1, `opc=5` (16 байт) |

Почему так, а не «просто `ct`»: `%ctpr` на входе нуль (тег `CTPEW`), а `ct` по такому ctpr —
исключение (`translate-ct.c:840-844`); системный вызов запускает только `CALL` с тегом `CTPSL`
(`translate-ct.c:1143-1145`), а тег `CTPSL` ставит только `sdisp` (`translate-ctp.c:174`); ABI
читает номер из оконного `r0` (`cpu_loop.c:164-170`), а `call` сдвигает окно на `wbs`
квадрослов — значит запись идёт в `%r8`/`%r9`, и окно должно быть расширено `setbn`
(`reg-index.h:30-52`).

`0xc1` — короткая непосредственная форма: поле `0xc0 | N`, значение лежит в самом поле
(`isShortImmediate`/`encodeShortImm`, `src/e2k/e2k-real.ts`); `0xd4` — ссылка на 16-битный литерал в
старшей половине последнего слова (`opcodes/e2k-dis.c:445-479`), `0x2a = 42` видно в байте 14;
`0x88`/`0x89` — поле регистра со старшим битом файла (`0x80 | N`), `0x60` — `ctp_opc=2` у `sdisp`.

## 3. Внешняя проверка: инструменты МЦСТ

Сборка binutils с `--target=e2k-linux` — `docs/e2k-external-validation.md` §4.1.

### 3.1. Дизассемблер разбирает ELF целиком

```
$ objdump -f e2k-minimal.elf
e2k-minimal.elf:     file format elf64-e2k
architecture: elbrus-8c:64, flags 0x00000112:
EXEC_P, HAS_SYMS, D_PAGED
start address 0x0000000000100000

$ objdump -d e2k-minimal.elf
0000000000100000 <_start>:
  100000:  setbn rbs = 0x0, rsz = 0x4, rcur = 0x0
  100008:  movts,0 0x1, %r8
  100010:  movts,0 _f16s 0x2a, %r9
  100020:  sdisp %ctpr1, 0x0
  100028:  ipd 3
           call %ctpr1, wbs = 0x4
```

**Перемерено 2026-09-24** (`.tmp/measure-minimal-elf-doc.ts`): первая `movts` печатается **без**
`_f16s` — `_f16s` внешний дизассемблер ставит только литеральной форме (§3.3), а номер вызова
кодируется короткой непосредственной формой. Адреса после неё сдвинулись на 8: `movts,0 42` —
`0x100010`, `sdisp` — `0x100020`, `call` — `0x100028`; `.text` — `0x38` = 56 байт.

Пять инструкций — ровно те, что задуманы; `_start` — из таблицы символов.

### 3.2. `readelf` видит таблицу секций и символ

```
$ readelf -S e2k-minimal.elf
There are 5 section headers, starting at offset 0x1088:
  [ 1] .text     PROGBITS  0000000000100000  00001000  00000028  AX
  [ 2] .symtab   SYMTAB    0000000000000000  00001028  00000030  link 3 info 1 entsize 0x18
  [ 3] .strtab   STRTAB    0000000000000000  00001058  00000008
  [ 4] .shstrtab STRTAB    0000000000000000  00001060  00000021

$ objdump -t e2k-minimal.elf
0000000000100000 g     F .text  0000000000000028 _start
```

**Измеренная особенность:** `objdump -h` для этой цели печатает **только** `.text`
(так же ведёт себя и прежний `e2k-samples.elf`), тогда как `readelf -S` видит все пять секций.
Это поведение BFD цели, а не дефект наших заголовков: `readelf` и таблица символов читают те же
поля.

### 3.3. Ассемблер: формы совпали побайтово, кроме одной измеренной разницы

**ИСПРАВЛЕНО 2026-09-24:** разница, о которой ниже, **устранена** — кодировщик теперь берёт для
значений **0…15** ту же короткую непосредственную форму `0xc0 | N`, и все пять текстов совпали с
`as` МЦСТ **побайтно** (замер `.tmp/measure-as-vs-ours.ts`; оракул — проверка «ассемблер МЦСТ: все
пять форм совпадают байтами» в `src/e2k/elfMinimal.test.ts`). Таблица ниже и абзац под ней оставлены
как запись замера 07.2026: в тот день форма действительно не была реализована.

| текст | ассемблер МЦСТ | наш кодировщик (07.2026) | вывод |
|---|---|---|---|
| `setbn rsz=4, rbs=0, rcur=0` | `01 80 00 00 00 01 00 44` | те же байты | **совпало** |
| `sdisp %ctpr1, 0` | `01 40 00 00 00 00 00 60` | те же байты | **совпало** |
| `movts,0 42, %r9` | `11 00 00 04 89 d4 c0 60 … 2a 00` | те же байты | **совпало** |
| `call %ctpr1, wbs=4` | `12 90 00 00 20 04 00 c0 04 00 00 50 …` | те же байты | **совпало** |
| `movts,0 1, %r8` | `01 00 00 04 88 c1 c0 60` (8 байт) | `11 00 00 04 88 d4 c0 60 … 01 00` (16 байт) | **разные формы** (сегодня — совпадают: `01 00 00 04 88 c1 c0 60`) |

Причина расхождения измерена: значение **0…15** ассемблер кладёт 4-битной **непосредственной**
формой (поле `0xc0 | N`, здесь `0xc1`), а наш кодировщик тогда всегда использовал **литерал LTS**
(`0xd4`). Поле регистра при этом одинаково (`0x88` = оконный `%r8`). Обе формы разбираются
дизассемблером МЦСТ (§3.1 — он печатает `_f16s 0x1` именно для литеральной), но по байтам и по длине
это разные записи. Тогда непосредственная форма в `e2k-real` реализована не была; **сегодня
реализована** (`isShortImmediate`/`encodeShortImm`, оракул `src/e2k/immShort.test.ts`).

## 4. Прогон в QEMU: без шима — `guest_base`, с шимом — **исполнение**

`qemu-e2k version 11.0.1` собран (`docs/e2k-qemu-build.md` §2.5). Запуск минимального ELF **без
шимa**:

```
$ qemu-e2k .tmp/e2k-minimal.elf
qemu-e2k: .tmp/e2k-minimal.elf: Unable to find a guest_base to satisfy all guest address
mapping requirements
  0000000000000000-000000003fffffff
(код возврата 0)
```

**Контрольные опыты** (нужны, чтобы утверждение «дело не в нашем ELF» было замером, а не
догадкой):

| опыт | результат |
|---|---|
| `qemu-e2k` на файле, который не ELF (`not-an-elf.bin`) | **другая** ошибка: `Error while loading …: Exec format error` — файл читается и проверяется |
| `qemu-e2k` на прежнем `e2k-samples.elf` (собран другой дорогой) | **та же** ошибка `guest_base` |
| `qemu-x86_64` той же сборки на своём бинарнике | код возврата 0 — user-mode QEMU в окружении работает |

**Что из этого следует:** до исполнения первой инструкции дело не доходит; `qemu-e2k` отвергает
**любой** e2k-образ в этом окружении (WSL1). Точная причина измерена отдельным зондом: в WSL1 нет
системного вызова, на котором стоит поиск гостевого резерва, — `MAP_FIXED_NOREPLACE`
(`linux-user/elfload.c:792`) отвечает `errno=95` (ENOTSUP), тогда как `MAP_FIXED` и обычный `mmap`
адрес выдают. Флаг добавлен в Linux 4.17, а WSL1 — слой трансляции, а не ядро; размер резерва
задаёт `TARGET_VIRT_ADDR_SPACE_BITS = 48` (`qemu/target/e2k/cpu-param.h:12`), но непреодолимым его
делает отсутствующий флаг. Подробности — `docs/e2k-qemu-run.md` §2.5.

### 4.1. Шим для `mmap`: преграда снята, и код ИСПОЛНЯЕТСЯ

Преграда не в e2k, а в хосте, поэтому лечится на хосте: небольшая библиотека подменяет `mmap` так,
что флаг `MAP_FIXED_NOREPLACE` получает смысл, которого QEMU и ждёт — адрес запрашивается
**подсказкой** (без `MAP_FIXED`, ничего не затирается), а потом сверяется с запрошенным; не совпал —
страница освобождается, возвращается `MAP_FAILED` с `errno = EEXIST` (ровно как поступило бы ядро).
Исходник — `src/scripts/e2kQemuExec.ts`, он же приведён в `docs/e2k-qemu-run.md` §2.8;
запуск: `LD_PRELOAD=<шим> qemu-e2k <elf>`.

На **первом** варианте ELF (три инструкции: `movts` в `%b[0]`, `movts` в `%b[1]`, `ct %ctpr1`) это
дало первую остановку:

```
$ LD_PRELOAD=/tmp/e2k-noreplace.so qemu-e2k .tmp/e2k-minimal.elf
qemu-e2k: qemu: exception at IP = 0x100020
qemu-e2k: qemu: exception handling is unimplemented - aborting
```

**Что здесь важно:** до шима прогон не доходил до исполнения вовсе. Теперь видно, что эмулятор
**исполнил** обе инструкции `movts` (адреса `0x100000` и `0x100010`, каждая 16 байт) и остановился на
третьей — `ct %ctpr1` по адресу `0x100020`. Этот вариант ELF **заменён** рабочим (§7), но именно он
показал, чего не хватает.

### 4.2. Почему остановка именно на `ct`: названо источником

| звено | источник |
|---|---|
| `%ctpr` на входе равен нулю | `E2K_SREG_INIT_CTPR = 0` — `qemu/target/e2k/cpu-sregs.h:149` (`DEF_E2K_SREG(CTPR, uint64_t, 0, …)`) |
| нулевой тег — это `CTPEW` («ctpr пуст») | `E2K_CTPR_TAG_CTPEW = 0` — `qemu/target/e2k/cpu-sregs.h:165-173` |
| `ct` по ctpr с тегом `CTPEW` — исключение | `helper_e2k_prep_ct_CT`: ветка `else` → `ctpr_tag == CTPEW` → `e2k_cpu_set_have_execption` — `qemu/target/e2k/tcg/translate-ct.c:840-844` |
| исключение убивает гостя | `EXCP_EXCEPTION` → `force_sig_fault(TARGET_SIGKILL, …)` — `qemu/linux-user/e2k/cpu_loop.c:221-232` |

Иначе говоря: **`ct %ctprN` требует подготовленного ctpr**, а в нашем ELF его никто не готовил.
Подготовка — это `disp %ctprN, <смещение>` (CS0), которая записывает в ctpr цель и тег `CTPLL`
(`qemu/target/e2k/tcg/translate-ctp.c:74-84`, цель = `ip + (disp << 3)`, то есть смещение в
8-байтных словах).

### 4.3. Наши байты проверены **исполнением**: опыт с передачей управления

Опыт (`src/e2k/e2kQemuExec.test.ts`) ставит четыре команды по 8 байт:

| № | адрес | команда | роль |
|---|---|---|---|
| 0 | `0x100000` | `disp %ctpr1, k` | подготовка перехода |
| 1 | `0x100008` | `ct %ctpr1` | переход |
| 2 | `0x100010` | `ct %ctpr3` | ловушка A (ctpr не подготовлен) |
| 3 | `0x100018` | `ct %ctpr2` | ловушка B (ctpr не подготовлен) |

| смещение `k` | ожидаемая цель | измеренный адрес остановки |
|---|---|---|
| 3 | `ip + 24` = `0x100018` (ловушка B) | **`0x100018`** |
| 2 | `ip + 16` = `0x100010` (ловушка A) | **`0x100010`** |

Пара прогонов и есть доказательство: при `k = 3` управление **перепрыгнуло** ловушку A, при `k = 2`
— нет. Один прогон доказывал бы только, что эмулятор где-то остановился.

**Что это доказывает:** наши кодировки CS0 (`disp`) и SS (`ct`) исполняются QEMU по смыслу —
адрес перехода вычисляется из смещения в байтах, а не «примерно так». Это проверка **сильнее**
дизассемблера: там байты читаются, здесь они исполняются.

**Чего это не доказывает:** что весь кодировщик верен (проверены формы `movts`, `disp`, `ct`), что
программа завершится `exit(42)` (§5) и что так поведёт себя железо (QEMU — модель).

**Отдельно измерено:** при отказе загрузки `qemu-e2k` завершается **кодом 0** и пишет причину в
stderr. Из этого следует практическое: проверять прогон по коду возврата **нельзя** — отказ
загрузки выглядел бы как успех.

## 5. Как достигнут `exit(42)`: три правки кодировщика и два послабления хоста

Первые препятствия измерены прогоном (§4.1): программа останавливалась на первом же, до остальных
дело не доходило.

| # | что мешало | чем снято |
|---|---|---|
| 1 | **`ct %ctpr1` по неподготовленному ctpr — исключение**: `%ctpr` на входе нуль, ноль — тег `CTPEW` (`cpu-sregs.h:149`, `:165-173`; `translate-ct.c:840-844`) | перед передачей управления ставится `disp`/`sdisp` (CS0), которая записывает в ctpr цель и тег |
| 2 | **Системный вызов запускает только `CALL` с тегом `CTPSL`**, а `CTPSL` ставит **только `sdisp`** (`translate-ctp.c:174`; `disp` всегда пишет `CTPLL` — `:81`) | в кодировщик добавлена форма **`sdisp`** (CS0, `ctp_opc=2`) |
| 3 | **ABI читает номер вызова из оконного `r0`** (`cpu_loop.c:164-170`), а `Operand` умел только базовый файл (`%b[N]` = `rf.global[0]`, а нужен `rf.window[0]` — `reg-index.h:79` против `:117`) | в `Operand` добавлен **файл регистров** (`file: "base" | "window"`, поле `0x80|N`) |
| 4 | **`call` сдвигает окно на `wbs`**, поэтому писать номер надо в **окно вызываемого** — `%r8` при `wbs=4`; а окно вращаемых регистров при входе нулевое (`BR = 0` → доступны два регистра, `reg-index.h:30-52`) | в кодировщик добавлена форма **`setbn`** (CS1, `opc=4`), расширяющая окно: `rsz=4` → доступны `%r0`…`%r9` |
| 5 | **Хост: `MAP_FIXED_NOREPLACE`** — WSL1 отвечает `errno=95`, QEMU не размещает гостя вовсе (`elfload.c:792`) | шим `LD_PRELOAD` (не правка эмулятора: только способ спросить у хоста свободный диапазон) |
| 6 | **Хост: порт QEMU не пишет поля `WD.size_d/base_d`**, только читает их (`reg-index.h:64-79`, `translate-ct.c:71-73`), а сам строит `WD` из `_q`-полей — системный вызов умирал с «syscall without proper WD configuration» (`cpu_loop.c:164-169`) | локальная правка порта: там, где пишутся `_q`-поля, пишутся и `_d = 2 * _q` (`MAXNR_D = MAXNR_Q * 2`, `cpu.h:58`). Текст — `docs/e2k-qemu-run.md` §2.9 |

**Что изменилось против прежней записи:** пункт 2 раньше стоял как «как записать эту подготовку —
**НЕТ В ИСТОЧНИКЕ**». Это оказалось неверно: в источнике **есть** — `SDISP`
(`translate-ctp.c:142-184`). Не хватало реализации `sdisp` в кодировщике, а не сведений. Мнемоник
«поставить тег» действительно нет: тег не мнемоника, а поле, которое пишет `sdisp`.

Что измерено ассемблером МЦСТ (`-mcpu=elbrus-v5`) — почему поиск «по мнемонике» ничего не дал:

| текст | ответ ассемблера |
|---|---|
| `syscall` | `Error: unknown instruction 'syscall'` |
| `ctpsl` | `Error: unknown instruction 'ctpsl'` |
| `ipush %ctpr1` | `Error: unknown instruction 'ipush'` |
| `ct %ctpr1, syscall` | `Error: end of line expected` |
| `ct %ctpr1` | собрано (тег `CTPSL` в выводе `objdump` отсутствует) |

Чего эти правки **не** доказывают: что так поведёт себя железо (QEMU — модель) и что правка порта
не нужна на настоящем ядре: `_d`-поля там заполняет ядро, а в linux-user их место — инициализация
загрузчика.

---

## 6. Что проверено, а что нет

| утверждение | статус |
|---|---|
| ELF валиден по заголовку (`e_machine`, класс, данные, машина) | **ФАКТ**: `objdump -f` → `elf64-e2k`, `elbrus-8c:64`, `start address 0x100000` |
| таблица секций и символов читается чужим инструментом | **ФАКТ**: `readelf -S` — 5 секций, `objdump -t` — `_start` |
| инструкции в `.text` — извлечённые формы, а не выдумка | **ФАКТ**: `setbn`, `sdisp`, `movts` 42 и `call` совпали с ассемблером; пятая — измеренная разница форм (§3.3) |
| дизассемблер МЦСТ читает этот ELF как программу | **ФАКТ**: §3.1 |
| **`exit(42)` выполняется** | **ФАКТ с шимом и правкой порта**: код возврата **42** (§7); без них — названные причины (§4–§5) |
| прогон в QEMU состоялся | **ФАКТ с шимом** (§7). Без шима — `guest_base` (§4) |

## 7. Прогон: **код возврата 42**

```
$ LD_PRELOAD=<шим> qemu-e2k .tmp/e2k-minimal.elf ; echo $?
42
```

Программа — пять инструкций из §2 (56 байт), каждая собрана **нашим** кодировщиком; прогон
повторяется оракулом `src/e2k/e2kQemuExec.test.ts` (проверка «exit(42): минимальный ELF даёт код
возврата 42»).

| что именно проверено | чем |
|---|---|
| байты пяти инструкций совпали с ассемблером МЦСТ (кроме измеренной разницы форм) | §3.3, `e2kSyllables.test.ts` |
| дизассемблер МЦСТ читает их как те же инструкции | §3.1, `elfMinimal.test.ts` |
| эмулятор их **исполняет**, и системный вызов доходит до `do_syscall` | `qemu-e2k -strace`: видно вызов; до правки порта — `151 restart_syscall` (номер читался не оттуда), после — `exit(42)` |
| передача управления исполняется по смыслу | §4.3 (опыт `disp` + `ct` с положительным и отрицательным контролем) |
| **гость завершается кодом 42** | код возврата `qemu-e2k` = `42` |

**Чего это не доказывает:** что то же произойдёт на **железе** (QEMU — модель) и что правки хоста
не нужны на настоящем ядре: там `WD._d` заполняет ядро, а `MAP_FIXED_NOREPLACE` есть с Linux 4.17.
Проверено ровно одно: **наши байты в этой модели делают то, что задумано**.
