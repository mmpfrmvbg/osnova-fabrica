# Упаковка инструкций в VLIW-пакеты: `packInstructions`

**Дата измерения:** 2026-09-15
**Метрика:** плотность упаковки = инструкций на элемент кода (статика, не скорость)
**Команды:** `npm run gate:pack`, `npm run gate:pack:negative`

---

## 0. ЧТО ИЗМЕРЯЕТСЯ — читать до чисел

**Плотность упаковки** — сколько инструкций приходится на один элемент кода:

```
плотность = инструкций / элементов кода
```

До упаковки она всегда `1.00`: одна инструкция — один элемент. После упаковки
она показывает, сколько инструкций удалось собрать в широкие команды.

Это **не ускорение**. Число ИСПОЛНЕННЫХ инструкций упаковка не меняет: VM
исполняет слоты пакета последовательно, те же самые инструкции в том же порядке.

Меняются две другие величины, и их надо различать:

| величина | что это | `while.osnova` | `ilp-high.osnova` |
|---|---|---|---|
| элементов кода | сколько широких команд в коде | 79 → 60 | 117 → 72 |
| плотность упаковки | инструкций на элемент | 1.00 → 1.32 | 1.00 → 1.63 |
| инструкций исполнено | те же инструкции, что и до упаковки | 249 → 249 | 3986 → 3986 |
| **шагов VM** | сколько раз VM сменила элемент кода | 249 → **183** | 3986 → **2193** |

Шаги VM падают потому, что **эта VM считает шагом элемент кода, а пакет — один
элемент**. Это свойство счётчика VM, а не измерение скорости: на настоящем e2k
один пакет — это один широкий выпуск, но сколько он занимает тактов, зависит от
длин операций, конфликтов каналов и кэша (`Ld L1/L2/L3/mem` = `3/11/40/~100`,
стр. 71–72). Ни одного прогона на железе или на симуляторе e2k не было, поэтому
«шагов VM стало на 40% меньше» **не означает** «программа быстрее на 40%».

По 18 завершающимся программам: инструкций исполнено `13709` (не меняется),
шагов VM `13709 → 8273`.

Что упаковка даёт точно: **код занимает меньше элементов**. Что она не даёт сама
по себе: ни одного такта.

## 1. Что обязан соблюдать упаковщик

`packInstructions(module, model)` собирает **соседние** инструкции и **не меняет
их порядок**. Перестановка — отдельный инструмент (`reorderScheduler.ts`):
смешивать две операции в одной нельзя, иначе при расхождении непонятно, что
именно его вызвало.

Правила делятся на две группы, и это деление существенно.

### Группа A: аппаратная легальность (проверяет `verifyPackets`)

| правило | почему |
|---|---|
| RAW внутри пакета | значение видно со следующего пакета |
| WAR внутри пакета | запись затирает ещё не прочитанное |
| WAW внутри пакета | два писателя — победитель не определён |
| пакет не шире машины | 24 канала e2k (стр. 54–56) |
| операция помещается в свой канал | деление и корень — только АЛУ5, запись — АЛУ2/АЛУ5 (стр. 56) |

Эти правила **прогон не видит**: VM исполняет слоты последовательно, поэтому
нарушение RAW не меняет результат в VM. Их ловит только верификатор — и это
доказано негативным контролем (§4): при снятой проверке регистров gate краснеет,
а расхождений прогонов **ноль**.

### Группа B: семантика пакета в VM (проверяет прогон)

| правило | почему |
|---|---|
| передача управления закрывает пакет | VM покидает пакет на `call`/`jmp*`/`ret`/`throw`, остальные слоты не исполнятся |
| цель перехода и начало процедуры открывают пакет | VM входит в пакет с нулевого слота и исполнит слоты, стоящие до цели |

Эти правила **верификатор увидеть не может**: в упакованном модуле `off` — индекс
элемента, и информация «какая инструкция была целью» теряется. Наоборот: при
снятой границе на цели перехода верификатор зелёный (0 красных), а прогоны
расходятся на 5 программах из 19.

Отсюда вывод, который дороже самих чисел: **ни один из двух контролей не является
лишним, и ни один не покрывает другой.**

## 2. Почему первая упаковка ломала эквивалентность (причина найдена)

Прежняя попытка (`packByIssueTime`, группировка по `issueAt`) давала
`while.osnova` = `49` вместо `1049`. Причина **не** RAW, как предполагалось, а
`call`:

- `case "call"` в `src/runtime/vm/reginterpreter.ts` возвращает `callee.codeOffset`;
- `executeElement` покидает пакет при `next !== packetPc + 1`;
- пакет `t=5` содержал `63(call)` в слоте 0 и `68(move d=6 a=0)` в слоте 1 —
  `move` не исполнился ни сразу, ни после возврата (`returnPc = packetPc + 1`
  перепрыгивает остаток пакета).

Измерено: потеряна ровно одна инструкция, шагов `249 → 248`, результат
`1049 → 49`. Полный разбор — `docs/vliw-pack-diagnosis.md`.

Верификатор первой версии этого не видел: в наборе передающих управление не было
`call`. Дефект нашла диагностика, а не тесты; теперь `call` в наборе, и тесты
случаев 8–9 падали до правки реализации.

## 4. Негативный контроль (`npm run gate:pack:negative`)

Дефект вносится в **настоящий** `packInstructions` через `PackDefects` (копия
алгоритма не годится: она стареет вместе с кодом). Флаги запрещены в рабочем пути
— за этим следит `packetPacker.audit.test.ts`.

| снятое правило | gate | поймал верификатор | поймал прогон |
|---|---|---|---|
| регистры (RAW/WAR/WAW) | КРАСНЫЙ | 19 программ | **0 программ** |
| передача управления закрывает пакет | КРАСНЫЙ | 13 программ | 5 программ |
| совместимость со слотами | КРАСНЫЙ | 9 программ | **0 программ** |
| цель перехода открывает пакет | КРАСНЫЙ | **0 программ** | 5 программ |

Первые причины красного (из отчёта скрипта):

- регистры: `hello.osnova` — `RAW: слот 1 («ret») читает регистр 0, записанный в этом же пакете`;
- передача управления: `task_stats.osnova` — `BRANCH: передача управления «jmp_if_not» в слоте 0 не последняя`;
- слоты: `task_stats.osnova` — `операция «ret» (слот 2) не помещается: машина допускает слоты [6]`;
- цель перехода: `cycle-array.osnova` — `эквивалентность: расхождение на шаге 34`.

Поймано 4 из 4. Базовая линия (без дефектов) — зелёная: красное вызвано именно
дефектом, а не самим gate'ом.

## 5. Что не сделано

1. **Замеров на железе нет.** Плотность упаковки — статика. Ни одного прогона на
   e2k не было, и «стало быстрее» из этих чисел не следует.
2. **Упаковка не подключена к рабочему пути.** `packInstructions` вызывают только
   инструмент измерений и тесты (`packetPacker.audit.test.ts` это фиксирует).
   Компилятор по-прежнему выдаёт линейный код.
3. **Перестановка и упаковка не объединены.** Планировщик переставляет, упаковщик
   пакует по порядку; вместе они не запускаются. Объединение — отдельная работа с
   отдельным оракулом.
4. **Задержки внутри пакета не проверяются.** Модель длительностей (стр. 71–72)
   описывает время готовности результата, но упаковщик ставит рядом инструкции,
   исходя из независимости регистров, без учёта времени. Для настоящего e2k рядом
   должны стоять операции, чьи операнды готовы к одному такту.
