## Исправления к первоначальному плану

Первоначальная редакция опиралась на верные посылки (проверено по коду), но
содержала четыре дефекта в самих критериях приёмки.

1. **Gate «три последовательных прогона `npx vitest run` дают одно и то же число
   падений» — фиктивен.** В конфиге `sequence.shuffle: false`, порядок файлов
   детерминирован, поэтому три прогона совпадали **и на сломанном дереве**
   (замер: 0 падений в default против 16 при `--sequence.shuffle --sequence.seed=42`).
   Правильный gate — не «три раза одно и то же», а «зелено и в default, и в
   перемешанном порядке»: `npm run gate:determinism`.
2. **`ok` при падении обеих VM.** Критерий «паритет на 8 фикстурах» был
   невыполним по существу: три из восьми — оконные приложения с бесконечным
   `цикл`, они не завершаются, и «совпадение» двух падений засчитывалось как
   успех. Теперь статус `both_hit_step_limit` отделён от `ok`.
3. **Bootstrap-хеш указывал на несуществующий файл.** `stage16.osvbc.json` нет:
   stage16 проверяется из исходника, а не через артефакт. Кроме того, 22 из 24
   артефактов были устаревшими. Правильный оракул — **детерминизм пересборки**:
   две сборки одного исходника дают одинаковый sha256, а артефакт на диске равен
   свежей сборке (`src/self-host/bootstrap-hash.test.ts`).
4. **`round-trip` как gate Фазы 3 доказывает самосогласованность, а не понимание
   e2k.** Ассемблер и дизассемблер, написанные из одной (возможно, ошибочной)
   спецификации, дадут 100 % round-trip на любой фикции. Это тот же класс ошибки,
   что «обе VM упали → OK». Нужен внешний эталон.

Кроме того: под B фаз **восемь** (0–7); валидация на железе — **Фаза 6**, и при
отсутствии доступа (ответ владельца 2026-09-15: ни железа, ни симулятора) её
критерий не может быть выполнен, поэтому критерии Фаз 3–4 переформулированы в
терминах внешнего эталона, а не собственного симулятора.

## Что меняет решение B

### Формулировка (уточнена владельцем)

**Целевой класс — B: специализированные задачи с высоким ILP. Цель — разноплановый
софт, который работает на e2k, с выигрышем там, где он возможен. Кратное ускорение
везде не является целью.**

B — это **не** «сделать всё быстрым». Это:

- строить **разноплановый** софт, который идёт на e2k;
- стремиться к выигрышу там, где он возможен (высокий ILP);
- признавать, что программы с низким ILP не ускорятся — **это свойство задачи, а не
  дефект**.

**Следствие для подмножества e2k:** оно должно быть достаточно **широким**, чтобы
поддерживать разноплановый софт, а не одну нишу. Иначе инфраструктура будет
построена под ML-инференс (или DSP, или обработку сигналов), а остальной софт
останется без эмиттера. Требования — `docs/e2k-subset-requirements.md`.

### Что откладывается (и почему это не потеря)

| Работа | Почему откладывается при B |
|---|---|
| Подключение конвейера к CLI под флагом `OSNOVA_VLIW_PACKETS` | На критическом пути только при A. При B важнее довести код до железа, а не до CLI. |
| Учёт задержек внутри пакета при упаковке | Оптимизация того, что ещё не подключено ни к симулятору, ни к железу. Сначала — измерение тактов, потом оптимизация под них. |

Обе работы **не отменяются**: они вернутся, когда появится симулятор и на нём
будет что оптимизировать.

### Фазы под B

| фаза | что делается | оракул / gate |
|---|---|---|
| **Фаза 3** | спецификация подмножества e2k, **достаточно широкая для разнопланового софта** | спецификация + внешний эталон (round-trip сам по себе не gate) |
| **Фаза 4** | **эмиттер e2k**: `RegModule` → машинный код подмножества | трассы эмиттер+симулятор совпадают с регистровой VM; плюс нефункциональный порог (заполненность пакетов / такты) |
| **Фаза 5** | **симулятор e2k**: исполняет машинный код, считает такты по модели | тестовые программы, сверенные с независимым эталоном; каждое предположение — в `docs/hardware-debt.md` |
| **Фаза 6** | **валидация на железе** | вывод реального e2k совпадает с симулятором на значимом наборе |
| **Фаза 7** | **корпус разноплановых программ** | N программ проходят цепочку стековая VM → регистровая VM → эмиттер → симулятор → (если есть) железо |

**Порядок подготовки внутри Фазы 3:** (1) выбрать задачу внутри B → (2) требования к
подмножеству под неё (плюс широкое ядро для разнопланового софта) → (3)
спецификация → дальше по фазам.

**Про доступ к железу (ответ владельца 2026-09-15): ни железа, ни симулятора e2k
нет.** Поэтому Фаза 6 не может закрыться, а критерии Фаз 3–4 **обязаны** быть
сформулированы в терминах внешнего эталона (опубликованные примеры кодировки,
независимый дизассемблер, опубликованные результаты) — иначе они доказывают только
самосогласованность. Список долга: `docs/hardware-debt.md`.

### Чего при B не делаем

- Не выбираем конкретную задачу внутри B: это решение владельца, оно будет принято
  после этого этапа.
- Не начинаем эмиттер: это Фаза 4.
- Не трогаем планировщик, упаковку и перестановку: всё сделанное зафиксировано
  (`src/vliw/vliwPipeline.ts`, gate `npm run gate:pack`).

### Требования к подмножеству ISA (описание, не спецификация)

Специфицировать подмножество сейчас нельзя: неизвестна задача. Но требования можно
описать — они различаются по кандидатам, и это и есть содержание решения.

| кандидат | что должно быть в подмножестве | чего достаточно для первого замера |
|---|---|---|
| **ML-инференс** | FMA; при свёртках — векторные операции и/или операции над упакованными данными; быстрая загрузка весов; длинные цепочки независимых умножений-сложений | скалярный FMA-цикл с развёрткой: ILP есть, вектор не обязателен |
| **DSP** | операции с насыщением, сдвиги, умножение с накоплением, работа с фиксированной точкой; предсказуемая задержка | MAC-цикл с накоплением + сдвиги |
| **обработка сигналов** | то же, что DSP, плюс возможно плавающая точка и табличные операции (БПФ) | БПФ-бабочка: короткие независимые цепочки, много обменов |

Общее для всех трёх (и то, что можно специфицировать **не ожидая** выбора):
целочисленная арифметика, сравнения, переходы, load/store, вызовы, упаковка в
широкие команды. Различие — в «тяжёлых» операциях, и именно они определяют
выигрыш.

**Порядок работы:** (1) выбрать задачу внутри B → (2) требования к подмножеству под
неё → (3) спецификация → (4) эмиттер → (5) симулятор → (6) замер.

### Долг перед железом

Всё, что нельзя проверить без реального Эльбруса, ведётся отдельно:
`docs/hardware-debt.md`. При B этот список — не формальность: замер тактов на
симуляторе без подтверждения на железе остаётся модельным числом, и так его и надо
называть.

## Фаза 2. Перестановка и латентности (в первоначальном плане не хватало первого)

**Почему порядок изменён.** Латентности влияют на решения только тогда, когда
планировщик **выбирает порядок**. Сейчас `src/vliw/regScheduler.ts` упаковывает
инструкции в порядке программы внутри линейного участка: граф зависимостей
(`regGraph.ts`) используется лишь как проверка «поместится ли инструкция в
текущий пакет». Пункт «планировщик использует латентности» на таком планировщике
выполнить нечем.

**Оракул:** верификатор расписания `verify_schedule(bundles, machine_model)`,
который отвергает расписание, если результат читается раньше латентности
операции. Создаётся **до** того, как планировщик начнёт использовать латентности.

| # | Работа | Gate |
|---|---|---|
| 1 | Реализовать list scheduling по готовности (перестановка), а не упаковку in-order | верификатор принимает расписание; `regOracle` зелёный |
| 2 | Подключить планировщик к компилятору и CLI `osnova schedule` (сейчас CLI работает со стековым) | планировщик достижим из CLI на регистровом коде |
| 3 | Модель латентностей в `e2kModel.ts`: ALU / MEM / MUL / BRANCH | таблица помечена `exact` / `estimated` / `unknown` |
| 4 | Планировщик использует латентности | ILP > 1 на реальном коде (`foreach.osnova`), а не на синтетике |

**Gate фазы:** верификатор отвергает расписания, нарушающие латентности;
`regOracle.test.ts` исполняется и подтверждает ILP > 1 на реальном коде;
`npm run gate:determinism` остаётся зелёным.

**Риск:** если латентности не соответствуют реальному e2k, планировщик будет
принимать неверные решения. На этой фазе вы всё ещё в симуляции — ошибки модели
не видны, но закладываются.

## Фаза 3. Спецификация подмножества e2k — достаточно широкая для разнопланового софта

**СОСТОЯНИЕ: НЕ НАЧАТА СОЗНАТЕЛЬНО.** Решение владельца — B, но конкретная задача
внутри B не выбрана; специфицировать «подмножество вообще» означало бы
специфицировать не то (требования трёх кандидатов различны — см. «Что меняет
решение B»). До выбора задачи: описываются требования, спецификация не пишется.

**Что уже есть:** требования к подмножеству — `docs/e2k-subset-requirements.md`:
универсальное ядро (2.1), расширение для разнопланового софта (2.2), расширение для
задач с высоким ILP по кандидатам (2.3), чего не будет (2.4), источники (2.5).

**Под B подмножество должно быть ШИРОКИМ**, а не «под одну нишу»: иначе
инфраструктура окажется построена под ML-инференс (или DSP, или обработку
сигналов), а остальной софт останется без эмиттера.

**Оракул:** спецификация + внешний эталон. Round-trip **не является** gate сам по
себе (см. «Исправления», п. 4). При отсутствии доступа к железу и симулятору
(ответ владельца 2026-09-15) внешним эталоном могут быть только опубликованные
примеры кодировки или независимый дизассемблер; если и их нет — доказательство
называется самосогласованным, и это записывается явно.

| # | Работа | Gate |
|---|---|---|
| 1 | Выбрать подмножество ISA: ядро 2.1 + расширения 2.2 и 2.3 под выбранную задачу | список опкодов, покрывающих большинство генерируемого кода **и** разноплановый корпус |
| 2 | Машинно-читаемая спецификация: кодировка, операнды, семантика, латентности | — |
| 3 | Ассемблер и дизассемблер | round-trip на 1000 инструкциях **и** совпадение с внешним дизассемблером e2k (или опубликованными примерами кодировки) на выборке |
| 4 | Правила легальности пакетов для подмножества | верификатор пакетов (`src/vliw/packetVerifier.ts`) принимает сгенерированный код |

**Риск:** спецификация e2k не полностью публична. Если внешнего эталона нет —
это надо признать явно и записать, что доказательство остаётся
самосогласованным; иначе фаза создаёт ложную уверенность.

## Фаза 4. Эмиттер e2k: RegIR → машинный код подмножества

**Оракул:** симулятор e2k против регистровой VM — по трассам.

| # | Работа | Gate |
|---|---|---|
| 1 | `RegModule` → машинный код подмножества | — |
| 2 | Аллокация реальных регистров e2k | все виртуальные регистры отображены, spill-корректность на симуляторе |
| 3 | Латентностно-осознанное расписание | верификатор расписания принимает |
| 4 | Прогон одной программы на регистровой VM и на симуляторе e2k | трассы совпадают |

**Минимальный эмиттер ≠ эмиттер для B.** Универсального набора из ~20 инструкций
(add, sub, mul, jmp, call, ret, load, store) достаточно, чтобы доказать, что
эмиттер собирает, а симулятор исполняет. Для B этого мало: выигрыш по тактам даёт
**специализация** — операции, на которых выбранная задача тратит время (2.3).
Собирать специализированный эмиттер до выбора задачи нельзя.

**Второй, нефункциональный gate (обязателен).** Корректность здесь достижима и
при провальном по цели результате: Itanium сломался не на корректности, а на
качестве кода. Поэтому к «трассы совпадают» добавляется измеримый порог
(заполненность пакетов / число тактов на реальном корпусе), иначе фаза может
быть «зелёной» при мёртвом результате.

**Риск:** аллокация регистров + планирование + латентности должны решаться
согласованно. Решать их строго последовательно — получить корректный, но
медленный код; решать одновременно — экспоненциальная сложность.

## Фаза 5. Симулятор e2k

**Оракул:** симулятор против независимого эталона; сам с собой он ничего не
доказывает.

## Фаза 6. Валидация на реальном железе

**Оракул:** вывод на реальном e2k против симулятора.

**Состояние:** доступа к железу **нет** (ответ владельца 2026-09-15). Поэтому фаза
не может быть закрыта, и это надо помнить до старта Фазы 3: критерии Фаз 3–4
опираются на внешний эталон, а не на собственный симулятор. Узнать об этом через
полгода — дорого.

**Gate:** на значимом наборе программ вывод реального железа совпадает с
симулятором; замеры `dprof` подтверждают модель длительностей.

**Риск:** доступа может не быть. Это не приговор, но тогда критерии Фаз 3–4 надо
переформулировать в терминах внешнего эталона, а не собственного симулятора.

## Фаза 7. Корпус разноплановых программ

**Оракул:** корпус программ; каждое проходит цепочку стековая VM → регистровая VM →
эмиттер → e2k-симулятор → (если есть) реальное железо.

**Gate:** N **разноплановых** программ (не только задача с высоким ILP: массивы,
объекты, строки, циклы с зависимостями) проходят цепочку и провалидированы; N
растёт.

**Почему разноплановых, а не «побольше одной задачи»:** цель B — разноплановый
софт, который идёт на e2k. Корпус из одной ниши проверяет эмиттер ровно на нише и
не покажет, что остальной софт остался без поддержки.

**Два разных замера, не смешивать:**

| что | по какому корпусу | как называется результат |
|---|---|---|
| корректность | весь разноплановый корпус | «трассы совпадают», «программа проходит цепочку» |
| выигрыш | программы с высоким ILP | модельные такты (до Фазы 6) / такты `dprof` (после) |

**Риск:** масштаб. Одно приложение — курьёз, сто — статистика, тысяча —
доказательство. И второе: смешать «прошло цепочку» с «стало быстрее» — так
появляется отчёт, где корректность выдана за выигрыш.
