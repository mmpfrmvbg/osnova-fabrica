# Калибровка выигрыша VLIW-перестановки

**Дата измерения:** 2026-09-15
**Измерял:** планировщик Основа, модель e2k

---

## 0. ЧТО ИМЕННО ИЗМЕРЯЕТСЯ — читать до всех чисел

**Измеряется статическая длина расписания по модели, а НЕ ускорение исполнения.**

Это не оговорка мелким шрифтом. Проверено прямой сверкой: **число исполненных
инструкций у линейного и переставленного кода совпадает до единицы на всех
программах корпуса.**

| программа | исполнено инструкций, линейно | переставлено |
|---|---|---|
| `ilp-low.osnova` | 822 | 822 |
| `ilp-mid.osnova` | 1639 | 1639 |
| `ilp-high.osnova` | 3986 | 3986 |
| `cycle-chains.osnova` | 4783 | 4783 |
| `reg-parity/while.osnova` | 249 | 249 |
| `reg-parity/foreach.osnova` | 463 | 463 |

**Причина:** `applyReorderToWholeModule` переупорядочивает инструкции, но **не
упаковывает их в VLIW-пакеты**. Каждая инструкция остаётся отдельным однослотовым
элементом кода. «Ноль пакетов» — проверено на переставленном модуле:

```
### ilp-high.osnova
  линейный          элементов=117 пакетов=0 одиночных=117
  переставленный    элементов=117 пакетов=0 одиночных=117
```

VM считает шагом один **элемент** кода. Элементов столько же — значит исполнение
не ускорилось ни на шаг.

**Попытка упаковать** (группировка по `issueAt`, функция `packByIssueTime`) была
сделана и **ломает эквивалентность** на программах с циклами: `while.osnova` дала
`49` вместо `1049`, `foreach.osnova` разошлась на шаге 51. Та функция удалена.

**ИСПРАВЛЕНО 2026-09-15 (позже в тот же день): причина найдена и упаковка
сделана.** Предполагалось RAW внутри пакета — **не подтвердилось**: на реальной
модели e2k верификатор не нашёл в той упаковке ни одного RAW/WAR/WAW. Причина —
`call`: он передаёт управление, VM покидает пакет на этом слоте, а `returnPc`
перепрыгивает остаток пакета. Пакет `t=5` содержал `63(call)` в слоте 0 и
`68(move d=6 a=0)` в слоте 1: `move` не исполнился никогда. Измерено: потеряна
ровно одна инструкция, шагов `249 → 248`, результат `1049 → 49`
(`docs/vliw-pack-diagnosis.md`).

Корректная упаковка — `packInstructions` (`docs/vliw-packing.md`), gate
`npm run gate:pack`: 18 завершающихся программ эквивалентны, `verifyPackets` — ok,
**плотность упаковки 1.00 → 1.40** по корпусу (1670 инструкций: элементов
`1670 → 1191`).

**Важно для чтения чисел ниже:** плотность упаковки — тоже статика, и она **не
ускоряет исполнение сама по себе**: число исполненных инструкций не изменилось
(`while` 249 → 249, `ilp-high` 3986 → 3986). Упаковка уменьшает размер кода.
Такт экономит широкий выпуск, поэтому упаковка — необходимое условие для
ускорения, но не доказательство его.

**Следствие для чтения всех чисел ниже:** «выигрыш 4.0%» означает «статическое
расписание короче на 4.0% по модели», а **не** «программа работает на 4% быстрее».

## 2. Калибровочная кривая (синтетическое ядро)

Ядро: цикл с N независимыми накоплениями и инкрементом, 200 итераций.

| цепочек в цикле | выигрыш статических тактов |
|---|---|
| 1 | **0.0%** |
| 2 | 5.6% |
| 3 | 9.0% |
| 4 | 11.3% |
| 6 | 14.0% |

**Выигрыш растёт с числом независимых цепочек.** Это закономерность, а не набор
чисел: она отвечает на вопрос «где VLIW вообще помогает».

**Ограничение кривой:** синтетическое ядро без условных переходов, без вызовов и
без обращений к памяти. На реальных программах выигрыш **ниже** (см. §3).

## 3. Реальные программы

### 3.1 Специально построенный корпус ILP

| программа | ILP | процедур | инструкций | такты модуля | выигрыш |
|---|---|---|---|---|---|
| `ilp-low` | низкий (1 цепочка) | 3 | 45 | 90 → 90 | **0.0%** |
| `ilp-mid` | средний (2–3) | 3 | 81 | 159 → 159 | **0.0%** |
| `ilp-high` | высокий (4–6) | 3 | 117 | 184 → 176 | **4.3%** |

Разбор `ilp-high` по процедурам:

| процедура | инструкций | такты | выигрыш |
|---|---|---|---|
| `шесть_каналов` (6 цепочек) | 65 | 93 → 88 | 5.4% |
| `четыре_операции` (4 цепочки) | 45 | 71 → 68 | 4.2% |
| `главная` | 7 | 20 → 20 | 0.0% |

### 3.2 Почему `ilp-mid` дал 0%, хотя в нём 2–3 цепочки

Проверено разбором: **порядок выдачи в этих процедурах не изменился вообще.**

```
#0 пара_счётчиков   инстр=32  63->63  0.0%  порядок изменён=нет
#1 три_агрегата     инстр=42  76->76  0.0%  порядок изменён=нет
```

То есть в них планировщик **не нашёл перестановок**, а не «ILP не помог».
Причина видна в коде: `пара_счётчиков` и `три_агрегата` содержат условные ветви
(`если`), которые делят тело на короткие линейные участки. Внутри участка из 2–3
инструкций переставлять нечего.

**Это уточнение к синтетической кривой:** число цепочек в исходнике ещё не
означает доступного ILP. Нужно, чтобы цепочки попали в **один линейный участок**
без ветвлений.

| `reg-parity/while` | 4 | 173 → 166 | **4.0%** | 43 → 36 (16.3%) |

заблуждение: на программе это 3.1–4.7%.

## 4. Три следствия, проверенные замером

1. **Цикл сам по себе выигрыша не даёт.** В `while.osnova` процедуры `сумма_до`,
   `первый_больше`, `сумма_нечётных_до` — циклы, и все три дают **0.0%**
   (`31→31`, `40→40`, `59→59`): цепочка одна, критический путь задан ею.
   Наивная модель «VLIW = циклы» **опровергнута**.
2. **Выигрыш даёт ILP внутри линейного участка.** Поэтому `главная` в том же
   файле даёт `43 → 36`.
3. **На программе эффект разбавляется.** 16.3% на процедуре → 4.0% на модуле:
   цепочки с ILP составляют лишь часть кода.

## 5. Ограничения этого измерения

- **Корпус мал.** Специально построенных программ с известным ILP — три.
  Калибровочная кривая — на синтетическом ядре. **Это первое измерение, не
  финальное.**
- **Метрика статическая** (см. §0) — главное ограничение.
- **Модель главы 6**, не главы 12. Погрешность неизвестна.
- **Замеров на железе нет.**
- **`ilp-mid` показал 0% не из-за отсутствия ILP в исходнике, а из-за ветвлений**,
  дробящих участки. Без разбора по процедурам этот результат был бы прочитан
  неверно.

## 6. Что это значит для стратегии (вопрос к владельцу)

Кривая говорит: **VLIW даёт выигрыш там, где задача содержит ILP по своей
природе.** Программы общего назначения (ОС, GUI, бизнес-логика) такого ILP почти
не содержат — там выигрыш единицы процентов. Обработка сигналов, матричные
операции, ML-инференс содержат ILP естественно — там он может быть на порядок
выше.

Отсюда развилка, которую определяет **владелец**, а не исполнитель:

- **A. Универсальная инфраструктура** — «на Эльбрусе работает хоть что-то».
  Выигрыш вторичен. Тогда подмножество e2k — базовые операции без оптимизаций.
- **B. Специализированные задачи** — «на Эльбрусе работает X быстрее».
  Тогда подмножество e2k — под X, с прицелом на высокий ILP.
- **C. Оба** — универсальная инфраструктура плюс специализированные модули.

Этот выбор определяет, что специфицировать в Фазе 3. **Пока он не сделан,
Фазу 3 начинать не следует.**
