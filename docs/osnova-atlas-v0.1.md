# Атлас ОС-НОВА v0.1 — единый софт из атомов

**Версия:** 0.1
**Дата:** 2026-09
**Статус:** живой документ — продолжает [osnova-vision.md](osnova-vision.md)

---

## Одна фраза

Весь возможный софт — это композиции **27 атомарных инвариантов**. Фабрика
переиспользует атомы, а не приложения: приложение — неверная единица, потому
что оно произвольно склеивает *немного существенного* и *много случайного*.

---

## Связь с существующим видением

`osnova-vision.md` ставит цель («весь софт в единственном экземпляре,
собирается из компонентов, метрика — покрытие») и называет первые компоненты
(`auth`, `db`, `ui.table`, `ui.form`, `notifications`, `reports`,
`calculator`). Настоящий документ отвечает на вопрос, который видение оставляет
открытым:

> **По какому признаку резать компоненты, чтобы они не повторялись?**

Ответ — резать по **инвариантам** (гарантиям), а не по технологиям и не по
доменам. Шов, разрезанный не по инварианту, течёт абстракцией и требует вечных
костылей — это и есть причина, по которой все прошлые попытки
«переиспользуемых компонентов» провалились.

---

## Принцип

1. **Единица переиспользования — атом, не приложение.** Атом = инвариант
   (гарантия, которая держится по построению), а не библиотека.
2. **Атомы не пересекаются.** Каждый инвариант доказывается один раз; дальше на
   него *ссылаются*, как в математике ссылаются на доказанную теорему.
3. **Подпись, не категория.** Приложение описывается точкой в произведении осей,
   а не плоским `category`. Подпись вскрывает реальное переиспользование,
   которое сейчас спрятано за разными названиями.
4. **Один источник истины → много проекций.** Схема БД, API, UI, аудит, права,
   деплой — это *проекции одной подписи*, а не четыре вещи, которые надо
   держать в согласии вручную.
5. **Структурное переиспользуется, семантическое — нет.** ~80% софта —
   структурный пламбинг (атомы), ~20% — уникальная семантика человеческого
   контекста. Цель — не устранить второе, а *изолировать* его до минимума и
   сделать единственным, что вообще пишется.

## Подпись приложения

Подпись — точка в произведении осей. Она заменяет плоское `category` в
`.osapp.yaml`. Пример — «Заявки на закупку с согласованием»:

```yaml
id: "osnova.approvals"
name: "Заявки на закупку с согласованием"

signature:
  states:
    - document: {имя: Заявка, поля: [автор, сумма, позиции, статус]}
    - log:      {события: [ЗаявкаСоздана, Отправлена, Одобрена, Отклонена, Оплачена]}
    - graph:    {имя: Оргструктура, рёбра: [подчинение, лимит_подписи]}
  transitions:
    - command_event: {СоздатьЗаявку → ЗаявкаСоздана}
    - command_event: {Одобрить → Одобрена}
    - transaction:   [СоздатьЗаявку, РезервироватьБюджет]
    - merge: CRDT.ORSet
  verbs:      [изменить, решить, наблюдать, сообщить, найти]
  trust:
    identity: SSO
    authz:    ReBAC
    audit:    полный
    money:    бюджет
  lifecycle: [deploy, scale, observe, migrate]
```

Из этой подписи Фабрика **выводит** (не пишет руками):

| Проекция | Выводится из |
|---|---|
| Схема хранения (таблицы + журнал) | `states` + `transitions` |
| API (эндпоинты + валидация) | `verbs` + `states` |
| Конечный автомат согласования | `transitions` + `решить` |
| UI (форма, карточка, список, экран согласования) | `изменить/показать/найти/решить` |
| Аудит-журнал | `log` + `trust.audit` |
| Дашборд | `наблюдать` |
| Матрица прав ReBAC | `graph` + `trust.authz` |
| Деплой-конфиг | `lifecycle` |

**Семантический остаток** (единственное, что реально пишется):
доменные термины («Заявка», «Позиция», «Сумма»); доменные правила
(«сумма > 100 000 → два согласующих»); данные оргструктуры; тексты и форматы.

**VLIW-готовность подписи (метаданные, не отбор).** У каждого из 27 атомов есть флаг
`optimizable`, который говорит эмиттеру, есть ли внутри атома вычислительное ядро.
Это **не** отбор атомов по критерию «хорошо ложится на VLIW»: все 27 остаются, флаг
лишь помечает, где планировщик может работать. Правило, ответы на три вопроса и
обоснование по каждому атому — `docs/osnova-signature-spec.md`; границы атомов —
`docs/osnova-atom-boundaries.md`; интерфейс к эмиттеру —
`docs/osnova-signature-to-emitter.md`.

## Как это встраивается в Фабрику

1. **Реестр компонентов = реестр атомов.** Формат описания компонентов
   (заявлен в `registry-v0.1.md` как «v0.2») вводится сразу как каталог из 27
   атомов: имя, ось, гарантия, каноническая реализация.
2. **`signature` в `.osapp.yaml`.** Поле подписи добавляется к манифесту;
   `category` остаётся как человекочитаемая метка, но классификацию ведёт
   подпись.
3. **Покрытие считается по подписям, а не по приложениям.** «Покрытие»
   из `osnova-vision.md` переопределяется как доля достижимых *подписей*.
   Граф зависимостей: какой атом разблокирует больше всего подписей — тот и
   генерируется следующим.
4. **Golden = проверка инвариантов, а не только вывода.** Для каждого атома —
   golden-тест, который ловит нарушение гарантии (например: CRDT обязан
   сходиться при любом порядке доставки; лог обязан сохранять состояние).
5. **Проекторы как компиляторы.** Подпись → артефакты — это компиляция с
   гарантией «рассинхрон невозможен», а не ручная синхронизация четырёх слоёв.

## Граница честности (что переиспользуется, что нет)

- **Переиспользуется** (структурное, ~80%): формы состояния, переходы, глаголы,
  доверие, жизненный цикл, слияние, синхронизация, проекции.
- **Не переиспользуется** (семантическое, ~20%): смысл «счёт», «пациент»,
  «заявка»; доменные правила; регуляторная специфика; человеческий контекст.

Все прошлые провалы — это попытки переиспользовать второе. Максимальная
амбиция — не «переиспользовать всё», а *свести уникальное к минимуму и
изолировать его*.

---

## Чего НЕТ в этом документе

- Нет полного отказа от существующего: SQL, CRDT, Kafka, S3, ReBAC — уже
  готовые проекции, мы их *признаём*, а не переписываем.
- Нет «переписать мир»: миграционная тропа — поднимать существующее до уровня
  спецификации постепенно.
- Нет устранения семантики: семантический остаток остаётся и оплачивается —
  инфраструктура общая и бесплатная, специфика частная и платная.

## Дорожная карта (первые шаги)

1. Зафиксировать 27 атомов как каталог (формат компонента v0.2).
2. Добавить `signature` в `.osapp.yaml`; разметить существующие golden-аппы
   (`todo`, `micro_crm`, `chat`, `notepad`, `viewer`, `game_rounds`) подписями.
3. Ввести golden-тесты инвариантов для первых атомов (лог, CRDT, граф).
4. Пересчитать «покрытие» по подписям и выбрать атом с максимальной отдачей.

> **Приближает ли это к тому, чтобы Фабрика собирала любую подпись из
> атомов без дублирования инвариантов?**

Если да — делаем. Если нет — откладываем.
