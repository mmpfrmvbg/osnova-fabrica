# Пример раскола: micro_crm → signature + skin

**Версия:** 0.1
**Дата:** 2026-09
**Статус:** живой пример к [osnova-semantic-skin.md](osnova-semantic-skin.md)

---

## Что это

Живой пример раскола реального golden-приложения
[`osnova.micro_crm`](golden-app-micro-crm.md) на атомную `signature` и
семантическую `skin` — ровно по границе из
[osnova-semantic-skin.md](osnova-semantic-skin.md).

Исходники: `src/runtime/fixtures/micro_crm.osapp.yaml` и
`micro_crm.osnova`. Приложение берёт массив клиентов (имя, баланс, статус) и
вычисляет четыре агрегата, записывая их в хранилище.

---

## Раскол

### Атомная часть — `signature`

```yaml
signature:
  states:      [record]              # список клиентов — множество записей (A1)
  transitions: [compute]             # агрегаты — чистое вычисление (B5)
  verbs:       [показать, спросить]  # окно со списком (C2) + аналитика (C7)
  trust:       []                    # однопользовательское, локальное
  lifecycle:   [deploy, observe]     # запуск (E1) + наблюдаемый результат (E3)
```

`trust` пуст — это честно: у текущего golden-приложения нет ни идентичности, ни
авторизации, ни аудита. Полноценный CRM (архетип «Дело» из
[osnova-apps-roadmap.md](osnova-apps-roadmap.md)) добавит `identity/authz/audit`
и глаголы `изменить/найти` — это и есть шаг «довести Дело».

### Семантическая часть — `skin`

```yaml
skin:
  locale: ru-RU
  terms:
    Клиент:
      форма: Запись
      поля:
        имя:    Строка
        баланс: Число
        статус: Перечисление[активен, закрыт, новый]
  labels:
    ru:
      Клиент: "Клиент"
      имя: "Имя"
      баланс: "Баланс"
      статус: "Статус"
      активен: "активен"
      закрыт: "закрыт"
      новый: "новый"
  rules:                            # четыре доменных агрегата — декларативно
    total_balance:       сумма(Клиент.баланс)
    active_count:        число(Клиент где статус = активен)
    balance_active:      сумма(Клиент.баланс где статус = активен и баланс > 0)
    active_or_new_count: число(Клиент где статус = активен или статус = новый)
  data:                             # тестовые данные из entry.args
    клиенты:
      - {имя: "А", баланс: 10, статус: активен}
      - {имя: "Б", баланс: 20, статус: активен}
      - {имя: "В", баланс: 30, статус: закрыт}
      - {имя: "Г", баланс: 5,  статус: новый}
  formats:
    валюта: RUB
  regulation: []
```

Ключевое: `сумма`, `число`, `где`, `и`, `или` — атомные примитивы
(fold/filter/булева логика); `Клиент`, `баланс`, `статус`, `активен`, `> 0` —
шкура. Тип/паттерн = атом, значение/имя = шкура.

## Покрытие: весь исходник классифицирован

| Артефакт исходника | Атом (генерируется) | Шкура (пишется) |
|---|---|---|
| `запуск()`: окно + цикл событий | verb `показать` + lifecycle | строки `"Клиенты"`, подпись окна |
| `handle_event()`: обработка закрытия | UI-каркас | — |
| `подсчитать_баланс()` | fold+sum | поле `баланс`, ключ `total_balance` |
| `количество_активных()` | filter+count | `статус = активен`, ключ `active_count` |
| `баланс_активных()` | filter+boolean+sum | `активен и баланс > 0` |
| `количество_активных_или_новых()` | filter+or+count | `активен или новый` |
| `run_golden()` | композиция | какие именно 4 правила |
| `id`, `entry.module/procedure` | инфраструктурные ссылки | — |
| `name` | — | лейбл |
| `entry.args` (А, Б, В, Г) | — | данные |
| `ui.kind`, `permissions`, `runtime` | атомы (verb/trust/lifecycle) | — |

Ничего не осталось неклассифицированным.

## Оракул границы: три теста

| Элемент | Строковый | Замкнутости | Инварианта | Итог |
|---|---|---|---|---|
| `Запись` (форма Клиента) | нет строк | один из 27 | да | **атом** |
| `сумма`, `число`, `где`, `и`, `или` | нет строк | примитивы B5 | да | **атом** |
| имя `Клиент`, поле `баланс` | строка | новый термин | зависит от домена | **шкура** |
| `"активен"`, `"закрыт"`, `"новый"` | строка | значения перечисления | домен | **шкура** |
| `> 0` в правиле | — | — | бизнес-правило | **шкура** |
| данные А/Б/В/Г | — | значения | факты | **шкура** |

## Доказательство переиспользования: micro_crm ≡ game_rounds

Самый сильный аргумент. Сравни `micro_crm.osnova` и `game_rounds.osnova`:

**Каркас — побайтово одинаковый** (`запуск()` + `handle_event()`): то же окно,
тот же цикл событий, тот же `система.время.спать(200)`. Отличаются только строки
(`"Клиенты"` vs `"Раунды"`) и размер окна — это шкура. Каркас скопирован в двух
файлах, а по Атласу должен быть сгенерирован один раз.

**Правила — тот же атом, другая шкура:**

| micro_crm (шкура) | game_rounds (шкура) | Общий атом |
|---|---|---|
| `сумма(баланс)` | `сумма(очки)` | fold+sum |
| `число(статус = активен)` | `число(результат = победа)` | filter+count |
| `сумма(баланс где активен и > 0)` | `число(где победа и очки >= 10)` | filter+boolean+aggregate |
| `число(активен или новый)` | — | filter+or+count |

Два разных «приложения» — один и тот же код, написанный дважды. Это и есть тот
дубль, который Атлас устраняет: каркас и агрегаторы генерируются из атомов,
пишется только `skin` (термины, правила, данные, лейблы).

## Что писалось бы против что генерировалось бы

В мире Атласа разработчик (или Фабрика) пишет **только `skin`** — 4 правила,
термины, данные, лейблы. Всё остальное — `запуск()`, `handle_event()`, циклы
`для_каждого`, `система.объект.получить`, `система.хранилище.записать` —
**проектируется** из `signature`. Сейчас этот атомный слой пишется руками в
каждом golden-аппе.

## Проверка

1. **Оракул + покрытие** — выполнено выше: каждый элемент исходника и манифеста
   отнесён к атому или шкуре, граница нигде не нарушена.
2. **Golden-прогон** — попытка запуска `npm run golden` заблокирована
   сломавшимся sandbox-бэкендом (`windows-acl-run`: не существует temp-каталог,
   exit 127); команда не выполнилась — это инфраструктура песочницы, а не
   приложение. Ожидаемые значения зафиксированы в
   [golden-app-micro-crm.md](golden-app-micro-crm.md) и проверяются
   `runMicroCrmApp()` в `src/runtime/goldenApps.ts`:
   `total_balance="65"`, `active_count="2"`, `balance_active="30"`,
   `active_or_new_count="3"`.
