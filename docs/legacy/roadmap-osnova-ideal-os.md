# Дорожная карта: от OS‑nova к «идеальной ОС»

> **Статус:** vision‑документ. Актуальная дорожная карта: [roadmap.md](roadmap.md).

Этот документ фиксирует путь от текущего прототипа OS‑nova (язык, VM, invoke‑API, манифесты, песочница, golden‑приложения и LLM‑pipeline) к более полной «идеальной ОС»:

- тонкое железо / хост (Node/браузер/нативный рантайм),
- богатое системное ядро (OS‑nova + VM + системные сервисы),
- единый реестр/магазин приложений и сервисов,
- LLM‑слой как «фабрика приложений» и мозг системы.

Карта разбита на четыре крупных этапа. Каждый этап предполагает, что предыдущий в основном **стабилен** (хотя бы для v0.1).

---

## Этап 1. «Жёсткое» ядро OS‑nova (3–6 недель)

**Цель:** довести текущий прототип до минимального, но стабильного ядра:

- язык Основа,
- байткод и VM,
- invoke‑API v0.2,
- песочница по манифесту,
- golden‑приложения (TODO, File Viewer),
- автоматический golden‑прогон в CI.

### 1.1. Уточнить формат байткода и VM (с акцентом на совместимость)

- **Формализовать `.osvbc` v0.1**:
  - В `compiler-v0.1.md` и `vm/bytecode.ts` зафиксировать:
    - структуру модуля (заголовок, constants, procedures, code),
    - минимальный набор инструкций (те, что уже реализованы в `VM`),
    - допустимые типы констант (`i32`, `f64`, `str`, `bool`, `null`).
- **Отдельно описать «политику совместимости байткода»**:
  - Какие изменения считаются **backwards‑совместимыми**:
    - добавление новых опкодов в конец диапазона,
    - добавление новых полей в заголовок с разумными значениями по умолчанию,
    - расширение типов констант без изменения существующих.
  - Какие изменения считаются **breaking** и требуют bump версии формата:
    - изменение бинарного/JSON‑формата `.osvbc` (порядок/тип полей, ключи),
    - изменение семантики существующих опкодов,
    - удаление или переименование опкодов.
  - Зафиксировать правило: VM v0.1 **гарантирует запуск** всех модулей `.osvbc` v0.1, собранных под эту спецификацию; для новых версий (v0.2+) ввести явный механизм обнаружения (`version` в заголовке) и миграции.

- **Упростить и «очистить» байткод golden‑приложений**:
  - Привести `todo.osvbc.json` и `viewer.osvbc.json` к максимально понятному виду:
    - убрать лишние/мертвые инструкции,
    - корректно выставить `codeOffset` и `jmp`/`jmp_if` смещения,
    - документировать в `golden-app-*.md`, какие фрагменты кода за что отвечают (init / loop / обработчики).
  - Добавить в `golden-app-todo.md` / `golden-app-viewer.md` раздел «Bytecode overview»:
    - список процедур,
    - кратко — какие invoke ожидаются внутри каждой.

### 1.2. Стабилизировать invoke‑API v0.2

- **Разметить API по стабильности** в `system-invoke-api-v0.2.md`:
  - для каждой функции (`система.файлы.*`, `система.хранилище.*`, `система.окно.*`, `система.интерфейс.*`, `система.сеть.*`, вспомогательные `массив/объект/строка`) указать:
    - статус: `stable`, `experimental`, `stub`,
    - минимальную гарантию: подписи аргументов/возврата, семантика ошибок.
  - В `vm-runner.ts` выдержать те же статусы (комментариями) над группами switch‑веток.

- **Добиться 1‑к‑1 соответствия спеки и реализации**:
  - Пройтись по `system-invoke-api-v0.2.md` и по коду `vm-runner.ts`:
    - всё, что описано как реализованное, действительно присутствует в switch и в `inferInvokeArgCount`,
    - всё, что реализовано, отражено в md (никаких «скрытых» invoke).

### 1.3. Усилить песочницу и права

- **Песочница файлов** (`sandbox.ts`):
  - Уже сейчас: строгий allowlist по `permissions.files.read/write`, `network.outbound`.
  - Зафиксировать это в отдельном разделе `app-manifest-v0.1.md` / `system-invoke-api-v0.2.md`:
    - поведение по умолчанию при пустых массивах (всё запрещено),
    - что именно проверяется перед `readFile/writeFile/readdir/mkdir/access`.

- **Ошибки песочницы**:
  - Ввести единый тип/код `SandboxError` для golden‑трасс:
    - в `trace-format-v0.1.md` добавить поле `sandbox_error` в секцию invoke,
    - golden‑приложения должны проходить без `SandboxError` при корректных сценариях.

### 1.4. Golden‑приложения как часть CI

- **`npm run osnova-golden:apps`**:
  - Запускает:
    - TODO‑app (`osnova.todo`) с мок‑событиями (`OSNOVA_VM_MOCK_EVENTS`), проверкой:
      - код выхода 0,
      - наличие ключа `items` в хранилище.
    - File Viewer (`osnova.viewer`) с проверкой:
      - код выхода 0,
      - soft‑проверка ключа `last_path` (ужесточить, когда появится реальный байткод viewer’а).
  - Фиксируется в `roadmap` и в `golden-app-*.md` как обязательный шаг сборки.

- **Интеграция в CI**:
  - Пайплайн: `typecheck` → unit‑tests → `validate:spec` → `osnova-golden:apps`.
  - Любая поломка invoke/песочницы/VM в будущем будет быстро ловиться на golden‑прогоне.

**Результат Этапа 1:** у нас есть **стабильное v0.1 ядро Основа‑ОСи**, с чётко описанным байткодом, invoke‑API, песочницей и двумя живыми golden‑приложениями, которые входят в автоматический прогон.

## Этап 2. Системные сервисы и реестр/магазин (4–8 недель)

**Цель:** перестать воспринимать приложения как «разрозненные манифесты» и сделать из них **реестр/магазин**, а часть invoke‑API поднять до **системных сервисов** с манифестами и IPC.

### 2.1. Мини‑реестр поверх манифестов

- **Спека реестра** (`docs/osnova/registry-v0.1.md`):
  - JSON‑описание записи:
    - `id`, `name`, `version`, `category`,
    - `entry` (module/procedure/ui),
    - `permissions` (агрегированное резюме),
    - тип (`app` / `service` / `asset`),
    - путь к манифесту и пакету (`.osvpk` или каталог).
  - Описать, как реестр синхронизируется с файловой системой:
    - сканирует `*.osapp.yaml`,
    - кеширует их в JSON/SQLite,
    - умеет обновляться при изменениях.

- **CLI `osnova-apps`** (как отдельный инструмент или подкоманда):
  - `osnova-apps list` — выводит краткий список id/name/version/ui.kind/permissions.summary.
  - `osnova-apps info <id>` — показывает полный манифест.
  - позже: `enable/disable`, `permissions`, `run <id>`.

### 2.2. Первые системные сервисы как приложения (без «скрытого ядра»)

- Выбрать **1–2 базовых системных сервиса** и оформить их как **полноценные приложения той же модели, что и остальные**:
  - Примеры:
    - `osnova.notifications` — системные уведомления:
      - манифест `notifications.osapp.yaml`,
      - invoke‑API `система.уведомления.*`,
      - простой байткод или прямой bridge к Node‑реализации.
    - `osnova.clipboard` — системный буфер обмена:
      - `система.буфер_обмена.записать_текст`, `прочитать_текст`.

- Для каждого сервиса:
  - отдельный golden‑тест (CLI/golden‑приложение), проверяющий, что:
    - манифест корректен (сервис виден в реестре так же, как обычное приложение),
    - invoke‑API работает под песочницей (уважает permissions),
    - LLM сможет использовать его как «готовый кирпич».
  - Явно подчеркнуть в документации: **нет «магических» системных модулей вне общей модели** — ядро ОСи строится из тех же кирпичей (манифест + байткод + invoke + permissions), что и пользовательские приложения.

### 2.3. Минимальный IPC/обмен

- **Локальный IPC внутри процесса** (`система.обмен.отправить_локально` / `получить_локально`):
  - Зафиксировать формат сообщения:
    - `{ от: id_отправителя, канал: строка, тело: строка | объект }`.
  - Реализовать простую очередную модель в VM/рантайме:
    - очереди по `каналу` или по `имени актора`,
    - неблокирующее чтение.

- **Golden‑пример IPC**:
  - Два модуля:
    - один шлёт сообщение `ping` в локальный канал,
    - другой читает и отвечает `pong`.
  - Это ещё не «отдельные процессы», но уже контракт для будущих системных сервисов.

**Результат Этапа 2:** у нас есть **реестр/магазин** на основе манифестов и хотя бы один‑два **системных сервиса** (notifications/clipboard) как полноценные приложения с манифестами и invoke‑API, плюс зачатки IPC.

## Этап 3. LLM‑фабрика приложений поверх ядра (6–12 недель)

**Цель:** связать LLM‑pipeline с реестром и golden‑приложениями, чтобы ИИ действительно «жил» в этой ОС, а не генерировал код в вакууме.

### 3.1. Интеграция реестра в LLM‑pipeline

- Обновить `pipeline-llm-osnova.md`:
  - добавить явный шаг:
    - `loadRegistry()` → получить список доступных приложений/сервисов с их манифестами,
    - преобразовать это в **контекст** для LLM:
      - какие invoke доступны,
      - какие appId/сервисы существуют.
  - В промптах чётко указывать:
    - «можно использовать только эти invoke и эти сервисы»,
    - манифесты системных сервисов как примеры.

### 3.2. Трассы с учётом invoke и песочницы

- Расширить `trace-format-v0.1.md`:
  - секция `invoke`:
    - `name`, `args`, `result` / `error`, `sandbox_error?`, `duration_ms`.
  - секция `permissions`:
    - какие права были у приложения на момент вызова,
    - были ли нарушены ограничения (для обучения).

- В golden‑прогоне:
  - писать трассы для TODO и File Viewer:
    - нормальные invoke (`файлы`, `хранилище`, `окно`),
    - отсутствие `SandboxError`.

### 3.3. Першие LLM‑задачи «под ОСь»

- Типовые сценарии для LLM:
  - «Сгенерировать новое приложение Основа, которое использует только `система.файлы` и `система.хранилище` и показывает список файлов в каталоге X».
  - «Изменить TODO‑app, чтобы он поддерживал флажок «выполнено» и фильтр по статусу».

- Автоматический цикл:
  1. Spec → LLM → Основа‑код.
  2. Компилятор → `.osvbc`.
  3. Регистрация в реестре (временный id).
  4. Запуск через `osnova-golden:apps` / отдельный runner.
  5. Сбор трасс (включая invoke и permissions).
  6. Анализ (успех/ошибка) и, при необходимости, дообучение.

**Результат Этапа 3:** LLM‑слой начинает работать не отдельно, а **внутри ОС‑экосистемы**, уважая манифесты, permissions, invoke‑API и golden‑контракты.

## Этап 4. Пользовательская «идеальная ОС» (12+ недель, итеративно)

**Цель:** превратить всё выше в одну живую среду: единый центр управления, системные сервисы, магазин, ассистенты и композицию приложений.

### 4.1. UI‑центр управления

- Простое desktop‑ или веб‑приложение (`osnova-center`):
  - вкладка **«Приложения»**:
    - список всех записей реестра (id, name, category, версия, установлен/нет),
    - кнопки «Запустить», «Открыть права», «Открыть трассы».
  - вкладка **«Сервисы»**:
    - системные приложения (`osnova.notifications`, `osnova.clipboard`, и т.п.),
    - в будущем — identity, payments, chat.
  - вкладка **«Права»**:
    - возможность просмотреть и (в будущем) отозвать permissions по appId.
  - вкладка **«Трассы»**:
    - просмотр последних запусков, invoke‑вызовов, ошибок песочницы.

### 4.2. Ассистент как гражданин первой категории

- Встроенный ассистент (LLM) в `osnova-center`, который:
  - видит реестр, трассы и golden‑спеки,
  - может:
    - запускать приложения по id с нужными аргументами,
    - генерировать новые приложения (через описанный pipeline) и сразу добавлять их в реестр,
    - предлагать композиции («вставить TODO‑виджет в File Viewer», «сделать mini‑dashboard из нескольких сервисов»).

### 4.3. Расширение системных сервисов

- Постепенно добавлять новые сервисы, каждый:
  - с манифестом (id, entry, permissions),
  - с invoke‑API,
  - с golden‑тестами и трассами:
    - `osnova.identity` — локальный «кто я» + профили,
    - `osnova.chat` — сервис обмена сообщениями,
    - `osnova.payments` — минимальная плата/подписки для приложений,
    - `osnova.storage` — единое хранилище профиля/настроек.

**Результат Этапа 4:** у тебя не просто язык и рантайм, а **цельная ОС‑экосистема**:
- ядро (OS‑nova + VM + invoke‑API + песочница),
- реестр/магазин приложений и сервисов,
- системные сервисы, которыми все пользуются через контракты,
- LLM‑фабрика приложений, встроенная в эту среду,
- пользовательский центр управления, где всё это прозрачно видно.

## Где фокусироваться прямо сейчас

С учётом текущего состояния репозитория:

1. **Додавить Этап 1 до стабильного CI:**
   - привести `.osvbc` golden‑приложений к аккуратному эталону,
   - разметить invoke‑API по стабильности,
   - добиться, чтобы `npm run osnova-golden:apps` стабильно зелёным проходил на любой машине.

2. **Сразу после этого — мини‑реестр (Этап 2.1):**
   - JSON‑спека записи реестра,
   - простой CLI `osnova-apps list/info`,
   - привязка этого к текущим манифестам (`todo`, `viewer`, системные будущие сервисы).

3. **Потом — интеграция реестра и golden‑трасс в LLM‑pipeline (Этап 3):**
   - чтобы ИИ‑слой сразу учился жить **внутри** этой ОС, а не отдельно от неё.

## Дальнейшие направления (после стабилизации ядра)

- **VLIW-оптимизирующий бэкенд**  
  После фиксации формата байткода v0.1 и стабильного интерпретатора — этап компилятора и/или расширения байткода для VLIW: пакетные инструкции, аннотации зависимостей, предикатное выполнение, планирование (trace scheduling, software pipelining). Подробнее: `docs/osnova/vliw-considerations.md`.

- **ИИ-центричная ОС**  
  Направления развития платформы с ИИ в центре: структурированное хранилище (семантическая ФС, граф, индексация), язык Основа с аннотациями и контрактами, системные вызовы с явной семантикой и реестром метаданных, код как данные (AST, связь трейсов с кодом), единое хранилище взаимодействий, обучение и адаптация, безопасность и прозрачность, микроядерная/распределённая архитектура. Подробнее: `docs/osnova/ai-centric-os-recommendations.md`.
