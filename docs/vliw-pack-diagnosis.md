# Диагностика: `while.osnova` дала 49 вместо 1049 при упаковке по `issueAt`

Статус: **причина установлена**, измерена, воспроизводится. Документ фиксирует
метод и данные, чтобы результат не зависел от памяти участников.

## Что проверялось

Упаковка по времени выдачи (`issueAt`) один раз сломала эквивалентность:
`while.osnova` вернула `49` вместо `1049`. Функция `packByIssueTime` была
удалена, но причина расхождения не была найдена.

Гипотеза владельца: **внутри пакета есть RAW** — потребитель читает регистр,
который производитель пишет в том же пакете, а VM исполняет слоты
последовательно, поэтому потребитель видит старое значение.

## Метод

Скрипты диагностики (вне репозитория, каталог `.tmp/`):

| скрипт | что делает |
| --- | --- |
| `diag-pack.ts` | упаковка по `issueAt` + вердикт `verifyPackets` на реальной модели e2k |
| `diag-cause2.ts` | два варианта упаковки: без границ и с границами пакетов; сравнение трасс по исходным индексам |
| `diag-dump.ts` | линейный код процедуры `главная` и порядок планировщика (`order`, `issueAt`) |
| `diag-lost.ts` | мультимножество исполненных инструкций: какая инструкция теряется |

Модель машины для верификатора — реальная модель e2k: 24 канала
(`E2K_ISSUE_WIDTH`), соответствие «класс операции → номера слотов» берётся из
`channelsForClass(regOpClass(...))` (`src/vliw/e2kDevices.ts`).

Компиляция: `src/runtime/fixtures/reg-parity/while.osnova` → регистровый модуль
(`regModuleOf`, `src/vliw/regOracle.ts`). Вход — процедура `главная`
(индекс 3, `codeOffset` 59).

## Факты

Линейный прогон: значение `1049`, `249` шагов.
Упакованный по `issueAt`: значение `49`, `248` шагов.

Процедура `главная` (`linear.code[59..78]`), начало:

```
59: const d=4
60: call d=3 argc=1
61: move d=0 a=3
62: const d=4
63: call d=3 argc=1
64: move d=1 a=3
...
68: move d=6 a=0
69: const d=7
70: mul d=5 a=6 b=7
```

Порядок планировщика (`scheduleRegWithReorder`, `offsetBase: 59`):

```
order:   59, 69, 72, 60, 61, 62, 63, 68, 70, 64, 65, 66, 67, 71, 73, 74, 75, 76, 77, 78
issueAt: 59@0, 69@0, 72@0, 60@1, 61@4, 62@4, 63@5, 68@5, 70@7, ...
```

Группировка по `issueAt` даёт пакеты:

```
пакет t=0: 59(const), 69(const), 72(const)
пакет t=1: 60(call)
пакет t=4: 61(move), 62(const)
пакет t=5: 63(call), 68(move)      ← здесь
пакет t=7: 70(mul)
...
```

Мультимножество исполненных инструкций (упаковано против линейно):

```
исполнено только линейно:   #68×1
исполнено только упаковано: —
  #68: {"op":"move","d":6,"a":0}
```

То есть потеряна **ровно одна** инструкция — `move d=6 a=0`.

## Причина

`call` **передаёт управление**, и VM покидает пакет на этом слоте:

- `src/runtime/vm/reginterpreter.ts` — `case "call"` возвращает
  `callee.codeOffset`, а не `next`;
- `executeElement`: `if (next !== packetPc + 1) return next;` — пакет
  прерывается;
- `returnPc` вызываемого равен `packetPc + 1`, поэтому после возврата
  исполнение продолжается со **следующего элемента**, а остаток пакета
  (`68: move d=6 a=0`) не исполняется ни сразу, ни позже.

Пакет `t=5` содержит `call` в слоте 0 и `move` в слоте 1. Упаковка по `issueAt`
не требует, чтобы `call` был последним, поэтому `move` теряется. Регистр 6
остаётся `null`, и `70: mul d=5 a=6 b=7` считает по неверному значению.

## Почему верификатор это пропустил

Первая версия `packetVerifier.ts` (коммит `299ad5b`) содержала набор
передающих управление `jmp`, `jmp_if`, `jmp_if_not`, `ret`, `throw` —
**без `call`**. Поэтому вердикт на сломанной упаковке был `{"ok": true}`.

Дефект нашла диагностика, а не тесты. Исправление:

- `isBranchInstruction` дополнен `call` (`src/vliw/packetVerifier.ts`);
- в `packetVerifier.test.ts` добавлены случаи 6, 7 (позитивные: `call` один в
  пакете; `call` последним) и 8, 9 (негативные: слот после `call`; `ret` не
  последним). До правки реализации тесты 8 и 9 падали — оракул был красен
  раньше кода.

После правки та же сломанная упаковка отвергается:

```
verifyPackets: {"ok":false,
  "reason":"BRANCH: передача управления «call» в слоте 0 не последняя —
            VM покинет пакет и слоты после неё не исполнятся",
  "at":50}
```

## Статус гипотезы владельца

**Не подтверждена.** На реальной модели e2k верификатор не нашёл в сломанной
упаковке ни `RAW`, ни `WAR`, ни `WAW`: все `14` пакетов проходили проверку
регистров. Причина оказалась в передаче управления, а не в порядке чтения
регистров.

## Что осталось непроверенным

Два инварианта **не проверяются** `verifyPackets`, потому что в упакованном
модуле `off` — индекс элемента, и информация «какая именно инструкция была
целью перехода» теряется:

1. цель перехода не внутри пакета (инструкция-цель обязана открывать пакет);
2. первая инструкция процедуры не внутри пакета.

На измеренном дефекте нарушений этих инвариантов было `0` — то есть здесь они
не были причиной, но и не были проверены оракулом. Обеспечивать их обязан
упаковщик `packInstructions`, и это его отдельное обязательство, а не следствие
`verifyPackets`.
