# Миграция на регистровую IR (RegIR) — план

**Дата:** 2026-09
**Статус:** частично реализовано (Шаг 1 — паритет — закрыт)
**Что уже есть в коде:** регистровый кодоген (`src/compiler/regcodegen.ts`),
регистровая VM (`src/runtime/vm/regcode.ts`, `reginterpreter.ts`), оракул паритета
(`src/oracle/parity.ts` + `parity.test.ts`) и корпус конструкций
(`src/runtime/fixtures/reg-parity/`, 4 файла). Ранее здесь стояло «план, не
начато» — это было неверно и вводило в заблуждение.
**Что ещё не сделано:** VLIW-планировщик на RegIR (`src/vliw/regScheduler.ts`)
написан, но **не подключён ни к компилятору, ни к CLI**, и не переставляет
инструкции (упаковка in-order внутри линейного участка). См.
`docs/vliw-reg-plan.md`.
**Цель, из которой он выведен (не меняется):** своя ОС под VLIW-процессоры, ИИ встроен в систему, весь софт собирается из атомов.

Почему это следствие цели, а не смена её: стековая VM имеет один последовательный
разделяемый ресурс — вершину стека. Каждая `push`/`pop` его трогает, поэтому две
независимые вычислительные цепочки сериализуются. Планировщик уже был вынужден
перейти на in-order упаковку (`src/vliw/scheduler.ts`), потому что любая
перестановка ломала порядок стека. На таком представлении настоящий ILP
недостижим по построению, а не по трудозатратам.

## 2. Формат RegIR (`.osvir.json`)

Отдельный артефакт, а не новая версия `.osvbc`: существующие фикстуры, self-host и
stages продолжают работать на v1, диффы остаются честными.

```jsonc
{
  "ir": "osnova-reg",
  "version": 1,
  "moduleName": "Пример",
  "constants": [42, "текст"],          // тот же пул и те же индексы, что в .osvbc
  "procedures": [
    {
      "name": "главная",
      "argc": 0,
      "vregs": 7,                       // сколько всего виртуальных регистров
      "blocks": [
        {
          "id": 0,
          "params": [],                 // vreg'и, приходящие по рёбрам (замена phi)
          "ops": [
            { "op": "const",  "d": 1, "type": "i32", "k": 0 },
            { "op": "add",    "d": 2, "a": 1, "b": 3 },
            { "op": "invoke", "d": 4, "name": "система.строка.объединить", "args": [2, 3] },
            { "op": "obj.set", "a": 5, "key": 6, "b": 4 }        // эффект, без d
          ],
          "term": { "kind": "brif", "cond": 2, "then": 1, "else": 2 }
        },
        { "id": 1, "params": [7], "ops": [], "term": { "kind": "ret", "v": 7 } },
        { "id": 2, "params": [],  "ops": [], "term": { "kind": "ret", "v": null } }
      ]
    }
  ]
}
```

Решения и их причины:

- **SSA + параметры блоков вместо phi.** Каждое значение определено один раз; граф
  зависимостей строится из def-use без симуляции стека. Параметры блоков — это ровно
  те слоты, которые нужно переименовывать при software pipelining; с phi это
  пришлось бы делать отдельным проходом.
- **Три адреса: `d`, `a`, `b`.** Один-к-одному на слоты `I0/I1/M/B` из
  `src/vliw/e2kModel.ts`. Больше трёх операндов в языке не требуется.
- **Терминатор — отдельное поле.** CFG корректна по построению, патчинг `off` по
  индексам (`(code[p] as {off:number}).off = code.length` в `codegen.ts`) исчезает.
- **Эффекты — операции без `d`, порядок между ними сохраняется.** То же правило,
  что уже реализовано в `dependencyGraph.ts` через `lastEffect`.
- **Куча остаётся в памяти.** Объекты/массивы — ссылки с мутацией; в SSA живут
  скаляры и ссылки. Mem2reg по объектам не делаем.
- **Исключения — маркеры блоков** (`try_begin`/`try_end`), без landing pad в v1:
  в VM нет разворачивания стека, ломать наивный SSA на этом не нужно.
- **Валидатор `isRegIr()`** — зеркало `isOsVbcModule()` из `src/runtime/vm/bytecode.ts`.

### Что происходит с текущими опкодами

| Стековый опкод | В RegIR |
|---|---|
| `const`, `const.true/false/null` | `const d, type, k` |
| `add`…`ge`, `and`, `or`, `not` | `op d, a, b` / `op d, a` |
| `local.get` / `local.set` | исчезают: локальные переменные промоутятся в vreg'и |
| `dup` / `pop` | исчезают: артефакты стека, в IR нет информации |
| `jmp` / `jmp_if` / `jmp_if_not` | `term: jmp/brif` + параметры целевого блока |
| `call`, `invoke` | `call d, fi, args[]`, `invoke d, name, args[]` |
| `obj.new/get/set` | то же, с явными операндами |
| `ret` | `term: ret` |
| `try_begin`/`try_end`/`throw` | маркеры блока / эффект-операция |

Четыре опкода (`dup`, `pop`, `local.get`, `local.set`) не имеют аналога, потому что
существуют только для обслуживания стека. Это и есть мера того, сколько
информации несёт текущее представление.

## 4. Сверка stack vs register на golden-аппах

Принцип: сравнивать не «passed», а **трассу наблюдений**. Golden-проверка может
совпасть при расхождении поведения; трасса — нет.

```ts
type Step =
  | { kind: 'invoke'; name: string; args: unknown[] }   // каждый syscall
  | { kind: 'return'; value: unknown }
  | { kind: 'throw';  error: string };
```

Обе VM запускаются с **одной и той же** invoke-фабрикой, один и тот же
`.osnova`-источник компилируется дважды. Сравниваются массивы шагов, состояние
`storage` после прогона и финальное значение. При расхождении печатается индекс
шага и обе записи — расхождение видно в первой точке ветвления поведения, а не в
конце.

### Корпус

- `src/runtime/fixtures/*.osnova` (7 аппов) — эталонные `.osvbc.json` уже лежат рядом;
- `apps/chat`, `apps/osnova-todo`, `apps/task-manager` — мультимодульные реальные программы;
- `docs/golden-tests.json` (`tests[]`) — языковой корпус;
- `src/self-host/stage1..15.osnova` — 15 больших реальных программ; `stage15` уже
  имеет числовой assert (self-check → 42). Это самый ценный корпус: бесплатный,
  с известным правильным ответом.

### Уровни

| Уровень | Что проверяет | Критерий |
|---|---|---|
| L0 | `src/ir/verify.ts` на всём корпусе | 100%, любая ошибка = стоп |
| L1 | stack VM vs reg VM (без пакетов), трасса | полное совпадение |
| L2 | reg VM: линейный код vs VLIW-пакеты | полное совпадение |
| L3 | ILP на реальных аппах (замена синтетических пар) | ILP ≥ 2 хотя бы на одном |

L2 — это уже существующий приём `runOracle` (сверка linear vs scheduled), только
перенесённый на реальные программы. L3 даёт ответ на вопрос «стоит ли продолжать»,
которого сейчас нет: ILP > 1 доказан только на синтетических независимых парах,
где он гарантирован конструкцией теста.

### CI

Новый скрипт `npm run parity` отдельным шагом после `golden`. Корпус
детерминированный: LLM-тесты (`agents`, `pipeline`) в него не входят, иначе
офлайн-Qwen будет маскировать паритет.

## 5. Критерий приёмки (тот самый гейт)

Бэкенд считается принятым, когда одновременно:

1. `verify.ts` — 100% корпуса;
2. L1: трассы совпадают на fixtures + apps + `golden-tests.json`;
3. L1: трассы совпадают на `stage1..15`;
4. L2: пакеты дают ту же трассу, что линейный RegIR;
5. L3: ILP ≥ 2 на хотя бы одном реальном аппе.

Только после этого `OSNOVA_BACKEND=reg` становится значением по умолчанию, а
стековый кодоген остаётся как bootstrap для self-host.

## 7. Ловушки

- **Self-host не мигрировать в этой работе.** `stage15.osnova` компилируется
  стековым компилятором и остаётся на нём. Попытка перенести и его превращает
  задачу в «переписать всё» — ровно то, чего нужно избежать.
- **Объекты и массивы — ссылки с мутацией.** SSA только для скаляров и ссылок;
  попытка полного mem2reg по объектам съест недели.
- **Исключения — место, где наивный SSA ломается.** Сохраняем текущую модель
  (`try_begin`/`try_end` как маркеры блока), landing pad не вводим.
- **Два пути держать зелёными до конца.** Стековый `codegen.ts` не удаляется: он
  bootstrap для self-host и эталон для L1.
- **Не мерить паритет через «golden passed».** Совпадение вывода при расхождении
  трассы маскирует баги — сравнение только по трассе.
- **Не смешивать с падениями LLM-тестов.** В `npm test` сейчас ~10 падений из-за
  офлайн-Qwen и legacy `Fabrika2.0`; корпус паритета должен быть детерминированным.
