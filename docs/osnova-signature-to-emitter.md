# Интерфейс «подпись → эмиттер»

**Дата:** 2026-09-15
**Что это:** описание интерфейса между подписью приложения и будущим эмиттером e2k.
**Это не эмиттер.** Ни эмиттера, ни симулятора не существует: Фазы 4–5
(`docs/vliw-phases-plan.md`) не начаты, и начинать их в этой работе запрещено
решением владельца. Смысл документа — зафиксировать обязательства эмиттера **до**
того, как он написан, чтобы он не оказался написан под неверные входы.

**Отношение к другим документам:** `docs/osnova-signature-spec.md` (флаг
`optimizable`), `docs/osnova-atom-boundaries.md` (границы как ABI),
`docs/e2k-subset-requirements.md` (что за подмножество), `docs/hardware-debt.md`
(что нельзя проверить без железа).

---

## 3.1. Что эмиттер получает на вход

Четыре вещи, и ничего больше:

| вход | что это | откуда берётся |
|---|---|---|
| **разрешённые атомы с флагами** | список `{id, optimizable, kernel}` по всем осям подписи | выводится Фабрикой из каталога `docs/osnova-signature-spec.md` §2 по `id`; руками не пишется |
| **границы** | для каждого атома — точки входа и выхода | `docs/osnova-atom-boundaries.md` §2.2 (вызов / интерфейс / передача данных) |
| **тела для оптимизации** | регистровый код (`RegModule`, `src/runtime/vm/regcode.ts`) внутренностей атомов с `optimizable: true` | кодоген `src/compiler/regcodegen.ts` |
| **целевое подмножество** | какие классы операций разрешены на выходе | `docs/e2k-subset-requirements.md`; задача внутри B выбрана (DSP, 2026-09-15, решение владельца), сама спецификация ещё **не написана** — Фаза 3 |

Форма входа (та же, что в §3 `docs/osnova-signature-spec.md`):

```yaml
emit:
  target: e2k-subset           # имя подмножества; сегодня не определено
  atoms:
    - {id: A6, optimizable: true,  kernel: "векторная арифметика", body: RegModule}
    - {id: B5, optimizable: true,  kernel: "чистое вычисление",    body: RegModule}
    - {id: B1, optimizable: false, kernel: null,                   body: RegModule}
  boundaries:
    - {from: A6, to: B5, kind: call}
    - {from: B5, to: B1, kind: data}
```

**Чего во входе нет:** человекочитаемых строк и доменных правил — это шкура
(`docs/osnova-semantic-skin.md`), а не атомная часть. Эмиттер не знает слов
«Заявка» и «Одобрена»; он знает `A1`, `B1`, `C5`.

---

## 3.2. Что эмиттер возвращает

Два законных вида выхода, и оба обязаны быть названы, потому что они появляются на
разных фазах:

| выход | что это | когда доступен |
|---|---|---|
| **пакеты** | `RegModule` с элементами-пакетами (`RegPacket`): код, который уже умеет исполнять регистровая VM | сегодня — только для целой программы через `src/vliw/vliwPipeline.ts`; **по атомам не разделён** |
| **машинный код подмножества** | поток команд e2k: кодировка, регистры, предикаты, пакеты | после Фазы 3 (спецификация) и Фазы 4 (эмиттер). Сейчас не существует |

Пакеты как промежуточный выход не заменяют машинный код: они проверяемы тем, что
есть (верификатор пакетов `src/vliw/packetVerifier.ts` и gate `npm run gate:pack`), и
именно поэтому названы первыми. Но **плотность упаковки и шаги VM — не метрика
скорости**: VM считает шагом элемент кода, а не такт e2k; замеров на железе нет
(`docs/hardware-debt.md` §3.3, §3.4).

Обязательный элемент выхода: **карта размещения** — какие элементы кода принадлежат
какому атому. Без неё невозможно сказать, чей инвариант нарушен, если что-то
разошлось.

## 3.3. Как эмиттер понимает, какие атомы оптимизировать

Правило ровно одно, и оно не оставляет места для догадок:

1. **`optimizable: true`** → эмиттер **вправе** применить к внутренностям атома
   перестановку и упаковку в пределах, описанных в
   `docs/osnova-atom-boundaries.md` §2.3.
2. **`optimizable: false`** → эмиттер **обязан** оставить порядок операций как есть
   (§3.4).
3. **Граница атома** → работа прекращается в обе стороны независимо от флагов
   (§2.4).

Флаг читается из каталога, а не из манифеста приложения: приложение ссылается на
атомы по `id`. Иначе автор приложения мог бы объявить ядро там, где его нет, и
планировщик получил бы разрешение переставлять код без гарантии детерминизма.

**Порядок применения внутри одного атома** (когда эмиттер появится): сначала
линейные участки — как в `src/vliw/vliwPipeline.ts`, потом перестановка
(`src/vliw/reorderScheduler.ts`), потом упаковка (`src/vliw/packetPacker.ts`), и
обязательная проверка `verifyPackets` на результат. Если проверка не проходит —
эмиттер возвращает ошибку, а не «почти легальный» код.

---

## 3.4. Что происходит с атомами `optimizable: false`

Три конкретных следствия:

1. **Перестановка запрещена.** Порядок операций внутри атома сохраняется: у таких
   атомов порядок либо объявлен гарантией (A3, A4, A7, B2, C5, D1–D4), либо
   вычисления нет вовсе.
2. **Упаковка в порядке допустима.** Группировка соседних инструкций в широкую
   команду не меняет порядок и потому семантически нейтральна — это подтверждено
   gate'ом на четырёх конфигурациях (`docs/vliw-packing.md` §3а). Однако и здесь
   действуют запреты §2.4: пакет не пересекает границу атома и не содержит эффектов,
   перенесённых относительно других эффектов.
3. **Ошибка вместо оптимизации.** Если для атома с `optimizable: false` планировщик
   не может собрать легальный код без перестановки, эмиттер сообщает об этом; он не
   «включает оптимизацию» в обход флага.

Отдельно: `optimizable: false` **не** означает «плохой атом» и **не** повод его
переписать. Атомы хранения, обхода, протокола и политики держат инварианты — это и
есть их работа.

## 3.5. Что нужно, чтобы этот интерфейс заработал

Всё перечисленное — долги, не сделанная работа:

| # | что нужно | где об этом | почему без этого интерфейс не работает |
|---|---|---|---|
| 1 | **спецификация подмножества e2k** | `docs/e2k-subset-requirements.md`, Фаза 3 | без кодировки «машинный код подмножества» не существует; задача выбрана (DSP), спецификация **не написана** |
| 2 | **эмиттер e2k** | Фаза 4 `docs/vliw-phases-plan.md` | сам предмет этого документа; не реализован |
| 3 | **симулятор e2k** | Фаза 5 | без него машинный код нечем исполнить и нечем сверить с регистровой VM |
| 4 | **корпус разноплановых программ** | Фаза 7 | на одной задаче эмиттер проверяется ровно на одной задаче |
| 5 | **доступ к железу** | `docs/hardware-debt.md` | без железа и без симулятора доказательство остаётся самосогласованным; это надо называть, а не забывать |
| 6 | **разделение кода по атомам** | этот документ, §3.2 | сегодня `vliwPipeline` планирует программу целиком; «тело атома» как отдельная единица планирования не выделено |

**Что можно сделать до Фаз 3–5, не нарушая запретов:** ничего из перечисленного не
требует выбора B-задачи, кроме пункта 1. Пункт 6 (разделение кода по атомам) — тоже
отдельная работа и в этом сеансе не делается.

**Чего этот интерфейс не обещает:** ни ускорения, ни сроков. Он фиксирует входы,
выходы и запреты, чтобы эмиттер, когда его начнут писать, не оказался написан под
неверную модель атома.
