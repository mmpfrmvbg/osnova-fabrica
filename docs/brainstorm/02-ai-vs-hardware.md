# Что знает hardware-предсказатель и что может знать AI-компилятор

**Сеанс:** 2026-09-19. **Источники здесь трёх родов, и их нельзя смешивать:**

| род | как помечен | пример |
|---|---|---|
| **код проекта** | `файл:строка` | `src/e2k/e2k-real.ts:97` |
| **измерение по трейсам** | команда + число | «4815 строк, проверено `node`» |
| **общее инженерное знание** | **ГИПОТЕЗА / ОБЩЕЕ ЗНАНИЕ** | как устроен аппаратный предсказатель переходов |

**Важное предупреждение по третьему роду.** В репозитории **нет** статьи-критика про
hardware-предсказатель, про Intel и про «ИИ против железа». Проверено: `grep` по `docs/**`,
`memory/**` и всему репозиторию (без `node_modules`/`.git`) по словам `предсказател`, `predictor`,
`спекуляц`, `Intel` даёт **ноль** содержательных совпадений — все попадания `Intel` ложные
(подстрока в `Intelligence`). Значит таблица «что знает hardware» ниже опирается на **общее
инженерное знание** и помечена как таковая, а не выдаётся за выписку из документа проекта.
Таблица «что может знать AI-компилятор» опирается на код и на числа, и это проверяемо.

## 1. Определение осей сравнения (без оценок)

Прежде чем сравнивать, надо назвать, **о чём** сравнение. Иначе получится спор о словах.

| ось | что это значит | где в проекте видно |
|---|---|---|
| **Когда решение** | до исполнения или во время | эмиттер и раскладка работают до запуска (`e2kRealRun.ts:729`) |
| **Что видно** | один линеаризованный поток или история событий | `liveSetsOf` видит **весь** поток с переходами (`liveness.ts:105-138`) |
| **Чем платит** | тактами простоя или размером кода | `nopCycles` в `ReorderMetrics` (`reorderScheduler.ts:225`) |
| **Область** | один базовый блок или межпроцедурная картина | в проекте — **внутри процедуры** (`regAlloc.ts:312-390`) |
| **Обратимость** | можно ли отменить решение | понижение необратимо: раскладка идёт **после** него по смыслу (`twoPassLayout.ts:592`) |

## 2. Что знает и чего не знает аппаратный предсказатель

**ГИПОТЕЗА / ОБЩЕЕ ЗНАНИЕ** (не из документов проекта): аппаратный предсказатель переходов — это
таблицы, обновляемые **на каждом событии исполнения**: счётчики направлений, буфер цели перехода,
история ветвлений. Ниже — что из этого следует. Ни одно утверждение этой таблицы в проекте не
измерялось: железа и симулятора нет (`docs/hardware-debt.md:9`).

| знает | не знает |
|---|---|
| исход **прошлых** исполнений этой ветви (история) | **семантику** программы: что ветвь означает |
| адрес цели перехода (буфер цели) | сколько раз ветвь **ещё** исполнится в этом запуске |
| что ветвь «почти всегда туда» — по счётчику | что **другая** ветвь в другой процедуре коррелирует с этой |
| — | что программа **собирается** делать дальше: план на несколько блоков |
| — | что за переходом стоит **чистое** вычисление, которое можно поднять |
| — | является ли ветвь частью **цикла** с известным числом итераций |
| — | какие значения попадут в память: адресный поток ему не виден |
| — | **цену ошибки**: он не знает, что промах стоит 5 тактов (`latencyMap.ts:185`) |

**Два ограничения, важных именно здесь, и оба — про источник информации:**

1. **Размер таблиц фиксирован, а программа — нет.** Он не может «запомнить» больше, чем есть
   места; при промахе таблицы решение принимается по умолчанию.
2. **Он учится на том, что уже исполнилось.** На **первом** проходе по коду он не знает ничего.
   Это не дефект: это свойство, из которого растёт вся разница.

**Что в проекте уже признано про железо — с цитатами (не гипотеза):**

- штраф за переход между кластерами АЛУ **неизвестен**, в модели принят нулевым
  (`docs/hardware-debt.md:46-48`; функция-заглушка `reorderScheduler.ts:303-312` возвращает `0`);
- штраф за передачу между целочисленным и вещественным доменами — **известен** (`+2`/`0`,
  `e2kDevices.ts:278-280`), то есть «какая-то часть железа описана, а какая-то нет»;
- погрешность модели длительностей **неизвестна** (`docs/hardware-debt.md:33`).

## 3. Что AI-компилятор может знать такого, чего предсказатель не может

Ниже — **по коду и по форматам**, а не по обещаниям. Для каждой строки указано, **есть ли это
знание уже сейчас** или его надо получить (и откуда).

| что может знать | есть ли сейчас | источник / препятствие |
|---|---|---|
| Живость значения на **всех** путях, включая обратные рёбра циклов | **да** | `liveSetsOf` — обратный анализ до неподвижной точки с переходами (`liveness.ts:105-138`), точная граница `peakLive` (`:74`) |
| Что пересылка снимается **безопасно** с учётом границ блоков | **да** | `blockStartsOf` + три условия (`copyElim.ts:75-98`, `:129-142`) |
| Что процедура объявлена **чистой** | **да, но не используется** | `RegProcedure.pure?: boolean` (`src/runtime/vm/regcode.ts:261-262`); вход `callPure` (`dependencyGraph.ts:22`) с умолчанием «любой invoke считается эффектом» (`:25-26`) |
| Сколько **регистров** нужно процедуре по существу | **да** | `peakLive` и `windowRegistersNeeded` (`regAlloc.ts:231-255`) |
| Что процедура **не может быть вызвана** (окно 8) | **да** | `calleeWindow` (`e2kRealRun.ts:663-669`, расчёт `:885-903`) |
| Какие вызовы в модуле вообще есть | **да** | `calledIndices` по `payload` носителя (`e2kRealRun.ts:879-884`) |
| Размер каждой команды и все смещения | **да** | `layoutOf`/`secondPass` (`twoPassLayout.ts:504`, `:592`) |
| **Профиль** программы: что горячо, что нет | **нет** | в трейсах нет ни одного поля профиля (см. §4); модель отказов языка даёт только распределение **ошибок** |
| **Число итераций цикла** | **нет** | понятия «цикл» в анализах нет: живость линейна (`liveness.ts:39-40`), области планирования — линейные участки (`reorderScheduler.ts` — `splitLinearRegions`) |
| **Уровень кэша** каждого чтения | **нет** | уровень — подсказка пользователя счётчиков, а не свойство кода (`pipelineCounters.ts:52-55`) |
| **Штраф** за кластер | **нет** | функции возвращают 0 (`reorderScheduler.ts:303-312`) |
| Реальный **такт** исполнения | **нет** | ни железа, ни симулятора (`docs/hardware-debt.md:9`); все числа тактов — модельные (`:325`) |

**Ключевая асимметрия, названная без прикрас.** Преимущество «знать заранее» реализуется только
там, где **есть чем** это знание выразить и **есть на чём** его проверить. Сейчас:
выразить — есть (форма `ld`/`st` реализована, `e2k-real.ts:269-276`; широкие команды
реализованы, `widePacker.ts:171`); проверить на **тактах** — нечем (`hardware-debt.md:9`).

## 4. Что в трейсах есть и чего в них нет (проверено)

**Файлы:** `runs/traces.jsonl` — 4 815 строк, 12 228 345 байт; `runs/repair-failures.jsonl` —
724 строки. Проверено скриптом `.tmp/brainstorm-trace-facts.cjs` (только чтение `runs/`).

### 4.1. Структура записи трейса

14 различных наборов ключей верхнего уровня; полный список ключей — 15:
`buildReport, goldenReport, intent, lastErrorKind, legacy_gate_bug, modelId, repairAttempts, runId,
semanticErrorCount, shadow_hits, source, spec, status, task, timestamp`.

Глубже: `buildReport.bytecode.{version, moduleName, code[], procedures[], constants[]}`,
`buildReport.procedures[].{name, argc, localsCount, codeOffset, pure}`, `goldenReport.{executed,
passed, durationMs, qualityScore, outputDiff, vmErrors[]}`, `source.{filename, source, tokensUsed}`.

### 4.2. Чего в трейсах **нет** — с проверкой

| чего нет | проверка | результат |
|---|---|---|
| тактов, циклов | поиск ключей `cycle`/`tick` по файлу | **0** — единственное массовое совпадение `passed` (ключ `goldenReport.passed`) |
| слотов, пакетов | поиск `slot`/`packet` | **0** |
| профиля | поиск `profil`/`branch`/`predict`/`hot`/`latency`/`wbs` | **0** |
| счётчика вызовов процедуры, глубины стека | поиск `call`/`stack`/`depth` | `stack` — 3 ложных (имя **параметра** процедуры); счётчиков вызовов нет |
| какого-либо прохода компилятора | поиск `pass` | **0** |
| «горячей» процедуры | поиск `hot` | **0** |

**Что есть вместо тактов — время компилятора:** `buildReport.durationMs` присутствует в **3495**
записях (из 4815), `goldenReport.durationMs` — в 3447. Это миллисекунды работы компилятора и
прогона, **не такты**. Смешивать их с тактами — та же ошибка, что «шаги VM как ускорение»
(`memory/_index.md:48-54`).

### 4.3. Состав реальных отказов — и почему он **не** про вызовы

**724 записи** в `repair-failures.jsonl`, ключи: `category, last_error_kind, task_summary, traceId, ts`.

- `category`: **одна на весь файл** — `утилита`, 724 из 724. Классифицирующей силы нет.
- `last_error_kind`: `unknown` 685, `vm_error` 29, `parser_error` 8, `compiler_error` 1,
  `syscall_argc` 1.
- `task_summary`: 18 различных значений, из них **702 записи** — буквально
  `"тест repair_exhausted"` (синтетический наполнитель).

**Про вызовы — ответ прямой:** поиск по каждой строке
`/(invoke|call|wbs|окн|процедур|функц)/i` даёт **ровно 1 совпадение**, и оно ложное — слово
`call` внутри значения `"last_error_kind":"syscall_argc"`. Ни `invoke`, ни `окно`, ни `wbs` в
файле не встречаются.

**Отсюда важное следствие для сеанса:** утверждение «в трейсах 100 реальных отказов, и часть из
них — про вызовы» **не подтверждается текущими файлами**. Реальных (несинтетических) записей —
22 на 17 формулировок; ни одна не классифицирована как «про вызовы».

**Единственная массовая «вызывная» тема** лежит не в отказах, а в семантических ошибках трейсов
(замер классификатором `src/scripts/failureKindMeasure.ts`, доля считается по файлу
`runs/traces.jsonl` целиком):
`buildReport.semanticErrors[].kind` — `syscall_argc` 52, `redeclare_var` 40, `undeclared_var` 7,
`unknown_syscall` 4, `invented_syntax` 4. И это **ошибки модели в языке** — сообщение вида
«`система.массив.создать` ожидает 0 аргументов, передано 1» встретилось 30 раз в поле
`buildReport.compilerErrors[].message` файла `runs/traces.jsonl` (локальный журнал, не в git), а не
отказы кодогенератора.

### 4.4. Число, которое ограничивает любую ставку на трейсы

По `docs/language-v2-requirements.md`: **79,5 %** трейсов — фикстуры (`:27`); на реальных задачах
успех 88,4 %, `repair_exhausted` 10,6 % (`:29-30`); состав реального отказа: парсер 37 %,
**исполнение 42 %**, семантика 14 %, **кодоген 5 %**, лексер 3 % (`:32-33`).

**Вывод без прикрас:** даже идеальное использование трейсов не улучшит кодоген, потому что кодоген
— **5 %** отказов, а сама задача сеанса (такты) в трейсах вообще не представлена. Трейсы — не
профиль исполнения, а журнал **частоты задач**, которые ставила модель.

## 5. Таблица «hardware vs AI-компилятор» — по осям §1

| ось | hardware-предсказатель | AI-компилятор в этом проекте | источник |
|---|---|---|---|
| Когда решает | во время исполнения, на каждом событии | до исполнения, один раз на модуль | `e2kRealRun.ts:729` (весь путь — статический) |
| Что видит | историю ветви | **весь** поток с переходами, живость всех путей | `liveness.ts:105-138` |
| Область | текущая ветвь | процедура целиком; межпроцедурно — **нет** | `regAlloc.ts:312-390` |
| Чем платит | простой конвейера при промахе | размер кода и такты простоя по модели | `reorderScheduler.ts:225` (`nopCycles`) |
| Источник знания о «горячем» | сам исполняемый код | **нечего**: профиля в трейсах нет | §4.2 |
| Знание о **чистоте** | ему не нужно: он не переставляет код | **есть флаг** `pure`, но конвейер его не читает | `regcode.ts:261-262` vs `e2kRealRun.ts:744-745` |
| Знание о цели перехода | буфер цели | **точный** адрес и смещение в 8-байтовых словах | `twoPassLayout.ts:592-607` |
| Обратимость | предсказание — гипотеза, снимается по факту | понижение и раскладка — **необратимы** | порядок шагов `e2kRealRun.ts:759-778` |
| Проверяемость сейчас | недоступна (нет железа) | есть: симулятор оболочки и модель тактов | `memory/_index.md:210-216` |
| Обязательное условие для выигрыша | — | **чем измерить**: ни такта на железе (`hardware-debt.md:9`) | — |

**Честный вывод по таблице.** У AI-компилятора есть **два** преимущества, видимых в коде: полная
живость по всем путям и право решать до исполнения. У него **нет** трёх вещей, без которых
преимущество не превращается в такты: профиля, модели штрафов (кластер, кэш) и способа проверить
результат, кроме модели. Любой ход из `03-candidates.md` обязан назвать, как он обходится с этими
тремя.

## 6. Чего в этой таблице сознательно нет

- **Нет утверждения «AI лучше».** Есть перечень того, чем каждый располагает. Где преимущество не
  превращается в замер — это названо.
- **Нет аппаратных предсказаний как предложения.** Сеанс — про компилятор; пункт «не предлагать
  hardware-предсказатель» соблюдён: ни один ход в `03-candidates.md` не меняет железо (в том числе
  не включает и не выключает предсказание переходов).
- **Нет цен на непроверенное.** Числа вида «промах стоит N тактов» взяты только из таблицы модели
  (`e2kDevices.ts:324-340`) и помечены как модельные.
