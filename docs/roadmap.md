    - [ ] отфильтровать трейсы по статусу (успех/ошибка/repair_exhausted),
    - [ ] увидеть, на каких шагах пайплайна чаще всего происходят проблемы,
    - [ ] быстро открыть связанный код/манифест.

---

### 5. UX вокруг LLM‑фабрики приложений

**Цель:** сделать один удобный вход в ИИ‑слой для пользователя ОС‑НОВА.

- **5.1. Общая команда CLI**
  - [ ] Реализовать/зафиксировать команду вида:
    - [ ] `osnova new-app --task "описание задачи"`:
      - [ ] запускает полный LLM‑пайплайн,
      - [ ] генерирует код и манифест приложения,
      [ ] прогоняет build + golden‑проверку,
      - [ ] сохраняет результат (код, манифест, трейсы) в стандартное место.

- **5.2. Интеграция с мини‑ОС**
  - [ ] После успешной генерации:
    - [ ] новое приложение автоматически появляется в списке `osnova list`,
    - [ ] его можно запустить как обычное приложение через launcher.

---

**Итог Фазы 3:** после выполнения чеклиста LLM‑слой ОС‑НОВА станет «фабрикой приложений», встроенной внутрь экосистемы: агенты знают о реестре, системных сервисах и golden‑контрактах, а пользователю доступен единый сценарий «опиши, что нужно → получи работающее приложение на Основе».

## Фаза 4 — Пользовательская «ОС‑НОВА» как единая среда

На этой фазе элементы ядра, мини‑ОС и LLM‑фабрики собираются в одну видимую и удобную для пользователя среду: центр управления, системные сервисы первого класса и ассистент, живущий внутри этой системы.

---

### 1. Центр управления ОС‑НОВА

**Цель:** дать пользователю единое место, где видно всё: приложения, сервисы, права, трассы.

- **1.1. Приложение `osnova-center`**
  - [ ] Определить формат: отдельное Основа‑приложение, веб‑UI или desktop‑оболочка (минимальный вариант).
  - [ ] Экран «Приложения»:
    - [ ] список записей реестра (id, name, category, версия, установлен/нет),
    - [ ] действия: «Запустить», «Показать манифест/права», «Открыть трейсы (если есть)».
  - [ ] Экран «Сервисы»:
    - [ ] список системных сервисов (notifications, clipboard и др.),
    - [ ] отображение их статуса и базовой статистики (частота вызовов, ошибки).

- **1.2. Просмотр прав и трасс**
  - [ ] В центре управления добавить:
    - [ ] экран/панель «Права»:
      - [ ] просмотр прав по `appId`,
      - [ ] (опционально) возможность отключить/ограничить некоторые permissions.
    - [ ] экран «Трассы»:
      - [ ] просмотр последних запусков приложений,
      - [ ] фильтрация по статусу (успех/ошибка/repair_exhausted),
      - [ ] ссылка на исходники/манифест (если доступны).

---

### 2. Ассистент как гражданин первой категории

**Цель:** встроить LLM‑ассистента внутрь `osnova-center`, чтобы он управлял системой, а не существовал отдельно.

- **2.1. Встроенный ассистент**
  - [ ] Добавить в `osnova-center` интерфейс ассистента (поле ввода + поток ответов).
  - [ ] Ассистент должен иметь доступ к:
    - [ ] реестру приложений и сервисов,
    - [ ] информации о правах приложений,
    - [ ] истории трейсов (минимальный набор метаданных).

- **2.2. Типовые действия ассистента**
  - [ ] Сценарии, которые ассистент умеет выполнять:
    - [ ] «Запусти приложение `<id>` с параметрами …».
    - [ ] «Создай новое приложение для задачи …» (обёртка вокруг `osnova new-app`).
    - [ ] «Покажи, какие приложения трогали хранилище/файлы/сеть за последний час».
  - [ ] Задокументировать эти сценарии (как минимум в отдельном разделе доки про ассистента), чтобы их можно было расширять.

---

### 3. Расширение и унификация системных сервисов

**Цель:** постепенно наращивать количество системных сервисов, при этом держать их в одной модели (манифест + invoke + permissions + golden‑тесты).

- **3.1. Новые системные сервисы**
  - [ ] Для каждого нового сервиса (identity, notifications, clipboard, chat и др.):
    - [ ] оформить манифест (`.osapp.yaml`) с типом `service`,
    - [ ] описать его invoke‑API в общем реестре системных вызовов,
    - [ ] добавить golden‑тесты, проверяющие ключевые сценарии работы.

- **3.2. Единые принципы для сервисов**
  - [ ] Зафиксировать в доке (можно отдельный раздел «Системные сервисы ОС‑НОВА»):
    - [ ] что любой системный сервис живёт по тем же правилам, что и приложение (манифест, permissions, песочница, invoke‑API),
    - [ ] как они регистрируются в реестре и отображаются в `osnova-center`.

---

### 4. Мини‑«опыт пользователя» как цель

**Цель:** сформировать набор сценариев, при которых ОС‑НОВА ощущается как цельная система, а не конструктор.

- [ ] Описать 3–5 целевых сценариев использования:
  - [ ] «Пользователь устанавливает и запускает новое приложение через центр управления».
  - [ ] «Пользователь просит ассистента создать маленькое приложение/скрипт под задачу, и оно появляется в списке приложений».
  - [ ] «Пользователь смотрит, что делало приложение (какие invoke вызывало, с какими правами)».
- [ ] Для каждого сценария:
  - [ ] убедиться, что все нужные части (реестр, launcher, ассистент, сервисы, трейсы) уже реализованы и согласованы,
  - [ ] опционально сделать end‑to‑end тесты или записать walkthrough в документации.

---

**Итог Фазы 4:** после выполнения этих пунктов у тебя будет не только язык, VM и LLM‑фабрика приложений, но и цельная пользовательская среда ОС‑НОВА: с центром управления, видимыми приложениями и сервисами, встроенным ассистентом и понятными сценариями использования.
