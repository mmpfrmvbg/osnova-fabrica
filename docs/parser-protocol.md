# Протокол парсера v0.1 — token tape, упаковка, backpatch (2026-11-08, docs-only)

**Статус:** контракт для Атома 3. **Реализация — Атом 3**, не этот документ.
На HEAD `src/e2k/parserProgram.ts` **отсутствует**; единственный артефакт — черновик
`.tmp/parser-target.osnova`, он не продакшен и не коммитится.

**Границы этого документа:**

- **Зафиксировано:** поля и stride token tape; фильтрация переводов строк; упаковка шага
  `4+24+24` (доказательство); backpatch ровно одного события `вернуть` со значением; таблица
  16 шагов для **AST 1.0**.
- **Не зафиксировано:** грамматика (D56/D57); семантика (D51/D52); модель/железо (Атом 4);
  реализация (Атом 3); представление `пока`/`пусть` в AST — **названный блокер**, см. §5.
- **Не «протокол готов для полной v0.1».** Token tape, упаковка и backpatch готовы для
  AST 1.0. `пока`/`пусть` в AST 1.0 не представимы; полная v0.1 требует формата 1.1/2.0
  или другого пути. Это названо, а не сглажено.

## 1. Token tape: интерфейс лексер → парсер

### 1.1. Запись

```
[вид, строка, offset, колонка, длина, лекс_длина, cp...]
stride = 7 + лекс_длина
```

| Поле | Смысл | Единица |
|---|---|---|
| `вид` | вид токена (число из реестра лексера) | — |
| `строка` | номер строки исходника, 1-based | строка |
| `offset` | смещение первой кодовой точки токена | **кодпоинты**, 0-based |
| `колонка` | колонка первой кодовой точки, 1-based | **кодпоинты** |
| `длина` | длина токена | **кодпоинты** |
| `лекс_длина` | число кодовых точек в `cp...` | кодпоинты |
| `cp...` | кодпоинты лексемы | кодпоинты |

`offset`/`колонка`/`длина` — **в кодовых точках** (D1), не в байтах и не в UTF-16. Символ вне
BMP — одна позиция, а не две. Парсер не пересчитывает байты.

### 1.2. Строки декодированы

Для строкового токена `cp...` — **декодированное значение**, как его выдаёт лексер, а не сырой
текст с escape. Парсер **не декодирует** повторно: `\n`, `\"`, `\\` уже раскрыты лексером.
Если лексер отдаёт и сырую, и декодированную форму, в tape едет **декодированная**; сырая не
нужна парсеру и не должна попадать в AST.

### 1.3. Переводы строк отфильтрованы

Tape содержит **только не-`новая_строка`**; `новая_строка` отбрасывается при генерации, а не
пропускается парсером. Это важно: парсер не обязан помнить о переводах строк в каждой ветке.
Позиции (`строка`, `offset`, `колонка`) — **исходные**, они не перенумеровываются после
фильтрации.

Tape заканчивается **ровно одним** `конец_файла`, последним. `конец_файла` — обычная запись
stride 7 с `лекс_длина = 0`; после неё ничего нет.

### 1.4. Границы (названный отказ, не усечение)

Для v0.1 генерация tape обязана отказать **по имени**, если:

- индекс записи в tape `≥ 2^24` (16 777 216 токенов);
- `offset`, `колонка` или `длина` `≥ 2^24` кодпоинтов;
- кодпоинт `≥ 2^21` (Unicode-максимум `0x10FFFF` = 1 114 111 < 2 097 152 — граница с запасом);
- `лекс_длина` не помещается в 24 бита (практически недостижимо, но проверяется, а не
  предполагается).

Не «обрежем и поедем»: усечение позиции — тихая ложь D4/D5. Код отказа — Атом 3; здесь
зафиксировано **требование** отказа, а не его номер.

## 2. Упаковка шага: 4 + 24 + 24 = 52 бита (доказано)

### 2.1. Формула

```
R = tag · 2^48 + value · 2^24 + pos
```

- `tag` — 4 бита, 16 шагов (0..15);
- `value` — 24 бита (кодпоинт/offset/token index/счётчик);
- `pos` — 24 бита (индекс записи token tape).

`tag` — **шаг протокола**, не «вид токена»: вид токена в tape — обычное число, не 4 бита.

### 2.2. Доказательство точности

Максимум при `tag = 15`, `value = 2^24 − 1`, `pos = 2^24 − 1`:

```
max = 15·2^48 + (2^24 − 1)·2^24 + (2^24 − 1)
    = 15·2^48 + 2^48 − 2^24 + 2^24 − 1
    = 16·2^48 − 1
    = 2^52 − 1
    < 2^53.
```

`2^52 − 1` — целое, меньше `2^53`, поэтому `Number` представляет его **точно** (мантисса 53
бита). Проверка из задания с `7·2^48` тоже верна и **консервативна**:

```
7·2^48 + (2^24 − 1)·2^24 + (2^24 − 1) = 8·2^48 − 1 = 2^51 − 1 < 2^53.
```

Но 4-битный `tag` допускает 15, и даже максимум 15 остаётся `< 2^53`; поэтому `7` в проверке
не обязателен. Ложная прежняя формула `tag·2^32 + value·2^16 + pos` **не используется**: она
требовала `value, pos < 2^16`, а кодпоинт — 21 бит, позиция — не 16 бит.

### 2.3. Распаковка

```
pos   = R % 2^24
R1    = R нацело 2^24
value = R1 % 2^24
tag   = R1 нацело 2^24
```

`нацело` и `%` — int64 (D52), не 32-битные побитовые операции JS. Все промежуточные значения
`< 2^53`, поэтому точность сохраняется. `2^24 = 16 777 216` — точная степень двойки.

### 2.4. Проверка границ при генерации

Перед упаковкой:

- `tag ≤ 15`;
- `value < 2^24`;
- `pos < 2^24`;
- `value` как кодпоинт `< 2^21`; как offset/column/length `< 2^24`; как token index `< 2^24`.

Нарушение — **названный отказ** на генерации tape, не усечение и не «повезло». Иначе `R`
выйдет за доказанный диапазон, и `Number` начнёт округлять — тихая ложь.

## 3. Backpatch: ровно одно событие `вернуть` со значением

### 3.1. Факт формата AST 1.0

Событие `вернуть` в `src/compiler-v3/astFormat.ts` пишется так:

```
[8, начало, строка, колонка, <конец>, <hasValue>]
```

То есть **`конец` — пятое поле, `hasValue` — шестое**. Это не «`hasValue`, потом заглушка»:
порядок полей — часть формата 1.0, и протокол обязан следовать ему. (В задании атома порядок
был записан наоборот; здесь исправлено по коду.)

### 3.2. `вернуть` со значением

1. Пишется `8, начало, строка, колонка, 0, 1` — `конец` пока **заглушка 0**.
2. Индекс заглушки (позиция поля `конец` в ленте) кладётся в стек кадров как
   `RETURN = 900 + индекс`.
3. После разбора выражения `посл_кон` (конец последнего токена выражения) пишется в
   `лента[индекс]`; стековый кадр `RETURN` снимается.
4. Патч — `система.массив.установить(лента, индекс, посл_кон)`, глубина 0/1 (проверено
   Phase A: 7). Не новый носитель, не запись в чужую клетку.

`RETURN = 900 + индекс` — **не новый регистр**: стек кадров уже живой, +0 регистров по
конструкции. Индекс — позиция в `лента`, а не в token tape; это разные ленты.

### 3.3. `вернуть` без значения

Пишется `8, начало, строка, колонка, начало + 7, 0` — `вернуть` занимает 7 кодпоинтов,
конец известен сразу. Заглушки и стекового кадра нет.

### 3.4. `посл_кон`

После каждого write-шага:

```
посл_кон = токены[поз + 2] + токены[поз + 4]
```

`токены[поз + 2]` — `offset`, `токены[поз + 4]` — `длина` текущего токена; сумма — конец
текущего токена в кодпоинтах. Это **один локальный** (не стековый) — `+0..1 vreg`; не
скрывать: на пике это одна дополнительная переменная.

### 3.5. Другие pre-order события: почему им не нужен патч

| Событие | Что пишется pre-order | Где настоящий конец | Патч? |
|---|---|---|---|
| `процедура_начало` | `1, start, line, col, start+9` | `процедура_конец` (post-order) | **нет**; `start+9` — конец ключевого слова, не конец узла |
| `параметр` | `2, start, line, col`, имя, тип | `end` сразу после типа | **нет** |
| `если_начало` | `5, start, line, col, start+4` | `если_конец` (post-order) | **нет**; `start+4` — конец `если`, не конец узла |
| `вернуть` со значением | `8, start, line, col, 0, 1` | после выражения | **ДА** — единственный |
| `вернуть` без значения | `8, start, line, col, start+7, 0` | сразу | **нет** |
| `вызов_начало` | `10, start, line, col` | `вызов_конец` (post-order) | **нет**; поля конца нет |
| `литерал` / `имя` | `12/13, start, end, line, col` | сразу | **нет** |
| `иначе`, `вызов_оператор` | без поля конца | внутренний/следующий | **нет** |

**Вывод:** pre-order событий, которые пишут **финальный** конец, ровно одно —
`вернуть` со значением. `процедура_начало`/`если_начало` тоже pre-order, но их пятое поле —
**конец ключевого слова**, а не конец узла; они закрываются отдельными `*_конец`. Поэтому
backpatch не «покрывает все pre-order события» — он покрывает **все события, которым нужен
финальный конец дочернего разбора**, и такое событие одно. Если Атом 3 добавит новое такое
событие, он обязан добавить патч; текущий набор — один.

**Названное расхождение:** `процедура_начало` жёстко пишет `start+9` (длина `процедура`).
Для `действие` длина 8, поэтому `start+9` — неверный конец ключевого слова. Это не backpatch,
но это **названный дефект** для D56.3; исправление — флаг/формат в Атоме 3, не в этом
docs-атоме.

### 3.6. Стоимость

По конструкции, **не замер**: +5–8 IR на патч, +80–200 байт; `RETURN` в стеке — +0 регистров;
`посл_кон` — +0..1 vreg, пик +0..1. Замер — Атом 3, не здесь. Числа не выдаются за факт.

## 4. Таблица шагов (tag → запись → stack op)

| tag | Шаг | Что пишет `главная` в `лента` | Stack op |
|---:|---|---|---|
| 0 | `конец` | `0` | none; на EOF стек пуст |
| 1 | `процедура_начало` | `1, start, line, col, start+9`, имя | push `P` |
| 2 | `параметр` | `2, start, line, col`, имя, тип, `end` | none |
| 3 | `заголовок` | `3, paramCount, returnFlag`, [тип возврата] | replace `P` header |
| 4 | `процедура_конец` | `4, end` | pop `P` |
| 5 | `если_начало` | `5, start, line, col, start+4` | push `I` |
| 6 | `иначе` | `6` | replace `I` branch |
| 7 | `если_конец` | `7, end` | pop `I` |
| 8 | `вернуть` | `8, start, line, col, end/0, hasValue` | push `R` если значение; pop+patch после выражения |
| 9 | `вызов_оператор` | `9, start, line, col` | none |
| 10 | `вызов_начало` | `10, start, line, col` | push `C` |
| 11 | `вызов_конец` | `11, argc, end` | pop `C` |
| 12 | `литерал` | `12, start, end, line, col`, payload | none |
| 13 | `имя` | `13, start, end, line, col`, имя | none |
| 14 | `типы` | код типа (`1/2/3`) + payload | none |
| 15 | `ошибка` | вид ленты ошибки + код | none |

`типы` и `ошибка` — **не события AST 1.0**: тип пишется inline после `параметр`/`заголовок`,
ошибка — отдельная лента `вид = 2`. Теги 14/15 — шаги протокола, не `КОД_СОБЫТИЯ`; в таблице
они стоят, чтобы 4-битное пространство было названо целиком. `P`/`I`/`C`/`R` — кадры стека
(процедура/если/вызов/патч возврата), не физические регистры.

## 5. Граница: `пока`/`пусть` в AST 1.0 не представимы

Это **главный блокер полной v0.1**, и он назван явно.

1. **D56.3 (решение владельца):** v0.1 **должен** принимать `пока`/`пусть`/`действие` —
   следствие «переходим на v3», а не выбор. Это грамматическое решение; оно записано.
2. **AST 1.0 не имеет для них событий.** `docs/ast-format.md` §11 прямо исключает `пусть` и
   циклы; `КОД_СОБЫТИЯ` в `astFormat.ts` содержит 14 событий, среди них нет ни `пока`, ни
   `пусть`. `пока`/`пусть` некуда положить в AST, не меняя формат.
3. **4-битное пространство tag занято.** 16 шагов (0..15) уже полны; новых тегов для `пока`/
   `пусть` нет. Даже если добавить события, `tag` 4 бита не хватит — нужен другой формат/ширина.
4. **`parserV01.ts` заморожен** и `пока`/`пусть`/`действие` отвергает; менять его в этом атоме
   запрещено. Ссылочный парсер остаётся subset; расширение — Атом 3/формат 1.1.
5. **`действие`** можно было бы свести к узлу `процедура` с `возвращает: null`, но
   `процедура_начало` пишет `start+9`, а `действие` — 8 кодпоинтов; нужен флаг/новое поле.
   Тоже формат.

**Следствие:** token tape, упаковка `4+24+24` и backpatch `вернуть` зафиксированы для
**AST 1.0**. Полная v0.1 с `пока`/`пусть` **не может быть объявлена реализованной** без
формата 1.1/2.0 или v2-AST-пути. Это **СТОП полной v0.1**, не «мелкая недоделка». Решение о
формате — владельца/Атома 3; в этом docs-атоме код не менялся.

  §5 называет, что AST 1.0 его не вмещает.
- **Семантику** — D51/D52; протокол использует, не определяет.
- **Модель/железо** — Атом 4; протокол от них не зависит.
- **Реализацию** — Атом 3; здесь спека.
- **Представление `пока`/`пусть`** — §5; без формата 1.1/2.0 не решается.
