# Протокол парсера v0.1 — token tape, упаковка, backpatch (2026-11-08, AST 1.1)

**Границы этого документа:**

  `5+23+24` (доказательство); backpatch **двух** событий — `вернуть` со значением и `пусть`;
  таблица 17 шагов из 32 для **AST 1.1**.
- **Не зафиксировано:** грамматика (D56/D57); семантика (D51/D52); модель/железо (Атом 4);
  реализация кодогена `пусть`/`пока` (Фазы 3/4).
- **Что изменилось против Атома 2.** AST 1.1 (D58) представляет `пусть`/`пока`/`действие`, поэтому
  `пусть` стал **вторым** pre-order событием с финальным концом. 4-битного `tag` больше не хватает;
  упаковка — `5+23+24` (32 шага). `пока` — AST-событие без backpatch; `действие` — событие 17 с
  концом ключевого слова 8, шаг тот же, что у `процедуры`, с флагом.

## 1. Token tape: интерфейс лексер → парсер

### 1.1. Запись

```
[вид, строка, offset, колонка, длина, лекс_длина, cp...]
stride = 7 + лекс_длина
```

| Поле | Смысл | Единица |
|---|---|---|
| `вид` | вид токена (число из реестра лексера) | — |
| `строка` | номер строки исходника, 1-based | строка |
| `offset` | смещение первой кодовой точки токена | **кодпоинты**, 0-based |
| `колонка` | колонка первой кодовой точки, 1-based | **кодпоинты** |
| `длина` | длина токена | **кодпоинты** |
| `лекс_длина` | число кодовых точек в `cp...` | кодпоинты |
| `cp...` | кодпоинты лексемы | кодпоинты |

`offset`/`колонка`/`длина` — **в кодовых точках** (D1), не в байтах и не в UTF-16. Символ вне
BMP — одна позиция, а не две. Парсер не пересчитывает байты.

### 1.2. Строки декодированы

Для строкового токена `cp...` — **декодированное значение**, как его выдаёт лексер, а не сырой
текст с escape. Парсер **не декодирует** повторно: `\n`, `\"`, `\\` уже раскрыты лексером.
Если лексер отдаёт и сырую, и декодированную форму, в tape едет **декодированная**; сырая не
нужна парсеру и не должна попадать в AST.

### 1.3. Переводы строк отфильтрованы

Tape содержит **только не-`новая_строка`**; `новая_строка` отбрасывается при генерации, а не
пропускается парсером. Это важно: парсер не обязан помнить о переводах строк в каждой ветке.
Позиции (`строка`, `offset`, `колонка`) — **исходные**, они не перенумеровываются после
фильтрации.

Tape заканчивается **ровно одним** `конец_файла`, последним. `конец_файла` — обычная запись
stride 7 с `лекс_длина = 0`; после неё ничего нет.

### 1.4. Границы (названный отказ, не усечение)

Упаковка 5+23+24 даёт `value` 23 бита. Для v0.1 генерация tape обязана отказать **по имени**, если:

- индекс записи в tape `≥ 2^23` (8 388 608 токенов);
- `offset`, `колонка` или `длина` `≥ 2^23` кодпоинтов;
- кодпоинт `≥ 2^21` (Unicode-максимум `0x10FFFF` = 1 114 111 < 2 097 152 — граница с запасом);
- `лекс_длина` не помещается в 23 бита (практически недостижимо, но проверяется, а не
  предполагается).

Это **ужесточение** прежних 2^24 из Атома 2: 23 бита нужны, чтобы 5-битный `tag` и 24-битный
`pos` влезли в 52. Для v0.1 8M токенов/кодпоинтов достаточно; превышение — отказ, а не усечение.
Не «обрежем и поедем»: усечение позиции — тихая ложь D4/D5. Код отказа — Атом 3; здесь
зафиксировано **требование** отказа, а не его номер.

## 2. Упаковка шага: 5 + 23 + 24 = 52 бита (доказано)

### 2.1. Формула

```
R = tag · 2^47 + value · 2^24 + pos
```

- `tag` — 5 бит, 32 шага (0..31);
- `value` — 23 бита (кодпоинт/offset/token index/счётчик);
- `pos` — 24 бита (индекс записи token tape).

`tag` — **шаг протокола**, не «вид токена»: вид токена в tape — обычное число, не 5 бит.

### 2.2. Доказательство точности

Максимум при `tag = 31`, `value = 2^23 − 1`, `pos = 2^24 − 1`:

```
max = 31·2^47 + (2^23 − 1)·2^24 + (2^24 − 1)
    = 31·2^47 + 2^47 − 2^24 + 2^24 − 1
    = 32·2^47 − 1
    = 2^52 − 1
    < 2^53.
```

`2^52 − 1` — целое, меньше `2^53`, поэтому `Number` представляет его **точно** (мантисса 53
бита). 5 бит дают 32 шага, 23 бита — `value`, 24 — `pos`; сумма 52, запас до 53 — один бит.
Прежняя 4+24+24 (`max = 2^52 − 1`) была верна для 16 шагов, но 16 шагов **полны**, а `пусть`
требует 17-го. Ложная формула `tag·2^32 + value·2^16 + pos` не используется.

### 2.3. Распаковка

```
pos   = R % 2^24
R1    = R нацело 2^24
value = R1 % 2^23
tag   = R1 нацело 2^23
```

`нацело` и `%` — int64 (D52), не 32-битные побитовые операции JS. Все промежуточные значения
`< 2^53`, поэтому точность сохраняется. `2^24 = 16 777 216`, `2^23 = 8 388 608` — точные степени
двойки.

### 2.4. Проверка границ при генерации

Перед упаковкой:

- `tag ≤ 31`;
- `value < 2^23`;
- `pos < 2^24`;
- `value` как кодпоинт `< 2^21`; как offset/column/length/token index `< 2^23`.

Нарушение — **названный отказ** на генерации tape, не усечение и не «повезло». Иначе `R`
выйдет за доказанный диапазон, и `Number` начнёт округлять — тихая ложь.

## 3. Backpatch: два события — `вернуть` со значением и `пусть`

### 3.1. Факт формата AST 1.1

Событие `вернуть` в `src/compiler-v3/astFormat.ts` пишется так:

```
[8, начало, строка, колонка, <конец>, <hasValue>]
```

То есть **`конец` — пятое поле, `hasValue` — шестое**. Это не «`hasValue`, потом заглушка»:
порядок полей — часть формата, и протокол обязан следовать ему. (В задании Атома 2 порядок был
записан наоборот; здесь исправлено по коду.)

Событие `пусть` в AST 1.1:

```
[14, начало, строка, колонка, <конец>, <есть_тип>, имя_длина, ...имя, [тип], <выражение>]
```

`конец` — пятое поле, `есть_тип` — шестое. `конец` локальной = конец выражения/типа, поэтому в
потоке он **неизвестен в момент записи события** — это второе pre-order событие с финальным концом.

### 3.2. `вернуть` со значением

1. Пишется `8, начало, строка, колонка, 0, 1` — `конец` пока **заглушка 0**.
2. Индекс заглушки (позиция поля `конец` в ленте) кладётся в стек кадров как
   `PATCH = 900 + индекс`.
3. После разбора выражения `посл_кон` (конец последнего токена выражения) пишется в
   `лента[индекс]`; стековый кадр `PATCH` снимается.
4. Патч — `система.массив.установить(лента, индекс, посл_кон)`, глубина 0/1 (проверено
   Phase A: 7). Не новый носитель, не запись в чужую клетку.

`PATCH = 900 + индекс` — **не новый регистр**: стек кадров уже живой, +0 регистров по
конструкции. Индекс — позиция в `лента`, а не в token tape; это разные ленты.

### 3.3. `пусть` (всегда со значением)

1. Пишется `14, начало, строка, колонка, 0, есть_тип` — `конец` пока **заглушка 0**.
2. `PATCH = 900 + индекс` кладётся в стек кадров; имя, тип (если есть), выражение.
3. После выражения `лента[индекс] = посл_кон`; кадр `PATCH` снимается.
4. Патч — тот же механизм, что у `вернуть`; отдельного регистра/носителя нет. Стек допускает
   несколько кадров `PATCH`; текущая грамматика не даёт вложенных `пусть` в одном выражении, но
   механизм не полагается на это.

**Порядок полей — не переставлять:** `конец` раньше `есть_тип`; иначе патч попадёт в признак типа.

### 3.4. `вернуть` без значения

Пишется `8, начало, строка, колонка, начало + 7, 0` — `вернуть` занимает 7 кодпоинтов,
конец известен сразу. Заглушки и стекового кадра нет.

### 3.5. `посл_кон`

После каждого write-шага:

```
посл_кон = токены[поз + 2] + токены[поз + 4]
```

`токены[поз + 2]` — `offset`, `токены[поз + 4]` — `длина` текущего токена; сумма — конец
текущего токена в кодпоинтах. Это **один локальный** (не стековый) — `+0..1 vreg`; не
скрывать: на пике это одна дополнительная переменная.

### 3.6. Другие pre-order события: почему им не нужен патч

| Событие | Что пишется pre-order | Где настоящий конец | Патч? |
|---|---|---|---|
| `процедура_начало` | `1, start, line, col, start+9` | `процедура_конец` (post-order) | **нет**; `start+9` — конец ключевого слова, не конец узла |
| `действие_начало` | `17, start, line, col, start+8` | `процедура_конец` (post-order) | **нет**; `start+8` — конец `действие` |
| `параметр` | `2, start, line, col`, имя, тип | `end` сразу после типа | **нет** |
| `если_начало` | `5, start, line, col, start+4` | `если_конец` (post-order) | **нет**; `start+4` — конец `если`, не конец узла |
| `вернуть` со значением | `8, start, line, col, 0, 1` | после выражения | **ДА** |
| `вернуть` без значения | `8, start, line, col, start+7, 0` | сразу | **нет** |
| `пусть` | `14, start, line, col, 0, hasType`, имя, [тип], выражение | после выражения/типа | **ДА** |
| `пока_начало` | `15, start, line, col`, условие | `пока_конец` (post-order) | **нет**; поля конца условия нет намеренно |
| `вызов_начало` | `10, start, line, col` | `вызов_конец` (post-order) | **нет**; поля конца нет |
| `литерал` / `имя` | `12/13, start, end, line, col` | сразу | **нет** |
| `иначе`, `вызов_оператор` | без поля конца | внутренний/следующий | **нет** |

**Вывод:** pre-order событий, которые пишут **финальный** конец, ровно два — `вернуть` со
значением и `пусть`. `процедура_начало`/`действие_начало`/`если_начало` тоже pre-order, но их
пятое поле — **конец ключевого слова**, а не конец узла; они закрываются отдельными `*_конец`.
`пока_начало` не пишет конец условия — иначе был бы третий патч; условие несёт свою позицию.
Если Атом 3 добавит новое такое событие, он обязан добавить патч; текущий набор — два.

**`пока`:** backpatch **не нужен**. `пока_начало` содержит только начало/строку/колонку, затем
условие; `пока_конец` пишет конец тела. Это факт формы, а не «пока не проверено».

### 3.7. Стоимость

По конструкции, **не замер**: +5–8 IR на патч, +80–200 байт; `PATCH` в стеке — +0 регистров;
`посл_кон` — +0..1 vreg, пик +0..1. `пусть` добавляет второй такой кадр в местах, где он есть.
Замер — Атом 3, не здесь. Числа не выдаются за факт.

## 4. Таблица шагов (tag → запись → stack op)

| tag | Шаг | Что пишет `главная` в `лента` | Stack op |
|---:|---|---|---|
| 0 | `конец` | `0` | none; на EOF стек пуст |
| 1 | `процедура_начало` / `действие_начало` | `1` или `17`, `start, line, col, start+9/8`, имя | push `P` |
| 2 | `параметр` | `2, start, line, col`, имя, тип, `end` | none |
| 3 | `заголовок` | `3, paramCount, returnFlag`, [тип возврата] | replace `P` header |
| 4 | `процедура_конец` | `4, end` | pop `P` |
| 5 | `если_начало` | `5, start, line, col, start+4` | push `I` |
| 6 | `иначе` | `6` | replace `I` branch |
| 7 | `если_конец` | `7, end` | pop `I` |
| 8 | `вернуть` | `8, start, line, col, end/0, hasValue` | push `PATCH` если значение; pop+patch после выражения |
| 9 | `вызов_оператор` | `9, start, line, col` | none |
| 10 | `вызов_начало` | `10, start, line, col` | push `C` |
| 11 | `вызов_конец` | `11, argc, end` | pop `C` |
| 12 | `литерал` | `12, start, end, line, col`, payload | none |
| 13 | `имя` | `13, start, end, line, col`, имя | none |
| 14 | `типы` | код типа (`1/2/3`) + payload | none |
| 15 | `ошибка` | вид ленты ошибки + код | none |
| 16 | `пусть` | `14, start, line, col, 0, hasType`, имя, [тип], выражение | push `PATCH`; pop+patch после выражения |
| 17..31 | резерв | — | — |

`типы` и `ошибка` — **не события AST**: тип пишется inline после `параметр`/`заголовок`,
ошибка — отдельная лента `вид = 2`. Теги 14/15 — шаги протокола, не `КОД_СОБЫТИЯ`; в таблице
они стоят, чтобы 5-битное пространство было названо. Тег 16 — `пусть`; 17..31 свободны.
`P`/`I`/`C`/`PATCH` — кадры стека (процедура/если/вызов/патч), не физические регистры.

**`пока`/`действие`/контракты — не шаги.** `пока` — два AST-события (15/16), шага нет;
`действие` — шаг 1 с `start+8` и событием 17; контракты — события 18–20, парсер v0.1 их не пишет.

## 5. Граница: что AST 1.1 уже представляет, а что нет

1. **D56.3/D58:** `пусть`/`пока`/`действие` **представимы** в AST 1.1. `пусть` — оператор с
   необязательным типом; `пока` — оператор с условием и телом; `действие` — процедура с
   `действие: true`, `возвращает: null`, концом ключевого слова 8.
2. **Полная v0.1 в AST 1.1** — да, для перечисленных конструкций. `parserV01.ts` принимает
   `пусть`/`пока`/`действие`; 10 валидных программ и 5 невалидных прогнаны оракулом.
3. **Чего в AST 1.1 нет:** `для`, `разбор`, `защита`, бинарные операторы, индексация, поля;
   контракты — только зарезервированные события, парсер их не читает. Это не «полная v0.1»,
   а её объявленное подмножество.
4. **Кодоген `пусть`/`пока`** — Фазы 3/4; AST 1.1 — формат, не компилятор. `src/e2k/**` не
   трогался; VLIW не трогался.
