# Протокол парсера v0.1 — token tape, протокол событий, упаковка, backpatch (2026-11-08, AST 2.1)

**Статус:** контракт под-атомов P1–P3. Реализация — `src/compiler-v3/parser-protocol-probe.ts`
(P2/P3), не этот документ. На HEAD `src/e2k/parserProgram.ts` **отсутствует**; единственный
артефакт — черновик `.tmp/parser-target.osnova`, он не продакшен и не коммитится (переписывание —
P4, отдельный атом).

**Границы этого документа:**

- **Зафиксировано:** поля и stride token tape; фильтрация переводов строк; упаковка шага
  `5+23+24` (доказательство); **форма протокола событий** — `главная` пишет AST-ленту, handlers
  возвращают `R`; 24 шага протокола; стек фреймов; арена только в `главная` (D12-2);
  `добавить` → runtime `система.массив.добавить` в `главная`.
- **Не зафиксировано:** грамматика (D56/D57); семантика (D51/D52); backpatch (P2/P3 его не
  используют); реализация кодогена `пусть`/`пока` (Фазы 3/4).
- **Что изменилось против редакции AST 1.1.** Формат — **2.1** (присваивание и
  квалифицированный вызов уже в AST). Протокол — не плоский автомат в одной процедуре, а
  **`главная` + handlers**: `главная` владеет лентой и стеком, handlers только читают токены и
  возвращают упакованный шаг. Причина — измеренная форма D48: малые процедуры укладываются в
  бюджет, а запись в арену из callee запрещена (D12-2).
- **Чего в P1 нет.** Чисел P2/P3 (peak/spills/код) здесь нет: они появятся в этом документе
  после прогона, а не выдаются за факт заранее (D19).

## 1. Token tape: интерфейс лексер → парсер

### 1.1. Запись

```
[вид, строка, offset, колонка, длина, лекс_длина, cp..., 0]
stride = 7 + лекс_длина
```

| Поле | Смысл | Единица |
|---|---|---|
| `вид` | вид токена (число из реестра лексера) | — |
| `строка` | номер строки исходника, 1-based | строка |
| `offset` | смещение первой кодовой точки токена | **кодпоинты**, 0-based |
| `колонка` | колонка первой кодовой точки, 1-based | **кодпоинты** |
| `длина` | длина токена в исходнике | **кодпоинты** |
| `лекс_длина` | число кодовых точек в `cp...` | кодпоинты |
| `cp...` | кодпоинты лексемы (для строки — декодированное значение) | кодпоинты |
| `0` | терминатор записи (смысла не несёт; держит stride одинаковым) | — |

`offset`/`колонка`/`длина` — **в кодовых точках** (D1), не в байтах и не в UTF-16. Символ вне
BMP — одна позиция, а не две. Парсер не пересчитывает байты.

Заголовок — **6** полей, затем `лекс_длина` кодпоинтов и терминатор. Следующий токен начинается
через `7 + лекс_длина`; это же число двигает `поз` в `главная`. Терминатор не «значение
литерала»: значение числа парсер считает из `cp...` (P2), строковое — из декодированных `cp...`
(§1.2).

### 1.2. Строки декодированы

Для строкового токена `cp...` — **декодированное значение**, как его выдаёт лексер, а не сырой
текст с escape. Парсер **не декодирует** повторно: `\n`, `\"`, `\\` уже раскрыты лексером.
Если лексер отдаёт и сырую, и декодированную форму, в tape едет **декодированная**; сырая не
нужна парсеру и не должна попадать в AST.

### 1.3. Переводы строк отфильтрованы

Tape содержит **только не-`новая_строка`**; `новая_строка` отбрасывается при генерации, а не
пропускается парсером. Это важно: парсер не обязан помнить о переводах строк в каждой ветке.
Позиции (`строка`, `offset`, `колонка`) — **исходные**, они не перенумеровываются после
фильтрации.

Tape заканчивается **ровно одним** `конец_файла`, последним. `конец_файла` — обычная запись
stride 7 с `лекс_длина = 0`; после неё ничего нет.

### 1.4. Границы (названный отказ, не усечение)

Упаковка 5+23+24 даёт `value` 23 бита. Для v0.1 генерация tape обязана отказать **по имени**, если:

- индекс записи в tape `≥ 2^23` (8 388 608 токенов);
- `offset`, `колонка` или `длина` `≥ 2^23` кодпоинтов;
- кодпоинт `≥ 2^21` (Unicode-максимум `0x10FFFF` = 1 114 111 < 2 097 152 — граница с запасом);
- `лекс_длина` не помещается в 23 бита (практически недостижимо, но проверяется, а не
  предполагается).

Это **ужесточение** прежних 2^24: 23 бита нужны, чтобы 5-битный `tag` и 24-битный `pos` влезли в
52. Для v0.1 8M токенов/кодпоинтов достаточно; превышение — отказ, а не усечение. Не «обрежем и
поедем»: усечение позиции — тихая ложь D4/D5. Код отказа — P2; здесь зафиксировано **требование**
отказа, а не его номер.

## 2. Упаковка шага: 5 + 23 + 24 = 52 бита (доказано)

### 2.1. Формула

```
R = tag · 2^47 + value · 2^24 + pos
```

- `tag` — 5 бит, 32 шага (0..31);
- `value` — 23 бита (кодпоинт/offset/token index/счётчик);
- `pos` — 24 бита (индекс записи token tape или позиция следующего шага).

`tag` — **шаг протокола**, не «вид токена»: вид токена в tape — обычное число, не 5 бит.

### 2.2. Доказательство точности

Максимум при `tag = 31`, `value = 2^23 − 1`, `pos = 2^24 − 1`:

```
max = 31·2^47 + (2^23 − 1)·2^24 + (2^24 − 1)
    = 31·2^47 + 2^47 − 2^24 + 2^24 − 1
    = 32·2^47 − 1
    = 2^52 − 1
    < 2^53.
```

`2^52 − 1` — целое, меньше `2^53`, поэтому `Number` представляет его **точно** (мантисса 53
бита). 5 бит дают 32 шага, 23 бита — `value`, 24 — `pos`; сумма 52, запас до 53 — один бит.
Прежняя 4+24+24 (`max = 2^52 − 1`) была верна для 16 шагов, но 16 шагов **полны**, а протокол
P2/P3 требует больше. Ложная формула `tag·2^32 + value·2^16 + pos` не используется.

**Проверка числа шагов.** Список §3.3 — **24** шага. `2^5 = 32 ≥ 24`; 5 бит хватает, 6 бит
**не нужны**. Если будущий шаг сделает 33-й, 6 бит дадут `6+23+24 = 53` — ровно граница
`2^53 − 1`: число ещё точно, но запаса нет. Тогда сначала уменьшают `value` до 22 бит
(`6+22+24 = 52`, значения до 4M) или заводят второй скаляр (D49 — названная цена), а не
«упихивают» молча.

### 2.3. Распаковка

```
pos   = R % 2^24
R1    = R нацело 2^24
value = R1 % 2^23
tag   = R1 нацело 2^23
```

`нацело` и `%` — int64 (D52), не 32-битные побитовые операции JS. Все промежуточные значения
`< 2^53`, поэтому точность сохраняется. `2^24 = 16 777 216`, `2^23 = 8 388 608` — точные степени
двойки.

### 2.4. Проверка границ при генерации

Перед упаковкой:

- `tag ≤ 31`;
- `value < 2^23`;
- `pos < 2^24`;
- `value` как кодпоинт `< 2^21`; как offset/column/length/token index `< 2^23`.

Нарушение — **названный отказ** на генерации tape, не усечение и не «повезло». Иначе `R`
выйдет за доказанный диапазон, и `Number` начнёт округлять — тихая ложь.

## 3. Протокол событий: `главная` пишет, handlers возвращают скаляр

### 3.1. Форма

```
главная (depth 0/1)                          handlers (depth 2+)
─────────────────────────────────────        ─────────────────────────────
arena AST-ленты (Список<Число>)              читают токены
стек фреймов (Список<Число>, верх)           возвращают R
цикл:
  R = разобрать_программу(токены, поз, кадр)
  (tag, value, pos2) = распаковать(R)
  система.массив.добавить(лента, событие)
  поз = pos2
```

`R` несёт **шаг** протокола: `tag` — что делать, `value` — что записать/на что сослаться,
`pos` — куда идти дальше. Концептуальная пара `(соб, поз2)` из постановки — это `tag/value` и
`pos` одного `R`, а не `Результат`-пара: пара занимает канал `%b[8]`/`%b[9]` и в бюджете точки
входа не помещается (D49, названная уступка). Один скаляр — не «упрощение», а измеренная форма.

**Handlers не пишут в ленту и не трогают арену.** Они читают `токены` (параметр-список) и
возвращают `Число`. Всё, что пишет, — `главная`. Это не workaround: при такой форме арена
остаётся в плоскости точки входа, и D12-2 (SIGILL при арене в callee) не наступает. Handlers
малы (≤3 аргумента, D43-форма), поэтому D48 (малые процедуры) выполняется.

### 3.2. Стек фреймов

`стек` — `Список<Число>`, предзаполненный `[TOP]`; `верх` — индекс последнего кадра.

- push: `система.массив.добавить(стек, кадр)`; `верх = верх + 1`;
- pop: `верх = верх - 1` (элемент не удаляется — список только растёт);
- текущий кадр: `стек[верх]`.

Список, а не отдельные переменные: кадры вкладываются (в `P3` — `если`/`пока`/`вызов`), и
фиксированный набор локальных переменных кончился бы на первом вложенном блоке. `верх` — один
локальный; `стек[верх]` читается в `главная`, не в handler'е.

| Код | Кадр | Когда |
|---:|---|---|
| 0 | `TOP` | верхний уровень файла |
| 1 | `PROC_HEADER` | после имени процедуры, до заголовка |
| 2 | `PROC_BODY` | тело процедуры |
| 3 | `PARAM` | параметр |
| 4 | `IF_THEN` | ветвь `тогда` |
| 5 | `IF_ELSE` | ветвь `иначе` |
| 6 | `WHILE_BODY` | тело `пока` |
| 7 | `RETURN` | выражение `вернуть` |
| 8 | `CALL_ARGS` | аргументы вызова |
| 9 | `EXPR` | выражение |
| 10 | `TYPE` | тип |
| 11 | `PAREN` | скобка |
| 12 | `LIST` | список |
| 13 | `INDEX` | индексация |
| 14 | `ASSIGN` | присваивание |
| 15 | `QUALIFY` | квалификация |
| 16 | `RESUME` | resume-кадр `EXPR` (после вложенного выражения) |

17 кадров; кодов хватает с запасом. `RESUME` нужен там, где выражение вложено в выражение:
вернувшись из внутреннего, `главная` восстанавливает внешний кадр, а не «угадывает» его по
токену.

`главная` по `R`, а не AST-код.

### 3.4. `посл_кон`

`посл_кон` — конец последнего токена: `токены[поз + 2] + токены[поз + 4]`. Один локальный в
`главная` (не стековый). На пике это `+1` живое значение; в P2 он не нужен, в P3 нужен для
`конец <имя>`/`параметр`/`если_конец`. Место — `главная`, потому что handler не имеет права
писать, а `посл_кон` — это позиция для записи.

### 3.5. `добавить` → runtime `система.массив.добавить` в `главная`

Запись в AST-ленту и в стек фреймов идёт **runtime-примитивом**
`система.массив.добавить(лента, элемент)`, а не `Списки.добавить`. Причины названы:

- **D43-библиотека не реализована.** Аудит: «записи в арену в API нет»; `Списки.добавить`
  сегодня — отказ, а не работа. Подставить её — тихая ложь.
- **Runtime-примитив работает в точке входа.** Это измерено лексером (`src/e2k/lexerProgram.ts`,
  D48/D49): `добавить в список элемент` в `главная` понижается и исполняется на модели и железе.
- **В callee запись запрещена** (D43-библиотека или размерный отказ рантайма). Поэтому пишет
  только `главная`; handlers возвращают скаляр.

Это **названное расхождение** с D43: runtime-примитив вместо библиотеки. D43-библиотека —
отдельный атом **после** парсера. Не «фиктивная арена»: список создаётся и живёт в `главная`,
а не подменяется заглушкой.

### 3.6. Backpatch — не в P2/P3

P2/P3 обходятся **lookahead** для `вернуть`/`пусть`: handler возвращает `R.value` = конец
выражения, `главная` пишет pre-order событие с уже известным концом, затем пишет событие
выражения. Заглушка и патч ленты не нужны.

Если в P3 появится конструкция, где конец нельзя узнать без записи (например, вложенный
`пусть` в выражении), это будет **названный стоп**, а не тихая запись `0`; backpatch — отдельный
атом (§5).

## 4. Backpatch: два события — `вернуть` со значением и `пусть`

### 4.1. Факт формата AST 2.1

Событие `вернуть` в `src/compiler-v3/astFormat.ts` пишется так:

```
[8, начало, строка, колонка, <конец>, <hasValue>]
```

То есть **`конец` — пятое поле, `hasValue` — шестое**. Это не «`hasValue`, потом заглушка»:
порядок полей — часть формата, и протокол обязан следовать ему.

Событие `пусть` в AST 2.1:

```
[14, начало, строка, колонка, <конец>, <есть_тип>, имя_длина, ...имя, [тип], <выражение>]
```

`конец` — пятое поле, `есть_тип` — шестое. `конец` локальной = конец выражения/типа, поэтому в
потоке он **неизвестен в момент записи события** — это второе pre-order событие с финальным
концом.

### 4.2. `вернуть` со значением

1. Пишется `8, начало, строка, колонка, 0, 1` — `конец` пока **заглушка 0**.
2. Индекс заглушки (позиция поля `конец` в ленте) кладётся в стек кадров как
   `PATCH = 900 + индекс`.
3. После разбора выражения `посл_кон` (конец последнего токена выражения) пишется в
   `лента[индекс]`; стековый кадр `PATCH` снимается.
4. Патч — `система.массив.установить(лента, индекс, посл_кон)`, глубина 0/1. Не новый носитель,
   не запись в чужую клетку.

`PATCH = 900 + индекс` — **не новый регистр**: стек кадров уже живой, +0 регистров по
конструкции. Индекс — позиция в `лента`, а не в token tape; это разные ленты.

### 4.3. `пусть` (всегда со значением)

1. Пишется `14, начало, строка, колонка, 0, есть_тип` — `конец` пока **заглушка 0**.
2. `PATCH = 900 + индекс` кладётся в стек кадров; имя, тип (если есть), выражение.
3. После выражения `лента[индекс] = посл_кон`; кадр `PATCH` снимается.
4. Патч — тот же механизм, что у `вернуть`; отдельного регистра/носителя нет.

**Порядок полей — не переставлять:** `конец` раньше `есть_тип`; иначе патч попадёт в признак типа.

### 4.4. `вернуть` без значения

Пишется `8, начало, строка, колонка, начало + 7, 0` — `вернуть` занимает 7 кодпоинтов,
конец известен сразу. Заглушки и стекового кадра нет.

### 4.5. Другие pre-order события: почему им не нужен патч

| Событие | Что пишется pre-order | Где настоящий конец | Патч? |
|---|---|---|---|
| `процедура_начало` | `1, start, line, col, start+9` | `процедура_конец` (post-order) | **нет**; `start+9` — конец ключевого слова, не конец узла |
| `действие_начало` | `17, start, line, col, start+8` | `процедура_конец` (post-order) | **нет**; `start+8` — конец `действие` |
| `параметр` | `2, start, line, col`, имя, тип | `end` сразу после типа | **нет** |
| `если_начало` | `5, start, line, col, start+4` | `если_конец` (post-order) | **нет**; `start+4` — конец `если`, не конец узла |
| `вернуть` со значением | `8, start, line, col, 0, 1` | после выражения | **ДА** (или lookahead, §3.6) |
| `вернуть` без значения | `8, start, line, col, start+7, 0` | сразу | **нет** |
| `пусть` | `14, start, line, col, 0, hasType`, имя, [тип], выражение | после выражения/типа | **ДА** (или lookahead) |
| `пока_начало` | `15, start, line, col`, условие | `пока_конец` (post-order) | **нет** |
| `вызов_начало` | `10, start, line, col` | `вызов_конец` (post-order) | **нет** |
| `литерал` / `имя` | `12/13, start, end, line, col` | сразу | **нет** |
| `иначе`, `вызов_оператор` | без поля конца | внутренний/следующий | **нет** |

**Вывод:** pre-order событий, которые пишут **финальный** конец, ровно два — `вернуть` со
значением и `пусть`. P2/P3 закрывают их lookahead-концом из `R.value`; если lookahead
невозможен — backpatch отдельным атомом.

### 4.6. Стоимость backpatch

По конструкции, **не замер**: +5–8 IR на патч, +80–200 байт; `PATCH` в стеке — +0 регистров;
`посл_кон` — +0..1 vreg, пик +0..1. Замер — P3, если backpatch понадобится. Числа не выдаются
за факт.

## 6. Граница: что протокол **не** решает

- **Грамматику** — D56/D57; протокол — транспорт, не грамматика. D56.3/D58 решают состав v0.1.
- **Семантику** — D51/D52; протокол использует, не определяет.
- **Модель/железо** — P2/P3; здесь только требование: числа с модели и железа, иначе D12/СТОП.
- **Реализацию** — P2/P3; здесь спека.
- **Backpatch** — отдельный атом, если P2/P3 его потребуют; сейчас выбран lookahead.
- **D43-библиотеки** — после парсера; `добавить` — runtime-примитив, названное расхождение.
- **`Результат`-пара в entry** — не влезает (D49); `R` — один скаляр, не пара.
