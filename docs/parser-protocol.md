# Протокол парсера v0.1 — token tape, протокол событий, упаковка, post-order (2026-11-10, AST 3.0)

**Статус:** контракт под-атомов P1–P3; **P2 — красный, см. §8**. Реализация P2 —
`.tmp/parser-protocol-probe.p2-red.ts` (218 строк; в HEAD **не** коммитится, потому что P2 не

**Границы этого документа:**

- **Зафиксировано:** поля и stride token tape; фильтрация переводов строк; **упаковка шага —
  31 бит** (`9+5+16`, §2); **форма протокола событий** — `главная` пишет AST-ленту, handlers
  возвращают `R`; 24 шага протокола; стек фреймов; арена только в `главная` (D12-2);
  `добавить` → runtime `система.массив.добавить` в `главная`.
- **Не зафиксировано:** грамматика (D56/D57); семантика (D51/D52); backpatch (P2/P3 его не

  квалифицированный вызов уже в AST). Протокол — не плоский автомат в одной процедуре, а

## 1. Token tape: интерфейс лексер → парсер

### 1.1. Запись

```
[вид, строка, offset, колонка, длина, лекс_длина, cp..., 0]
stride = 7 + лекс_длина
```

| Поле | Смысл | Единица |
|---|---|---|
| `вид` | вид токена (число из реестра лексера) | — |
| `строка` | номер строки исходника, 1-based | строка |
| `offset` | смещение первой кодовой точки токена | **кодпоинты**, 0-based |
| `колонка` | колонка первой кодовой точки, 1-based | **кодпоинты** |
| `длина` | длина токена в исходнике | **кодпоинты** |
| `лекс_длина` | число кодовых точек в `cp...` | кодпоинты |
| `cp...` | кодпоинты лексемы (для строки — декодированное значение) | кодпоинты |
| `0` | терминатор записи (смысла не несёт; держит stride одинаковым) | — |

`offset`/`колонка`/`длина` — **в кодовых точках** (D1), не в байтах и не в UTF-16. Символ вне
BMP — одна позиция, а не две. Парсер не пересчитывает байты.

Заголовок — **6** полей, затем `лекс_длина` кодпоинтов и терминатор. Следующий токен начинается
через `7 + лекс_длина`; это же число двигает `поз` в `главная`. Терминатор не «значение
литерала»: значение числа парсер считает из `cp...` (P2), строковое — из декодированных `cp...`
(§1.2).

### 1.2. Строки декодированы

Для строкового токена `cp...` — **декодированное значение**, как его выдаёт лексер, а не сырой
текст с escape. Парсер **не декодирует** повторно: `\n`, `\"`, `\\` уже раскрыты лексером.
Если лексер отдаёт и сырую, и декодированную форму, в tape едет **декодированная**; сырая не
нужна парсеру и не должна попадать в AST.

### 1.3. Переводы строк отфильтрованы

Tape содержит **только не-`новая_строка`**; `новая_строка` отбрасывается при генерации, а не
пропускается парсером. Это важно: парсер не обязан помнить о переводах строк в каждой ветке.
Позиции (`строка`, `offset`, `колонка`) — **исходные**, они не перенумеровываются после
фильтрации.

Tape заканчивается **ровно одним** `конец_файла`, последним. `конец_файла` — обычная запись
stride 7 с `лекс_длина = 0`; после неё ничего нет.

### 1.4. Границы (названный отказ, не усечение)

Клетки tape — обычные **32-битные знаковые** числа; упаковка шага — 31 бит (§2). Для v0.1 генерация
tape обязана отказать **по имени**, если:

- `offset`, `колонка` или `длина` `≥ 2^31 − 1` (в 32-битное Число не влезает);
- кодпоинт `≥ 2^21` (Unicode-максимум `0x10FFFF` = 1 114 111 < 2 097 152 — граница с запасом);
- **позиция шага** `≥ 2^9 = 512` или **нагрузка** `≥ 2^16 = 65536` (§2.4).

Это **ужесточение** прежних 2^23: 9 бит позиции и 16 бит нагрузки — потому что R обязан влезать в
31 бит, а не в 52 (§2.2). Для v0.1 511 позиций и 65535 нагрузки достаточно; превышение — отказ, а не
усечение. Не «обрежем и поедем»: усечение позиции — тихая ложь D4/D5. Код отказа — P2; здесь
зафиксировано **требование** отказа, а не его номер.

## 2. Упаковка шага: 9 + 5 + 16 = 30 бит, предел 2^31−1 (доказано)

### 2.1. Формула

```
R = поз · 2^21 + тег · 2^16 + значение
```

- `поз` — 9 бит (0..511): **аргумент диспетчера** — куда идти дальше (позиция следующего шага в tape);
- `тег` — 5 бит, 32 шага (0..31);
- `значение` — 16 бит (0..65535): **нагрузка события** — позиция токена, имя, конец.

`тег` — **шаг протокола**, не «вид токена»: вид токена в tape — обычное число, не 5 бит.

### 2.2. Доказательство: 31 бит, а не 52

Максимум при `поз = 511`, `тег = 31`, `значение = 65535`:

```
max = 511·2^21 + 31·2^16 + 65535
    = (2^30 − 2^21) + (2^21 − 2^16) + (2^16 − 1)
    = 2^30 − 1
    = 1 073 741 823 < 2^31 − 1
```

**Число цели — 32-битное знаковое** (`sdivs`/`muls`/`adds`). `2^30 − 1` не трогает знаковый бит и
оставляет целый бит запаса. Прежняя раскладка P2 (`value·2^29 + tag·2^24 + pos`, `R ≤ 2^52 − 1`)
точнá в `Number`, но **на цели переполняется**: уже `поз = 4` даёт `4·2^29 = 2^31` → `r`
отрицателен → индекс `r % 2^24` = `0xFF000052` → адрес `8·0xFF000052 + база` = `0x7f8112a0`;
железо падает кодом **139**, модель петляет (измерено, `docs/hardware-debt.md` §3.193.4). Парсер
v0.1 будет исполняться на той же цели, поэтому шаг **31 бит**, а не 52.

### 2.3. Распаковка

```
поз      = R нацело 2^21
R1       = R % 2^21
тег      = R1 нацело 2^16
значение = R1 % 2^16
```

`нацело` и `%` на цели — `idiv`/`rem` с **отсечением к нулю** (знак по делимому), как в VM
(`src/runtime/vm/interpreter.ts`, ветки `idiv` и `rem`). Для положительного R это совпадает с `Math.trunc`;
`Math.floor` для отрицательных дал бы другое число, поэтому в эталоне — `Math.trunc`.

### 2.4. Проверка границ при генерации

Перед упаковкой:

- `тег ≤ 31`;
- `значение < 2^16` (65536);
- `поз < 2^9` (512);
- `R ≤ 2^31 − 1` (сумма первых трёх уже это гарантирует — проверка оставлена как сторож).

Нарушение — **названный отказ** на генерации шага, не усечение и не «повезло». Иначе `R` выйдет за
31 бит, станет отрицательным, и `r % 2^24` уведёт индекс в дикий адрес.

### 2.5. Ограничение кодировщика e2k: литерал `2^47` не влезает (история)

**Измерено 2026-11-08 (P2).** Предписанная формула `tag·2^47 + value·2^24 + pos` требует литерала
`2^47 = 140 737 488 355 328`. Кодировщик e2k отказывает:

```
«movts»: литерал 140737488355328 не влезает в 32 бита;
64-битная форма (0xdc, два слова литералов) не реализована
```

Это **стена кодировщика**, а не арифметики: 52-битный диапазон раскладывается эквивалентно,
если поставить `tag` в середину:

```
R = value·2^29 + tag·2^24 + pos
```

`value` — биты 29..51 (23 бита), `tag` — 24..28 (5 бит), `pos` — 0..23 (24 бита). Максимум
`(2^23−1)·2^29 + 31·2^24 + (2^24−1) = 2^52−1 < 2^53` — **та же точность и тот же счёт 5+23+24**,
а все литералы (`2^29`, `2^24`, `32`) влезают в 32 бита. Распаковка:
`pos = R % 2^24`, `tag = (R // 2^24) % 32`, `value = (R // 2^24) // 32`.

**Отозвано в §2 (2026-11-09):** эта раскладка не годится как протокол для цели — она даёт R > 2^31.
Оставлена как замер кодировщика; действующая раскладка — §2.1–§2.4 (31 бит).

Это **названное расхождение с формулой §2.1**, а не тихая замена: формула §2.1 остаётся
математическим контрактом; реализация P2 использует эквивалентную раскладку полей, потому что
прямая запись `2^47` не кодируется. Если кодировщик получит 64-битную форму литерала, формулу
можно вернуть без смены 52-битного контракта.

## 3. Протокол событий: `главная` пишет, handlers возвращают скаляр

### 3.1. Форма

```
главная (depth 0/1)                          handlers (depth 2+)
─────────────────────────────────────        ─────────────────────────────
arena AST-ленты (Список<Число>)              читают токены
стек фреймов (Список<Число>, верх)           возвращают R
цикл:
  R = разобрать_программу(токены, поз, кадр)
  (tag, value, pos2) = распаковать(R)
  система.массив.добавить(лента, событие)
  поз = pos2
```

`R` несёт **шаг** протокола: `tag` — что делать, `value` — что записать/на что сослаться,
`pos` — куда идти дальше. Концептуальная пара `(соб, поз2)` из постановки — это `tag/value` и
`pos` одного `R`, а не `Результат`-пара: пара занимает канал `%b[8]`/`%b[9]` и в бюджете точки
входа не помещается (D49, названная уступка). Один скаляр — не «упрощение», а измеренная форма.

**Handlers не пишут в ленту и не трогают арену.** Они читают `токены` (параметр-список) и
возвращают `Число`. Всё, что пишет, — `главная`. Это не workaround: при такой форме арена
остаётся в плоскости точки входа, и D12-2 (SIGILL при арене в callee) не наступает. Handlers
малы (≤3 аргумента, D43-форма), поэтому D48 (малые процедуры) выполняется.

### 3.2. Стек фреймов

`стек` — `Список<Число>`, предзаполненный `[TOP]`; `верх` — индекс последнего кадра.

- push: `система.массив.добавить(стек, кадр)`; `верх = верх + 1`;
- pop: `верх = верх - 1` (элемент не удаляется — список только растёт);
- текущий кадр: `стек[верх]`.

Список, а не отдельные переменные: кадры вкладываются (в `P3` — `если`/`пока`/`вызов`), и
фиксированный набор локальных переменных кончился бы на первом вложенном блоке. `верх` — один
локальный; `стек[верх]` читается в `главная`, не в handler'е.

| Код | Кадр | Когда |
|---:|---|---|
| 0 | `TOP` | верхний уровень файла |
| 1 | `PROC_HEADER` | после имени процедуры, до заголовка |
| 2 | `PROC_BODY` | тело процедуры |
| 3 | `PARAM` | параметр |
| 4 | `IF_THEN` | ветвь `тогда` |
| 5 | `IF_ELSE` | ветвь `иначе` |
| 6 | `WHILE_BODY` | тело `пока` |
| 7 | `RETURN` | выражение `вернуть` |
| 8 | `CALL_ARGS` | аргументы вызова |
| 9 | `EXPR` | выражение |
| 10 | `TYPE` | тип |
| 11 | `PAREN` | скобка |
| 12 | `LIST` | список |
| 13 | `INDEX` | индексация |
| 14 | `ASSIGN` | присваивание |
| 15 | `QUALIFY` | квалификация |
| 16 | `RESUME` | resume-кадр `EXPR` (после вложенного выражения) |

17 кадров; кодов хватает с запасом. `RESUME` нужен там, где выражение вложено в выражение:
вернувшись из внутреннего, `главная` восстанавливает внешний кадр, а не «угадывает» его по
токену.

### 3.4. `посл_кон`

`посл_кон` — конец последнего токена: `токены[поз + 2] + токены[поз + 4]`. Один локальный в
`главная` (не стековый). На пике это `+1` живое значение; в P2 он не нужен, в P3 нужен для
`конец <имя>`/`параметр`/`если_конец`. Место — `главная`, потому что handler не имеет права
писать, а `посл_кон` — это позиция для записи.

### 3.5. `добавить` → runtime `система.массив.добавить` в `главная`

Запись в AST-ленту и в стек фреймов идёт **runtime-примитивом**
`система.массив.добавить(лента, элемент)`, а не `Списки.добавить`. Причины названы:

- **D43-библиотека не реализована.** Аудит: «записи в арену в API нет»; `Списки.добавить`
  сегодня — отказ, а не работа. Подставить её — тихая ложь.
- **Runtime-примитив работает в точке входа.** Это измерено лексером (`src/e2k/lexerProgram.ts`,
  D48/D49): `добавить в список элемент` в `главная` понижается и исполняется на модели и железе.
- **В callee запись запрещена** (D43-библиотека или размерный отказ рантайма). Поэтому пишет
  только `главная`; handlers возвращают скаляр.

Это **названное расхождение** с D43: runtime-примитив вместо библиотеки. D43-библиотека —
отдельный атом **после** парсера. Не «фиктивная арена»: список создаётся и живёт в `главная`,
а не подменяется заглушкой.

### 3.6. Backpatch — не в P2/P3

P2/P3 обходятся **lookahead** для `вернуть`/`пусть`: handler возвращает `R.value` = конец
выражения, `главная` пишет pre-order событие с уже известным концом, затем пишет событие
выражения. Заглушка и патч ленты не нужны.

Если в P3 появится конструкция, где конец нельзя узнать без записи (например, вложенный
`пусть` в выражении), это будет **названный стоп**, а не тихая запись `0`; backpatch — отдельный
атом (§5).

## 4. Backpatch: два события — `вернуть` со значением и `пусть`

### 4.1. Факт формата AST 2.1

Событие `вернуть` в `src/compiler-v3/astFormat.ts` пишется так:

```
[8, начало, строка, колонка, <конец>, <hasValue>]
```

То есть **`конец` — пятое поле, `hasValue` — шестое**. Это не «`hasValue`, потом заглушка»:
порядок полей — часть формата, и протокол обязан следовать ему.

Событие `пусть` в AST 2.1:

```
[14, начало, строка, колонка, <конец>, <есть_тип>, имя_длина, ...имя, [тип], <выражение>]
```

`конец` — пятое поле, `есть_тип` — шестое. `конец` локальной = конец выражения/типа, поэтому в
потоке он **неизвестен в момент записи события** — это второе pre-order событие с финальным
концом.

### 4.2. `вернуть` со значением

1. Пишется `8, начало, строка, колонка, 0, 1` — `конец` пока **заглушка 0**.
2. Индекс заглушки (позиция поля `конец` в ленте) кладётся в стек кадров как
   `PATCH = 900 + индекс`.
3. После разбора выражения `посл_кон` (конец последнего токена выражения) пишется в
   `лента[индекс]`; стековый кадр `PATCH` снимается.
4. Патч — `система.массив.установить(лента, индекс, посл_кон)`, глубина 0/1. Не новый носитель,
   не запись в чужую клетку.

`PATCH = 900 + индекс` — **не новый регистр**: стек кадров уже живой, +0 регистров по
конструкции. Индекс — позиция в `лента`, а не в token tape; это разные ленты.

### 4.3. `пусть` (всегда со значением)

1. Пишется `14, начало, строка, колонка, 0, есть_тип` — `конец` пока **заглушка 0**.
2. `PATCH = 900 + индекс` кладётся в стек кадров; имя, тип (если есть), выражение.
3. После выражения `лента[индекс] = посл_кон`; кадр `PATCH` снимается.
4. Патч — тот же механизм, что у `вернуть`; отдельного регистра/носителя нет.

**Порядок полей — не переставлять:** `конец` раньше `есть_тип`; иначе патч попадёт в признак типа.

### 4.4. `вернуть` без значения

Пишется `8, начало, строка, колонка, начало + 7, 0` — `вернуть` занимает 7 кодпоинтов,
конец известен сразу. Заглушки и стекового кадра нет.

### 4.5. Другие pre-order события: почему им не нужен патч

| Событие | Что пишется pre-order | Где настоящий конец | Патч? |
|---|---|---|---|
| `процедура_начало` | `1, start, line, col, start+9` | `процедура_конец` (post-order) | **нет**; `start+9` — конец ключевого слова, не конец узла |
| `действие_начало` | `17, start, line, col, start+8` | `процедура_конец` (post-order) | **нет**; `start+8` — конец `действие` |
| `параметр` | `2, start, line, col`, имя, тип | `end` сразу после типа | **нет** |
| `если_начало` | `5, start, line, col, start+4` | `если_конец` (post-order) | **нет**; `start+4` — конец `если`, не конец узла |
| `вернуть` со значением | `8, start, line, col, 0, 1` | после выражения | **ДА** (или lookahead, §3.6) |
| `вернуть` без значения | `8, start, line, col, start+7, 0` | сразу | **нет** |
| `пусть` | `14, start, line, col, 0, hasType`, имя, [тип], выражение | после выражения/типа | **ДА** (или lookahead) |
| `пока_начало` | `15, start, line, col`, условие | `пока_конец` (post-order) | **нет** |
| `вызов_начало` | `10, start, line, col` | `вызов_конец` (post-order) | **нет** |
| `литерал` / `имя` | `12/13, start, end, line, col` | сразу | **нет** |
| `иначе`, `вызов_оператор` | без поля конца | внутренний/следующий | **нет** |

**Вывод:** pre-order событий, которые пишут **финальный** конец, ровно два — `вернуть` со
значением и `пусть`. P2/P3 закрывают их lookahead-концом из `R.value`; если lookahead
невозможен — backpatch отдельным атомом.

### 4.6. Стоимость backpatch

По конструкции, **не замер**: +5–8 IR на патч, +80–200 байт; `PATCH` в стеке — +0 регистров;
`посл_кон` — +0..1 vreg, пик +0..1. Замер — P3, если backpatch понадобится. Числа не выдаются
за факт.

## 9. P2a-retry: упаковка 31 бит — P2a 43 клетки на ЖЕЛЕЗЕ (2026-11-09, §3.193.5)

**Что было.** P2a (одна петля диспетчера + писатели, `parser-protocol-probe.ts`) на железе падал
кодом **139** на `0x7f8112a0`, модель петляла. Причина — не окно и не codegen, а **упаковка шага**:
`R = значение·2^29 + тег·2^24 + позиция` при `поз ≥ 4` даёт `R ≥ 2^31`; Число цели — 32-битное
знаковое, `r` становится отрицательным, `r % 2^24 = 0xFF000052`, адрес `8·0xFF000052 + 0x111008 +
8 = 0x7f8112a0` (`docs/hardware-debt.md` §3.193.4). `%` и `нацело` здесь **верны** — измерено на
железе и модели одинаково (`-16777134`, `-117`, `-21`) и совпадает с VM (`idiv`/`rem` — отсечение
к нулю).

**Что сделано.** Раскладка переведена на **31 бит** (§2.1–§2.4): `R = поз·2^21 + тег·2^16 +
значение`, максимум `2^30 − 1 < 2^31 − 1`. В генераторе: возвраты обработчиков собирают
`R` в новом порядке полей (нагрузка — внизу, позиция диспетчера — сверху), диспетчер читает
`поз = r нацело 2^21`, `тег = (r нацело 2^16) % 32`, `значение = r % 2^16`. Эталон `распаковатьШаг`
— `Math.trunc` (не `Math.floor`). Сторож — `src/compiler-v3/parser-protocol-probe.test.ts`
(5 проверок: границы полей, круг «туда-обратно», отказы по имени, новые веса в генераторе, AST 43).

**Измерено.**

| где | вывод | код |
|---|---|---|
| **E8C2 (железо)** | **43 клетки**, побайтово = эталон | **0** |
| модель QEMU | 43 клетки, побайтово = эталон | 0 |
| эталон `эталоннаяЛента()` | 43 клетки | — |
| **до правки** (ELF `289345f6…`) | — | **139** на `0x7f8112a0` |

Самопокраснение: тот же образ **до** правки на железе даёт 139 — сторож ловит именно упаковку, а не
«что-то ещё». **Это число (43) — оракул AST v0.1; литерал `42` в исходнике P2a — клетки `52 50`
ленты, а не счётчик.** N = 1 (P2a). Дрейф codegen — 0 %: `src/e2k/**` не тронут.

**Диагноз «W2 = порт» отозван (2026-11-09, docs-only).** Петля модели на прежнем образе была
**следствием** нашей упаковки (дикий адрес от отрицательного `r`), а не дефектом порта: на исправленном
образе модель **не петляет** (43 клетки = эталон). D-3 в `tools/qemu-e2k/DEVIATIONS.md` ждёт отдельного
docs-атома (этот атом запрещал `tools/qemu-e2k/**`). Случай 94 `docs/verification-debt.md`.

## 10. P3a — названные пробелы (2026-11-09, не чинились)

P3a (шаги `ЕСЛИ_НАЧАЛО`, `ИНАЧЕ`, `ИНАЧЕ_ЕСЛИ`, `ЕСЛИ_КОНЕЦ`, `ПОКА_НАЧАЛО`, `ПОКА_КОНЕЦ`) **не сдан**;
шаги 4–9 в §3.3 — **спека**, а не реализация. Ниже — четыре пробела задания, названные, а не обойдённые.

### 10.1. Выражения не покрыты

P2a обходилась литералом (`вернуть 42`). P3a требует `если x > 0` — **имя** и **оператор сравнения**. В
шагах протокола нет шага «выражение»: `ИМЯ` (15) в P2a — объявление параметра, `ЛИТЕРАЛ` (14) —
литерал; коды AST для `x` и `>` обработчики писать умеют, но **шага**, который бы вызвал их для
условия, в задании нет. «6 новых тегов» этого не решают: либо `ЕСЛИ_НАЧАЛО`/`ПОКА_НАЧАЛО` пишут условие
**целиком** по полю `поз_условия` (тогда шаги `>`, `имя` не нужны, но условие ограничено формой
`левый > правый`), либо нужны ещё шаги — и тогда «6 тегов» становится ≥ 8. Выбор заданием **не сделан**.

### 10.2. Фреймы: «как P2a» — противоречие

§3.3 предполагает стек фреймов (`IF_THEN`/`IF_ELSE`/`WHILE_BODY`, replace/pop). P2a прошла **без**
стека: одна петля диспетчера, линейный поток. Задание P3a говорит «диспетчер + фреймы (как P2a)» — но у
P2a фреймов **не было**. Для вложенности `если` внутри `пока` нужен либо фрейм, либо бесстековая форма:
`конец` + имя следующего токена (`если`/`пока`/имя процедуры) решает, какой блок закрывается, без
состояния. Обе формы названы; какая выбрана — не задано, а это влияет на `peak` (стек — живые значения
через всю петлю).

### 10.3. Упаковка трёх полей не доказана

P2a-формула — `R = поз·2^21 + тег·2^16 + значение` (9+5+16). У `ЕСЛИ_НАЧАЛО` **три** поля:
`[тег, поз_если, поз_условия]`. 9-битного поля на две позиции не хватает; 16-битное — хватает (позиция
≤ 511), то есть `R = поз·2^21 + тег·2^16 + поз_условия` формально возможно, но **ширины не названы** и
**границы не проверены** — урок D52 («53 бита доказаны при ложных посылках») здесь повторяется один в
один. Retry обязан: назвать ширины, доказать `R < 2^31` на **худшей** ленте, дать отказ по имени при
выходе за границу.

### 10.4. Тег-резерв: 14 из 32, но не на всё

P2a 8 + P3a 6 = **14 ≤ 32**. Дальше P3b (`пусть`, `ПРИСВАИВАНИЕ`) — +2 → 16, P3c (`ВЫЗОВ_НАЧАЛО`/
`ВЫЗОВ_КОНЕЦ`, `СПИСОК_НАЧАЛО`/`КОНЕЦ`, `ИНДЕКСАЦИЯ`, `КВАЛИФИКАЦИЯ`) — ещё 4–6 → 20–22. Struct
literal, `.`-поле, модули/перечисления и `разбор` (коды AST 18–20, 44) **в 32 не влезают** без
расширения поля тега до 6 бит (`тег > 32` в §1 задания названо, но бюджет не посчитан). Решение — до
P3b, а не после.

## 11. P3a: измерено — плоская форма, 14 тегов, глубина 1–2 на модели и на железе

**Решения по §10 приняты владельцем (карт-бланш 2026-11-09) и здесь исполнены, а не описаны.**

- **Теги — 14 из 32** (P2a 8 + `ЕСЛИ_НАЧАЛО` 4, `ИНАЧЕ` 5, `ИНАЧЕ_ЕСЛИ` 6, `ЕСЛИ_КОНЕЦ` 7,

- **Фреймов нет** (§10.2 решён в пользу бесстековой формы): `конец` + имя следующего токена

  пишет операнды вторым разом, а вложенность не требует стека.

- **Упаковка (§10.3) не понадобилась:** `R` несёт одно поле `значение` — позицию токена `если`/`пока`
  **или** вычисленный `конец` блока; второго поля нет, ширины прежние 9+5+16, `R ≤ 2^30−1`.

**Стена глубины: писатель списка на глубине ≥ 2 зацикливает МОДЕЛЬ (новый замер).** Пробой на
модели измерено: `Списки.установить` из вызываемой (глубина 2) не даёт ни выхода, ни исключения за
90 с, тогда как та же запись на глубине 1 возвращает значение, а чтение на глубине 2 работает. Тот же
класс на ЖЕЛЕЗЕ завершается (прецедент A4, §3.137.5) — то есть это стена **модели**, а не байтов.
Поэтому принята форма: **все записи — на глубине 1** (в `главная` или в писателях, которые она
вызывает), обработчики глубины 2 только читают ленту и возвращают `R`.

**Второй замер той же природы: вложенный вызов в аргументе на цели не исполняется.** Запись
`записать_вид_операнда(лента, разобрать_право(лента, поз), индекс)` падала на модели (исключение

аргументе (`Списки.установить(…, разобрать_код_оператора(…))`) работает. Обойдено без правки
кодогена: два «правых» писателя (`записать_вид_правого`, `записать_тело_правого`) вычисляют позицию
правого операнда сами, без вложенного вызова.

## 13. P3c: вызов, квалификация, приоритеты — семантика ДА, протокол STOP на окне

**Семантика P3c снята фактом (не «работает» целиком):**

- `parserV01` на `2 + 3 * 4` даёт корень `+` с правым ребёнком `*` — это `2 + (3 * 4)`.
  Исходник на модели возвращает **14**; `(2 + 3) * 4` дало бы 20.
- `г(5)` при `г(х) = х * 2` возвращает **10** (две процедуры, вызов в выражении).
- `Печать.число(42)` **разбирается** (AST `квалифицированный_вызов`), но понижение
  отказывает: `OSN-LOW-003 … «Печать.число»: у рантайма массивов нет такой операции`.
  Это **названный пробел lowering**, отдельный атом; в P3c он не «работает».

**Протокольная проба P3c — STOP на геометрии окна, не на тегах.** Два списка
(`лента` токенов и `рамки` стека обхода) держат в `главная` **12 живых отрезков** при
**9 свободных** клетках (`%b[0..8]`); `%b[9]` занят остатком (`IR.rem`), а блок
рантайма массивов точки входа стоит в `%b[10..14]` и пул не отнимает. Отчёт:
`раскладка по отрезкам невозможна: … живы 12 отрезков, свободных регистров 9`.

**Почему «обход в callee depth 1» не спасает.** `CALLEE_REGISTERS` — `%b[8..15]` без
`%b[12]`, то есть **7** клеток, а не 16; блок рантайма вызываемой — **3**
(`CALLEE_ARRAY_BLOCK_SIZE`), остаётся **4 свободных**. Обход с лентой, стеком и
временными в 4 клетки не влезает. Запись `a[0] = 7` на глубине 1 работает потому, что
несёт **одну** клетку значения, а не 12 живых.

**Один список вместо двух — хуже.** Попытка (лента 256, стек в хвосте 240..255,
`рамки` удалён, наполнение через `Списки.создать` + `Списки.установить`) дала **17
живых** и `вытеснение не минимально: значений в память нужно больше 8`: наполнение и
обход в одной процедуре, а каждый `установить` добавляет временные. WIP-диффы:
`.tmp/p3c-generator-wip.diff`, `.tmp/p3c-single-tape-attempt.diff`; разбор —
`.tmp/p3c-window-diagnose.md`.

**Единственный bounded-путь — (C) упрощение пробы** под конкретные формы P3c (`2 + 3 * 4`
и `г(5)`) без `рамки`/стека, с выносом наполнения ленты. Это **убирает общий обход
выражений**, поэтому решение владельца, а не молчаливая правка. Пока P3c-протокол не
собран, P3d не начинается (зависимость), а AST=эталон для пробы не снят — **коммита
P3c нет**.

## 14. AST 3.0: post-order и P3c заново

Спека формата — §14 `docs/ast-format.md`. Здесь — что это меняет в протоколе.

### 14.1. Что меняется в записи

`главная`-писатель пишет **после** детей: ребёнок разобран — событие записано. Backpatch
(заглушка + патч) в 3.0 **не нужен ни на одном событии**: `вернуть`/`пусть`/`присваивание`
стоят после значения, у `вызова`/`списка` счётчик стоит в закрывающем событии, у `если`/`пока`
условие пишется до `если_начало`/`пока_начало`. Контейнеры сохраняют рамку начало/конец —
поэтому `рамки`/стек обхода из P3c не нужны для **порядка**: порядок задаёт сам рекурсивный
спуск.

**Индексация — не новое в 3.0.** Факт: событие `индексация` (код 39) есть уже в 2.0
(`src/compiler-v3/astFormat.ts`, оракул `astFormat.test.ts` 2.0-редакции). Утверждение §13/P4
«в AST 2.1 нет события индексирования» — **устарело**: 3.0 меняет только его место (после базы
и индекса). Блокер P4 из-за индексации снимается не форматом, а понижением `база[и]`.

### 14.2. P2a/P3a/P3b: эталоны обновлены

Длины лент те же (43 / 86 / 113 / 141 / 85): клеток столько же, изменился **порядок**. Тест
`parser-protocol-probe.test.ts` держит длины и коды; QEMU-шлюз P3b сверяет ленту побайтово,
поэтому генератор P3b обязан писать post-order (§14.3). Цепочка `иначе если` в 3.0 теряет
поле `конец` у события 40 (конец берётся из `если_конец`); в P2a/P3a/P3b её нет.

### 14.3. P3c: рекурсивный спуск, 4 уровня, post-order

Цель — снять STOP §13 не «упрощением пробы», а форматом: писать детей до родителя и не
патчить. Уровни: `главная` (depth 0) вызывает `разобрать_выражение` (depth 1), та —
`разобрать_слагаемое` (depth 2), та — `разобрать_множитель` (depth 3). Уровни 1–3 **только
читают** токенную ленту и возвращают `R`; пишет `главная` (или depth-1 писатель — решается
замером, не словом). Глубина записи ≥ 2 в модели зацикливается (замер 2026-10-29,
`OSN-LOW-004`), поэтому запись остаётся на depth ≤ 1.

**Замер P3b после перехода на post-order (2026-11-10) — STOP на двух клетках, СНЯТ тем же днём.**
Генератор P3b обновлён на post-order, прогон дал 83/85: две клетки — первые события ветвей
`иначе если` — писались адресом элемента списка (1179656) вместо значения. Причина оказалась в
плоскости оболочки (D35, «clobber-boundary»), правка легла в `src/e2k/**`, и **P3b снова 85/85**
(`src/e2k/parserProtocolP3b.test.ts`: проба печатает эталон, `+` = 8, `-`/`*` = 14). Числа и
разбор — §15.1.

## 15. P3c: что измерено и где стена (2026-11-10)

рантайма массивов (`%b[10]`, `%b[11]`, `%b[13]`) → **свободно 12**. ВЫТЕСНЕНИЕ В ВЫЗЫВАЕМОЙ ЗАПРЕЩЕНО

(%b[0]…%b[8]); вытеснять больше нечего». Это ровно тот критерий STOP, который атом задал сам:
**peak > 10**.

Структурная причина, а не «не дожали»: событие 3.0 на литерал — это 8 клеток ленты, и две из них
требуют СУММЫ двух чтений (`конец = начало + длина`), а `Списки.установить(лента, индекс + k, …)`
считает индекс и значение одновременно; в вызываемой это 5–6 одновременных значений плюс четыре
постоянных (лента, индекс, т, ожидающий оператор) — 9 клеток только «постоянных», и на сумме с
вызовом лимит 12 исчерпан. У точки входа на цепочку `+`/`-` нужно шесть постоянных (начало
выражения, начало группы, последний лист, ожидающий оператор, `индекс`, `ток`) плюс её собственные
`лента`/`тег`/`r` — 9, уже потолок.

### 15.3. Вывод и что из этого следует

* **Спуск** (4 уровня, рекурсивный, чтение) — работает и проверен на модели, N = 2.
* **Писатель** post-order событий at depth ≤ 1 — в бюджет не влезает; STOP по собственному критерию
  атома (peak 15–16 > 10). Требуется либо другой формат события (без суммы чтений, без копирования
  текста в вызываемой), либо расширение бюджета вызываемой — это работа по `src/e2k/**` и по
  масштабу ближе к VLIW-перестройке, чем к шагу протокола.
* **D48 работает для базового протокола** (P2a/P3a/P3b — зелены, P3b 85/85 после post-order).
  Отказ P3c не отменяет ни одного из этих шагов и не трогает их числа.
* Отказ `OSN-LOW-003` в пробе закреплён тестом: стена названа и не «обойдена» упрощением ленты.

## 17. AST 3.1: лёгкое событие — замер бюджета (2026-11-10)

Атом «AST 3.1 + entry refactor» предложил два уровня облегчения события. Замер сделан ДО миграции
формата, на той форме, которую писатель писал бы на самом деле (`.tmp/p3c31-budget.ts`,
`allocateProgram` с `collectAnalysis`; бюджет окна измерен в §15.2: вызываемая 12, точка входа 11).

| архитектура и форма события | писатель (depth 1, бюджет 12) | точка входа, цепочка `+`/`-` (бюджет 11) |
|---|---|---|
| **групповой** писатель, форма 3.0 (как P3b) | **16** (peak 23) — отказ | **13–14** — отказ |
| **по событию** (`выписать_X` на одно событие, рассылка из точки входа), форма 3.0 | **12** — влезает ровно | **8** — влезает |
| то же, **A1** (`конец` убран: `тег, начало, строка, колонка, длина, …`) | **12** | **8** |
| то же, **A2** (`тег, индекс_токена`) | **10** — запас 2 клетки | **7** |

Отказов **0** во всех вариантах «по событию». Рычаг оказался **архитектурным**, а не форматным: сама
по себе рассылка «одно событие — один вызов писателя» снимает стену 16 → 12 и 13–14 → 8, потому что
постоянное состояние группы (`начало группы`, `последний лист`, `ожидающий оператор`) переезжает из
вызываемой в точку входа, где бюджет шире. Формат A1 не добавляет ничего сверх этого (12/8), а **A2
даёт запас в две клетки** (10/7) — это и есть настоящий уровень «лёгкого события», а не A1.

Порядок атома («A1, потом A2 если мало») по факту замера переставлен: A1 **не нужен** как отдельный
шаг (12 = 12 без запаса), ценность имеет сразу **A2** — две клетки запаса и вдвое меньше клеток ленты
на событие.

**Чего нет.** Сама переделка пробы на «одно событие — один вызов» (писатели по видам события плюс
рассылка из точки входа с отложенным оператором) и, если нужен запас, A2 в `astFormat.ts`
(`[тег, индекс_токена]`, читатель берёт `начало/длина/текст` из ленты токенов) — работа, которая
затрагивает эталоны P2a/P3a/P3b и формулы клеток в четырёх генераторах проб. В отведённое окно она не
влезла: сделана её решающая часть — замер бюджета и закрепление чисел тестом
(`src/e2k/parserProtocolP3c31Budget.test.ts`, 4 проверки, живёт в полном прогоне, потому что модели не
нужна). Поэтому P3c остаётся **STOP**, но STOP назван **ограниченной работой по архитектуре пробы**
(см. `docs/verification-debt.md`, случай 99), а не VLIW-треком: замер прямо показывает, что бюджет
сходится.

**Чем стережётся сейчас.** `src/e2k/parserProtocolP3c.test.ts` — стена 3.0 названа отказом
`OSN-LOW-003` (не пропуск), эталон 69 клеток и работающий спуск (33 на модели, N = 2) — зелены.
## 18. P3c: per-event писатели — замер на настоящем дереве (2026-11-10)

Проба переписана на `per-event` архитектуру (писатель на вид события, рассылка из точки входа),
group writer удалён. Замер шёл через НАСТОЯЩИЙ конвейер (`parseV3` → `loweredProgram`), а не через
`allocateProgram` изолированно, и он развёл два факта, которые прежний замер (§17) смешивал.

**Факт 1: точка входа теперь влезает.** Цепочка из шести значений (`т`, `нэ`, `оп`, `индекс`, `ток`,
`лента`) — границы операндов не держатся в переменных, а ПЕРЕСЧИТЫВАЮТСЯ чтением ленты
(`начало_группы`, `лист_перед`, обе — read-only) — даёт `ok=true`, peak 18, live 11 против 9
свободных клеток `%b[0..8]`. Прежний вид цепочки (`гн`, `кг`, `посл`, `зн`, `оп`, `пара`) отказывал:
«в тесный момент живы 11 отрезков, свободных регистров 9 … вытеснять больше нечего».

**Факт 2: писатели НЕ влезают, и не по числу живых, а по базе рантайма.** В настоящем конвейере
КАЖДЫЙ писатель события отказал `OSN-LOW-003` («раскладка не выдала базу блока рантайма, операнд 6
носителя»): `выписать_литерал`, `выписать_имя`, `выписать_плюс`, `выписать_минус`,
`выписать_умножить`, `выписать_разделить`, `выписать_вернуть`. Причина: событие — это 4–8 вызовов
`Списки.установить`, а каждый вызов требует базу блока рантайма массивов (три клетки) ПЛЮС живые
значения; в окне вызываемой `%b[8..23]` (12 свободных) база и значения вместе не помещаются.
Замер `allocateProgram` без полного конвейера (§17) этого не показывал, потому что он не требовал
базу для каждого носителя.

**Что это меняет в выводе §17.** Рычаг «архитектура, а не формат» подтверждён для ТОЧКИ ВХОДА, но
писатель события по-прежнему упирается — и упирается не в формат события, а в то, что событие
пишется несколькими вызовами рантайма. Отсюда следует направление, названное честно: писать событие
ОДНИМ носителем (или убрать `Списки.установить` из писателя — например, отдавать событие накоплением
в `лента` без промежуточных вызовов), либо расширить окно вызываемой под базу рантайма. Оба пути —
работа по `src/e2k/**` (запрещена в этом атоме) или новая форма носителя, то есть решение владельца.

**Что в дереве.** Проба оставлена в прежней (P3b-совместимой) редакции, group writer не удалён —
иначе дерево стало бы красным без названного отказа. Разведка per-event цепочки — этот раздел и
`.tmp/p3c-branchpeak.ts` / `.tmp/p3c-branch2.txt`.

## 19. P3c ЗЕЛЁН: причина стены §18 найдена замером, фикс — в пробе (2026-11-10)

### 19.1. Диагноз: база выдаётся ОДИН раз на процедуру, и стена — не она

§18 утверждал, что «каждый `Списки.установить` требует базу блока рантайма массивов». Это **неверно**,
и замер это развёл (`.tmp/p3c-writer-diagnose.md`, `.tmp/p3c-report.ts` — оба через настоящий конвейер
`parseV3` → `loweredProgram`, те же `reserved`/`freeFor`/`arrayProcedures`, что в
`src/e2k/guards/loweredUnchecked.ts`):

- `src/e2k/regAlloc.ts#arrayBases` — `arrayBases` живёт по процедурам, а
  `regAlloc.ts#chooseArrayBlock` вызывает `chooseArrayBlock(free, forbidden, ownHalfFrom)` **одну**
  строку на процедуру;
- `src/e2k/programImage.ts#ARRAY_VALUES_CARRIER` — база уезжает в ОДИН носитель
  `ARRAY_VALUES_CARRIER` пролога;
- `src/e2k/predicatePairing.ts#registersOf` для `IR.invoke` базу **не называет вовсе** — её
  подставляет понижение (`arrayRuntime.ts#lowerArrayCall`, `options.base`), то есть для живости её
  не существует.

Значит класс — **(B)**, а не (A) и не (C): база одна, но **значения + три клетки базы не влезают**.
`chooseArrayBlock` ищет три подряд идущие клетки, которых **не коснулось ни одно значение** (ноль и
восемь пишет пролог значений и они живут всю процедуру), в бюджете вызываемой из **15** клеток
(`CALLEE_REGISTERS` = `%b[8..23]` без нуля `%b[12]`; `%b[15]` не закреплён — в пробе нет `создать`).
Различающий замер: простой писатель на 5 записей — `used 9`, база 18; те же 5 записей **с упаковкой
пары** (`нацело 4096` + `% 4096`) — `used 13`, клетки `[9, 23]`, тройки нет, базы нет. `%` — это
`IR.rem`, и он резервирует себе регистр; упаковка стоила ~4 клеток.

### 19.2. Фикс (bounded, в пробе; `src/e2k/**` и VLIW не тронуты)

`программаПротоколаP3cПоСобытиям` (`src/compiler-v3/parser-protocol-probe.ts`) — «по событию, а

| событие `+`/`-` | писатель пишет 4 клетки (`тег, начало, строка, колонка`), `конец` кладёт точка входа `записать_число` |

**Число «210» в отказе читать как «пересекающихся», а не «живых одновременно»:**
`src/e2k/regAlloc.ts#overlaps` считает `overlaps(other, segment)`. Реальная одновременность — `peakLive`.

**Что черновику НЕ мешает (исполнено на модели):** `а[2]` → **30**, `4 == 4`/`4 != 5`/`3 < 4` → **3**,
`9 нацело 2` → **4**, `длина` + `а[к]` в `пока` → **18**. Событие `индексация` есть в формате 2.0/3.0
(`src/compiler-v3/astFormat.ts#индексация`, писатель post-order 763–768, читатель 1062) — **AST 3.1 для
индексации не нужен**, и AST 3.0 major замером не требуется ни для одной конструкции.

**В вызываемой (глубина 1):** `[i]`, `==`, `!=`, `нацело`, `длина`, `вывести`, `Списки.установить`,
`создать` — **ОК**; `добавить` — **названный размерный отказ** («блоку ТРИ клетки, а `добавить` нужно
пять различных ролей», `src/e2k/arrayRuntime.ts#arrayValuePrologue`), и поэтому список-литерал в вызываемой тоже
отказывает. Отказ обходится БЕЗ правки `src/**`: `установить` в вызываемой работает → автомат пишет в
заранее нарезанный список с собственным индексом (приём P3c).

**Две новые границы, названные тем же замером:**

1. **Вызов несёт не больше ТРЁХ аргументов** (`src/e2k/emitterShell.ts#EmitterRefusalError`): ветвь с 7 аргументами —
   не отказ, а **бросок** `EmitterRefusalError: call: аргументов 7, носитель несёт не больше 3`.
   Следствие: состояние автомата (`поз, посл, режим, ошибка, н, тсост, кадры, эсост`) НЕЛЬЗЯ передать
   параметрами — его место список `состояние[0..7]`, и тогда вызов = 3 аргумента.
2. **Литерал списка в точке входа ограничен длиной:** 1×8 — ОК, 1×**16** — отказ (живы 18 / свободно
   10); 3×8 — ОК, 3×16 — отказ. Черновик стоит на границе (литералы 8 и `[]`), а растущая лента
   строится операторами, поэтому его эта стена не добивает — но 16-клеточную ленту литералом записать
   нельзя.

**Классификация.** bounded (проба, дни): давление точки входа (разбить автомат на ветви-процедуры,
состояние — в список, `добавить` в ветвях → `установить`, `%`/`нацело` из входа убрать, вернув `%b[9]`)
+ `добавить` в вызываемой (обходится; либо блок 3→5 — данные `src/e2k`, не алгоритм). Форма ≤3
аргументов и предел литерала 8 — не блокеры, а ФОРМА. Не блокеры: `[`, `==`, `!=`, `<`, `нацело`,
`длина`, `вывести`, `Списки.взять` (**0 вхождений**, D49 — долг пользовательских программ), AST 3.1,
AST 3.0 major. VLIW — только если после P4a кусок всё равно не влезет: тогда речь о
`MAX_SPILLS_PER_PROCEDURE` (слой `src/vliw`, политика «со своим замером»), но НЕ об алгоритме
`regAlloc`/`liveness`/`spill`.

**Порядок (рекомендация, не решение):** P4a — bounded-переделка пробы (дни) → замер; если кусок
по-прежнему > 15 живых — отдельный замер по пределу вытеснения (решение владельца) — и только потом
остальное. P4 целиком (полный парсер) остаётся **месяцами**: строки отложены решением A4 s4, объектов и
полей нет; но это НЕ VLIW-трек, и стена куска это подтверждает.

## 25. P4c-fix: `%` → `a - (a нацело b)*b` — проба, НЕ P4 full (2026-11-10)

## 29. P4a-fix (A): пер-событийные писатели — 3 аргумента, return-index (2026-11-11)

**Форма задания была физически невыразима, и это названо, а не обойдено.** Носитель вызова несёт не
больше **3** аргументов (`MAX_CALL_ARGS = 3`, `src/e2k/emitterShell.ts`); четвёртый даёт
`EmitterRefusalError: call: аргументов 4, носитель несёт не больше 3`. Поэтому писатели из задания
`(лента, инд, поз, имя_поз)` и `(лента, инд, поз, арг)` заменены на **3-аргументные return-index**:
`инд` — аргумент, новое значение возвращается; никакого `состояние[0]`.

**Второй названный предел — 32-битный литерал.** `2^32 = 4294967296` не влезает в литерал `movts`
(`EncodingRefusedError: литерал 4294967296 не влезает в 32 бита; 64-битная форма не реализована`), тем
более `2^37`. Поэтому упаковка/распаковка идёт **двумя шагами по 16 бит**:
`R нацело 65536`, `R - (R нацело 65536) * 65536` — без `2^32` и без `2^37`. Это не «упрощение»: обе
величины проверены отказом, а не предположением.

**Писатели (замер `peak/live/used` на настоящем дереве, P1—P4):**

| писатель | записывает | peak | live |
|---|---|---:|---:|
| `записать_число_инд` | одно число | 8 | **7** |
| `записать_текст_из_инд` | длину + кодпоинты | 14 | **11** |
| `выписать_действие_начало_инд` | `[17, поз]` | 15 | **12** |
| `записать_имя_инд` | `[13, поз]` | 12 | **11** |
| `записать_литерал_инд` | `[12, поз]` | 12 | **11** |
| `записать_начало_инд` | `[10, поз]` | 15 | **12** |
| `записать_конец_инд` | `[11, арг]` | 13 | **11** |
| `записать_оператор_инд` | `[9, поз]` | 15 | **12** |
| `главная` (вход) | последовательность | 9 | **7** |

**Почему имя/литерал пишут только два поля.** Пять `Списки.установить` в одном листе дали **live 14**
(peak 15) — выше бюджета. Поэтому лист пишет `[код, поз]`, а `конец`, строку/колонку, тип и текст
дописывает `главная` тем же `записать_число_инд`/`записать_текст_из_инд`. Это не потеря события:
порядок клеток AST сохранён байт-в-байт, а бюджет листа стал **11–12 live**, вход — **7**.

**Что осталось за границей.** `peak` 13–15 — это пик носителей, а не живых значений; предел D48 в
этом замере считается по `live`. Если владелец потребует `peak ≤ 12`, потребуется разрезать и
четырёхпольные листы (`начало`, `оператор`, действие) — это отдельный замер, не выданный за сделанный.

## 30. B2a: пять программ — AST = эталон, QEMU = 0 (2026-11-11, ЗЕЛЁН на модели)

**Пять программ, а не «B2 целиком».** B2a — ограниченная форма: P1 `ф(х)`, P2 `ф(г(х))`, P3 `ф(у)`
(оператор вызова с другим именем, чтобы P1/P3 не были одним ответом), P4
`пусть z = 1 + ф(х)` — вызов в выражении, P5 `ф(г(ч(х)))` — глубже двух, поэтому **отказ сборки**
`OSN-PAR-031`, а не QEMU.

**P4 и эталонный парсер.** `parseV01` отвергает `1 + ф(х)` как выражение-оператор
(`конструкция «1» вне подмножества парсера v0.1`), но принимает `пусть z = 1 + ф(х)`; AST-эталон для
этой формы содержит `литерал(1)`, `имя(х)`, `вызов(ф)`, `бинарный_плюс` и `пусть`. Поэтому P4 — именно
`пусть z = 1 + ф(х)`, а не подмена «просто вызов».

**Что измерено.** `src/e2k/parserProtocolB2a.test.ts` (N=5): для P1—P4 — `loweredProgram` без отказов,
ELF, живой QEMU, код **0**, stdout **побайтово равен** `эталоннаяЛента` (`parseV01` → `лентаИзAst`),
включая magic `20261108`, версию `3`, заголовок модуля и все события. P5 — `toThrow(/OSN-PAR-031/)`.
Шестая проверка — само-красный контроль: P1 и P3 различаются и программой, и эталонной лентой; жёстко
зашитый ответ её не проходит.

**Чем B2a НЕ является.** (1) Это **не B2** и не P4 full: последовательность событий для этих пяти
программ известна на сборке из token tape, а read-only `разобрать_вызов`/`разобрать_аргумент`
формализованы, но `главная` их в B2a не вызывает; B2 — это цикл по произвольной ленте. (2) `peak`
писателей 13–15 (live 11–12) — не то же, что 24 у B2. (3) P4a-fix (A) — не P4 full. (4) Красный
GitVerse-CI — отдельный атом. B2b — после B2a.

**Граница проверки.** QEMU — модель; живая машина E8C2 проверена отдельным замером 2026-11-11:
`P1 OK, P2 OK, P3 OK, P4 OK, RESULT ok=4 bad=0` (те же ELF, sha256 залиты после сборки; P5 — отказ
`OSN-PAR-031` на сборке, ELF нет). `npm test` этот файл не содержит (внешний ресурс, случай 12); он
живёт в `npm run gate:qemu`.

## 32.1. Код 9 на глубине 5 — ёмкость кучи, а не форма (2026-11-12)

**Класс: C — ёмкость данных.** Один и тот же ELF глубины 5, меняется только `p_memsz` сегмента
данных (`src/e2k/elfMinimal.ts#DATA_SEGMENT_BYTES`, `#buildElfFromCode`):

| `dataSegmentBytes` | QEMU | факт/эталон |
|---|---|---|
| `0x2000` (умолчание) | **9**, `exception at IP = 0x103240` | 0/83 |
| `0x3000` | **0** | 83/83 |
| `0x4000` | **0** | 83/83 |
| `0x6000` | **0** | 83/83 |
| `0x8000` | **0** | 83/83 |

8192 байта / 16 байт на клетку ≈ 511 клеток кучи; список глубины 4 — 509 клеток (влезает),
глубины 5 — 609 (не влезает). Падение на `ldd,0 %db[15], %db[12], %db[10]` — это доступ за
отображённую страницу; порт печатает `exception at IP` и завершает процесс, поэтому код 9 —
**следствие**, а не отказ понижения. `readelf -l` исключает пересечение сегментов, `objdump` —
подмену команды: depth3/4 исполняют тот же `%db[15]`.

**Почему умолчание не поднято.** `src/e2k/elfMinimal.ts#DATA_SEGMENT_BYTES` фиксирует: `p_memsz` входит в файл,
смена умолчания сдвинула бы `sha256/16` всех образов и закреплённые пины. Сайт, которому нужно
больше, передаёт `dataSegmentBytes` сам (так делает лексер, `0x14000`). Поэтому предел `>4`
оставлен, а его сообщение теперь называет ёмкость: 511 клеток против 609. Полный разбор —
`.tmp/depth5-code9.md`; железо глубины 5 с `0x3000` не гонялось.

## 33. B2 через рекурсию: разбор рекурсивен, запись из рекурсии — `#16` (2026-11-12)

**P5 — НЕ runtime-рекурсия.** `P5 depth 4` собирается **статически**: генератор
`программаПротоколаB2aPerEvent` рекурсивно обходит token tape в TypeScript
(`событияАргумента`, `src/compiler-v3/parser-protocol-probe.ts`) и пишет в
исходник **готовую последовательность** вызовов писателей. В сгенерированной `главная` **нет ни
одного `разобрать_*`**: только `записать_начало_инд`, `записать_текст_из_инд`, … Поэтому P5
доказывает работу **статического разворота**, а не рекурсивного вызова на цели. Глубина 4 на
железе не гонялась: в §32 у глубины 4 стоит «не гонялось», железо есть только для глубины 3
(65/65). Утверждение «P5 depth 4 — 76/76 на железе» **не подтверждено замером**.

**Рекурсия в рантайме уже есть — и она read-only.** `разобрать_вызов` вызывает
`разобрать_аргумент` для вложенного вызова, `разобрать_аргумент` вызывает `разобрать_вызов`
(`src/compiler-v3/parser-protocol-probe.ts`). Эти процедуры **не пишут** в список;
они только читают ленту и возвращают упакованную позицию. Минимальный цикл с `разобрать_вызов`
и одним писателем понижается (`.tmp/b2-min.ts` → `lowered ok`).

**Почему B2 нельзя достроить рекурсией-писателем.** Эмиссия POST-ORDER требует, чтобы рекурсивная
процедура **писала** события после возврата из вложенного вызова. Но `Списки.установить` из
плоскости, вошедшей выращенным кадром, — **названный отказ**:

```
#16 Списки.установить: запись в память рантайма массивов из плоскости, вошедшей выращенным
кадром (глубина 2) — … МОДЕЛЬ зацикливается РОВНО на `std` … а ТА ЖЕ проба на ЖЕЛЕЗЕ проходит
```

Это не liveness 16/9: отказ стоит **до** раскладки, на глубине 2, и воспроизводится минимальной
пробой `src/e2k/parserProtocolB2Rec.test.ts` (рекурсивная `рекурс` вызывает `записать`, тест
требует `#16` и глубину 2). Поэтому «рекурсией вместо явного стека» B2 не собирается: либо
писатель на глубине ≥2 (отказ `#16`), либо явный стек в `главная` (пик 16 при 9 свободных,
`#623` на базе блока рантайма).

**Что это значит.** B2 требует решения владельца по одному из двух слоёв: (а) разрешить запись
массива из выращенного кадра (модель/`std`, §3.137.5 — стена **модели**, не цели), либо
(б) разрешить изменение liveness/regAlloc для явного стека. Оба — стоп-условия §4; ни один не
делался самовольно. Форма «P5-цикл + `записать_вызов_инд`» из присланного наброска **не
реализуема**: такого писателя нет, и одного `R3` (end+argc) недостаточно, чтобы выписать
POST-ORDER всего поддерева.

## 34. B2 hardware-only: 8/8 на железе, AST = эталон (2026-11-12)

> **Заменено §35 (та же дата).** Ниже — историческая рекурсивная редакция `выписать_вызов`; рабочая
> форма теперь — цикл `обойти` по произвольной ленте, см. §35. Политика «hardware-only» и `#180` в
> QEMU сохранены.

**Итог.** B2 работает: `главная` читает ленту, рекурсивный `выписать_вызов` пишет события
POST-ORDER, **8 из 8** программ на E8C2 дают **ровно `эталоннаяЛента`** (0 расхождений). QEMU
по-прежнему обязан давать **названный отказ** `#180`, а не исполнять.

**Решение владельца.** Вариант (а) — запись массива из выращенного кадра — **разрешён**; вариант
(б) — liveness/regAlloc для явного стека — **не разрешён**. Модель на `std` в таком кадре
зацикливается (A4 §3.137.5), поэтому B2 принимается **только по железу**; QEMU обязан давать
**названный отказ**, а не исполнять.

**Что уже в коде.** В `src/e2k/programImage.ts#imageOfCarriers` добавлена ручка
`allowDeepArrayWrites`; без неё отказ `#180`/`OSN-LOW-004` на месте, с ней образ собирается.
Публичная дверь — `src/e2k/guards/loweredUnchecked.ts` (`ОпцииСырогоПути`). Развилка закреплена
`src/e2k/parserProtocolB2Hardware.test.ts`: без флага — `#180`, с флагом — образ есть.

**Форма B2.** `src/compiler-v3/parser-protocol-b2.ts#программаПротоколаB2` берёт шапку B2a
(писатели) и заменяет статический разворот на **рекурсивный** `выписать_вызов`: `главная` читает
ленту, `выписать_вызов` рекурсивно обходит аргументы и пишет POST-ORDER. Один оператор-вызов в
`главная`; несколько операторов/`пусть`/выражения — B2b.

**Причина прежнего SIGFPE — не писатель.** `главная` начинала `выписать_вызов` с токена `(`
объявления действия (`тело.индекс`), а не с токена вызова `ф`: разбор уходил в чужие токены.
Замер изоляции: **все четыре** одиночных писателя всё равно давали SIGFPE/SEGV, а пробы
«писатель отдельно», «пара писателей», «вся последовательность писателей» — `rc=0`. То есть
писатели и их порядок были целы; ошибочен был **стартовый токен**. После перехода на токен
вызова (пропуск `(` и `)` заголовка) `ф(г(ч(х)))` дал `rc=0` и **68/68** событий эталона.

**Вторая правка — `вызов_оператор` только у корня.** Рекурсивный `выписать_вызов` писал
`записать_оператор_инд` на каждом уровне, а эталон — **один** оператор у внешнего вызова.
Оператор вынесен в `главная` после возврата `R`; на 8 программах это дало точное совпадение.

## 35. B2: произвольная лента в цикле — AST = эталон на железе (2026-11-12)

**Форма, которая работает.** `src/compiler-v3/parser-protocol-b2.ts#программаПротоколаB2` больше
не разворачивает фиксированные формы: `главная` строит ленту токенов один раз и вызывает
`обойти(лента, инд, предел * 65536 + первый.индекс)` — **три** аргумента (носитель вызова несёт не
больше трёх). `обойти` (глубина 1) идёт циклом `пока т < предел`, держит явный стек
`[токен_вызова, число_аргументов]` в клетках `1100+` той же `лента` и пишет события POST-ORDER:
имена/литералы — на месте, `вызов_начало`/`текст`/`вызов_конец` — на `)`, `вызов_оператор` — только
у корня. Рекурсивного писателя нет; писатели остаются листьями.

**Старт и предел — не длина исходника.** Токен `т` — это **индекс в ленте** (шаг `7 + длина токена`),
а `конецДействия` — длина ИСХОДНОГО текста в символах; у короткой программы `ф(х)` токен вызова
равен 45, а длина исходника 39. Прежняя граница `т < конецДействия` давала пустой цикл (на железе
видно: только `действие_начало` и `действие_конец`). Предел теперь — `токеннаяЛента(...).length`;
`разобрать_вызов`/`разобрать_аргумент` (только чтение) вызываются в цикле: аргумент-лист — для
перехода к следующему токену, закрытие вызова — для счёта аргументов. По дороге исправлен
`разобрать_аргумент`: он проверял `лента[п]` уже **после** имени и потому никогда не распознавал
вложенный вызов; теперь проверка `лента[ток]` + `лента[п] == '('`, возврат `разобрать_вызов(лента, ток)`.

**Стена входа названа числом и обойдена формой, а не liveness.** Первая редакция держала весь
цикл в `главная`: раскладка отказала `#623` — «15 отрезков при 10 свободных, вытеснять нечего».
Это ровно стоп §2 «entry live > 10», а не дефект базы. Цикл вынесен в `обойти`; `главная` теперь
только строит ленту и печатает. Стек/события лежат в нулевом хвосте `лента` (1400 клеток): события
начинаются после шапки, стек — с 1100, поэтому запись события не затирает кадр. Метаданные
(`предел`, старт) упакованы в третий аргумент, а не пишутся в ленту: запись по индексу 490 на
короткой ленте дала SIGSEGV (её длина ~412), это измерено и снято.

## 36. B2b: `пусть`, присваивание, выражения, `если`/`пока` — AST = эталон на E8C2 (2026-11-12)

**Форма.** `src/compiler-v3/parser-protocol-b2b.ts#программаПротоколаB2b` (строка 35) собирает
исходник так же, как B2: `главная` кладёт ленту токенов и вызывает
`обойти(лента, инд, предел * 65536 + первый.индекс)`; `обойти` (строка 531) — **цикл** `пока`,
без рекурсии, события пишутся POST-ORDER. Шапка (писатели, `напечатать`, `разобрать_*`) берётся из
B2a-генератора от **неподвижного** входа `действие главная()\n  ф(х)\nконец главная\n`: B2a целиком
на B2b-теле падает (`B2a: не найдена «)»`, он ждёт вызов-оператор), а шапка от входа не зависит —
сверены две разные программы, шапки совпали побайтово (обе — 3325 символов).

**Выражения — приоритет эталона, а не «слева направо».** Задание говорит «без приоритета», но
`parseV01` приоритет **имеет**, а шлюз требует AST = эталон. `выразить` (строка 274) —
итеративный shunting-yard; `приоритет` кодирует `prec * 100 + код_события`:
`==`/`!=` (1) < `< <= > >=` (2) < `+ -` (3) < `* /` (4). Поэтому
`пусть а = 1 + 2 * 3` даёт `2 * 3`, затем `1 + …`, как эталон. Позиция бинарного — от начала
левого до конца правого; позиции `пусть`/присваивания/`если`/`пока`/`вернуть` — по правилам
`parseV01`.

**События.** `пусть` — `[14, начало, строка, колонка, конец, 0]` и имя; присваивание —
`[41, начало, конец, строка, колонка]` и имя; `если` — условие, затем

условие, затем `[40, offset(если), строка, колонка]` (порядок именно такой: `[40]` — POST-ORDER);
`пока` — условие, `[15, начало, строка, колонка]`, тело, `[16, конец]`; `вернуть` —
`[8, начало, строка, колонка, конец, hasValue]`. Вложенность блоков отдельного стека не требует:

- **`и`/`или`** (коды 32/33), **`%`** (25) и **`нацело`** (34) — **поддержаны с L2 (2026-11-13)**:

- **Унарные** `-`/`не` (35/36) — **поддержаны с L2**: префиксный разбор по состоянию `С[6]`,
  `а - -б` и `- -а` различаются. (`нет` — литерал ложного значения, не унарный оператор.)
- **Тип в `пусть`** (`пусть а: Число = 5`) — **поддержан с L2**: пишется `hasType=1` и тип-событие.
- **Литералы** — числовые, имена и **простые строки без escape** (L2). Логические литералы в
  `выразить` по-прежнему не разбираются; escape-последовательности строк — граница.
- **Многострочные выражения** — **поддержаны с L2**: перенос разрешён после оператора/`(` и перед
  бинарным оператором/`)`; смена строки без продолжения по-прежнему останавливает `выразить`.
- **`прервать`** в `пока` не поддержан (в AST v0.1 его нет); `конец`/`конец если`/`конец пока`
  различаются по следующему токену.

**Что не сделано.** B2b не расширяет публичную грамматику `parser.ts` (запрещено §5). L2 закрыл
`и`/`или`, `%`/`нацело`, унарные, `: Тип`, простые строки и многострочность; **не** закрыты вызовы
в выражениях, `прервать` (его нет в AST v0.1), escape-строки, индексация/списки в выражениях,
заголовки `процедура`. `parser-protocol-b2b.ts` — новый файл, старые генераторы не менялись.

**L2: вход файлом и разбор собственного ИСХОДНИКА не сделаны — стены названы (§1/§2 отчёта
`.tmp/l2-report.md`).** `обойти` действительно идёт по параметру `лента`, но единственный вызов
`главная` запекает `токеннаяЛента(источник)` литералами: класс **A в ядре / B в производителе**.
Целевого лексера нет (`src/self-host/lexer.osnova` — 144 отказа, тело 141), а
`система.файлы.читать` отказывает на `IR.invoke` (`#2`), поэтому «файл → байты → лента» на цели
пока не собирается. B2b разбирает **готовую числовую ленту**, а не байты исходника; называть это
«self-parse исходника» нельзя.

**Коммит.** `10688664` на ветке `feat/b2b` (от `e22f0c82`). PR #114 (B2) смержен в `main`
(`171cd4b8`); B2b — отдельная ветка, PR открыт после этого замера.

## 37. P4a: бюджет 15 закрыт формой B2b; черновик 764 строк — стена КОДА, не регистров (2026-11-12)

**Задание и что оказалось устаревшим.** Задание P4a: снизить бюджет точки входа черновика парсера
(764 строки) с **19** до **≤15**. Число `19/10` — реальный замер (`§25`, строки 1309–1314), но он
снят на ревизии `dcaf81dd` и **на HEAD не воспроизводится**: там другой поток носителей после B2b.
На HEAD черновик (`parser-target-spec.osnova`, 765 строк) даёт **`peak=22 peakLive=16 used=0
ok=false`**, отказ — «в тесный момент живы **1831** отрезков, свободных регистров 9»; живые
`[0,1,2,4,7,8,9,10,11,12,13,14,18,20,22,23]` — это `токены`, `лента`, десять клеток состояния
(`поз`, `ошибка`, `посл`, `режим`, `стек`, `типы`, `кадры`, `эсост`, `тсост`, `после_типа`) и
временные `t18,t20,t22,t23`. Пул входа 10, net 9 (`ALLOCATABLE_REGISTERS` минус `%b[12]` и

`allocateSegments` по **1831 пересекающимся отрезкам**, а не по числу живых. Это видно на

1. **CODE_PLACEMENT.** Дизассемблер E8C2 на 8204 инструкциях: **8** адресов возврата `call`, **5**

3. **`.text`.** `readelf -S`: `.text` ровно `0x1f000 = 126 976`; `elfMinimal` кладёт в сегмент

**Дешёвое лечение — не multi-section.** Только для союза: `dataSegmentBytes` 0x8000 → **0x10000**
(64 КиБ); тот же `.text` 126 976 на E8C2 даёт **RC=0**, **2908 байт** вывода, sha256
`31744b7abd1eb718…` — **байт в байт** с `эталоннаяЛента`. Случай `b2b/all` **возвращён в кит** с

сдвинулись. QEMU здесь не арбитр — глубина ≥2 зацикливает модель (`#180`).

в 126 976 байт (137–170 КБ), а state-list форма отказывает по 3019 отрезкам. Это **не**

**Что сделано — одна строка, но не «замена ради замены».** Шапка B2b (`программаПротоколаB2aPerEvent`,
которую B2b берёт как `шапка`) печатала ленту словом `вывести лента[пт]`. Это слово — библиотека D43,
а не языковая инструкция, и эталон (`parseV01`) его **ОТВЕРГАЕТ**:

```
OSN-PAR-030: «вывести» — библиотека D43, а не языковая инструкция:
             используйте Печать.число/Списки.длина/Списки.добавить
```

Пока шапка печатала им, **свой исходник был для эталона неразбираем** — а значит self-parse невозможен
по определению: B2b не может разобрать программу, которой эталон не разбирает. Замена —
`Печать.число(лента[пт])`, ровно в той же позиции. Она живёт в одном месте
(`src/compiler-v3/parser-protocol-b2b.ts`, функция `заменитьПечать`) и **падает сборкой**, если
вхождений не одно: при нуле исходник молча остался бы неразбираемым, при двух замена одной строки
оставила бы вторую.

**Почему на цели это ТА ЖЕ печать, а не новая операция.** `Печать.число` — квалифицированный вызов
D43; он сводится к канону `система.лог.вывести` записью в

применяется в разборе: `src/compiler-v3/parser.ts#встроенныйВызов`). Поэтому печать идёт тем же
рантаймом, что и раньше: **никакого D43 не реализовано**, `вывести` остаётся библиотечным словом,
AST v0.1 не тронут.

1. **Эталон принимает исходник B2b.** `parseV01` на сгенерированном исходнике: **40/40 форм** и

## 41. L2: ИНДЕКСАЦИЯ `а[…]` и `Список T` с литералом `[…]` — кластеры 1 и 3, ленты = эталон (2026-11-13)

**Срез снял два кластера из четырёх и оба — ЛЕНТОЙ, а не словами.** До него: `а[0]` в выражении
писатель не разбирал вовсе (лента обрывалась на имени `а`: 66 клеток против 79), а
`пусть а: Список Число` уезжало типом `Список` — эталон ждёт `[КОД_ТИПА.список, элемент]` (51
клетка против 58). После: **9 форм §41 совпадают с `эталоннаяЛента` клетка в клетку** (58/74/59/63 и
79/92/92/106/78), и по дороге выяснилось, что ЧИСЛО, названное в §39 стеной кластера 3 («нужен тип
`Список T`»), было лишь половиной: тип уже собирался, а **литерала `[]` у писателя не было** — пустой
список давал НОЛЬ клеток значения, и `пусть` писал конец `0`.

**Как это работает и почему именно так.** Скобки `[`/`]` не завели новую технику разбора — они легли
в ТУ ЖЕ стековую машину, что бинарные операторы (`толкнуть`/`свернуть`), и это не упрощение, а
требование формата:

1. **Индексация** (`[` ПОСЛЕ операнда) — постфиксный оператор с точностью **7** (выше `*` = 6),
   событие **39**. `толкнуть` уже кладёт в запись стека `С1/С3/С4` — позиции ЛЕВОГО операнда, а
   `свернуть` подставляет `С2` концом. Эталон пишет ровно это: `[39, начало_БАЗЫ, конец_после_],
   строка_базы, колонка_базы]` (замер по `пусть б = а[0]`: `39 45 49 3 13`, где 45 — смещение `а`,
   а `]` кончается на 48). Поэтому `шаг_индекс_открыть` лишь кладёт маркер **97** поверх записи 39,
   а `шаг_индекс_закрыть` снимает маркер, подставляет конец `]` в `С2` и даёт `свернуть` сделать
   событие — новых форматов ноль.
2. **Литерал списка** (`[` НА МЕСТЕ ОПЕРАНДА) — маркер **98** с токеном `[`; позиции НЕ хранятся, а
   читаются из ленты токенов при `]` (`открытие + 1/2/3` — строка/начало/колонка). Счётчик
   разделителей лежит в `С7`; пустота определяется не «счётчиком 0», а СРАВНЕНИЕМ: токен после `[`
   равен `]` ⇔ список пуст (`[]` → `[37, начало, строка, колонка, 38, 0, конец]`, `[1, 2]` → счёт 2).
3. **`]` и `,` не останавливают выражение.** Прежний сторож `приоритет == 0 → стоп` останавливал
   разбор на них, оставляя маркер в стеке; теперь исключение названо явно, а «не наша скобка»
   ловится возвратом **−1** из `шаг_квадрат_закрыть`/`шаг_запятая`.

**Тип `Список T` — не косметика, а формат.** `типВЛенту` пишет список как `[2, <элемент>]`, то есть
`Список Число` → `2 1 5`, `Список Строка` → `2 1 6`. B2b писал `1 <длина> <буквы>` — то есть
«имя с пробелом». Исправлено в `шаг_пусть`: вид типа берётся из ячейки `Список` токена типа, а
элемент — следующий токен; `КОД_ТИПА.список` = 2 приезжает из `astFormat` (число не дублируется).

**Цена названа числом, и она — ГЛАВНОЕ ограничение среза.** Шесть новых процедур и потяжелевший
`выразить` стоили **+12 040 байт кода**: конец кода 15-формной сборки (`b2b-all`, та, по которой идут
закреплённые числа §39/§40) **70 494 → 82 534**, запас до статики `106 072` — **35 578 → 23 538**.
Каждая форма `b2b6` по отдельности влезает: конец кода **74 006…74 462**, запас **32 066…31 610**,
эталон принимает 9/9. А **все 49 форм одной программой в потолок образа НЕ влезают**: `PrintCallRefusal`

**Правило бюджета вызываемой (§3.135/§3.137) сработало как стена, и первая редакция была отвергнута
замером.** Толстая `шаг_квадрат_закрыть` (одна процедура на оба вида скобок) дала `used 12` при

### §41.1 — ЖЕЛЕЗО НАШЛО ТИХУЮ ЛОЖЬ, которой не было на VM (2026-11-13)

**Первый прогон кита на живой E8C2: `совпало 95, расхождений 1, файлов нет 0`.** Единственное
расхождение — `bin/b2b6p7.elf`, форма `пусть а: Список Число = [1, 2]`: код 0 (как ждали), вывод
214 байт против эталона 214, и разница ровно в ОДНОМ числе — эталон `38 2 51` (список_конец,
**счёт 2**), цель напечатала `38 1 51` (**счёт 1**). Лента на стековой VM эту же форму выдавала
клетка в клетку, то есть оракул был зелёным, а цель — неверной: это ровно класс «программа
исполняется, число неверное».

**Причина — не формат, а способ считать.** Первая редакция держала счётчик запятых в клетке
состояния `С7` и увеличивала его ЧТЕНИЕМ-ЗАПИСЬЮ одной и той же клетки ленты через
`Списки.установить(лента, С7, лента[С7] + 1)`. На цели такая пара дала СТАРОЕ значение (0), поэтому
закрывающая процедура посчитала `0 + 1 = 1`. На стековой VM тот же код работал.

**Исправление — счётчик убран целиком.** Число элементов теперь считается ОБХОДОМ ЛЕНТЫ ТОКЕНОВ от
`[` до `]` (`счёт_элементов`), между токенами состояние не нужно: `[` + следующий токен `]` ⇔ 0,
иначе 1 плюс число запятых. Это дороже (обход на каждое закрытие), зато убирает зависимость от
поведения «прочитать-записать клетку ленты» и делает границу честной: вложенные списки и запятые
внутри аргументов вызова по-прежнему не поддерживаются.

### §42 — ФАЙЛОВЫЙ ВВОД: НАЗВАННАЯ ГРАНИЦА, не сделано

Модуль `src/self-host/fileRuntime.ts` содержит `openInstructions` / `readInstructions` /
`closeInstructions`, номера `SYS_OPEN=5`, `SYS_READ=3`, `SYS_CLOSE=6`, флаги `O_RDONLY/O_WRONLY/
O_CREAT/O_TRUNC` и разбор `outcomeOf` (знак — отказ, ноль у `read` — конец файла). Формы проверены
сторожем `fileRuntimeShapeProblems`, но **в понижение не подключены**: четвёртой ветки
`isFileRuntimeCall`/`lowerFileCall` в `src/e2k/e2kRealRun.ts` нет, `ARITY` для `система.файлы.*` нет,
`главная` не читает `argv[1]`.

Причина названа числом и слоем, а не «не успели»: `readInstructions` принимает **статический** адрес
буфера (`bufferAddress: number`) и **статический** `count`; буфер обязан лежать в СЕГМЕНТЕ ДАННЫХ
(замер §3.145: буфер в `R|X` даёт `EFAULT`). Для чтения файла с цели нужен адрес, известный только
рантайму (куча/арена), и дескриптор из `open`; текущий ABI не передаёт `argv` в `главная` и не даёт
`read` динамический буфер. Это отдельный атом: «файловый вызов в понижении + argv», а не правка
таблицы. До него §44 (self-parse из файла) заблокирован той же границей.

### §43 — ПОТОЛОК КОДА ПОДНЯТ ОДНИМ ЧИСЛОМ: 126 976 → 192 512 (2026-11-13)

**Причина.** Кластер 2 вырастил писатель B2b: 54 формы перестали помещаться в прежний потолок —
статика начинается на **78 576**, а код вырос за неё (прежний потолок `126 976` был пройден). Это не
«многосекционный образ» и не новая раскладка: сдвинуто ОДНО число.

**Что сдвинуто.** `src/e2k/elfMinimal.ts#IMAGE_TAIL_OFFSET`: `0x20000 → 0x30000`. Вместе с ним
выведены `DATA_SEGMENT_BASE = 0x12F000`, `WRITE_ZONE_EXTRA_MEMORY = 0x31000`, `DEFAULT_SPILL_BASE`,
`HEAP_OFFSET = 0x30000`, площадка печати и слоты вытеснения — они считаются от этого же числа.
Потолок кода — **192 512** байт (+65 536), страница области записи — `0x12F000`.

**Замер.** Все **54** формы B2b понижаются, отказов **0**; `.text` = 192 512. Граница печати
перемерена: **770 сайтов** собираются (код 192 512, конец ровно `0x12F000`), **771** — названный отказ
`PrintCallRefusal` (код 192 760, конец `0x12F0F8`). `b2b-all` — 15 форм, 52 процедуры, 0 отказов,
192 512 кода + 65 536 данных.

**Перемер закреплённых чисел.** 24 sha256 проб конъюнкции сдвинулись (адрес кучи входит в образ
непосредственностью) и перенесены тем же прогоном: `1a deaef2e3…`, `2a 2506439b…`, `3a 40cdbd77…`,
`8d 435df315…` (полная карта — `src/e2k/conjunctionValue.test.ts`). Адрес байтов «абв»:
1 175 546 → **1 241 082** (+0x10000). `foundationE2k`: `кодовБайт` 126 976 → **192 512** (это
`DATA_SEGMENT_BASE − MINIMAL_BASE`, а не длина кода). Точечные прогоны: 25 файлов, **405 зелёных**,
30 пропущено.

**Чего НЕ сделано.** Многосекционный образ не понадобился; если одного числа не хватит — это отдельный
атом (условие §7). Печать/строки/self-host не перемерялись на ЖЕЛЕЗЕ в этом срезе: кит пересобран,
`gate:hardware` — следующий шаг.

### §44 — SELF-PARSE ИЗ ФАЙЛА: НЕ СДЕЛАНО (заблокировано §42)

B2b умеет разобрать ЛЕНТУ ТОКЕНОВ, поданную из памяти (`обойти`), и AST совпадает с эталоном на 54
формах (§41.2). Но «прочитать СВОЙ ИСХОДНИК из файла» требует §42: `open`/`read`/`close` в
понижении и динамического буфера. Без этого шага `rc=0` на E8C2 нечем получить: программа не знает
имени файла (`argv[1]`) и не имеет буфера в сегменте данных, адрес которого известен только рантайму.
Это названная граница, а не «зелёная» запись: §42/§44 остаются открытыми, пока не появится
файловый вызов в ABI понижения.
