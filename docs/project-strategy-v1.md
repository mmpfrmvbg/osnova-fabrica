# Стратегия проекта ОС-НОВА v1

Документ отвечает на вопросы «зачем», «для кого» и «как докажем, что работает» — в дополнение к техническим спекам. Источник: итоги архитектурного и продуктового ревью (март 2025).

Это не техническая спека — **якорь**. Пригодится именно тогда, когда будет соблазн «добавить ещё одну фичу» вместо того, чтобы найти первого пользователя.

---

## 1. Зачем ОС-НОВА

**Основа — это язык, спроектированный под LLM как первичного автора кода, а не как вспомогательный инструмент.**

Аналогия с SQL: SQL ограничен по сравнению с Python, но именно поэтому LLM генерирует SQL надёжнее, чем произвольный Python-код для работы с базами. Жёсткие контракты (один модуль, явные конструкции, фиксированный invoke-API) — не слабость, а дизайн-решение: они сужают пространство возможных программ и делают repair-цикл сходящимся. Чем меньше степеней свободы, тем предсказуемее результат генерации.

Дополнительные аргументы:
- **Кириллица** — снижает барьер для целевой аудитории (аналитики, бухгалтеры, операторы), которые не пишут код на английском. LLM получает запрос и выдаёт код на одном языке.
- **Контроль байткода** — для целевого железа (в т.ч. Эльбрус) и VLIW-оптимизаций нужен собственный стек.
- **Не замена Python/JS** — цель не общее программирование, а специализированный язык для LLM-генерируемых приложений в экосистеме ОС-НОВА.

Подробнее: `docs/why-osnova.md` (рекомендуется выделить отдельно для внешней аудитории).

## 2. Три задачи проекта

ОС-НОВА решает три разные задачи одновременно. Они не противоречат друг другу — усиливают:

- **Языковая задача** — дать людям, которые никогда не были программистами, возможность читать и понимать логику своих приложений. Не через интерфейс, не через кнопки — через текст на родном языке. Это радикальнее, чем кажется.

- **Инженерная задача** — спроектировать язык так, чтобы LLM генерировал его надёжно. Обратная задача по отношению к обычному проектированию языков: обычно думают о разработчике, здесь основной автор — модель. Ограничения языка — не бедность, а дизайн под конкретного исполнителя.

- **Платформенная задача** — создать замкнутую экосистему для российского рынка, где каждый слой (язык, VM, байткод, рантайм, лаунчер, реестр) под контролем и совместим с отечественным железом.

Три задачи в одном проекте — это либо сила, либо риск размытия. Определится в момент, когда появится первый человек вне команды, который скажет «это работает, это моё». До этого — гипотеза: красивая, задокументированная, но гипотеза.

## 3. Вопрос трёх месяцев

Этот документ — не только намерения. Он содержит **эксперимент с фальсифицируемыми условиями**. Если через три месяца никто не попробовал — нельзя сдвинуть сроки. Нужен честный ответ.

**Дата проверки:** 2025-06-18 (или +3 месяца от даты публикации стратегии)

**Гипотезы, которые мы проверяем:**

1. Разработчик-энтузиаст может запустить пайплайн и получить работающее приложение за < 30 минут от клонирования репо.
2. Micro-CRM генерируется с success rate ≥ 70% за 1–2 попытки repair.
3. Хотя бы один внешний человек сказал: «я бы использовал это для [задача]».

**Если ни одна из трёх не подтвердилась — меняем:**
- Либо входную точку (GETTING-STARTED слишком сложный).
- Либо планку демо (Micro-CRM слишком рано, нужен TODO).
- Либо аудиторию (энтузиаст не та аудитория — нужен интегратор).

**Если подтвердилась только #3** — ценность есть, но барьер входа высок.

**Если подтвердилась только #2** — пайплайн работает, но некому показать.

Без этого блока через три месяца будет соблазн сказать «почти готово, ещё чуть-чуть» — и так ещё три месяца. Этот блок — минимальная система обратной связи с самим собой.

## 4. Первый пользователь: разработчик-энтузиаст

**Выбор первого пользователя важнее выбора следующей фичи.**

Три варианта и их последствия:

| Первый пользователь      | Что нужно в первую очередь     | Чего не нужно сейчас      |
|--------------------------|--------------------------------|----------------------------|
| Разработчик-энтузиаст    | Docs, local run, SDK, язык     | Продакшен-UI, SLA          |
| Малый бизнес через UI    | Web UI фабрики, один клик      | Документация языка, API    |
| Системный интегратор     | API, SLA, встраивание         | «Красивый» публичный UI    |

**Рекомендация:** первым пользователем должен быть **разработчик-энтузиаст**, а не бизнес-пользователь.

Бизнес-пользователь требует законченного продукта: работающий веб-интерфейс, стабильный пайплайн, понятный onboarding. Приводить его раньше времени — риск негативного первого опыта.

Разработчик-энтузиаст может работать с `npm run pipeline`, читать спеку, прощать нестабильность — и даёт фидбек по тому, что сейчас важнее всего: качество генерации, диагностика ошибок, паттерны языка. Первые 3–5 таких людей закроют больше вопросов, чем 50 бизнес-пользователей, которые уйдут молча.

**Практически:** написать `GETTING-STARTED.md` с «запусти пайплайн и сгенерируй своё первое приложение» — и пригласить 3–5 человек. Не SaaS, не лендинг, а живой Github + явное приглашение.

## 5. Приоритеты MVP

### 5.1. Планка: Micro-CRM, не TODO

TODO — слишком низкая планка. Micro-CRM — первый сценарий, где проявляются структурные ограничения языка. Чтобы он стал демонстрацией мощи, а не ограничений, нужно заранее закрыть три вопроса:

1. **Связанные хранилища** — модель «клиент → контакты → история» и рекомендации по организации ключей (см. п. 5.2).
2. **Навигация между экранами** — именованный паттерн «Многоэкранное приложение» с few-shot (см. п. 6).
3. **Минимальная обработка ошибок** — хотя бы явные проверки; желательно примитивы `система.ошибка.*` без полноценного Result.

### 5.2. Scope хранилища: честные границы

Префикс-модель (`клиент_1_контакт_1`) — по сути ручная реализация key-value без индексов. Для «найти все контакты клиента 42» придётся перебирать всё хранилище. Для TODO и записной книжки — ок. Для CRM с поиском и фильтрами при 100+ клиентах — уже нет.

**Документировать в `golden-app-micro-crm.md`:** что работает при 10–20 клиентах, где стена, и что для масштаба нужен другой подход.

**Roadmap:** добавить `система.хранилище.найти(паттерн)` с glob-поиском по ключам — даст «найти все ключи с префиксом `клиент_`» без полного обхода. Небольшое расширение invoke-API с большим эффектом для офисных сценариев.

## 6. Навигация: именованный паттерн

Схема «один цикл `пока` + `текущий_экран` + `если`» — конечный автомат вручную. LLM будет генерировать её плохо, если паттерн нигде не описан как конструкция с именем. Без имени модель изобретает велосипед каждый раз — repair тратит попытки на нормализацию структуры, а не на логику.

**Рекомендация:** добавить в `pipeline-llm-osnova.md` именованный паттерн «Многоэкранное приложение» (`multi_screen_app`) с few-shot примером. Реестр паттернов (новый раздел в `language-registry` или `docs/patterns-registry.md`): id, name, syntax-каркас, typical_use, example_snippet. LLM в кодогене активирует паттерн по имени, а не синтезирует с нуля.

## 7. human_verdict: структурированный провал

`human_verdict` — не только оценка качества, но и **сигнал о природе провала**. Без детализации «no» мало полезен для улучшения.

**Схема (добавить в TraceEntry и traces-v1):**

```
human_verdict?: {
  result: "solved" | "partial" | "no",
  failure_stage?: "intake" | "spec" | "codegen" | "build" | "runtime" | "ux" | "dx"
}
```

- `intake` — задача понята неверно
- `spec` — спека неверна
- `codegen` — код не соответствует спеке
- `build` — ошибки компиляции
- `runtime` — VM/рантайм
- `ux` — UI неудобен / не тот
- `dx` — непонятно, как запустить / пользоваться

Один дополнительный выбор в UI — и датасет для файн-тюна адресует ошибки к конкретной фазе пайплайна. Добавить в схему трейса, пока она свежая.

## 8. Flywheel: батч и real-time

### 8.1. Батч: трейсы → файн-тюн

- Фильтрация: только success (и при желании высокий rating).
- Разметка «хорошего repair»: `repairAttempts > 0` и `status === success` — пример успешного исправления; пары (до → после) ценны для обучения.
- Разнообразие синтетики важнее объёма: разные категории (crm, todo, game, utility), типы ошибок, длины модулей.
- Человеческий фидбек — самый ценный сигнал; `human_verdict` критичен.

### 8.2. Real-time: куратор few-shot

**Few-shot в промпте кодогена — это живой обучающий сигнал**, который можно менять без переобучения модели.

Если в трейсах накопились примеры «LLM генерирует `массив[i]` → repair исправляет на `система.массив.получить`» — этот паттерн можно добавить в few-shot уже сейчас. Частота такой ошибки снизится немедленно.

**Куратор few-shot** — процесс (хотя бы раз в неделю вручную), который по топ-ошибкам из трейсов добавляет пары «неправильно → правильно» в промпт. Самый дешёвый способ улучшать генерацию до накопления датасета для файн-тюна.

## 9. Позиционирование lock-in

Для российского B2B lock-in воспринимается по-разному:
- **IT-директор** — риск, от которого защищаются (открытый формат, экспорт).
- **Руководитель бизнеса** — иногда преимущество («конкуренты не скопируют мою автоматизацию»).

**Формулировка:** «Открытый формат данных + закрытая логика генерации». Данные (хранилище JSON, байткод открыт) — ваши. То, как платформа генерирует под ваш бизнес-процесс — ценность платформы, не ловушка.

## 10. VLIW и кириллица

### VLIW

VLIW — не «отложенная фича», а часть идентичности проекта. Ориентация на Эльбрус и отечественное железо — то, что отличает Основа от других DSL на кириллице.

**Подход:** изолировать в отдельный трек. Ядро MVP развивается без VLIW в критическом пути; VLIW-scheduler существует как экспериментальный модуль. Разные задачи, а не конкуренция.

### Кириллица

Язык на кириллице — ставка на **нового пользователя**, а не на опытного разработчика. Не пытаться угодить обоим лагерям. Целевая аудитория: аналитики, операторы, предметные эксперты, которые читают код на родном языке. Явно зафиксировать в позиционировании.

## 11. SaaS vs on-premise: последовательность

SaaS — не отменяется как конечная цель, но **порядок фаз** стоит пересмотреть.

SaaS предполагает: инфраструктуру, биллинг, поддержку, SLA, безопасность данных (ФЗ-152, требования к хранению для бухгалтерии и POS). Это отдельный продукт, не следствие хорошего компилятора и пайплайна.

**Альтернативная последовательность:**
1. **On-premise инструмент** для нескольких компаний, которые сами его хостят. Данные у клиента, не в облаке. Это снимает регуляторные вопросы, упрощает первые продажи («мы ваши данные не храним»), и даёт реальный опыт до SaaS-фазы.
2. **SaaS** — после реального трафика задач, отработанной unit-экономики и понимания, какие данные клиенты готовы отдавать в облако.

Зафиксировать в roadmap явно: on-premise как первый этап монетизации, SaaS — последующий.
