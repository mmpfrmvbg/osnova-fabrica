# Системная модель e2k (`qemu-system-e2k`) — сборка и пробы

Это **не** та модель, которой измерены закреплённые числа `src/e2k/**` и `src/vliw/**`.
Та — **user-mode** `qemu-e2k` (паспорт `src/e2k/qemuModelPassport.ts`, правка порта и
инструкция — в `tools/qemu-e2k/README.md`). Здесь — **системная** модель: полная машина
`-M e2k`, ядро вместо процесса. Собрана 2026-10-03, разбор и замеры — `docs/e2k-qemu-system.md`.

## Как собрать и что померить

```bash
# в WSL-дистрибутиве e2k, от root
bash tools/qemu-e2k/system/build-system.sh            # как есть  → sha256 5ace3dae…, сверка встроена
bash tools/qemu-e2k/system/build-system.sh --window   # с правкой → sha256 1a321ebf…, сверка встроена
bash tools/qemu-e2k/system/probe-system.sh            # прогон корпусного ELF на ОБЕИХ сборках рядом
```

`build-system.sh` печатает **вердикт сверки** `sha256` с записанным здесь и в доке: совпал —
сборка воспроизвелась побайтово; разошёлся — числа требуют перемера (красное, а не «ну и ладно»).
Перед сборкой файл `target/e2k/cpu.c` восстанавливается из `cpu.c.orig`, поэтому переключение
режимов идемпотентно.

## Правка окна — одна строка (и зачем)

`target/e2k/cpu.c#e2k_cpu_reset` задавал `env->wd.size = 16` — это `size_q = 8`, геометрия **до**
нашей правки окна в user-mode. Образы корпуса объявлены под `size_q = 12` → `24` регистра
(`src/e2k/qemuModelPassport.ts`, поле `window`; `src/e2k/windowGeometry.ts`). Правка приводит
системный сброс к той же геометрии. Единицы — **регистры** (`target/e2k/helper-tcg.h:56-57`).

Замер на бинаре корпуса `11-минимум-массива.elf` (эталон возврата 2):

| | без правок | с правкой |
|---|---|---|
| окно вызывающего `wsz` | 16 | **24** |
| окно вызываемой | 8 | **16** |
| где встала | `0x100338` | `0x100358` — бандл `sdisp`/`ipd 3`/`call`, **вход в syscall** |
| исключение | `9` = `EXCP_WINDOW_BOUNDS` | `0` = `EXCP_ILLEGAL_OPCODE` |
| в окне вызова | — | `r0 = 1` (номер `exit`), `r1 = 2` (код = эталон) |

## Почему chroot, а не сборка на современном Alpine

Замер 2026-10-03: `configure` на Alpine 3.24 (gcc 15.2.0, meson 1.11.1) проходит, а `ninja`
падает на несовместимостях QEMU 6.0.91 с новым инструментом:

- `hw/vfio/pci.c:2833`: `implicit declaration of function 'basename'`;
- `fpu/softfloat.c` + `fpu/softfloat-parts.c.inc:1294`: `conflicting types for 'parts128_compare'`.

Alpine 3.14 — ровесник ветки (2021), на нём собирается. Правок в исходники ветки у нас **одна** —
та, что в патче рядом; всё остальное — как в ветке.

## Границы (кратко)

1. Окно процедур — **закрыто** нашей правкой (было: ловушка на первом `call`).
2. **Вход в системный вызов — стена.** `sdisp` (он и делает `call` системным вызовом) в ветке
   реализован только под `CONFIG_USER_ONLY` и там **подделывает** цель (`E2K_FAKE_KERN_START`).
   В системном режиме вход в syscall = вход в ядро.
3. Обработчик исключений — заглушка `exit(1)` (`target/e2k/cpu.c`).
4. `initrd` не поддержан, устройств хранения у машины нет.
5. Прошивки `e2k.bin` публично нет; bootblock гостю не передаётся; консоль машины — `escc`,
   а не `lmscon`, который ищет ядро Эльбруса.

**Решение владельца (2026-10-03):** за прошивку не идти — свою не изобретать, bootblock не
подделывать. Стена названа долгом, работа остановлена. Подробности — `docs/e2k-qemu-system.md`.

## Долг: паспорт и сторож — случай 38 реестра проверок

Числа этого кита (версия `6.0.91`, `sha256` двух сборок `5ace3dae…` / `1a321ebf…`, `sha256` патча
`68c45cbb…`, окно `16 → 24`, исключения `9` / `0`, адреса `0x100338` / `0x100358`) сверяет
**скрипт**, то есть инструмент для человека: он молчит ровно тогда, когда его не запустили. Ни одна
проверка `src/e2k/**` живую системную сборку не спрашивает — в отличие от user-mode модели, где
`src/e2k/qemuModelIdentity.test.ts` краснеет на живой сборке. Это **названный долг**, заведённый
случаем **38** (`docs/verification-debt.md`, класс «дрейф артефактов»): лечится паспортом-модулем и
оракулом к живой сборке в шлюзе. Пока его нет — вердикт `build-system.sh` читать как вердикт
скрипта, а не как показание сторожа.
